# D014 — Extensible DX12 dispatch inputs and sharpening

- Recorded: 2026-09-30.
- Revised: 2026-10-07 (explicit native sharpening mode and borrowed getter;
  verification status clarified; original protocol unchanged).
- Revised: 2026-10-09 (M8 implementation and direct-native M9 integration
  protocol selected; original experiment and its failed criteria unchanged).
- Revised: 2026-10-10 (M9 verified; combined release includes D013 and its artifact/native checks).
- Accepted: 2026-10-07 (explicit maintainer approval after API review).
- Status: **accepted** — M8 implemented; M9 native and local candidate
  verification passed on 2026-10-10 for the recorded configuration.
  Publication remains pending; see the dated M9 amendment below.
- Intended release: `fsr-sdk` 0.2.0, SDK v2.3.0, existing Windows/DX12 profile.
- Decision relationship: supersedes D011's public input representation and
  fixed sharpening setting for 0.2.0; extends its bounded provider trust to the
  native sharpening pass. D011's other obligations remain in force, and its
  published 0.1.0 API remains available; current source implements the migration.

## Decision

Make `UpscaleDispatch` private-field configuration with one unchanged unsafe
dispatch method. Group the five textures in private-field `UpscaleResources`;
keep jitter, timing, camera and reset explicit in frame construction. Require
an explicit exposure texture in the resource constructor and expose it through
an optional-return getter. Add checked `NativeSharpness` and a non-exhaustive
`Sharpening` selection with `Disabled` and `Native(NativeSharpness)` variants.
The frame defaults to `Disabled`, exposes a borrowed `&Sharpening` getter and
accepts an owned selection in its setter. `Native` identifies direct parameter
control of the selected FSR provider, not a quality level or a temporary maturity
label. It reserves room for later modes without committing to any of them.

The migration changes how callers construct and inspect a frame. With
sharpening disabled, it must preserve the current native descriptor and recording
behavior. Sharpening is the only additional GPU capability selected for 0.2.0.

## Context and evidence

[D011](D011.md) deliberately exposes ten public dispatch fields for a narrow
first profile. Adding even an optional field breaks exhaustive consumer literals.
[D012](D012.md) already made creation options private and extensible;
[D009](D009.md) and the current error implementation leave error categories open.
Neither needs another structural change for sharpening.

The [post-release surface research](../research/records/2026-09-29-src-dx12-upscaler-api-surface.md)
maps sharpening, pre-exposure, masks and active sizes to per-frame inputs;
exposure mode, depth/MV conventions and HDR also involve creation policy.
It supports either retaining a legacy dispatch alongside an extensible route,
or making an early break with one extensible frame. It does not require a builder
or establish runtime support for all these fields. This decision chooses the
single route because the roadmap anticipates additional frame capabilities.

The existing [raw descriptor](../../crates/fsr-sdk-sys/src/upscale.rs)
already contains `enableSharpening` and `sharpness`. The wrapper's
[descriptor translation](../../crates/fsr-sdk/src/upscaler/dx12/dispatch/descriptor.rs)
maps Disabled to `false` and positive `0.0`, and Native to `true` and the checked
parameter unchanged. No new DLL export or native descriptor is needed.

The [native sharpening spike](../research/records/2026-09-30-exp-d014-native-sharpening.md)
used a fresh context for each setting. It therefore does not verify per-frame
mode changes within one context with continuing temporal history. Gate 5 must
cover that path through the final public API.

The [controlled semantic experiment](../research/records/2026-09-30-exp-dispatch-semantics.md)
adds a horizontal-motion/jitter/history-reset regression on one provider/GPU
configuration. It corrected an earlier test-image jitter assumption. It supplies
a baseline for this change, not sharpening, general image-quality or thread-transfer
evidence. [D013](D013.md) is a separate accepted threading track with an
implemented optional API. The 2026-10-10 release-scope amendment includes it
in `0.2.0` without changing this decision's GPU profile or sharpening contract.

## Concrete public API

All new names below are reexported from `fsr_sdk::upscaler` under the existing
Windows plus `dx12` gate, also through `upscaler::dx12` under D015. Signatures
describe the implemented API; private-field declarations below are schematic.
Existing common scalar types and their domains stay.

```rust
// Private fields, Debug + Clone; no Copy or equality contract.
pub struct UpscaleResources<'a> { /* private */ }

impl<'a> UpscaleResources<'a> {
    pub fn new(
        color: &'a ID3D12Resource,
        depth: &'a ID3D12Resource,
        motion_vectors: &'a ID3D12Resource,
        exposure: &'a ID3D12Resource,
        output: &'a ID3D12Resource,
    ) -> Self;

    pub fn color(&self) -> &'a ID3D12Resource;
    pub fn depth(&self) -> &'a ID3D12Resource;
    pub fn motion_vectors(&self) -> &'a ID3D12Resource;
    pub fn exposure(&self) -> Option<&'a ID3D12Resource>;
    pub fn output(&self) -> &'a ID3D12Resource;
}

// Private scalar, Debug + Clone + Copy + PartialEq.
pub struct NativeSharpness { /* private f32 */ }

impl NativeSharpness {
    pub fn new(value: f32) -> Result<Self, Error>;
    pub fn value(self) -> f32;
}

// Debug + Clone; no Copy, equality or Default trait contract.
#[non_exhaustive]
pub enum Sharpening {
    Disabled,
    Native(NativeSharpness),
}

// Private fields; no derives, as in the existing UpscaleDispatch.
pub struct UpscaleDispatch<'a> { /* private */ }

impl<'a> UpscaleDispatch<'a> {
    pub fn new(
        command_list: &'a ID3D12GraphicsCommandList,
        resources: UpscaleResources<'a>,
        jitter: JitterOffsetPixels,
        frame_time: FrameTimeMillis,
        camera: CameraParameters,
        reset: bool,
    ) -> Self;

    pub fn command_list(&self) -> &'a ID3D12GraphicsCommandList;
    pub fn resources(&self) -> &UpscaleResources<'a>;
    pub fn jitter(&self) -> JitterOffsetPixels;
    pub fn frame_time(&self) -> FrameTimeMillis;
    pub fn camera(&self) -> CameraParameters;
    pub fn reset(&self) -> bool;
    pub fn sharpening(&self) -> &Sharpening;

    pub fn set_sharpening(&mut self, value: Sharpening);
}

impl Upscaler {
    pub unsafe fn dispatch(&mut self, frame: UpscaleDispatch<'_>) -> Result<(), Error>;
}
```

### Construction, borrowing and mutation

`UpscaleResources::new` requires all five roles, including a borrowed exposure
resource. There is no default or optional exposure constructor parameter.
`exposure()` returns `Some` for every currently constructible value. Its
optional return permits a later constructor for a mode without an exposure
texture; 0.2.0 provides neither that constructor nor automatic exposure.

These safe constructors only assemble borrowed inputs. They make no native calls
or COM inspection and certify neither resource compatibility nor pixel contents.
Device identity, shape, format, extent, access capabilities and distinct COM
identities remain dispatch preflight checks. Construction takes no independent
COM references; cloning a resource bundle duplicates its borrows. None of these
types retains objects for GPU use after the CPU call.

The frame constructor requires renderer-selected jitter, time, camera and reset.
There is no fabricated camera, time interval, zero-jitter sequence or inferred
first-frame reset. Callers explicitly pulse reset on first frames/cuts as today.
Only `set_sharpening` is provided, returning `()`. Changes to required resources,
jitter, timing, camera or reset construct a new frame, reusing a cloned resource
bundle where appropriate. Dispatch already consumes the frame, so ordinary
per-frame use needs construction rather than mutation. Additional setters can
be added for demonstrated caller needs later. No fluent `with_*` API or separate
builder is selected.

Frame construction initializes sharpening to `Sharpening::Disabled`.
`sharpening()` borrows the stored selection; reading it does not clone it.
Callers that need an owned selection explicitly call `.clone()`.
`set_sharpening` replaces that selection by value and makes no native call.
The frame-construction default does not promise a `Default` implementation for
the selection type.

Every configuration field is private, including those in the resource bundle.
Neither type needs `#[non_exhaustive]` to prevent external construction; no
public required-field carrier recreates the original literal problem.
`NativeSharpness` has `Debug + Clone + Copy + PartialEq`, as a checked scalar.
`Sharpening` has `Debug + Clone` without `Copy` or an equality contract. Its
`#[non_exhaustive]` enum requires external matches to include a fallback arm,
so additional variants can be introduced later. The resource bundle permits
explicit Clone reuse. The frame retains its absence of derives, including Debug;
a new Debug implementation can be considered additively if useful.

The intended auto-trait contract is `Send + Sync` for `UpscaleResources`,
`UpscaleDispatch`, `NativeSharpness` and `Sharpening`. The current public frame
already inherits these traits from its borrows and scalar fields. The pinned `windows` 0.62.2
source explicitly implements Send/Sync for both `ID3D12Resource` and
`ID3D12GraphicsCommandList`.
Public consumer compile-time assertions confirm this matrix in the
[M8 implementation checks](../release/2026-10-09-m8-implementation-verification.md).

Moving/sharing an input value does not transfer the thread-confined `Runtime` or
`Upscaler`, permit simultaneous dispatch, or establish GPU lifetime. No manual
Send/Sync implementations or changed runtime-family traits are selected.
These auto traits still count toward compatibility when adding future fields.
Future sharpening variants must preserve the promised `Debug + Clone` selection
traits and `Send + Sync` input/frame traits. Omitting `Copy` avoids requiring all
future variant payloads to be Copy; it does not remove the other compatibility
obligations.

### Sharpening domain and native mapping

`NativeSharpness::new` accepts finite values in inclusive `[0,1]`, including
negative zero. It rejects NaN, either infinity and values outside that interval; it does
not clamp. Invalid construction returns the existing shape:

```rust
Error::InvalidDispatch {
    reason: DispatchValidation::Scalar(DispatchScalar::NativeSharpness),
}
```

`DispatchScalar::NativeSharpness` is an additive variant of the already
non-exhaustive enum. Invalid scalar construction makes no native call and cannot poison a
context. A typed setter cannot introduce an invalid value through safe Rust.

| Frame setting | `enableSharpening` | `sharpness` |
|---|---:|---:|
| Default / `Sharpening::Disabled` | `false` | `0.0` |
| `Sharpening::Native(NativeSharpness::new(0.0)?)` | `true` | `0.0` |
| `Sharpening::Native(NativeSharpness::new(v)?)` | `true` | `v` |

Enabled zero remains distinguishable from disabling the pass in descriptor
mapping. This is not a promise of a measurable image difference between those
two settings. Strength is the native documented scalar, not a perceptual preset
or a wrapper-defined filter amount. Frame-local settings do not persist on the
context or require Configure. The native enablement and parameter are forwarded
unchanged, with no wrapper-defined filtering, output clamping or perceptual
remapping. Forwarding preserves the `f32` bits, including negative zero; Disabled
uses positive zero. `Native` describes how the pass is controlled; it does not
promise sharpening gain, better image quality, mean-brightness preservation,
strength monotonicity or a calibrated strength.
Both `Disabled` and `Native` retain these meanings if other modes are added.

The public `NativeSharpness` and `Sharpening` Rustdoc must state the distinction
explicitly, for example:

```text
Checked native parameter for an enabled sharpening pass, in [0, 1].
0.0 is the lower endpoint of the parameter range; it does not disable the pass.
Native forwards this checked parameter unchanged to the selected FSR provider.
To disable sharpening, use UpscaleDispatch::set_sharpening(Sharpening::Disabled).
```

Do not describe zero as "off", "no sharpening" or a guaranteed identity filter.
After native verification, link the enabled-zero versus disabled observations
from consumer documentation, with their scene/provider/GPU/driver limits. Report
equality or differences as observations of that configuration rather than a
universal semantic guarantee or a claim about internal filter implementation.
Consumer documentation must also link the already recorded brightness changes
and edge overshoot/undershoot in the
[native spike](../research/records/2026-09-30-exp-d014-native-sharpening.md).
Its gradient metric measures horizontal neighboring-pixel differences, not
general detail recovery or image-quality improvement. The independent audit
confirms the measured values, not the provider's internal mechanism. The mode
name does not replace these qualifications.

## Migration example

This sketch assumes the same renderer-owned objects, checked scalar values and
unsafe caller obligations as the current public example.

Before, in 0.1.0:

```rust
let frame = UpscaleDispatch {
    command_list,
    color,
    depth,
    motion_vectors,
    exposure,
    output,
    jitter,
    frame_time,
    camera,
    reset: true,
};
// SAFETY: The renderer establishes the full dispatch contract.
unsafe { upscaler.dispatch(frame)?; }
```

After, in the `0.2.0` API:

```rust
use fsr_sdk::upscaler::{NativeSharpness, Sharpening, UpscaleDispatch, UpscaleResources};

let resources = UpscaleResources::new(
    color,
    depth,
    motion_vectors,
    exposure,
    output,
);
let mut frame = UpscaleDispatch::new(
    command_list, resources, jitter, frame_time, camera, true,
);

// Optional: omit this line to preserve the old sharpening-disabled behavior.
frame.set_sharpening(Sharpening::Native(NativeSharpness::new(0.35)?));

// Borrow for inspection; explicitly clone only when an owned selection is needed.
let selection = frame.sharpening();
match selection {
    Sharpening::Disabled => { /* pass disabled */ }
    Sharpening::Native(value) => { let _parameter = value.value(); }
    _ => { /* handle a future mode */ }
}

// SAFETY: The renderer establishes the same full dispatch contract.
unsafe { upscaler.dispatch(frame)?; }
```

Existing field reads become accessors; reading exposure now returns an Option.
Direct assignments to required fields construct a replacement frame or resource
bundle. Sharpening uses its single setter. Do not retain a legacy public-field type,
`dispatch_legacy` method, implicit conversion or deprecation path in 0.2.0.
Published 0.1.0 stays available for callers that do not migrate.

## Safety, validation and failure behavior

Preserve [D011](D011.md) and the existing
[public dispatch contract](../../crates/fsr-sdk/src/upscaler/dx12/dispatch.rs).
The following obligations must remain explicit in the resulting Rustdoc:

- The caller supplies an open recording DIRECT list. Inputs enter in
  `NON_PIXEL_SHADER_RESOURCE`, output in `UNORDERED_ACCESS`, with residency,
  non-overlapping backing storage and no conflicting access.
- All five resources and storage, list/allocator and upscaler/context stay valid
  through submitted GPU completion. CPU borrows and COM object identity checks
  do not establish GPU lifetime, actual states or heap non-aliasing.
- Submit each successful recording once and execute same-context dispatches in
  recording order; establish queue/fence dependencies. Dispatch neither closes,
  submits nor waits. Restore renderer bindings affected by FidelityFX.
- After a native error, never submit the failed list. Invalidate it, complete
  earlier submitted work and destroy the poisoned context. An abandoned OK
  recording likewise requires stopping dispatch and invalidating it before
  destruction; the wrapper cannot observe abandonment.
- Complete GPU work and invalidate abandoned/failed recordings before consuming
  destroy or Drop. Cleanup remains terminal and never waits or retries; D005
  exceptional dependency retention remains.
- Runtime/provider trust and allocation assumptions remain bounded to the
  selected signed v2.3.0 profile. Calls remain on the acquiring thread, with
  externally coordinated serialization/non-reentrancy under D008.

Preserve poison-first rejection, preflight rejection without native dispatch,
lossless native code propagation and poison-on-native-error. `Ok(())` continues
to mean successful native recording only. Keep validation/image semantics
distinct from unsafe GPU-lifetime/state obligations in documentation.

With sharpening disabled, descriptor tags/chains, five resource conversions,
motion-vector scale, active extents, exposure, pre-exposure `1.0`, camera,
jitter, frame time, reset and zero flags must match the existing mapping.
Creation flags remain zero. No resource format/state or numerical size policy
changes are selected.

For enabled sharpening, the accepted policy extends D011's bounded dispatch
runtime trust to the additional native pass at checked finite strengths in
`[0,1]`, under the same signed-runtime and renderer preconditions. This is a
maintainer trust choice, not proof of provider allocation behavior.
Acceptance and M8 implementation checks alone establish no AMD/GPU verification:
the disabled regressions and selected integration protocol below are required
before release claims.

## Future extension audit

This table is **non-binding design exploration**, not a commitment to later API
names, representations, features or release sequencing. These are compatibility
scenarios for review; each needs its own later contract and evidence.

| Researched capability | Proposed place to grow | Constraint |
|---|---|---|
| Pre-exposure | Private frame setting plus a typed setter; default `1.0` | Matching input signal and normalized-output comparison |
| Reactive / T&C masks | Optional private resource fields plus setters on `UpscaleResources`; default absent | Provider resource requirements, format/state/content and image tests |
| Automatic exposure | An additional resource constructor without an exposure texture plus an `UpscalerOptions` creation mode | Keep today's constructor; `exposure()` can return `None`; validate frame input against context mode before FFI |
| Active render/output sizes | Optional private frame settings; default to today's maxima | Distinguish allocation, maxima and active extents; dynamic render and variable output are separate capabilities |
| HDR / non-linear color | Typed creation settings plus frame encoding where required | Provider-aware support; sRGB/PQ mutual exclusion |
| Depth / MV profiles | Typed creation policy and reviewed matching frame/camera contracts | Current `CameraParameters` certifies ordinary finite depth; private fields alone do not solve incompatible camera domains |
| Queries / provider metadata | Separate discovery and utility operations | Owned names/opaque IDs and routing; no new dispatch path needed |
| Reactive-mask generation | Separate GPU operation | Distinct native operation and its own resource/failure contract |
| Evidence-based sharpening profiles or additional control | Potential later `Sharpening` variant, after a concrete use case and contract | May still use the native pass internally; preserve existing meanings/traits and separately review resource, context or additional-pass requirements |

Private resource fields allow an additional constructor later without changing
today's required exposure parameter. The Option-return getter preserves that
possibility without an `ExposureInput` type or a currently unsupported mode.
The getter's always-Some result in 0.2.0 is the explicit cost of that choice.
It does not guarantee that a future automatic-exposure mode as a whole can be
introduced without a breaking change.

The non-exhaustive sharpening enum allows future variants without invalidating
external matches that already handle unknown modes. It commits to no future
variant, profile or independent sharpening implementation. An evidence-based
profile could still use the native pass: its distinction would be calibrated
parameter selection or additional control, not whether the provider executes
native code. Extra resources, context requirements or GPU passes are not made
automatically compatible by this enum. They need separate contracts and must
preserve existing public traits and the meanings of `Disabled` and `Native`.

No promise of compatibility for every future capability follows. In particular,
the current camera type and its finite-value getters remain a genuine boundary;
a future infinite/reversed-depth contract may need an additional construction
path or another breaking decision. This decision does not silently broaden its
invariants. New mandatory inputs or changes to established meanings can still
require a break, even with private configuration.

## Alternatives and costs

| Alternative | Assessment |
|---|---|
| Preserve 0.1.0 and add an advanced frame/dispatch route | Technically sound; retains two public upscale concepts and their migration/documentation cost |
| One ten-argument constructor with private fields | Smallest new type surface; repeated resource and scalar arguments are less readable. A viable simplification if the bundle proves unnecessary |
| Opaque `ExposureInput` accepting only explicit exposure | Supports a future mode factory with one constructor, but adds a public type now. A later additional resource constructor is also additive, so prefer the required reference and Option-return getter |
| Optional exposure reference, default absent | Extensible but permits omission in today's explicit profile and needs missing-input validation; avoid weakening current required-input construction |
| Public required-input struct plus private optional settings | Readable literals, but the required carrier repeats the same compatibility constraint when its shape changes |
| Builder with unset required fields | More machinery and either type-state or build-time missing-field errors; all required inputs fit two constructors with checked scalar types |
| Mutable per-context frame settings | Hides per-frame resources/reset/sharpening state and complicates failed-recording behavior |
| `Option<NativeSharpness>` | Compact off/on encoding, but the call site does not explicitly distinguish direct native control from a later profile or controlled mode |
| An `Experimental` mode label | Describes maturity rather than a lasting control contract; does not explain quality limits or distinguish future parameter policies |
| Raw native descriptors / flag masks | Conflicts with the wrapper boundary and bypasses supported profiles/validation |

The recommended shape adds three public types (`UpscaleResources`,
`NativeSharpness`, `Sharpening`) and accessor documentation plus one setter.
It increases construction syntax compared with a literal and does not statically distinguish
five same-typed texture roles. Existing role validation remains important.
No new ownership framework, public native chain, dependency or backend is needed.

### Texture-role validation limit

The current inspection checks role-specific formats, exact extents, output UAV
capability, shader readability, identities and device membership. For the usual
unequal render/output sizes, swapping color and output is rejected by extents
or, if the color lacks UAV capability, an earlier capability check. Depth versus
exposure uses the same R32F format but different extents; swapping it is rejected
when render size differs from 1x1. Other format-distinct roles are rejected by
format validation.

These checks are not semantic role types. With equal render/output extents,
distinct shader-readable RGBA16F textures that are both UAV-capable can pass
preflight even with color/output exchanged. The wrapper cannot inspect their
contents or actual states. This existing limit must be documented and tested
with COM/runtime fixtures, never by violating states or content assumptions
against the live AMD runtime.

## Implementation and verification gates

Acceptance selects the API design. Implementation and release readiness
require separate evidence. M8's public API, consumer, mapping and migration
checks are recorded in the [implementation verification](../release/2026-10-09-m8-implementation-verification.md);
M9 native and final artifact verification are recorded in the
[2026-10-10 M9 verification](../release/2026-10-10-m9-verification.md).
The original test-only
sharpening protocol was executed on 2026-09-30: execution and repeat
controls passed, but the original effect criteria failed in all three repetitions
and in the independent readback audit. See the
[spike record](../research/records/2026-09-30-exp-d014-native-sharpening.md).
Those results do not verify a future public implementation. API acceptance
and sharpening evidence remain separate. The 2026-10-09 amendment selects an
integration gate without new sharpening image-effect thresholds; it preserves
the original failed protocol and does not retrospectively pass it.

1. **Public consumer interface:** migrate README, crate Rustdoc, the DX12
   example, COM fixtures and native test inputs. Add external consumer coverage
   using only the reexports; verify private construction, accessors, the single
   setter, explicit bundle cloning and unchanged unsafe dispatch signature. Compile
   positive use on Windows/DX12 and negative controls against public literals.
   Assert Send/Sync for `UpscaleDispatch<'static>`, `UpscaleResources<'static>`
   and both sharpening types; Clone/Debug for resources and `Sharpening`, and
   Debug/Clone/Copy/PartialEq for `NativeSharpness`. Verify the borrowed selection
   getter, explicit cloning and an external non-exhaustive match with a fallback.
   Preserve the existing negative Send/Sync assertions for Runtime/Upscaler;
   add negative Copy/Clone checks for the frame and non-Copy checks for resources
   and `Sharpening`.
   Input auto traits are not native transfer tests.
2. **Scalar and mapping checks:** cover default disabled, enabled zero,
   intermediate and maximum strength, negative zero, out-of-range values,

   Fixture cases must also cover swapped format-distinct roles, depth/exposure

3. **Build and documentation:** use the applicable stable/MSRV, feature-disabled,
   Clippy, Rustdoc and pinned-header ABI checks from
   [development guidance](../DEVELOPMENT.md). Report Windows compilation,
   fixtures and GPU execution separately; do not use `--all-features`.
4. **Native regression:** repeat lifecycle, single-frame, three-frame and
   controlled motion/jitter/reset cases with sharpening disabled. Use the
   recorded profile and retain submission/fences, debug/device checks,
   watchdog isolation and terminal cleanup.
5. **Sharpening integration protocol — executed 2026-10-10:** follow the
   [2026-10-09 protocol](../release/2026-10-09-m9-native-sharpening-protocol.md).
   It combines gate 2's exact descriptor/controlled-FFI checks with successful
   public-API native recording and completed GPU execution. Require
   `Disabled → Native(0) → Native(0.35) → Native(1) → Disabled` through one
   `Upscaler`, continuing temporal history with no reset solely for a mode change.
   The protocol fixes scenes, matching controls, diagnostics and three isolated
   repetitions with the 180-second watchdog, finite readbacks, output writes,
   completed fences and clean debug/device/terminal cleanup checks. Unexpected
   native errors fail that valid-input run; expected error tests stay separate.
   Native errors remain possible under the existing API contract. An OK return
   or image difference alone is not mapping evidence. No added sharpening
   gradient, mean-preservation, image-difference or changed-area threshold is
   selected, and return to Disabled promises no identical output to a control
   with different history. All other gates remain in force. This explicit policy
   selection uses the known failed experiment without reinterpreting it.
6. **Migration and artifacts:** verify packaged consumer examples/Rustdoc and

   `fsr-sdk-sys = 0.1.0` dependency if raw source/API remains unchanged.
   Do not bump sys solely to match wrapper numbering. SDK pin, Windows dependency
   version, runtime acquisition and distribution policy remain unchanged.
   Publication requires separate authorization.

The native comparisons establish only their recorded workload/provider scope.
GBV, other providers and thread transfer remain existing limits, not new gates

requires revisiting the affected contract.

### Predeclared sharpening comparison protocol

The following is the **original protocol executed on 2026-09-30**, preserved
with its failed effect criteria. Its scene, metrics, thresholds and repeat
policy are unchanged by this API revision. It is not a selected replacement
release protocol; gate 5 above remains a separate decision. The original text
follows.

This is a proposed fixture-specific acceptance policy, not measured data, an
AMD guarantee or an image-quality standard. Approve and record the fixture,
metrics and thresholds before inspecting enabled-sharpening outputs. The
thresholds below apply to the normalized grayscale frequency scene and require
a directional detail response in addition to output differences.

Use 320x180 render and 640x360 output, the existing fixed formats/flags, explicit
exposure `1.0`, ordinary constant depth `0.5`, camera/time values and eight jitter
pairs from the [semantic experiment](../research/records/2026-09-30-exp-dispatch-semantics.md).
Keep motion zero and the scene stationary. For unjittered render coordinates
`u = x + 0.5 - jitter_x`, `v = y + 0.5 - jitter_y`, use two separate scenes:

- Frequency detail: RGB `0.5 + 0.4*sin(0.8*(u + 0.37*v))`, alpha `1`.
- Slanted edge: RGB `0.1` for `u < 128 + 0.37*v`, otherwise `0.9`, alpha `1`.

Each repetition runs both scenes. For each scene create five fresh contexts:
disabled A, disabled B, enabled zero, enabled `0.35` and enabled `1`. Each context
processes the same eight-frame sequence, resetting only on frame zero. Keep
resources/list/allocator lifetimes, submission order and fence/readback cleanup
identical. Use three independent isolated process repetitions, each with the
180-second watchdog. Record SDK/DLL/provider/GPU/driver and fixture fingerprints.

The primary comparison uses final-frame red-channel values in the output ROI
`x=[32,608), y=[32,328)`. First compare the raw half-float red-component bits
of disabled A and B inside that ROI, excluding row padding. Bit-identical values
are the primary repeat control. Compute the following metrics in f64 from the
read-back half-float values as well:

- `N`: mean absolute difference between disabled A and B (repeat noise).
- `D_v`: mean absolute difference between strength `v` and disabled A.
- `C_v`: fraction of ROI pixels with absolute difference at least `1/1024`.
- `G_v`: mean absolute horizontal neighboring-pixel difference, with both
  neighboring pixels inside the ROI; `G_off` is the disabled-A value.
- `B_v`: absolute difference of ROI mean red between `v` and disabled A.

For the frequency scene, **each of the three repetitions** must meet:

| Measure | Predeclared criterion |
|---|---|
| Repeat control (default) | Bit-identical disabled-A/B red components throughout the ROI |
| Repeat control (predeclared numerical fallback) | `N <= 0.0001`, only under the fallback policy below |
| Nonzero-strength change | `D_v >= 0.001` for both `v=0.35` and `v=1` |
| Changed region | `C_v >= 0.01` for both nonzero strengths |
| Detail response | `G_v >= 1.01*G_off` for both nonzero strengths, with `G_off > 0` |
| Mean preservation | `B_v <= 0.005` for both nonzero strengths |
| Execution | Finite RGBA throughout every output, completed fences/readbacks, clean debug/device checks and cleanup |

Bit equality tests deterministic repetition directly. Record `N` even when it
is zero. The numerical fallback is available only for a configuration whose
non-bit-identical repetition has been investigated and documented separately,
with that policy chosen before the validation run. It is not an automatic pass
when the default control fails. Report which policy was used; a failed default
run stays a failure and a changed policy requires a new complete run.
Because `N` averages the ROI, it may be below a single half-float spacing when
only some pixels differ; it is not a claim that each pixel changed by that amount.

The difference floor is ten times the permitted fallback repeat noise; `1/1024` is an
explicit pixel-level difference cutoff for this normalized half-float signal.
The 1% gradient increase measures response in the expected sharpening direction;
the mean bound prevents a simple brightness shift satisfying the effect gate.
These are deliberately selected test thresholds, not inferred SDK requirements.

Report all metrics for enabled zero as well, without requiring a difference from
disabled. For the edge scene, report repeat noise, profiles normal to the known
edge, transition width and bright/dark overshoot for every setting. The edge
scene must pass execution checks, but no universal edge-width, overshoot or
strength-monotonicity bound is asserted by this proposal. It is an execution
and diagnostic case, not an independent sharpening-effect gate. Its successful
execution alone must not be described as evidence of sharpening effect or quality.

If repeat noise or effect criteria fail, investigate fixture, mapping and provider
behavior and report the failure. Changing thresholds/scene requires an explicit
documented amendment and a new complete run; do not relax thresholds after seeing
results and report the original gate as passed. This protocol establishes a
bounded sharpening response on its recorded configuration, not broad quality.

## Review brief and acceptance

The [native sharpening spike](../research/records/2026-09-30-exp-d014-native-sharpening.md)
executed this protocol on 2026-09-30. Execution and repeat controls passed;
the nonzero effect criteria failed in all three repetitions, confirmed by an
independent readback audit. Enabled zero differed from disabled. The thresholds
above are preserved as the original failed proposal; acceptance of the API
does not adopt them as a release gate or retrospectively pass that experiment.

The pre-acceptance review considered the proposal against the current source,
D008/D011/D012 and the linked research. It distinguished concrete contract
defects from ergonomic preferences and later features' missing runtime evidence.
The review questions were:

1. Whether one breaking dispatch representation is preferable to a retained
   legacy route for the documented evolution path.
2. Whether the resource bundle and Option-return exposure getter justify their
   surface, and whether the six-argument frame constructor reads well in real
   callers. Propose an exact simpler alternative if they do not.
3. Whether required inputs, setters, getters, traits and default/native mappings
   are complete and internally consistent, including the borrowed `&Sharpening`
   getter, non-exhaustive selection, no Copy contract and enabled-zero sharpening.
4. Whether the exposure/mask/active-size extension scenarios remain additive,
   and whether the explicit camera limitation is an acceptable separate boundary.
5. Whether borrowing, GPU completion, poison, abandonment and cleanup obligations
   survive the redesign, and whether the explicit sharpening trust extension is
   justified without silently widening other guarantees.
6. Whether a separately chosen release protocol combines exact parameter mapping
   with final-public-route GPU evidence for direct native control, documents its
   dependence on known outcomes and preserves the original failed quality-policy
   experiment without overstating image-quality coverage.

### Acceptance outcome — 2026-10-07

The maintainer explicitly accepted the reviewed API and migration contract,
including `Sharpening::{Disabled, Native(...)}`, the borrowed getter, the
specified traits and the bounded provider-trust extension for native sharpening.
M7's contract decision is complete. The same-context switching requirement in
gate 5 is part of the required release verification, not completed evidence.

Implementation, public-route checks and native release verification remain
pending. Gate 5's scenes, matching controls, metrics, thresholds and repeat
policy must still be selected and recorded before execution, explicitly in
knowledge of the 2026-09-30 results. The original failed protocol is unchanged.
Acceptance makes no image-quality guarantee and authorizes no publication.

### Implementation and integration amendment — 2026-10-09

The authorized implementation strategy keeps M8 to the accepted frame API and
native sharpening control. Current source implements the private resource/frame
constructors, accessors, borrowed sharpening getter, one setter, checked scalar
and exact native mapping. The [M8 verification](../release/2026-10-09-m8-implementation-verification.md)
records Windows compilation, controlled-FFI tests, public consumers, traits,
stable/MSRV checks and migration. It supplies no AMD/GPU release evidence.

Gate 5 now selects the [M9 integration protocol](../release/2026-10-09-m9-native-sharpening-protocol.md),
requiring correct control and successful bounded native/GPU execution, with no
additional sharpening image-effect thresholds. The historical gradient increase,
mean-preservation, image-difference and changed-area criteria were never adopted
as release gates and remain unchanged in the failed original experiment above.
This is an explicit integration-policy selection informed by those results, not
a passing rerun or changed interpretation. No own filters, profiles, extra quality
parameters, generic abstraction or visual guarantees are added.

M8 is complete as implementation; M9 GPU execution and final release artifact
checks remain pending. Existing validation, runtime trust, failure/poisoning,
GPU-lifetime and terminal cleanup obligations remain in force. Crate release
versions and publication are still separate M9 steps.
