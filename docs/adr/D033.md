# D033 — Boundary between native SDK abstractions and optional utilities

- Date: 2026-10-19.
- Status: **accepted** — 2026-10-19, under the maintainer's instruction to integrate the boundary audit and reflect the new decision in project scope. Accepts the architectural boundary and the audit's two clarifications; no utility implementation is authorised.
- Scope: `fsr-sdk` core responsibilities versus a possible optional `fsr_sdk::utils` module. The `fsr-sdk-sys` boundary remains unchanged.
- Release: none selected. No new feature, module, crate, dependency, public API or quality policy is implemented by this record.
- Relationship: complements [D001](D001.md), [D015](D015.md) and [D016](D016.md); does not supersede their accepted contracts or reopen the deferral in [POST_1_0](../POST_1_0.md).

## Context

The two existing crates distinguish a faithful native ABI (`fsr-sdk-sys`) from the Rust interface (`fsr-sdk`) that owns lifetimes, validates inputs and exposes native operations. That distinction does not alone determine where optional calculations and integration policies belong. Calling a function a *helper* is insufficient: a direct AMD jitter query may be convenient but remains part of faithful SDK access, whereas a separately designed jitter sequence or dynamic-resolution controller selects behaviour not specified by that query.

[D016](D016.md) already requires direct provider controls to remain independently available, with project-authored quality policies explicit and separately evidenced. It does not require an additional crate or module. This decision specifies an **internal responsibility boundary within `fsr-sdk`**, not a new fidelity, safety or quality guarantee. Through 1.0.0, faithful SDK access remains the priority; custom quality policies and calibration are [explicitly deferred](../POST_1_0.md) until later maintainer selection.

## Decision

### 1. Keep the existing crate boundary

- **`fsr-sdk-sys`:** Curated declarations of the pinned native ABI, preserving upstream layouts, symbols and contracts. It is not a home for utility policies or renderer algorithms.
- **`fsr-sdk` core:** Faithful, typed access to supported native capabilities, including necessary semantic modelling, validated inputs, representation/unit mappings, ownership, native error preservation, and explicit unsafe obligations. Representational convenience remains core when it expresses the same native contract without independently selecting behaviour, even if the caller could reproduce the calculation externally. This includes alternate constructors, simple accessors and optional preflight checks.
- **Optional `fsr_sdk::utils`:** Caller-selected functionality with behaviour independently defined by this project: additional calculations, selection rules or renderer-independent state management. Utilities may use public core APIs but must not require privileged FFI access, bypass core validation or replace the direct route.

If a concrete utility is later selected, initially prefer an opt-in `utils` Cargo feature and `fsr_sdk::utils` module **in the existing crate**. Do not add a third published crate or an implementation now. Further feature subdivision needs a demonstrated dependency or compilation-cost reason; this record does not select individual utility signatures.

### 2. Classification test

Classify functionality by its **contract**, not by its name, implementation size or whether it is mathematically simple.

1. **Native correspondence:** Does it expose an AMD operation, parameter, capability or provider-reported result, with only the checking and conversion needed to represent that contract in Rust? **Core.** This includes official native convenience queries.
2. **Safety and faithful usability:** Is it required to enforce ownership, native ABI invariants, resource validity, error/eligibility rules or caller-visible GPU obligations? **Core**, including optional preflight operations that repeat mandatory validation.
3. **Independent choice:** Does it compute, select, adapt, smooth or combine settings according to a project-defined algorithm, recommendation or policy beyond representing a native contract? **Utility candidate.** Its semantics, assumptions and effects must be explicit. Documented core defaults define a supported native profile; that alone does not make them a quality preset.
4. **Renderer ownership:** Does it need camera/render-graph ownership, renderer resource allocation, queue submission, texture transitions, temporal histories or the application's presentation loop? **Application or integration crate**, not a generic utility merely because the code is reusable. Native SDK object ownership and supported native presentation operations remain core responsibilities; the long-term Frame Generation/presentation goal is unchanged.
5. **Mixed operations:** Keep direct provider control and its mandatory checks in core; expose an independent opt-in policy separately. If the separation cannot be made without changing the core contract, require a concrete design review rather than silently reclassifying or relocating the API.

The classification does not imply that every conceivable native function must be bound or that every application convenience deserves a public API.

### 3. Application to the current surface

| Current or proposed functionality | Classification and reason |
|---|---|
| `Runtime`, `MovableRuntime`, context creation/destruction, native coordination contracts | **Core:** native lifetime and safety boundaries; `Send + !Sync` is not a convenience policy. |
| `UpscalerOptions`, `UpscaleDispatch`, checked dimensions/camera/frame values, `CameraParameters::new_infinite`, `UpscaleResources::without_exposure`, flag accessors and `validate_dispatch_inputs` | **Core:** representation, validation and faithful native recording, even where the API is ergonomic. |
| `QualityMode`, native upscale-ratio/render-size and jitter-phase/offset queries | **Core:** these ask AMD for provider-defined values; they are not custom presets or jitter generators. |
| Provider discovery/selection, resource and memory queries, native Configure/tuning | **Core:** direct native capabilities and checked controls. |
| Native automatic exposure, pre-exposure, colour hints, sharpening and supplied masks | **Core:** caller-selected native functionality; no implicit image conversion, filtering or tuning. |
| Proposed native reactive-mask generation ([D030](D030.md)) | **Core if accepted and implemented:** it is a distinct AMD GPU operation, not a project-generated heuristic. |
| Independent jitter-sequence or frame-index manager; dynamic-resolution controller; render-size selection policy | **Potential utilities:** project-defined calculations or stateful decisions, not native query passthrough. |
| Explicit sRGB/PQ transforms, exposure arithmetic, motion-vector data/unit conversion, optional configuration presets | **Potential utilities:** only when they have specified mathematical conventions, domains and independently testable effects. Native descriptor/unit mapping remains core. |
| Bevy/wgpu adapters, GPU-texture conversion or allocation, command-list submission and temporal renderer history | **Outside these generic layers:** renderer- or backend-integration responsibility. |

Existing APIs remain where they are. This table is not an inventory of implemented utilities and does not approve the examples in its last three rows.

### 4. Invariants for any later utility implementation

- **Opt-in and additive:** Without the optional feature, all existing core types and semantics remain available and unchanged. Cargo feature unification must not change native defaults, direct-control mapping, error handling or safety contracts.
- **No hidden native policy:** A utility must reveal which native settings or additional operations it selects, and distinguish provider-reported values from project-computed recommendations. Explicit core choices must remain usable without a utility.
- **Compose through core values:** Prefer returning existing checked core inputs for explicit use through ordinary constructors/setters, keeping core independent of policy provenance. Multiple outputs may form a utility-owned plan; no universal trait, builder, policy enum variant or competing effect API is required. Policy-specific core hooks need a downstream caller demonstrating a missing supported capability. Preserve creation-time, per-frame, native-query, live Configure and GPU-operation boundaries; a plan does not hot-reconfigure a context or make Configure and dispatch transactional.
- **No safety laundering:** A utility invoking unsafe native operations must uphold their preconditions itself or expose an appropriate unsafe contract. It must not claim that Rust ownership proves GPU completion, resource states, provider support or cross-thread native safety.
- **Keep renderer ownership explicit:** Pure scalar/CPU calculations may be generic utilities. Ownership of renderer textures, command lists, transitions, queues, temporal histories and engine lifecycles stays with the application/integration layer. Core native-object retention, terminal cleanup and cross-thread coordination retain their existing contracts; a utility must not silently absorb these obligations.
- **No disguised FSR reimplementation:** Numerical conversions and renderer-independent parameter planning may be legitimate utilities; implementing reconstruction, exposure or mask algorithms as if they were AMD's provider behaviour is not implied or authorised.
- **Evidence proportional to claims:** Pure numerical utilities need unit/domain/edge-case tests. Stateful strategies need transition and negative tests. A utility claiming image quality, compatibility or performance requires independent evidence under [D016](D016.md), not merely working core dispatch. Provider/version-dependent inputs need stated compatibility limits.
- **Portable by default, explicit when not:** Keep general-purpose utilities independent of Windows/DX12. Any truly backend-specific utility needs separate gating and justification; no new platform guarantee follows from a common module name.

### 5. Timing and acceptance boundary

This decision establishes **no active utility milestone** and does not change the selected `0.3.0` upscaler coverage or the project-wide priority through `1.0.0`. In particular, custom quality presets, calibration and resumed image-quality research stay deferred under [POST_1_0](../POST_1_0.md). A future concrete utility needs its own scoped API, justification, verification and maintainer authorisation. Acceptance of this boundary alone is not approval to add `utils` to Cargo features or publish a new crate. Introduce a feature/module only with the first selected utility, keep it off by default, and avoid speculative empty features.

## Alternatives

**First concrete utility selection — 2026-10-22:** the maintainer separately
accepted and authorised [D036](D036.md)'s provider-name resolver. Its implementation
introduces the off-by-default `utils` feature/module described above, without a
core migration, new dependency or quality-policy selection. Statements here that
the boundary alone selects no utility retain their original scope; D036 records
the later concrete decision and verification. Release inclusion remains separate.

| Alternative | Assessment |
|---|---|
| Put every convenience directly in core | Rejected: project-defined policies could silently become part of native contracts and increase core maintenance and compatibility costs. |
| Create `fsr-sdk-utils` immediately | Not selected: no independent release cadence, dependency split or user need has yet justified another published crate. Extraction remains possible later. |
| Make one Cargo feature per hypothetical helper immediately | Not selected: speculative complexity without known dependencies or concrete APIs. |
| Disallow utilities entirely | Too restrictive for reusable, well-specified integration mathematics and user-selected policies, but does preserve the correct current default of implementing none. |
| Make renderer/engine adapters part of `utils` | Rejected: it would blur the existing engine-independent boundary and GPU ownership contracts. |

## Consequences and basis

The [boundary audit](../research/records/2026-10-19-src-core-utils-boundary-audit.md) found no production policy requiring extraction. Existing public APIs and imports stay in place, including the four provider-routed queries in the private `query/native/utilities.rs`; the filename does not make them optional project-authored utilities. No structural migration or speculative utility framework is selected.

This accepted boundary is reflected in [SCOPE.md](../../SCOPE.md#core-and-optional-utilities). It preserves [D016](D016.md)'s direct-control guarantee, current safety contracts and release scope. Future utilities need independent documentation and verification; this source audit establishes no new runtime, quality or performance result. The [topic synthesis](../research/core-and-utilities.md) preserves the audit's provenance and limits.

### Composability clarification — 2026-10-19

The maintainer's subsequent synthesis/documentation request integrates the
[composability study](../research/records/2026-10-19-src-core-utility-composability-and-future-extension.md).
It clarifies the existing public-core-API requirement: utility-selected values
should feed the same native-facing API as direct caller choices, with each
operation retaining its timing, ownership and failure contract. Current setters
and checked values already support this pattern; no required core refactor was
identified. Future-effect abstractions, utility error types and query-snapshot
APIs remain unselected design possibilities, not new contracts or implementation
work. The study's proposed-D033 baseline predates this record's acceptance.
