# D025 — Supplied upscaler masks and provider-aware dispatch validation

- Date: 2026-10-15.
- Status: **accepted** under explicit maintainer implementation authorization
  after reviewing the concept against the API and code heuristics.
- Amendment: **accepted 2026-10-15** under explicit maintainer direction after
  Windows verification exposed the query-based mask rejection described below.
- Scope: pinned SDK v2.3.0, existing DX12 upscaler and both ownership families.
- Extends D014's private resource bundle and D024's allocation/active-region
  contract. Replaces D023's automatic-only construction query and rejection of
  required masks. D018's live public query and native trust remain in force.

## Decision

Add two private `Option<&'a ID3D12Resource>` fields to `UpscaleResources`, exposed
through `reactive_mask` / `set_reactive_mask` and
`transparency_and_composition_mask` / `set_transparency_and_composition_mask`.
Both getters return the actual optional borrow; both setters take that same
optional borrow and return `()`. Existing `new` and `without_exposure` signatures
remain, initializing both masks to None. Setters assemble borrows without native
calls, COM inspection, pixel transformations or independent COM retention.
Preserve `Debug + Clone` and `Send + Sync`; no builder, public fields, generated
mask selection enum, or new resource ownership abstraction is introduced.

Each supplied mask is a distinct shader-readable R8_UNORM Texture2D, single
sample/mip/slice on the context device. Its allocation equals `max_render_size`;
jitter-aligned content occupies the same top-left active render region as
colour/depth, independently of motion-vector resolution. UNORM values represent
`[0, 1]` signals and pass unchanged. The reactive mask controls reliance on pixel
history; transparency/composition supplies the separate history-protection input.
The wrapper validates metadata and identity, not pixel meaning or heap aliasing.

Every successful native context creation performs one live resource-requirements
query before returning the public owner, including explicit exposure. Store the
result privately for the immutable context profile. Unknown required bits reject
construction with the original complete `UnsupportedResourceRequirements` mask.
Known required masks are now supported and do not reject construction. Exposure
is satisfied by the explicit texture or the automatic creation flag.

A query failure preserves its native `Operation::Query` code. Query/profile
rejection makes the ordinary single terminal cleanup attempt through the native
owner, with no wrapper GPU recording or submission. Destruction failure retains
the critical ownership bundle under D005; no retry or replacement of the original
construction error occurs. This intentionally adds possible construction errors
for previously query-free explicit-exposure contexts.

Before COM inspection/native dispatch, require every mask reported as required.
Reject absence with `DispatchValidation::MissingRequiredResource(ResourceRole)`.
For the two SDK-defined mask inputs, accept supplied resources independently of
whether their bits appear in `required_resources` or `optional_resources`, subject
to all ordinary resource validation and caller obligations. Forward supplied masks
unchanged; do not silently omit them or introduce a strict/permissive forwarding
mode. A missing query bit is not sufficient evidence that supplying that input
violates the SDK contract.

Required/optional overlap is accepted, with presence required. Preserve unknown
optional bits without introducing inputs or errors. Unknown required bits still
reject construction because the wrapper cannot satisfy those requirements.
Retain both mask roles in the non-exhaustive `ResourceRole`. The existing
`UnsupportedResource` variant must no longer be emitted merely because a supplied
mask is absent from both query bitfields; removing the public variant is not
required by this amendment.

Supplied resources participate in ordinary format/extent/device/canonical-identity
checks. Absent resources are not inspected and map to entirely zero native resource
descriptors. Present masks use compute-read state and exact native allocation
metadata. Validation/inspection errors record no FSR commands and do not poison
a usable context; native dispatch errors retain the existing poison policy.
Both families share construction, validation and descriptor conversion.

The public `resource_requirements()` stays a live query with its existing poison
and native-error rules. The internal snapshot is not a public lifetime guarantee:
future Configure operations affecting resource consumption must refresh it as
part of their own successful state transition before permitting dispatch. No
public Configure or mutable provider selection exists today. There is no query,
GPU wait or heap allocation added to the dispatch validation by this snapshot.
This is a source-level design statement, not a measured performance claim.

## Safety, compatibility and alternatives

Extend input Rustdoc to cover masks' compute-readable boundary states, residency,
content alignment, non-overlapping backing storage and retention through GPU
completion. The trusted provider must uphold the documented contract for supplied
mask resources; query metadata alone establishes neither safety nor a prohibition.
Existing unsafe dispatch, native acquisition/coordination and terminal ownership rules
continue; a Rust borrow still covers only the CPU call.

Existing constructor calls compile unchanged. Optional private fields allow later
settings, while non-exhaustive errors permit new rejection cases. Additional
supported formats can be introduced without changing these signatures. Automatic
mask generation remains a separately selected GPU operation producing a
renderer-managed resource that this same API can borrow. HDR, variable output,
subresource/view support and quality policies are not selected here.

Requiring mask arguments in existing constructors would break callers. A generic
mask-source enum would anticipate an unselected generator/ownership contract.
Querying every dispatch adds unnecessary native work for today's immutable
profile. Inferring support from provider names or silently dropping supplied
masks would obscure the actual native contract. An override mode for unlisted
masks would preserve an exclusion unsupported by the documented contract and
make ordinary forwarding depend on a misleading capability label.

## Amendment rationale and implementation status

The original decision rejected supplied masks absent from both query bitfields
as a conservative profile restriction, intended to avoid passing inputs the
provider did not advertise consuming. That clause is superseded by this
amendment; the rest of D025 remains accepted.

The [Windows batch and correction](../release/2026-10-15-windows-feature-batch.md)
record provider 4.1.1 returning `required=15`, `optional=0`, followed by the
wrapper's `UnsupportedResource(ReactiveMask)` before native dispatch. AMD's
pinned 4.1.1 guide explicitly permits supplying both masks to FSR4. The query
header describes required inputs and optional inputs consumed if supplied; it
does not explicitly define a prohibition on supplying other documented inputs.
The observed rejection therefore establishes wrapper behaviour, not an AMD
dispatch denial, hardware limitation or memory-safety failure.

Separate four questions: whether an input is valid under the SDK contract,
whether it is required, whether the provider reports consuming it, and whether
native execution has actually been verified. Absence of reported consumption
does not establish either unsafe forwarding or guaranteed non-consumption.
Resource validation and GPU lifetime/state obligations remain mandatory even
when an input may not be consumed. A mode bypassing the removed query-membership
restriction would add no established safety guarantee.

This is an accepted decision amendment, not an implementation or verification
claim. At amendment time `check_mask_requirements` and its unit/Windows fixtures
still implement the original rejection. Follow-up implementation must retain
missing-required-mask checks, accept all supplied-mask presence combinations
independently of optional bits, and preserve metadata/device/identity validation,
reference balance, retry and native-error poisoning for both ownership families.
Update tests that currently expect query-based `UnsupportedResource` rejection;
test that unlisted masks reach exact descriptor forwarding instead. Then rerun
the native mask protocol. Successful recording, fencing and cleanup would verify
bounded acceptance/integration, not that the provider reads or benefits from
the masks. Original failed attempts remain historical evidence.

The amendment is now implemented and passes
[Windows CI/MSRV/C++ ABI and native confirmation](../release/2026-10-15-mask-forwarding-verification.md)
on 2026-10-15. The resource query still returns no optional mask bits, yet all
six mask/exposure combinations and 18 submitted/fenced frames pass with unchanged
native criteria. Controlled fixtures verify both ownership families. The standard
native profile passes all 29 cases without the earlier supplemental selection.
These results establish bounded acceptance/integration, not mask consumption.
