# D036 — Optional FSR generation provider-choice utility

- Date: 2026-10-22.
- Status: **accepted**, 2026-10-22, under the maintainer's explicit instruction
  to accept and implement the reviewed design. Implemented in development;
  verification is recorded below.
- Target: `fsr-sdk 0.3.0`, pinned AMD FSR SDK v2.3.0. Release inclusion was
  explicitly selected on 2026-10-27; publication and final package checks remain open.
- Scope: a pure, optional upscaling-provider resolver in
  `fsr_sdk::utils::provider`, behind an off-by-default `utils` feature.
- Relationship: applies [D033](D033.md)'s utility boundary, preserves
  [D016](D016.md)'s direct controls, [D018](D018.md)'s opaque metadata and
  [D028](D028.md)'s explicit selection. No accepted contract is superseded.

## Problem and basis

The current core API lets applications enumerate providers with
`Runtime::upscaler_providers_dx12`, inspect owned `ProviderInfo` entries, and
pass an opaque ID to `UpscalerOptions::set_provider`. `None` retains the SDK's
default-provider route. The optional movable family exposes the same native
operations.

An application wanting an FSR generation must currently interpret provider
display names itself. Existing native evidence includes the strings `2.3.4`,
`3.1.5` and `4.1.1`; see the [Windows provider verification](../release/2026-10-19-windows-upscaler-verification.md)
and [selected-provider experiment](../research/records/2026-10-19-exp-reactive-mask-providers.md).
These are observed names, not an AMD naming or compatibility guarantee.

D018 gives names and IDs no semantic-version, ordering, persistent-identity or
capability contract. D033 classifies an independently defined selection rule as
a utility candidate, while native discovery and checked selection remain core.
It did not approve a utility feature or implementation. This decision supplies
the separate concrete API and rules for review.

The scope excludes Frame Generation, hot-switching a live context, provider
compatibility certification and image-quality optimisation. It does not resume
the [deferred quality-policy work](../POST_1_0.md).

## Public contract

Expose the following API in `fsr_sdk::utils::provider`:

```rust
use crate::query::{ProviderId, ProviderInfo};

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[non_exhaustive]
pub enum FsrChoice {
    Auto,
    Fsr2,
    Fsr3,
    Fsr4,
}

#[derive(Debug, Clone, PartialEq, Eq)]
#[non_exhaustive]
pub enum SelectionError {
    /// No entry in the supplied snapshot was recognisable as this generation.
    NoRecognizedMatch { requested: FsrChoice },
    /// Multiple entries matched; no implicit version ranking was attempted.
    Ambiguous { requested: FsrChoice, matches: usize },
}

pub fn select_provider(
    providers: &[ProviderInfo],
    choice: FsrChoice,
) -> Result<Option<ProviderId>, SelectionError>;
```

Implement `Display` and `std::error::Error` for `SelectionError`. Diagnostics
must describe failure to resolve the supplied snapshot, without asserting a
native SDK failure or absence of hardware support. This error remains separate
from `fsr_sdk::error::Error`; no native code is fabricated or core error variant
added. Standard error traits support application logging and error propagation.

Both enums are non-exhaustive to permit future choices or error categories
without breaking exhaustive downstream matches, following [D009](D009.md)'s
extensibility rationale. This decision selects no additional variants or
`Default` implementation.

`FsrChoice` names a generation, not an exact SDK or technology version. A string
such as `4.1.1` is not a stable public enum discriminant. The resolver returns
the existing `Option<ProviderId>` input for explicit application through core.

## Exact resolution and name-recognition rules

| Choice or observation | Result |
|---|---|
| `Auto` | `Ok(None)`, independently of the supplied list |
| `Fsr2`, with exactly one recognised major-2 entry | `Ok(Some(id))` for that entry |
| `Fsr3`, with exactly one recognised major-3 entry | `Ok(Some(id))` for that entry |
| `Fsr4`, with exactly one recognised major-4 entry | `Ok(Some(id))` for that entry |
| No recognised entry for the requested generation | `NoRecognizedMatch`, with no fallback |
| Two or more recognised entries for the requested generation | `Ambiguous`, with the exact matching-entry count |

Recognise a name only when its entire string consists of exactly three
nonempty components separated by ASCII full stops. Every component consists
only of ASCII digits `0` through `9` and has a numeric value representable as a
non-negative `u32`. The parsed major must equal 2, 3 or 4. The lexical grammar is
`[0-9]+\.[0-9]+\.[0-9]+`; it describes the rule, not a regex dependency.

Leading zeros are accepted: `04.01.001` is classified as generation 4. Minor
and patch may be zero or `u32::MAX`. Overflow in any component makes the whole
name unrecognised. Signs, whitespace, Unicode digits, empty components,
prefixes, suffixes and extra components are unrecognised. Thus `4.1`,
`4.1.1-extra`, `14.1.1`, `4.1.1.2` and `FSR 4.1.1` do not match.

Unrecognised names are ignored during classification; they are not independent
resolver errors. They mean that this utility cannot classify those entries,
not that the SDK or GPU lacks a generation. Strict ASCII recognition also
rejects names containing replacement characters from core's lossy UTF-8 decode.
Additional naming formats need a separately reviewed and tested rule.

Count matching entries, including repeated entries with the same ID. Do not
deduplicate, rank minor/patch versions, inspect numeric ID order, use prefix or
substring matching, or choose the first match. Resolution and ambiguity counts
must be independent of input order. An explicit `Fsr4` request never falls back
to FSR 3 or FSR 2. `Auto` delegates policy to the SDK's default route and does
not implement a highest-generation or fallback strategy.

Successful resolution classifies only the supplied snapshot. It does not
guarantee that a later context executes that FSR generation or establish runtime
compatibility. Enumeration is bounded and need not be complete; a snapshot or
ID is not guaranteed to remain valid between calls. Fresh membership and live
identity checks retain D028's limits, including inability to detect reuse of
the same native ID for a different provider.

## Intended use and operation boundaries

The following sketch assumes the ordinary core objects and an application
error type that can represent both core and resolver failures, such as
`Box<dyn std::error::Error>`:

```rust
use fsr_sdk::upscaler::Upscaler;
use fsr_sdk::utils::provider::{FsrChoice, select_provider};

let providers = runtime.upscaler_providers_dx12(&device)?;
let selected = select_provider(&providers, FsrChoice::Fsr4)?;
options.set_provider(selected);
let upscaler = Upscaler::new(&runtime, &device, options)?;
```

For `Auto`, callers may skip enumeration and set `None` directly. The resolver
is CPU-only: it neither enumerates nor constructs a context, performs native
calls, owns renderer resources or mutates the supplied snapshot.

Related pre-create ratio, render-size and jitter queries must use the same ID
through the existing explicit-provider methods. Resource-requirement queries
take the same selection; memory estimates and creation use matching options.
Default query helpers do not inherit options. Core continues fresh selected-ID
validation, exact override forwarding, native error preservation and
post-creation effective-identity checks.

Applications retain backend/resource ownership, context recreation and GPU
coordination. Selecting a provider is a context-creation decision; this API
cannot switch an existing upscaler.

## Integration boundaries

- Add `utils = []` to the wrapper's Cargo features. Preserve the default feature
  set; `utils` implies neither `dx12` nor `movable` and adds no dependency.
- Expose `#[cfg(feature = "utils")] pub mod utils;` and `utils::provider`, with
  the implementation at `crates/fsr-sdk/src/utils/provider.rs`. Production code
  uses only public core inputs and getters, with no privileged native access.
- Keep the resolver portable, including non-Windows builds with
  `--no-default-features --features utils`. Native enumeration retains its
  separate Windows/DX12 gates.
- Preserve `fsr-sdk-sys`, DLL acquisition/loading, `ProviderInfo`, `ProviderId`,
  `UpscalerOptions`, core defaults, query routing, unsafe contracts and
  construction semantics. Add no public constructors solely for tests.
- Include `utils` alongside `movable` in the wrapper's docs.rs feature list so
  hosted documentation exposes the new opt-in API. Document feature activation
  and preserve existing platform/documentation boundaries.

## Verification requirements

1. **Pure resolver and parser tests.** Cover `Auto` with empty, nonempty,
   malformed and ambiguous lists; unique matches for every generation; no
   recognised match; mixed generations; no fallback; duplicates with the same
   ID and distinct IDs; different minor/patch values; exact ambiguity counts;
   and input-order independence. Cover the malformed examples above, empty
   names/components, signs, whitespace, Unicode digits, replacement characters,
   leading zeros, zero components, unsupported majors, `u32::MAX` minor/patch
   and overflow in each component. Keep full resolver tests portable alongside
   parser tests. Test-local values may be constructed within the owning query
   module's privacy boundary; no public metadata constructor is needed.
2. **Public API path.** Use controlled enumeration fixtures with version-shaped
   names and pass the resolver's returned ID through
   `UpscalerOptions::set_provider`. Existing D028 fixtures use
   `selected-fixture`, which must remain unrecognised under this rule; provide
   suitable fixture data for the new tests without changing core selection to
   depend on names. Exercise both ownership families where enabled and include
   downstream error-trait/propagation and public-import checks.
3. **Feature, MSRV and documentation checks.** Verify current default and
   no-default builds; portable utils-only builds/tests; Windows
   `dx12,utils`; and `dx12,movable,utils` through existing verification where
   supported. Preserve Rust 1.88/MSRV checks and confirm the feature does not
   introduce Windows dependencies into portable builds. Verify feature-off
   API gating and build the feature-enabled documentation/examples with
   documentation warnings denied.
4. **Native boundary regression.** Reuse D028's selected query/construction,
   absent-ID, enumeration/native error, identity-mismatch and failure-cleanup
   coverage. Resolver success establishes no GPU execution or compatibility.
   Distinguish portable tests, Windows compilation, fixture execution and
   existing actual-provider evidence; a new GPU compatibility campaign is not
   selected for this pure utility.
5. **User documentation.** State the exact naming heuristic and observed
   strings, show inspection/logging of every `ProviderInfo` through `name()`
   and diagnostic `id()`, explain `Auto` and explicit no-fallback behaviour,
   distinguish resolver and native errors, and require consistent provider
   selection across related pre-create operations. State snapshot/identity,
   compatibility and context-recreation limits.

Implementation verification is recorded in the dated results linked below.
The original proposal itself established no build, native test or GPU observation.

## Alternatives and consequences

| Alternative | Assessment |
|---|---|
| Add an FSR-generation enum or field to core options | Reject: presents a display-name heuristic as a native-facing contract, contrary to D018/D033 |
| Add a third `fsr-sdk-utils` crate | Unnecessary for this small dependency-free utility; D033 favours an optional module in the existing crate |
| Automatically prefer the highest minor/patch | Exclude: AMD supplies no ordering/preference contract; ambiguous entries fail |
| Automatically fall back from FSR 4 to 3 to 2 | Exclude: silently changes an explicit choice and adds provider-eligibility policy |
| Add a naming registry, regex dependency or plugin mechanism | Defer until observed naming variants or a concrete consumer need justify it |
| Keep name interpretation entirely in application code | Remains valid through the unchanged public enumeration and explicit-ID route |

The utility reduces repeated application code while taking responsibility for a
small, documented heuristic. Conservative recognition can reject usable
providers with unfamiliar names. That is an intentional resolver limit rather
than a compatibility verdict. Adding a future format or generation remains a
public-contract review, and no ranking or eligibility policy follows from this
decision.

## Release selection amendment — 2026-10-27

The maintainer selected the implemented provider resolver for publication with
`fsr-sdk 0.3.0`. It remains behind the off-by-default `utils` feature, adds no
dependencies and enables neither DX12 nor movable ownership. The current
resolver returns `ProviderSelection` for setup `with_provider` under D042;
the original optional-ID sketch above describes its earlier API baseline.
Recognition, ambiguity, no-fallback and native trust rules remain unchanged.

U12 must include feature-on/off consumers, portable composition and current
documentation for this utility. Final archive/registry-consumer checks must
cover its inclusion; existing source checks do not publish or certify those
archives. Other utilities and deferred quality policies remain unselected.

## Implementation and verification

The off-by-default `utils` feature exposes the portable resolver through public
core metadata getters. Resolver tests construct private metadata within `query`'s
test boundary; version-shaped controlled enumeration also feeds both DX12
ownership families through public options and context creation. No public test
constructor, raw ABI change or additional dependency is introduced.

See the [implementation verification](../release/2026-10-22-provider-utils-verification.md)
for commands, results and limits. The seven stable/MSRV feature configurations,
resolver/controlled-path tests and fresh consumer checks pass; the initial broad
profiles retain their recorded concurrent-input and test-harness failures.
The [complete example](../../crates/fsr-sdk/examples/provider_choice.rs) uses one
selection across planning and creation. Existing provider GPU observations remain
historical evidence; this pure utility selects no new GPU compatibility campaign.
