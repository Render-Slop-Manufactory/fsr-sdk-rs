# D005 — Own effect-independent context lifecycles with terminal teardown

- Recorded: 2026-09-22
- Status: accepted — authorized finalization after evidence review; private M4
  implementation and bounded Windows execution verification complete

Windows fixtures, paired native ABI checks and production-owner AMD
create/query/destroy passed on the tested Windows x64/MSVC configuration; see
the [M4 verification record](../research/records/2026-09-22-exp-m4-windows-verification.md)
for inputs and limits. This establishes neither dispatch nor general native
thread safety.

**Context:** Milestone 4 needs an owner for the first Windows/DX12 upscaler
context. Native handle bits do not establish liveness: successful destruction
has been observed to leave them unchanged. Destroy failures have no established
transactional or retry guarantee. Returned create-error cleanup relies on the
bounded runtime trust assumption below, not a universal signed/external-provider
guarantee. The lifecycle mechanism should not depend on upscaler descriptor
types, without claiming support for other effects.

**Ownership contract:** A successfully created context has one Rust
owner, neither Copy nor Clone, explicitly neither Send nor Sync, with no public
native-handle accessor. The owner independently retains its runtime, a DX12
device COM reference and a private, audited effect-specific dependency bundle.
All natively referenced storage has stable addresses and cannot be externally
mutated or invalidated by moves of the outer owner. Keeping the bundle must
actually keep its pointees and resources alive, including on retention paths;
merely storing borrowed references or raw pointers does not establish this.
Dependency destructors must not panic and must run while their own dependencies
remain alive. The runtime survives all cleanup that may require it.

Descriptor construction is effect-specific. A common internal mechanism owns
the dependencies during create, validates the native outcome and handles
teardown without interpreting the effect's descriptor payloads. There is no
general Effect trait, provider hierarchy or public generic constructor. Runtime
acquisition remains separate and unsafe under D004; no path-taking safe
constructor is introduced. M4 uses null host allocators for create and destroy,
a null message callback, and no backend allocation-callback extension.

**Result and teardown policy:**

| Outcome | Owner and cleanup behavior |
|---|---|
| Create returns OK and a non-null handle | Establish exactly one owner; retain dependencies. Non-null is a necessary check, not independent validation of native pointer validity. |
| Create returns non-OK, with any output handle | Return the original native code; create no owner, never destroy or dereference the output, and release wrapper inputs through RAII, under the runtime trust assumption below. This does not assert provider-internal rollback. |
| Create returns OK with a null handle | Report a native invariant violation; do not destroy; retain effect-specific retained state, the owned device reference and runtime/library ownership as an exceptional fallback. |
| Destroy returns OK | Release retained state and device ownership while keeping the runtime alive through dependent cleanup. |
| Destroy returns non-OK | Remain terminal; preserve the original code and retain effect-specific retained state, the owned device reference and runtime/library ownership without later recovery or retry. |

Consuming `destroy(self) -> Result<(), Error>` and Drop share one teardown
mechanism. It removes live ownership before calling native destroy and never
consults the resulting handle to decide whether to retry. Each context receives
at most one native destroy attempt; ordinary explicit destruction or Drop of a
live owner makes that attempt once. Forgotten owners or process termination may
receive none. Drop discards the error without panicking. Errors distinguish the
Create/Destroy operation, unchanged open `u32` native codes, and native invariant
violations; loader errors remain separate.

Retention is an exceptional safety fallback, not normal cleanup. The mechanism
retains the entire audited critical bundle rather than guessing which opaque
parts survive. It creates no global quarantine, recovery service or retry path.
It prevents additional releases by the wrapper, but cannot repair native partial
destruction or prevent provider-internal unload. No valid-context 4.1.1 destroy
failure or OK/null creation has been observed; these policies are defensive
choices, not experimentally established postconditions.

**Runtime trust assumption for returned create failure:** For the supported
v2.3.0 Windows/DX12 upscaler runtime path, once `ffxCreateContext` returns non-OK,
the wrapper assumes that native code performs no further accesses to caller-owned
dependencies and those dependencies may be released. This is not explicitly
guaranteed by the inspected public header and is not a universal native
postcondition. It is consistent with inspected v2.3.0 source paths and the signed-
runtime returned-error experiment: dedicated descriptor pages were made
inaccessible, and a separate process released descriptor storage, the caller's
device reference and FfxLibrary without an observed subsequent fault or process
failure during the two-second observation window.

The experiment covers one duplicate-backend rejection. The failed call's provider
identity and internal depth remain unknown; internally handled access faults,
other failures and later accesses are not excluded. Successful controls identify
4.1.1, not the failed call's provider. Neither this assumption nor caller cleanup
claims complete rollback of provider-internal allocations.

This evidence-backed assumption is the accepted M4 cleanup policy, not an open
M4 blocker. It remains subject to revision: contradicting evidence requires
reconsidering the supported runtime scope, failed-create cleanup policy or safe
API contract, rather than dismissing it as an irrelevant native bug. The private
`unsafe` construction boundary documents actual caller obligations for valid
inputs, lifetimes and threading; it does not prove this runtime assumption or
transfer that proof to the caller. Public safe APIs must still uphold their
other safety obligations within the supported scope.

**Rationale and consequences:** Independent ownership state avoids double
destruction and reliance on stale handles. Effect-independent retention permits
reuse of the mechanics without a speculative effect framework. Address-stable
storage, explicit dependency ownership and exceptional retention follow the
[code heuristics](../CODE_HEURISTICS.md); representation choices belong in the
[M4 plan](../MILESTONE_4.md), including pinning, COM bindings and initially exclusive
runtime ownership. Future shared runtime ownership is not prohibited.

This is an effect-independent Windows/DX12 slice, not a general backend contract.
Later effects must separately establish shutdown, synchronization, callback and
additional dependency requirements; no refactor-free integration is promised.
Neither Send/Sync exclusion nor successful fixtures establishes global native
thread safety. Dispatch, resource abstractions, query/configure APIs, custom
allocators/callbacks, provider selection and additional backends remain deferred.
Accepting this policy completes no implementation milestone.
