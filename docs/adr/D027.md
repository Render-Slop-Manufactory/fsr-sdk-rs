> [Production verification](../release/2026-10-27-frame-composition-verification.md).

- Date: 2026-10-15.
- Status: **accepted** under explicit maintainer authorization after discussing
  checked defaults and caller-selected exceptions.
- Scope: M16, pinned SDK v2.3.0, existing DX12 resources and both ownership families.
- Extends D012/D014's private configuration, D016's direct native controls and

## Decision

Add portable, non-exhaustive `InputColorSpace::{Linear, NonLinear}` and
`ColorEncodingHint::{Unspecified, Srgb, Pq}`. Defaults are Linear and Unspecified.
`UpscalerOptions::input_color_space` / `set_input_color_space` select the creation
classification. Shared creation/memory-estimate mapping adds the native
`FFX_UPSCALE_ENABLE_NON_LINEAR_COLORSPACE` bit (`1 << 8`) only for NonLinear.
HDR, exposure, depth, motion and dynamic resolution remain independent.
Contexts retain their creation options.

`UpscaleDispatch::color_encoding_hint` / `set_color_encoding_hint` select a
per-frame native hint: Unspecified is zero, Srgb is `1 << 1`, Pq is `1 << 2`.
The enum prevents simultaneous sRGB/PQ hint bits. Unspecified does not assert
linear input and is valid with either classification.

By default, Srgb/Pq require a NonLinear context. A mismatch returns
`Error::InvalidDispatch { reason: DispatchValidation::ColorEncodingContext }`
before COM/native inspection without poisoning a usable context. This is the
wrapper's conservative default, not a universal native precondition established
by upstream evidence.

`set_color_encoding_hint_allow_context_mismatch(hint)` explicitly bypasses only
that pairing check for this frame. `allows_color_encoding_context_mismatch()`
reports the selection; a fresh frame defaults to false. Calling the ordinary
setter restores checking, even when selecting the same hint. No context-wide
bypass, implicit fallback or `unsafe` setter is introduced: setters store
configuration; dispatch remains unsafe. Dispatch poison still rejects first,
and all resource, mask, exposure, scalar, device and lifetime rules remain.

The three native constants receive paired Rust/C++ assertions; descriptor
layouts and exports are unchanged. Both ownership families use the same mapping
and validation. No pixel conversion, PQ luminance normalization, pre-exposure
rewriting, provider detection, extra query or automatic history reset occurs.

## Safety and limits

Actual providers must support the selected creation/hint combination and supplied
signal through estimation, creation, recording and teardown. The caller establishes
encoding, normalization, exposure ordering, output interpretation and temporal
transitions under the existing unsafe acquisition/dispatch contracts. Allowing
a mismatch preserves those obligations. Native OK and resource requirements
alone establish no colour capability or signal interpretation.

RGBA16F colour/output remain required. In the default linear profile, existing
pre-exposure and input-domain output meanings remain. Exposing native controls
does not establish a universal non-linear signal contract, verified PQ pipeline,
quality/performance result or new platform support.

## Basis and verification

The [source investigation](../research/records/2026-10-15-src-non-linear-colour-contract.md)
records the pinned header, guide and sample. The guide recommends NonLinear plus
optional hints; the sample sets creation and dispatch selections independently.
That ambiguity motivates the explicit exception rather than a global prohibition.
PQ normalization, exposure ordering and output interpretation remain unresolved
for the actual provider.

Portable tests cover defaults, exact bits, creation/estimate independence and the
pairing matrix. Prepared Windows controlled fixtures cover both families, exact
per-frame forwarding, restoring checks after an override, pre-COM rejection,
unchanged pre-exposure/reset/exposure selection, resource validation and native
failure poisoning. These fixtures record no GPU work. The
[implementation checks](../release/2026-10-15-colour-encoding-verification.md)
distinguish local execution from pending Windows fixture, C++ ABI, MSRV and
provider/GPU verification at that checkpoint. Subsequent verification and the
current completion boundary are recorded below.

## SDK-access completion boundary, 2026-10-18

The maintainer accepted completion of M16 as faithful SDK-control access with
documented signal limitations. The public [colour and exposure contract](../../crates/fsr-sdk/src/upscaler.rs)
collects the linear profile, independent native controls, checked pairing and
caller obligations for both ownership families. No API, mapping, validation or
unsafe boundary changes are introduced by this clarification.

The [Windows batch](../release/2026-10-15-windows-feature-batch.md) passes controlled
colour mapping/validation, MSRV and independent C++ ABI checks, plus six linear-HDR
GPU frames. The [signal experiment](../research/records/2026-10-15-exp-non-linear-colour-signals.md)
adds 270 integration-passing frames on one GPU/driver/provider. Its 15 failed
changing-pre-exposure predictions remain failures; passing static/reset controls
do not choose a universal non-linear packing rule or establish a wrapper defect.

M16's bounded SDK-access checkpoint is complete. PQ normalization/reference
luminance, non-linear exposure ordering and general temporal/output semantics
remain provider-specific limitations, not promised wrapper behaviour. Choosing a
renderer colour pipeline or reverse-engineering provider internals is not a
completion requirement. No converter, automatic history-reset policy or further
signal experiment is selected. Concrete wrapper correctness or safety defects
remain in scope; upstream contract clarification can require documentation or
implementation corrections.

This completion uses the existing evidence and adds no native execution. Final
release-archive verification remains separate, as do untested providers, formats,
signal ranges and movable non-linear GPU dispatch.
