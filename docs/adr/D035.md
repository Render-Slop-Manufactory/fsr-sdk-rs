# D035 — Typed colour, output and half-float depth formats

- Date: 2026-10-22.
- Status: **accepted**, 2026-10-22, under explicit maintainer instruction to
  accept and implement, including role-bearing device-query errors. Implementation
  and verification are separate checkpoints below.
- Scope: next U05 slice for development wrapper `0.3.0` / sys `0.1.2` under
  [amended D031](D031.md), pinned SDK v2.3.0, Windows x64/MSVC + DX12 and both
  ownership families. This slice
  does not complete U05 or narrow the selected complete-upscaling release target.
- Relationship: extends [D011](D011.md)'s typed resource profile after
  [D034](D034.md); preserves [D024](D024.md)'s allocations/active regions,
  [D027](D027.md)'s colour controls, [D030](D030.md)'s generator contract and
  [D032](D032.md)'s shared preflight/recording validation.

## Problem and basis

At proposal time, D034 had added explicit native motion scales and RG32F motion.
Main colour/output and both reactive-generation colour inputs still required
RGBA16F; device depth still required R32F. A renderer using other ordinary typed
formats had to supply additional textures even when the SDK could represent its
original allocation.

The [existing source record](../research/records/2026-10-19-src-upscaling-formats-and-motion-scale.md)
and [dispatch assessment](../research/upscaling-dispatch.md#external-formats-and-explicit-motion-scales)
separate external role semantics, native conversion, generated DX12 views and
actual-provider support. Their evidence supports selecting a typed extension
for implementation and verification, not declaring all converter formats usable.
The record's source/provenance limitations remain as documented in the assessment.

This proposal uses that evidence and targeted primary-documentation checks. It
adds no research result, runtime observation or provider-support claim. D034's
[passing verification](../release/2026-10-21-native-motion-verification.md) covers
its motion slice only.

## Accepted role/format matrix

Read actual `ID3D12Resource::GetDesc().Format`; retain the existing borrowed
resource constructors. Add these exact typed allocations, subject to the device
checks and caller-established actual-provider contract below:

| Operation / role | Previously accepted formats | Added formats |
|---|---|---|
| Main colour | `R16G16B16A16_FLOAT` | `R32G32B32A32_FLOAT`, `R11G11B10_FLOAT`, `R10G10B10A2_UNORM`, `R8G8B8A8_UNORM` |
| Main output | `R16G16B16A16_FLOAT` | The same four additions, independently validated as output roles |
| Main device depth | `R32_FLOAT` | `R16_FLOAT` |
| Main motion | `R16G16_FLOAT`, `R32G32_FLOAT` | None; D034 remains the motion contract |
| Explicit exposure | `R32_FLOAT`, 1×1 | None |
| Supplied reactive and transparency/composition masks | `R8_UNORM` | None |
| Reactive generation: opaque-only colour | `R16G16B16A16_FLOAT` | The four proposed colour additions, independently verified for generation |
| Reactive generation: colour including translucency | `R16G16B16A16_FLOAT` | The same four additions, independently verified for this input |
| Reactive generation: output | `R8_UNORM` | None |

Main input and output formats are independent. Generation colours may also use
different accepted formats: the renderer must supply comparable decoded signals
and account for their different quantization. Do not require format equality or
infer generator support from a main-colour test. Existing read-only aliasing and
output non-aliasing rules remain operation-specific.

RGBA32F provides a straightforward additional floating representation; packed
floating and UNORM formats cover common renderer colour allocations. R16F is a
separate scalar floating device-depth option. Output acceptance is an explicit
choice to verify each candidate's store path, including packed RGB output; it
is not an exact output-format guarantee found in AMD's documentation.

The pinned [DX12 helper](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/dx12/ffx_api_dx12.h#L59-L180)
contains conversions for these additions. Preserve its
[surface-enum values](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/ffx_api_types.h#L25-L68)
in the raw layer:

| New `FFX_API_SURFACE_FORMAT_` suffix | Value |
|---|---|
| `R32G32B32A32_FLOAT` | 3 |
| `R8G8B8A8_UNORM` | 10 |
| `R11G11B10_FLOAT` | 16 |
| `R10G10B10A2_UNORM` | 17 |
| `R16_FLOAT` | 21 |

These five constants extend the selected raw declarations; adding a constant
does not accept it in another role. Preserve C layouts, descriptor tags, AMD
attribution and notices. No dependency, SDK pin or acquisition change is needed.

## Representation and public contract

No public format enum, view selector, format override or new resource wrapper
is needed. Selection follows the real typed allocation. Keep native conversion,
operation/role acceptance and device requirements distinct in small private
helpers shared by both owners and their optional preflight paths.

Keep the selected format in native metadata and preserve real usage flags.
Do not reinterpret, copy, expand channels, normalize values or hide UAV
capability. New formats in unselected roles reject with the existing
`DispatchValidation::Resource` / `ResourceProperty::Format` error.

Storage and signal interpretation remain separate:

- UNORM colour values are normalized by the typed view; `_UNORM` does not select
  an sRGB decode, native colour-space flag, PQ normalization or exposure policy.
  Existing D027 options/hints remain independent, with their existing checks.
- R11G11B10F has no alpha and cannot represent negative colour. UNORM output
  cannot preserve values outside its representable range. The renderer selects
  compatible signals and accepts storage quantization/clamping; the wrapper
  promises neither an alpha-preservation contract nor a tone-mapping operation.
- R16F contains device depth with the selected standard/reversed and
  finite/infinite projection contract. It is not linearized eye-space distance.
  The renderer owns precision loss and depth-range suitability; no numeric
  promotion, depth conversion or new camera default occurs.

The actual provider must support the selected operation, roles, formats, flags
and signals under the existing unsafe acquisition/dispatch contracts. Device
support bits, provider identity and resource-requirement queries are not a
provider-format certificate. Add no provider allow-list, fallback or probe hidden
inside dispatch. A native recording error retains the existing terminal policy.

## DX12 inspection and generated views

Preserve the existing single-sample/mip/slice Texture2D shape, exact maximum
allocations, active-size rules, canonical identity/device checks and aliasing
contracts. Perform all device-format queries after metadata and canonical device
membership checks, before FidelityFX entry. Existing poison still rejects first.

For every newly admitted role/format pair, query the retained context device
with `D3D12_FEATURE_FORMAT_SUPPORT` for the real typed format. Select this profile:

| New role / allocation capability | Required support |
|---|---|
| Main/generation colour input or R16F depth | `Support1::TEXTURE2D`, `SHADER_LOAD`, `SHADER_SAMPLE` |
| Any such input also carrying `ALLOW_UNORDERED_ACCESS` | Additionally `Support1::TYPED_UNORDERED_ACCESS_VIEW` |
| New main output format | `Support1::TEXTURE2D`, `SHADER_LOAD`, `TYPED_UNORDERED_ACCESS_VIEW`, plus `Support2::UAV_TYPED_STORE` |

The input load/sample pair is a conservative wrapper profile consistent with
D034, not a claim that every provider uses both instructions. New outputs must
have `ALLOW_UNORDERED_ACCESS` and must not have `DENY_SHADER_RESOURCE`: the
reported backend also constructs an SRV. Its SRV motivates the output load bit;
the output role does not add a sampling requirement. Shader-read denial reports
the existing `ResourceProperty::ShaderReadable` before device-format queries.

UAV descriptor creation and typed shader access are separate checks. Read-only
inputs acquire no typed-UAV load/store requirement merely because their real
allocation permits a UAV. For new outputs require typed stores; do not add typed
loads without an established output-read requirement. Microsoft's
[support bits](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ne-d3d12-d3d12_format_support2)
distinguish those operations. The pinned open FSR3
[output callback](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/include/gpu/fsr3upscaler/ffx_fsr3upscaler_callbacks_hlsl.h#L477-L484)
stores the external result; it does not establish closed-provider access rules.
If a selected provider/path needs additional accesses, resolve and record that
contract before advertising its integration. Device bits alone cannot do so.

Retain `ResourceProperty::FormatSupport` in the role-bearing
`DispatchValidation::Resource` error for missing required bits. For failed
queries on newly admitted role/format pairs,
add `InspectionObject::ContextDeviceForResource(ResourceRole)` to the existing
non-exhaustive enum. Return `Error::Dx12Inspection` with that role-bearing object,
`InspectionOperation::CheckFormatSupport` and the exact HRESULT. The object
identifies the retained context device inspected on behalf of the supplied
resource role; it does not imply a query on the resource itself. Existing
`InspectionObject::ContextDevice` and D034's RG32F query-error behaviour remain
unchanged.

Both new-format failure paths identify the resource role without relying on
query order. Neither error poisons a usable context or enters FidelityFX.
Inspect in a documented fixed role order; avoid persistent caches or independent
resource retention. Dispatch repeats inspection even after a successful optional
preflight.

D034's RG32F checks remain intact. Previously accepted role/format pairs keep
their existing validation and query behaviour, including baseline RGBA16F output
and R8 generator output. The stricter new-format output profile is deliberate;
this proposal does not retrospectively claim all existing paths are device- or
view-certified. Changes to an existing contract require their own justification.

## Implementation and verification after acceptance

Implement and verify in three increments: typed main colour/output; R16F depth;
then reactive-generation colour. The matrix above is the accepted scope of all
three increments. Acceptance authorizes these changes and bounded checks,
without turning incomplete or failed evidence into a passing checkpoint.

1. **Raw and controlled contracts.** Add the five constants and independent
   Rust/MSVC header assertions. Compare each conversion with the pinned C++
   helper, including actual usage bits and full resource metadata. Cover the
   complete accepted/rejected role matrix for both owners and both operations,
   including unchanged exposure, masks, motion and generator output.
2. **Device/error paths.** Exercise every missing support bit, failed query,
   new-output shader-read denial, input UAV capability, identity/device mismatch,
   deterministic error precedence and unchanged baseline query counts. Verify
   failed queries separately for every newly queried role in both operations and
   owners, using the same HRESULT to prove the errors retain distinct roles,
   `CheckFormatSupport` and exact HRESULT bits. Preserve D034's existing RG32F
   error representation. Verify preflight/dispatch agreement, no native entry on
   rejection, repeat inspection, successful retry after metadata/inspection
   errors and terminal native failure.
3. **Bounded main-upscaling execution.** Use selected 4.1.1/3.1.5 on the recorded
   Windows/DX12 setup and both public owners. Change one role at a time against
   existing formats: four new main-colour formats, four new output formats and
   R16F depth. Each arm uses a reset frame and two continuing frames. Include
   distinct RGB content, standard/reversed depth, sharpening disabled/enabled
   for each new output, and supported UAV-capable versus ordinary input arms.
   Add one mixed-new-format arm and one D024 active-output shrink/grow sequence
   per owner/provider; a full format cross-product is unnecessary.
4. **Independent observations.** Encode and decode uploaded data independently,
   checking actual quantized values, row pitches and channel order. Compare the
   wrapper with a pinned-header C++ direct call using the same provider, options,
   formats and input bytes. Establish repeatability and freeze equality/tolerance
   criteria before confirmation. Cross-format bit equality is not an acceptance
   condition. Require complete active-region writes, finite decoded floating
   results, input-sensitive controls, fences, ordinary debug/device checks and
   cleanup. Choose values within each format's range; separately check distinct
   above-one floating colour without interpreting quantization as a wrapper defect.
5. **Generator-specific execution.** On selected 3.1.5, exercise each added colour
   format in each generator input against the existing format in the other role,
   for both owners. Include an equal-decoded-colour zero-mask control, a contrast
   pattern, active-region shrink/grow and subsequent supplied-mask consumption.
   R8 output, ordering and state obligations stay unchanged. The existing
   [4.1.1/2.3.4 no-write outcomes](../research/records/2026-10-19-exp-reactive-mask-providers.md)
   remain explicit failures; they provide no new-format generator verification.
6. **Consumers and documentation.** Run appropriate stable/MSRV and portable/
   no-default checks, independent Windows ABI checks and public downstream
   consumers. Keep DX12 inspection private to its Windows/backend gates. Update
   Rustdoc's role/format tables, examples, raw inventory and release coverage
   with actual results and limits. Final extracted-package verification remains
   a separate release-closure step.

An absent adapter capability is a recorded unsupported configuration, not a
passing GPU case. A skipped or failed role/provider arm establishes no support
for that combination. Reconcile such outcomes explicitly before claiming this
slice verified; a failure may require a reviewed scope/contract amendment.

These are mapping, resource and integration checks. They select no image-quality
or performance gate and require no broad provider campaign or automatic GBV run.
Sentinel/readback observations and clean debug output do not prove bounded
shader access or untouched padding. D024's actual-provider trust and whole-output
write allowance remain. The renderer still owns state transitions, residency,
submission, fencing, backing-storage non-overlap and terminal cleanup.

## Alternatives and acceptance boundary

Adding every native converter entry would conflate format representation with
operation/view/provider support. A public raw-format bypass would also permit
metadata that disagrees with the resource. Keeping only RGBA16F/R32F would leave
ordinary typed renderer allocations outside the selected coverage objective.
The selected matrix adds explicit roles without another public configuration
layer, at the cost of device queries for the newly admitted pairs.

The maintainer accepted this matrix, the new-format device/view profile,
generator format independence, role-bearing query errors and bounded verification
plan on 2026-10-22, with explicit implementation authorization. Neither U05
completion nor final release readiness follows from accepting this slice.
