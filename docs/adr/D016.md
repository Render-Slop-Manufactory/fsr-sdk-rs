# D016 — Separation of Native Provider Controls and SDK-Level Policies

- Recorded: 2026-10-09.
- Accepted: 2026-10-09, by explicit maintainer authorization after consistency review.
- Status: **accepted** — cross-feature architectural constraint; documentation-only decision.
- Scope: public parameter controls and quality-oriented selection or signal-processing policies in `fsr-sdk`.
- Release: no release selected; no public API, module, dependency or native capability added.
- Relationship: complements D014 without superseding it or any other accepted decision.

## Context

[D001](D001.md) separates faithful raw bindings from ergonomic Rust ownership and validation. That boundary does not by itself distinguish a caller-selected provider parameter from an SDK-selected quality strategy: both can belong in the ergonomic wrapper and both may execute the same native implementation.

[D014](D014.md) accepts `Sharpening::Native(NativeSharpness)` as direct control of the selected provider's checked parameter, separately from `Disabled`. Enabled zero is not disabling the pass. D014 preserves room for later evidence-based profiles without selecting one. Its public input migration and sharpening API are implemented in current source under M8. Its recorded native experiment passed execution and repeat checks but failed the original effect criteria; those failures remain evidence. D014's 2026-10-09 amendment selects the direct-native M9 integration protocol, whose GPU execution and final artefact verification remain pending.

Future work may introduce SDK-selected settings for sharpening, render resolution, masks or exposure. Such strategies could use the existing provider or introduce additional processing. Without an explicit contract, adding them could silently reinterpret an existing direct control or present a preset as a general quality improvement. Conversely, imposing the same modes on every resource and utility would obscure useful domain distinctions.

[The code heuristics](../CODE_HEURISTICS.md#direct-provider-controls-and-sdk-level-policies) refer to this record for the distinction. This decision makes the preservation of public direct-control semantics a durable architectural constraint. Naming conventions remain subordinate to concrete feature contracts.

## Decision

This record governs the cross-feature separation of direct controls and SDK
quality policies. Existing feature decisions retain authority over their concrete
contracts; no accepted decision is superseded.

### Preserve supported direct controls

1. When a public feature offers direct control of a provider parameter or behaviour, optional SDK quality policies must not make that control dependent on selecting an SDK policy. Preserve an independently selectable direct route within its documented supported domain. This does not require wrapping every native feature, adding a route for an unsupported provider, or offering every policy combination on the same context.
2. Preserve the direct route's documented meaning. Checked types, rejection of invalid inputs, descriptor construction and necessary, documented representation or unit conversions are permitted. Quality-driven parameter substitution, hidden clamping, heuristic tuning or extra signal filtering must not be introduced into that route implicitly. A policy that internally invokes the same native pass is still an SDK policy when the SDK chooses or transforms the setting.
3. SDK quality policies must be explicit and describe the parameters or signals they select or transform. They may complement native capabilities, but must not silently replace an existing direct route or alter established defaults. State affected creation/frame settings, relevant state and interactions, and any additional resource or execution obligations in the concrete feature contract.
4. Claims about reproducibility, effects, image quality or performance require evidence appropriate to the specific claim and a stated scope. Mapping correctness, successful execution, observed output changes, calibrated parameter selection and validated quality outcomes are separate claims. Native access does not need to satisfy an SDK quality target, but still needs the applicable mapping, execution and safety verification.
5. Introduce additional abstraction only for an implemented policy or a concrete requirement that justifies it. This record introduces no public types, variants, traits, modules, profile registry, generic policy framework or cross-backend interface. It selects no policy implementation or new experimental programme.

These rules concern control provenance and quality behaviour. They do not remove support-profile restrictions, native trust assumptions, validation, ownership, poisoning, terminal cleanup, threading or renderer obligations. Any evidence-driven change to a supported safety domain still needs the existing contract and compatibility review.

### Semantic naming conventions

Use these terms only where they clarify a real feature distinction. They are not required variants, a hierarchy of quality levels, or a mutually exclusive taxonomy.

| Term | Meaning when used by this SDK | Limits |
|---|---|---|
| `Native` | Direct control of a documented provider parameter or behaviour, with its meaning preserved by the SDK. | Does not mean raw or unchecked access, an execution backend, experimental status, identical output across providers, or a quality guarantee. The term applies to the named control, not automatically to the whole rendering pipeline. |
| `Calibrated` | An SDK policy whose selection or transformation rule was empirically determined through an identified, reproducible calibration procedure for a stated domain. | Calibration is not validation of universal quality. Document the calibration target and evidence; claim an outcome only to the extent independently supported. |
| `Preset` | A predefined named configuration. | The term alone adds no quality assurance and does not identify who defined the configuration. A preset may also be calibrated; document provider, SDK or caller provenance separately. |
| `Disabled` | Explicit deactivation of the named capability according to its contract. | Do not equate it with a native zero parameter, a neutral factor, an absent resource or an identity output without the feature-specific semantic basis. |

Prefer domain names when they describe the choice more accurately: explicit exposure, caller-supplied masks, provider recommendations, camera conventions and units need not use this vocabulary. Provider-side internal heuristics do not become SDK policies merely because the SDK exposes their native controls.

`Default` describes what applies without an explicit choice; `Recommended` describes an endorsed configuration and should identify who recommends it. A maintainer-recommended configuration can be a preset without being calibrated, and can be selected as a default by a separate feature decision. None of these properties implies the others. A single recommended native value may need only documentation rather than a new preset abstraction. These words select neither additional enum variants nor a Rust `Default` implementation; D014's implicit sharpening setting remains `Disabled`.

### Calibration evidence and scope

A policy described as calibrated must identify its target, selection or transformation rule, calibration inputs and references, evaluation method, relevant SDK/runtime/provider and hardware configuration, tolerances or repeat criteria, and a reproducible procedure. Identify the procedure or profile revision and retain negative or inconclusive results. Reproducibility does not require identical output on every device.

State the domain covered by the evidence, including workload and interacting settings where material. A calibrated parameter table does not by itself establish improved output or compliance with a quality bound. Claims extending beyond the calibration inputs need validation suited to that extension; repeating the tuning set alone does not establish generalization. The documentation must distinguish an empirical observation from a conditional promise, and must not imply universal quality from bounded tests.

If a policy depends on configuration matching, its concrete contract must define how relevant assumptions are established and what happens outside the covered domain. An error, an explicitly requested unverified application, or a documented fallback may be appropriate. A fallback must not continue to imply validated calibration coverage. This record selects neither automatic provider discovery nor a fallback mechanism.

Provider changes, driver updates and different combinations of exposure, colour encoding, render scale, masks or temporal state do not automatically inherit calibration evidence. A combined policy needs evidence for the combination's claimed outcome. A locally direct parameter remains direct even when another independently selected control uses an SDK policy.

## Rationale

The stable boundary is who selects or transforms a control, not who executes the GPU code. Preserving that boundary allows applications to retain provider behaviour, apply their own strategies and compare later SDK strategies without reinterpreting an existing public parameter.

The existing sharpening findings show why successful native execution and a selected quality criterion must remain separate. A failed bounded quality criterion does not justify hiding native functionality; a native label does not justify claiming improved images. Reproducible calibration makes parameter provenance auditable without promoting a finite test suite to a universal quality guarantee.

Local feature contracts remain necessary because creation settings, per-frame parameters, provider queries and separate GPU operations have different state and lifetime boundaries. The project already has suitable encapsulation and extension mechanisms; semantic separation does not justify new modules or generic abstractions by itself.

## Alternatives

| Alternative | Assessment |
|---|---|
| Keep only D014 and the code heuristics | Sufficient for the current implementation, but not selected because a durable project-wide direct-control invariant is intended. |
| Defer this record until the first concrete SDK quality policy | Not selected. Concrete implementation will inform profile revisions, matching and interactions; preserving existing direct controls does not require selecting such a policy now. |
| Require `Native`, `Calibrated`, `Preset` and `Disabled` for every feature | Rejected. The terms describe different dimensions, are not disjoint, and fit resource and utility contracts poorly. |
| Expose all provider functionality through raw escape hatches | Not selected. This bypasses or duplicates the curated ergonomic boundary and incurs explicit safety and compatibility costs without a demonstrated requirement. |
| Introduce a generic policy trait or dedicated policy modules now | Not selected. No common implementation contract has been established, and unrelated context, frame and GPU-operation boundaries should not be flattened. |
| Use only feature-specific names and parameter helpers | Compatible with this decision. Often the simplest implementation when a concrete policy only computes values and needs no privileged access. |

## Consequences

Existing direct controls retain their documented mapping and independently selectable route when optional quality strategies are added. This is a semantic and documentation constraint, not a commitment to complete native coverage or forever-fixed hardware support.

Future policies incur explicit evidence, scope and compatibility work. Private fields and non-exhaustive enums do not guarantee that new payloads, resources, required inputs, defaults or traits are compatible. Preserve existing public traits and meanings; review later additions under D009, D012 and D014. An identifiable calibration revision may help reproducibility, but no public representation or versioning format is selected here.

Verification must remain proportionate and separated: deterministic mapping/validation checks, downstream API/trait checks, applicable native execution checks, and experimental validation of any claimed policy outcome. Additional GPU processing requires its own resource-state, lifetime, ordering, failure and cleanup contract. No new Rust tests or native runs follow merely from recording these principles.

This record is the normative source for the cross-feature invariant; the code heuristics refer to it rather than maintain competing rules. Concrete APIs and evidence remain in their existing feature records. Acceptance changes no other ADR status, existing technical contract, implementation, release scope or publication authorization.
