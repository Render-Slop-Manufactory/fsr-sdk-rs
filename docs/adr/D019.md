# D019 — Proton as an Explicit DX12 Verification Environment

- Date: 2026-10-12
- Status: **accepted — 2026-10-13, explicit maintainer authorization**
- Scope: Verification infrastructure, Linux-hosted Windows/DX12 execution
- Related decisions: D002, D007, D017, D018
- Related roadmap items: V03, B01, V07, V07d, V07e, V08, V09
- Release impact: None; no public Rust API changes

## Context

`fsr-sdk-rs` currently supports the official AMD FidelityFX SDK through a Windows x64/MSVC DirectX 12 integration.

Its verification infrastructure already provides native GPU workloads, ABI validation, independent result analysis, bounded execution, and reproducible evidence records.

At proposal time, native GPU verification depended on a Windows execution
environment. This limited accessible hardware configurations and prevented
Linux-based development systems from running the Windows/DX12 workloads directly.
The bounded Proton proofs below subsequently demonstrated that execution path.

Proton provides a potential additional execution environment:

```text
Linux verification host
          |
Windows x64/MSVC test executable
          |
AMD FidelityFX DX12 runtime
          |
Proton / Wine
          |
VKD3D-Proton
          |
Vulkan / host GPU driver
          |
GPU
```

This could allow the same Windows/DX12 verification workloads to execute on Linux hardware, including SteamOS-based devices such as Steam Deck and Steam Machine.

The existing D017 acquisition infrastructure can supply pinned AMD SDK artefacts independently of the host operating system.

Successful Proton execution is not yet established for the project's complete native SDK workload.

The purpose of this decision is to make Proton-based verification an explicit, durable project objective without expanding the supported native SDK platform contract.

## Decision

### 1. Verification scope

The project will pursue **a reproducible Proton verification path** for Windows/DX12 binaries executed on Linux, beginning with a bounded feasibility proof on one Linux/GPU configuration.

Acceptance selects this objective and the initial proof; it does not describe Proton as an already supported verification environment. Maintaining a supported path is the longer-term objective, contingent on useful GPU execution evidence and the explicitly covered regression cases.

The first deliverable covers Linux-hosted cross-compilation, Proton launch, pinned AMD runtime loading, context creation, one existing deterministic upscaler workload, GPU completion, checked readback and teardown. It does not require the complete native/temporal suite or a second hardware configuration. The acceptance criteria and later extensions are defined under [Verification and rollout](#verification-and-rollout).

It does not establish a compatibility guarantee for every Proton version, GPU, driver, SDK provider, or effect.

The supported native Rust SDK target remains `x86_64-pc-windows-msvc` with DirectX 12.

Proton execution:

- Does not constitute native Linux support.
- Does not constitute a native Vulkan backend.
- Does not imply that the AMD SDK officially supports Proton.
- Does not establish FSR 4 or any particular provider's availability.
- Does not extend the public API, native ownership contracts, or `unsafe` guarantees.

Native Vulkan support remains a separate concern under B01.

### 2. One device-independent verification profile

Develop one named verification profile, initially exposing the bounded proof's declared cases:

`proton`

The profile shall use common orchestration for compatible Linux hosts regardless of their GPU model. The first verified baseline covers only the configuration actually exercised; portability remains a separate follow-up.

Steam Deck, Steam Machine, and conventional Linux PCs shall not require separate profile implementations.

Hardware, driver, selected provider, and runtime capabilities are detected and recorded at execution time.

Hardware-specific differences may influence available test cases, execution timeouts, and interpretation of results, but must not silently weaken shared correctness criteria.

The intended CLI is:

```bash
python tools/verification/run.py plan proton

python tools/verification/run.py run proton \
    --native
```

The precise options remain an implementation detail and must follow the existing verification CLI conventions.

No graphical Steam interaction, manual game registration, or per-device launch configuration shall be required.

### 3. Cross-compilation and execution

Infrastructure development may begin on Windows. A preliminary runtime spike
may prepare verified Windows-built binaries there and execute them later on a
real Linux host, including the Steam Deck, without WSL. This isolates Proton
execution questions from cross-build questions; it does not satisfy V07a's
Linux-hosted build checkpoint. The ultimate workflow below retains that checkpoint.

The [experimental handoff protocol](../../tools/verification/proton-spike.md)
documents this preliminary split and its narrower evidence limits. It is historical
spike evidence, separate from the later Linux-hosted proof and this acceptance.

The intended complete workflow is entirely Linux-hosted:

1. Check the required build and execution tools.
2. Cross-compile the relevant Rust tests for `x86_64-pc-windows-msvc`.
3. Cross-compile the existing Windows C++ GPU verification helper.
4. Stage the executable, helper DLLs, and verified AMD SDK runtime files.
5. Launch the Windows test executable through Proton.
6. Collect exit status, logs, GPU outputs, and environment information.
7. Evaluate results through the existing verification infrastructure.
8. Record complete reproducibility evidence.

The verified initial path uses `cargo-xwin`, LLVM/Clang and LLD for Windows
cross-compilation and `umu-run` for CLI-driven Proton execution. The evidence
records identify the concrete tested versions, Microsoft SDK/CRT inputs and
runtime dependencies; these establish the bounded baseline, not compatibility
with arbitrary installations.

Before executing the first proof, select and record concrete versions and provenance for the Rust toolchain, cross-build tools, Windows SDK/CRT inputs, Proton distribution, runner and execution runtime. Identify bundled Wine/VKD3D components through the selected distribution's version and provenance where independent version reporting is unavailable. Record the host GPU and driver separately. Tool names or mutable labels alone do not identify the tested configuration.

These are verification tools, not public crate dependencies. Any required
acquisition remains an explicit setup action; no automatic tool installation
is implied by profile execution. Full runtime bootstrap/offline policy is V08.

Proton must remain a runtime execution choice rather than a new Rust compilation target.

Global Cargo runner configuration must not accidentally redirect ordinary Windows verification through Proton.

### 4. Implementation boundaries

The Proton-specific implementation should initially reside in:

`tools/verification/proton.py`

This module owns Proton-specific environment preparation, cross-build coordination, staging, process invocation, and environment identification.

Existing infrastructure remains responsible for:

| Component | Responsibility |
|---|---|
| `run.py` | CLI and orchestration |
| `profiles.py` | Profile registration and case inventory |
| `execution.py` | Process execution, watchdogs and failure reporting |
| `records.py` | Provenance and evidence records |
| `analysis.py` | GPU output and image-quality analysis |
| `native.py` | Existing Windows-native execution |
| `sdk.py` | Explicit pinned SDK acquisition and verification |

Existing native test cases should be reused wherever their execution and acceptance contracts are applicable.

Windows-specific test preparation may be factored into shared helpers where necessary, but wholesale duplication of native workloads is not acceptable.

Further module splitting is deferred until justified by actual implementation complexity.

### 5. SDK acquisition and deployment

Proton verification shall reuse the existing SDK acquisition mechanism established by D017.

The AMD SDK remains pinned to the selected project baseline. Required files shall be loaded from a verified local SDK installation, normally under:

`external/FidelityFX-SDK/v2.3.0/`

Verification shall preserve existing file-integrity requirements and respect the distinction between SHA-256 verification and Authenticode trust validation.

The initial proof must declare its trust inputs and signature-check method before AMD execution. D017's offline hash verification is not Windows strict-mode trust verification. An unavailable Linux-side signature check must remain explicitly unavailable; it cannot be reported as a Windows trust-policy pass or silently satisfy an equivalent requirement. The staged loader/provider layout and observed loaded module paths must also be recorded rather than assuming D007's Windows observations establish Proton resolution.

No SDK acquisition, Proton installation, or other network operation may occur implicitly during ordinary Cargo builds.

An explicit bootstrap operation may acquire missing development tools and runtime components.

Any such acquisition must have a defined version/provenance policy, bounded downloads, and appropriate integrity checks. Mutable upstream labels alone are insufficient for claiming reproducibility.

After initial setup, offline execution should be supported wherever all required artefacts are locally available.

SDK acquisition and Proton environment preparation remain separate responsibilities.

### 6. Verification contracts and evidence

The Proton profile must distinguish the following observations:

1. **Build:** Windows binaries compile successfully on the Linux host.
2. **Launch:** Proton starts the executable successfully.
3. **Runtime:** The AMD SDK DLLs load and the required symbols resolve.
4. **Context:** A native FSR context can be created and destroyed.
5. **Dispatch:** An SDK operation successfully records GPU work.
6. **Execution:** The GPU completes the submitted work.
7. **Output:** A GPU readback confirms the expected output properties.
8. **Quality:** Applicable temporal and image-quality tests satisfy their declared criteria.

Success at one level does not establish success at subsequent levels.

In particular, a successful context creation or native return code does not prove correct GPU output.

Where the same workload can execute under Windows and Proton, retain common inputs, selectors, and correctness checks as far as the environments permit.

Platform-specific differences must remain explicit.

Windows DirectX debug-layer and GPU-based validation guarantees must not be silently removed or treated as equivalent to Vulkan-side diagnostics.

Unavailable validations are recorded as unavailable or not executed, and cannot satisfy a required acceptance criterion.

The current [GPU helper](../../crates/fsr-sdk/tests/native/gpu.cpp) returns failure from `m6_enable_debug` when `D3D12GetDebugInterface` is unavailable. The initial proof must establish what the selected Proton configuration provides before reusing a Windows case whose contract requires that layer.

Declare a validation matrix before the run: which checks are required for the bounded Proton proof, which Windows diagnostics are available, and which remain outside its claims. Missing required validation blocks acceptance. If Windows debug diagnostics are unavailable, a separately declared Proton case may still establish dispatch, completion and checked output using the common workload and numerical checks, while explicitly retaining the missing Windows validation as a limitation. It cannot pass the unchanged Windows case or claim equivalent diagnostic coverage.

Any helper adaptation must select that execution mode explicitly, preserve the existing Windows behaviour, and report diagnostic availability independently of error counts. A zero count from an unavailable debug interface is not evidence of zero validation errors. Vulkan-side diagnostics must be named and recorded separately, with no assumed equivalence to the DirectX debug layer or GPU-based validation.

The initial output checks must be frozen before execution and retain the selected Windows workload's applicable input, dimension, finite-value and output-write checks, successful dispatch/submission/fencing/readback and no device removal. Temporal quality thresholds and hardware-dependent tolerances are outside the initial proof; later regression stages must declare their own applicable contracts before execution. No cross-platform byte-identical output is required unless a particular protocol explicitly justifies it.

### 7. Environment and provider identification

Each native Proton verification run shall record sufficient information to identify its execution environment, including where available:

- Linux distribution, kernel and architecture
- GPU identity and relevant capabilities
- Mesa or proprietary driver version
- Vulkan device and driver identity
- Proton and Wine versions
- VKD3D-Proton version
- Steam Linux Runtime or equivalent execution environment
- Rust toolchain, Windows target and cross-build tools
- AMD SDK version and loaded DLL hashes
- Selected SDK provider identity and reported version
- Test binary identity and executed test cases

Provider metadata obtained through M10 Queries may contribute to this evidence.

A reported provider version alone is not sufficient proof that a particular ML implementation or execution path actually ran.

Expected FSR selection based on GPU architecture must be distinguished from observed provider selection and independently verified GPU behaviour.

A Steam Deck may exercise an FSR 3 fallback, while another device may exercise an FSR 4 path. Neither outcome shall be assumed before execution.

### 8. Execution safety and reproducibility

The Proton profile shall retain the verification infrastructure's existing principles:

- Bounded execution and explicit watchdogs
- Failure isolation for GPU workloads
- Independent execution and evaluation outcomes
- No reuse of stale successful results
- Explicit environment and input identity
- Reproducible case selection
- Preservation of negative controls
- Controlled staging and cleanup
- No weakening of existing Windows acceptance criteria

A dedicated or otherwise safely isolated Proton prefix should be used to prevent unrelated applications or concurrent test runs from affecting the verification environment.

Failed launches, missing Vulkan capabilities, unsupported providers, GPU device loss, and invalid readbacks must be distinguishable in the resulting evidence.

Unsupported capability is not equivalent to a successful test.

## Alternatives considered

**Manual Steam registration:** Rejected because GUI-based configuration and manual launch steps undermine reproducibility and unattended execution.

**Wine without Proton:** Remains a possible future execution strategy, but Proton is selected as the initial target because of its established DirectX 12 translation infrastructure.

**Separate profiles for Steam Deck and Steam Machine:** Rejected. Hardware differences belong in environment identification and capability-aware test evaluation, not duplicated orchestration.

**Native Linux/Vulkan SDK integration:** Not a substitute. It requires an independently supported native AMD integration path and remains governed by B01.

**Separate verification framework:** Rejected. Existing orchestration, watchdogs, result analysis, and evidence infrastructure should be reused.

## Consequences

### Benefits

- Expands the range of hardware available for real GPU verification.
- Enables Linux-hosted development and verification of the Windows/DX12 implementation.
- Creates opportunities to observe provider fallback and runtime compatibility.
- Reuses existing GPU tests and analytical infrastructure.
- Supports unattended, reproducible experiments on SteamOS devices.
- Provides additional evidence about DX12 execution through a translation layer.

### Costs and limitations

- Adds cross-compilation and Proton toolchain maintenance.
- Introduces translation-layer-specific failure modes.
- May require adaptation of the existing C++ GPU helper.
- Cannot reproduce all Windows debugging guarantees.
- Later regression work may require runtime- or hardware-dependent tolerances, declared and justified separately; the initial proof must not relax output checks after observing results.
- Cannot guarantee that every AMD runtime or provider is compatible with Proton.
- Does not replace native Windows verification.

The additional maintenance burden is justified only if actual GPU workloads can be executed and their results evaluated meaningfully.

## Verification and rollout

Track the initial implementation and evidence under the roadmap item:

**V07 — Proton DX12 Compatibility Verification**

Initial bounded deliverable, on one explicitly identified Linux/GPU configuration:

| Stage | Required evidence |
|---|---|
| V07a — Environment | Recorded tool/runtime versions and provenance, reproducible CLI preparation, Linux-hosted Windows Rust/C++ cross-build and exact executable/helper identities |
| V07b — Runtime | Proton launch, pinned AMD DLL hashes and observed module paths, declared trust-check outcomes, provider identity, context creation and teardown |
| V07c — GPU | One existing deterministic upscaler workload with frozen applicable output checks, successful SDK dispatch/submission/fencing/readback, no device removal, explicit validation availability and successful teardown |

The initial V07 deliverable can be marked Verified when V07a–V07c pass together and a self-contained record states the inputs, commands, observations and validation limits. Cross-compilation, launch or context creation alone cannot complete it. A failed or unsupported GPU path must remain a recorded failed or blocked proof, not a verified GPU baseline.

Subsequent extensions have independent selection and completion status:

| Follow-up | Status | Required evidence |
|---|---|---|
| V07d — Regression | Deferred until after 1.0.0; explicit selection required | Four selected temporal protocols ran on Deck and Machine; reset passes, other image criteria fail, and Deck jitter remains blocked ([comparison](../research/upscaling-dispatch.md#selected-proton-temporal-regressions)). Maintainer deferred further quality validation until after 1.0.0 on 2026-10-18 ([priority](../../SCOPE.md#verification-priority)) |
| V07e — Portability | Verified for the bounded proof | The same selected protocol exercised on a second independent Linux/GPU configuration, with a comparison of capabilities, providers and results |
| V08 — Runtime bootstrap/offline execution | Verified for local import | Two Deck confirmations verify bounded local import, runtime inventories and execution with networking disabled; missing inputs fail without downloads ([record](../research/records/2026-10-14-exp-proton-offline-runtime.md)). Remote acquisition and a pinned host closure remain outside this policy |
| V09 — Timeout cleanup | Verified for the tested stack | Two Deck confirmations terminate PID-contained launcher/Wine descendants on forced watchdog expiry, preserve an unrelated prefix and pass subsequent query/GPU controls ([record](../research/records/2026-10-14-exp-proton-timeout-cleanup.md)). GPU/kernel hangs remain outside this proof |

None of these follow-ups is a prerequisite for closing the first bounded GPU
proof. V07a–V07c and bounded V07e portability are verified by the records below.
The remaining work is tracked separately in the roadmap; a maintained-path claim
must still identify the cases and runtime/cleanup policies actually verified.

A successful first configuration establishes only its recorded Proton GPU baseline. Regression coverage and maintenance claims must name the cases actually verified. A second tested configuration extends the evidence but does not imply general hardware compatibility.

Results may contribute to V03 — Second hardware/provider configuration — only when they actually demonstrate an independent relevant hardware/provider combination under the required verification protocol.

## Evidence update — 2026-10-14

The [selected temporal comparison](../research/upscaling-dispatch.md#selected-proton-temporal-regressions)
left V07d active at evidence intake: reset passes on Deck and Machine, other image criteria fail,
and Deck jitter remains blocked by its launcher exit. The
[exit-status diagnosis](../research/records/2026-10-14-exp-proton-exit-status.md)
neither reproduced that exit nor established its cause; successful replays do
not accept the original failed launch.

The [offline-runtime record](../research/records/2026-10-14-exp-proton-offline-runtime.md)
and [timeout-cleanup record](../research/records/2026-10-14-exp-proton-timeout-cleanup.md)
complete bounded V08 and V09 checkpoints on Deck. V08 imports trusted local
installations and enforces network isolation; it does not provide remote
acquisition or a complete OS dependency closure. V09 retains the failed group-only
baseline and verifies PID containment across detached sessions, unrelated-prefix
survival and subsequent same-prefix GPU controls. Prepared ordinary, temporal and
offline Proton launches now require PID containment; unavailable isolation blocks
launch. These results do not establish general regression compatibility, provider
termination or recovery from GPU/kernel hangs, and do not change native support.
