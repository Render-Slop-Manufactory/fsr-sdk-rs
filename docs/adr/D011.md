# D011 — Bound the first public DX12 upscaler dispatch contract

- Recorded: 2026-09-24
- Accepted: 2026-09-25
- Status: accepted — maintainer choices reviewed against the synthesized
  evidence and current ownership/error architecture. M6b implementation and
  [bounded public-route verification](../research/records/2026-09-25-m6b-public-dispatch-verification.md)
  completed on 2026-09-25. D008's zero-create-flags construction contract is unchanged.

**Context:** D008 exposes a Windows/DX12 `Upscaler` whose creation flags are
fixed to zero. M6a used that constructor and a private dispatch path to record
work; its test harness submitted, fenced and read back one plausible output on
a tested SDK v2.3.0/provider 4.1.1 configuration. It supplied a separate 1×1
exposure texture. The result establishes that this path can execute GPU work;
it does not establish public API safety, image quality, temporal behavior or
broad provider support. The
[research contract recommendation](../research/records/2026-09-24-src-m6-dispatch-contract-recommendation.md)
instead proposes auto exposure, which changes both the create flags and the
resource profile. It is input to this decision, not an accepted contract.

**Scope:** One immediate-return dispatch call for the existing
Windows/DX12 upscaler and SDK v2.3.0 baseline. The caller owns the renderer,
resource transitions, command-list recording and submission, and GPU
synchronization. This is not a general FSR dispatch design or a promise that
the selected formats are the SDK's full supported range.

## Public input and fixed profile

Expose a DX12-specific **unsafe function** with this input shape (design sketch,
not an implemented API):

```rust
pub struct UpscaleDispatch<'a> {
    pub command_list: &'a ID3D12GraphicsCommandList,
    pub color: &'a ID3D12Resource,
    pub depth: &'a ID3D12Resource,
    pub motion_vectors: &'a ID3D12Resource,
    pub exposure: &'a ID3D12Resource,
    pub output: &'a ID3D12Resource,
    pub jitter: JitterOffsetPixels,
    pub frame_time: FrameTimeMillis,
    pub camera: CameraParameters,
    pub reset: bool,
}

// On Upscaler:
pub unsafe fn dispatch(&mut self, dispatch: UpscaleDispatch<'_>) -> Result<(), Error>;
```

The input borrows a
`windows` 0.62 `ID3D12GraphicsCommandList` and five `ID3D12Resource` values:
color, depth, motion vectors, explicit exposure and output. The wrapper neither
owns nor submits the list. It does not take a queue or fence. `&mut self`
prevents simultaneous CPU calls through this upscaler; it does not prove GPU
completion or temporal execution order. Reexport the exact command-list and
resource interface types as for D008's device. The borrow lasts through the
CPU call only; it does not retain any object for later GPU use. The struct is
a frame-level value, with no builder, resource wrapper or descriptor chain.
Public fields permit direct construction. Adding a required field later is a
compatibility change; a struct does not by itself make such additions compatible.

The input also carries the applied jitter offset in pixels, frame time in
milliseconds, camera near/far distances, vertical field of view in radians,
view-space-to-metres factor, and a history-reset pulse. The wrapper requires
finite values throughout, positive frame time and near plane, far greater than
near, FOV strictly between zero and pi, and a positive view-space-to-metres factor before
FFI. It derives render and output extents from the textures. The first profile
fixes the motion-vector convention to jitter-free, current-to-previous UV
displacement at render resolution; the wrapper derives its native scale from
the render extent. It fixes `preExposure` to `1.0`, sharpening and dispatch
flags to zero, and both
optional masks to null. Callers must supply image content consistent with those
conventions. Use small checked value types with private fields and fallible
constructors: `JitterOffsetPixels::new(x, y)`,
`FrameTimeMillis::new(milliseconds)`, and
`CameraParameters::new(near, far, vertical_fov_radians, view_space_to_meters)`.
Near/far use the same view-space units. These constructors enforce the scalar
rules above and return crate-owned validation errors; named getters retain
the units. No unchecked public mutation is provided. Pulse `reset` on the first
frame and camera cuts/history discontinuities; it is not a fence or recovery
from poison. No arbitrary jitter magnitude bound or jitter generator is added.

The first supported resource profile deliberately matches M6a:

| Role | Required resource |
|---|---|
| Color | Render-size `R16G16B16A16_FLOAT` Texture2D containing linear, non-HDR scene color |
| Depth | Render-size `R32_FLOAT` Texture2D containing standard finite device depth, shader-readable |
| Motion vectors | Render-size `R16G16_FLOAT` Texture2D |
| Exposure | 1×1 `R32_FLOAT` Texture2D containing a positive finite multiplier, shader-readable |
| Output | Output-size `R16G16B16A16_FLOAT` Texture2D with UAV capability |

The renderer supplies the exposure multiplier used by its subsequent
tonemapping; M6a tested `1.0`, not a range of values. The caller must ensure
that texture's content is positive and finite because the wrapper cannot
inspect it without GPU work. Color is supplied before final tonemapping and
without pre-exposure, matching fixed `preExposure = 1.0`. Color and depth use
the same jittered projection. With zero create flags, depth is the device's
ordinary finite-depth value (near toward zero, far toward one), not linearized
view-space distance or reversed/infinite depth. Motion vectors use top-down UV
axes (+X right, +Y down) and represent current-to-previous displacement with
projection jitter removed. These are application-provided semantic inputs;
the wrapper cannot validate their pixel values.

The [motion/jitter investigation](../research/records/2026-09-24-src-m6-motion-vector-jitter-semantics.md)
supports this deliberately fixed UV profile and `(render_width, render_height)`
scale. Raw NDC requires an additional `(0.5, -0.5)` conversion into top-down UV;
the guide's literal raw-NDC plus `(W,H)` example is inconsistent with that
mapping and the official sample. Do not copy that example into this API.
Dispatch jitter reports the actual applied pixel offset, not necessarily the
unmodified value from a jitter query. Source supports these semantics; M6a's
zero-motion reset frame does not runtime-validate temporal reconstruction.

All five are distinct, single-sample, single-mip, single-slice resources on
the context's device.
For this first profile, the active render and output extents equal the
respective context maxima. The fixed-zero constructor enables neither the
[HDR](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/include/ffx_upscale.h#L49)
nor the [dynamic-resolution](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/include/ffx_upscale.h#L55)
creation flag; accepting smaller or changing active sizes
would require a separate contract and evidence.
The command list must be DIRECT and belong to that device. The wrapper checks
the properties it can inspect, including descriptions, extents, device,
shader-resource eligibility of every input, output UAV capability, and exact
COM-resource identity through canonical `IUnknown`, before native dispatch.
This narrow whitelist is an initial support choice, not an assertion that other
SDK formats or shapes are invalid. The wrapper cannot generally infer
backing-heap aliasing or actual D3D12 state from the COM objects.

At the call boundary, color, depth, motion vectors and exposure must be in
`D3D12_RESOURCE_STATE_NON_PIXEL_SHADER_RESOURCE`, declared to FidelityFX as
`FFX_API_RESOURCE_STATE_COMPUTE_READ`. Output must be in
`D3D12_RESOURCE_STATE_UNORDERED_ACCESS`, declared as
`FFX_API_RESOURCE_STATE_UNORDERED_ACCESS`. The wrapper does not perform
external transitions. After a successful native dispatch, the supported baseline
is trusted to restore registered resources to their declared states before
the recorded dispatch ends; M6a successfully recorded an output UAV-to-copy
transition. This expectation is bounded to the selected baseline and is not a
universal provider guarantee.
No post-state is promised after a native dispatch error.
The caller must restore application descriptor heaps and bindings after the
call as needed; FidelityFX can change command-list binding state.

Keep the existing zero create flags and require the explicit exposure resource
for this first public method. M6a exercised exactly that combination. Auto
exposure would require a separate create option/flag and a null exposure
resource. It may be added after a bounded runtime verification and an explicit
extension of this decision; the source recommendation alone is not that proof.

## Recording and in-flight work

**Evidence:** the [allocation investigation](../research/records/2026-09-24-src-m6-backend-allocation-inflight-scope.md)
identifies finite wrapping descriptor/upload rings per open backend interface,
and separate interfaces for modern open FSR3 sibling contexts. It does not
identify the signed FSR4.1.1 provider's allocation or sharing model. The internal
`FFX_MAX_QUEUED_FRAMES = 4` is a capacity multiplier, not a public dispatch limit.
No ordinary per-dispatch completion rule was found. The
[recording-ahead experiment](../research/records/2026-09-24-exp-m6-recording-ahead.md)
completed 2/5/8 same-context and 2/5 sibling-context recordings before submission
on the tested configuration. This establishes neither unlimited capacity nor a
supported numeric queue depth, but provides no basis for requiring immediate
completion after every dispatch.

**Policy:** impose neither a wait after every dispatch nor a numeric maximum
of recorded or GPU-in-flight calls. The wrapper records commands and does not
wait, submit, track fences or expose an allocation-domain concept. It promises
no particular supported amount of recording-ahead or GPU-in-flight work.
Application resource/list/allocator reuse and context destruction must still
follow the concrete lifetime and ordering obligations below.

**Bounded dispatch runtime trust assumption:** for the supported signed
v2.3.0 Windows/DX12 upscaler path acquired under D004/D007/D008, with this
profile's known preconditions and caller obligations satisfied, the wrapper
trusts the selected native runtime/provider to manage provider-owned transient
allocations without memory unsafety at the native/GPU boundary. This includes
reuse across serialized recordings and sibling contexts; it is an explicit
maintainer policy, not a demonstrated allocator guarantee. It extends the
project's native trust model to dispatch, rather than deriving dispatch safety
from D008's numerical construction assumption. Public documentation must expose
this boundary; callers are not asked to discover an undocumented ring capacity.

The open backend's unchecked wrapping is a concrete reason to preserve this
qualification, not evidence that the closed provider has the same allocator.
Arbitrary replacements, source-built providers, other releases and general
concurrent execution are not covered. D008's acquiring-thread confinement,
external-call serialization/non-reentrancy and dependency obligations remain
in force across runtime families that may share native state. A different
path/device does not establish isolation. No new process-wide fence cadence
is inferred from those CPU-call rules.

Unknown signed-provider sharing remains an unresolved fact, but is no longer
an architecture acceptance gate under this explicit policy. A discovered
provider safety precondition or unsafe allocation reuse requires revisiting
validation, supported runtime scope or the dispatch contract; it cannot be
ignored merely as a trusted-provider bug. No guarantee of success or conversion
of every native fault into a Rust error follows from this assumption.

Temporal GPU work on one context must execute in dispatch-recording order.
Separate ordered `ExecuteCommandLists` calls on one queue are the exercised
route. Merely putting successive lists in one submission batch does not prove
the required execution order. Cross-queue dependencies require explicit waits;
this obligation does not establish general cross-queue/provider support.

## Why the call is unsafe

A safe immediate-return method with temporary COM borrows would permit callers
to drop textures or the upscaler as soon as the Rust call returns, possibly
before the GPU executes the recorded work. `&mut self` constrains CPU access,
and cloning COM objects only for the call keeps them alive only until return.
Neither checks real resource state, backing-memory aliasing, residency or
queue ordering. The caller can also reset an allocator before GPU completion.

A smaller **safe** public contract was considered. To make asynchronous
dispatch safe for ordinary callers, this crate would need to own or reliably
track submission and fence completion, retain all referenced resources and
the context through that completion, and control or otherwise prove the
relevant resource states and ordering. A token that merely holds COM clones
until its own `Drop` cannot prove completion. Such an execution owner is a
possible later API but exceeds this first renderer-independent DX12 boundary.
Moving the unchecked requirements to an unsafe constructor or token would
still leave an unsafe boundary. The immediate-return call therefore
places those obligations explicitly on its caller.

The public `# Safety` contract must require the caller to:

1. Supply an open, recording DIRECT list and keep it and its allocator valid
   through recording, submission and completion as D3D12 requires.
2. Supply truthful boundary states, shader-readable inputs and a UAV-capable
   output; keep the five resources' active backing storage non-overlapping
   during dispatch, avoid conflicting access, and maintain resource residency.
   Any reuse/aliasing outside that work requires the necessary barriers and
   synchronization; distinct COM identities alone do not establish this.
3. Keep all referenced textures, backing allocations and this `Upscaler`
   alive until all GPU work recorded by the dispatch completes. Keeping the
   upscaler alive retains its device, context and runtime dependencies.
4. Submit the list and establish the necessary queue/fence ordering, including
   cross-queue waits and ordered execution of successive dispatches using the
   same temporal context. Do not assume that `&mut self` orders GPU execution.
5. Do not overwrite inputs, reuse output/backing storage, reset command
   allocators or reuse recording objects prematurely. Follow DX12's respective
   recording, resubmission and GPU-completion rules; CPU return is not a reuse
   signal. Execute each successful FSR recording once, in temporal order.
6. Before `destroy` or `Drop`, establish completion of every submitted
   dispatch on that context. Follow the terminal rules for failed or abandoned
   recordings below.

Jitter, motion-vector and camera conventions are documented input semantics;
bad values may spoil reconstruction but are not themselves Rust memory-safety
obligations. The wrapper should reject inspectable invalid values regardless
of the call's `unsafe` status.

## Native errors and abandoned recordings

Validation and DX12/COM inspection errors returned **before** entering
`ffxDispatch` leave the native context usable: no FSR commands were recorded
by this call. They do not repair application-side state or commands the caller
already recorded on the list.

After `ffxDispatch` has been entered, a non-OK return has no established
rollback or resource post-state guarantee. The conservative wrapper policy is
terminal: preserve the native code, mark the `Upscaler` unusable for further
dispatch, and never submit the command list containing the failed recording.
The caller discards that list's recorded work, waits for any earlier submitted
work on the context to complete, and only then destroys or drops the context.
The wrapper must enforce the no-further-dispatch state; the caller remains
responsible for list handling and GPU completion. This is a wrapper recovery
policy, not an AMD guarantee that a failed native call left the context or
recorded list intact.

Represent dispatch eligibility privately on `Upscaler`, independently of the
live native owner (for example, Ready/Poisoned). Check it before inspection or
FFI. Set Poisoned on a non-OK native return before returning
`Error::Native { operation: Operation::Dispatch, code }`; an OK return leaves
it Ready. Rust validation and pre-native COM failures never poison a Ready
context. Do not clear or destroy the owner's handle to represent poison and
do not expose provider state or a recovery method.

Poison forbids further dispatch, not teardown. Consuming `destroy` and `Drop`
still use D005's one native destroy attempt after the caller has satisfied GPU
lifetime obligations. A destroy failure retains the complete dependency bundle
without retry; Drop discards the error. This relies on the bounded native trust
that a returned dispatch failure leaves the owned context eligible for that
teardown, not that it is reusable or rolled back. No assertion that all native
failure modes return normally is made.

If `ffxDispatch` returns OK but the application abandons the recording or
cannot submit it, it must likewise stop dispatching through that context and
destroy it after earlier submitted work completes. The wrapper cannot observe
whether the application submitted the list, so this remains an unsafe caller
obligation. A later recovery contract would need evidence that discarding a
recording leaves the provider's temporal and backend state reusable.
Invalidate every unsubmitted recording that references a context before its
destruction, so none can later be submitted. If a failed list also contains
successful recordings from other contexts, discarding it abandons those
recordings too and applies the same terminal rule to those contexts. Earlier
successfully recorded work may be submitted in order and completed, or discarded
under this rule; a list containing a failed dispatch must never be submitted.
Abandonment ends the future GPU-use obligation for discarded commands only once
they cannot execute; it does not end obligations for earlier submitted work.

## Return and error contract

`Ok(())` means that `ffxDispatch` returned `FFX_API_RETURN_OK` while recording
to the supplied list. It does **not** mean that the list was closed or
submitted, a fence completed, the GPU wrote correct pixels, temporal history
is valid, or the application can release resources or the context.

Extend the existing crate-wide `Error`; introduce no public `DispatchError`.
Add `Operation::Dispatch` and preserve every native `ffxReturnCode_t` value,
including unknown values, as `Error::Native { operation: Dispatch, code }`.
Keep pre-call validation failures distinct from native failures, and preserve
the HRESULT of any DX12/COM inspection failure in a distinct error category.
An attempt to dispatch through a context made terminal by a prior native
failure must return a distinct wrapper error without another native call.
No `fsr-sdk-sys` ABI type enters the ordinary public error surface. The
existing non-exhaustive error enums permit these new categories. Use
`InvalidDispatch` with a crate-owned structured validation reason (scalar or
resource role/property), `Dx12Inspection` with the inspected object/operation
and the original HRESULT as an owned `i32`, and `DispatchPoisoned` for the
terminal state. Supporting reason/role enums remain small and non-exhaustive;
exact naming is an implementation detail, not an invitation to merge categories.
An HRESULT is not a FidelityFX return code: display its exact bits in hexadecimal
and retain it losslessly. This representation can preserve the existing
`Debug`, `Clone`, `Copy`, `PartialEq` and `Eq` traits without boxing a Windows
error. Do not leak `windows::core::Error` or sys types. D010 requires an owned
boundary, not identical storage for load and inspection errors. Existing load
errors remain separate. Broaden `Operation`'s lifecycle-only documentation to
include dispatch; it still identifies the native operation that failed.

## Review outcome and consequences

| Maintainer choice | Review against evidence and accepted architecture |
|---|---|
| 1. No invented per-dispatch fence cadence | Accepted as bounded provider-trust policy. Neither source nor experiments establishes a numeric limit. The explicit dispatch allocation assumption above closes the policy gate without claiming the unresolved signed-provider topology is known. Concrete application lifetime/order obligations remain. |
| 2. Native failure poisons dispatch | Accepted as conservative wrapper policy because rollback/reuse is unestablished. Poison is separate from D005 ownership; pre-native errors do not poison, and destruction remains available exactly once. The failed list and abandoned recordings require the explicit handling above. |
| 3. Value/borrow input struct | Accepted: the five-resource fixed profile maps directly onto the private descriptor path and D008's native Windows types. Checked jitter/time/camera values expose units. Borrows do not enforce GPU lifetime, and public fields do not promise compatible future required additions. No builder is needed. |
| 4. Extend crate-wide Error | Accepted under D009/D010. Native operation/code, structured validation, owned HRESULT inspection and poison remain distinct. Code-only HRESULT storage preserves existing value traits and avoids a duplicate public dispatch error hierarchy. |

The narrow formats, fixed extents, zero creation flags and explicit exposure
are wrapper support policy informed by M6a, not the complete AMD input domain.
The executed proof used exposure `1.0`, zero motion and a reset frame. Source
supports nonzero motion conventions; temporal quality, varying exposure and
arbitrary provider compatibility are not experimentally established. GBV stalled
inside native dispatch on the tested setup and remains inconclusive. None of
these limits supplies a new factual blocker to this bounded architecture choice.

**Verdict: D011 ready to accept after these edits; accepted.** No new research
cycle was required to close this gate. Public dispatch was unimplemented at
acceptance and was added in M6b.
This decision does not expand into auto exposure, dynamic resolution, HDR,
sharpening/masks, renderer/resource frameworks, Bevy/wgpu, Vulkan, image-quality
guarantees or general concurrency.

## M6b implementation and verification requirements

Adapt the private proof path rather than exporting it unchanged:

- Expose the input/value types and error categories above; retain native ABI
  construction internally, following D006. Keep validation, conversion and the
  native call separately reviewable. Preserve D008's constructor and threading.
- Require exact active extents equal to context maxima (the proof currently
  accepts smaller extents). Reject shader-resource denial on every input,
  inspect list/resource devices, and compare all resource identities through
  canonical `IUnknown` (the proof compares resource interface pointers).
  These checks cannot establish heap non-aliasing, residency or actual states.
- Add the private dispatch-poison state without changing D005 teardown. Fixtures
  must cover pre-native validation/COM failure with no native call and no poison,
  exact known/unknown native code propagation, OK remaining usable, non-OK
  poisoning, rejection of later dispatch without FFI, and teardown after poison
  including D005 retention/no-retry behavior on destroy failure.
- Document the complete resource/profile, native trust, failure/abandonment and
  post-return lifetime contract at the public method and on `Upscaler` teardown.
  No completion wait is hidden in dispatch or Drop. Restore application bindings
  as needed after FSR. The public success-state contract for this supported
  baseline is restoration to the declared boundary states; source restoration
  and M6a's transition are its bounded basis, not a universal provider guarantee.
  Native failure promises no post-state.
- Reuse paired ABI/helper-parity checks; exercise descriptor values and all
  inspectable rejection categories. Run the public route through a submitted,
  fenced native readback on the tested profile before declaring M6b verified.
  Keep compile/fixture results separate from actual GPU execution.
- Document frame-path `GetDesc`, `GetDevice` and COM-identity inspection work;
  introduce no implicit wait or wrapper heap allocation merely to package the
  inputs. Measure cost before making performance claims. An analytic moving
  multi-frame test is follow-on evidence for temporal claims, not a prerequisite
  for accepting this architecture.
