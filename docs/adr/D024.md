# D024 — Dynamic active render and output regions

> **U08 public-shape amendment, 2026-10-27:** [D042](D042.md) now implements
> portable frame/generator parameters, named resource builders and separate
> command-list/resources/parameters recording. Motion and colour each store one
> complete request; native sharpening is portable. Reviewed native mappings,
> defaults, validation order, GPU duties and historical provider limits remain.
> [Production verification](../release/2026-10-27-frame-composition-verification.md).

- Date: 2026-10-14.
- Status: **accepted** under explicit maintainer authorization to proceed with M14
  and defer P01 because a Windows test machine is unavailable.
- Scope: first render-size slice, SDK v2.3.0, DX12 and both ownership families.
- Extends D011's exact active-size profile and D014's additive frame settings;
  preserves D021 motion units and D023 exposure. The accepted output amendment
  below extends the original render-only decision while retaining maximum allocations.

## Original render-only decision, 2026-10-14

The following decision, safety and verification sections record the original
render slice. The accepted output amendment below supersedes fixed-output rules.

Add `UpscalerOptions::{dynamic_resolution,set_dynamic_resolution}`; default false.
Enabling it forwards `FFX_UPSCALE_ENABLE_DYNAMIC_RESOLUTION` (`1 << 6`) through the
same flag conversion used by creation and memory estimation. Maxima and all
profile settings are immutable after creation.

Add private optional `Dimensions` to `UpscaleDispatch`, exposed through
`active_render_size()` and `set_active_render_size(Option<Dimensions>)`.
None defaults to the context maximum. A fixed context accepts only that maximum;
a dynamic context accepts nonzero sizes bounded independently on both axes by
the maximum. Reject violations with `DispatchValidation::ActiveRenderSize` before
COM inspection or native recording, without poisoning a usable context.

Keep allocation requirements exact: colour/depth and render-resolution motion
equal `max_render_size`; display-resolution motion and output equal
`max_upscale_size`; supplied exposure remains 1×1. Smaller or oversized allocations
still reject, even when they cover the active image. Active images occupy the
top-left region, with no offset control. Native resource descriptions report
actual allocation dimensions; `renderSize` reports the selected image region.
`upscaleSize` always reports the fixed full output, never a zero sentinel.

UV vectors describe normalized displacement in the active motion region. Their
native scale is active render dimensions for render-resolution motion, and the
fixed output dimensions for display motion. Pixel vectors keep `(1, 1)` scaling.
The wrapper rewrites no pixels, jitter or camera values and infers no reset.
First-frame/cut reset and temporal continuity remain the caller's responsibility.
The wrapper neither resizes textures nor submits commands or waits for the GPU.

## Safety and limits

The renderer supplies matching active colour, depth and motion content, truthful
resource states and non-overlapping backing storage. Existing GPU ordering,
lifetime, abandonment, poison and terminal cleanup obligations remain unchanged.
The unsafe dispatch contract requires a trusted provider supporting the selected
dynamic flag and active-size transitions. Bounds do not certify every numerical
domain, aspect ratio or provider-supported scale. Loading or compilation does not
establish native execution. No universal-provider or performance claim is made.

P01 measurements are deferred, not passed; a future baseline must name the actual
feature set measured. Bounded native integration passed on 2026-10-15 on the
[recorded Windows configuration](../release/2026-10-15-windows-m11-m14-verification.md). Image
quality validation remains on hold. Variable output and variable allocation sizes
need separately selected contracts and verification; this slice does not add them.

## Variable-output source follow-up, 2026-10-19

The [source record](../research/records/2026-10-19-src-variable-output-resolution.md)
is integrated in the [dispatch assessment](../research/upscaling-dispatch.md#variable-output-resolution-source-contract).
It reports distinct context capacity, actual allocation and active output, FSR3
forwarding/bounds/defaults, omission of `upscaleSize` by the FSR2 adapter, and
active-output-based display-motion normalization. It does not establish a
provider-independent external-allocation contract or padding preservation;
rounded output/sharpening workgroups require explicit safety review.

The maintainer selected variable output as the next implementation work. Its
allocation/profile contract still needs resolution: permitted output/display-motion
allocations (including above maxima), actual-provider support/safety, whether
output variation is gated by the dynamic option, and whether render-side
allocation relaxation belongs in the same change. An optional active output
size and coverage checks are research recommendations, not an accepted API here.
`UpscaleDispatch` remains a DX12-gated borrowed request; portable checked values
must not acquire Windows dependencies. No automatic reset or GPU synchronization
policy is selected. This intake changes neither the accepted fixed-output slice
above nor its historical native verification, and adds no implementation or
Windows/GPU evidence.

## Amendment: active output within maximum allocations, 2026-10-19

**Status: accepted, 2026-10-19**, by explicit maintainer review acceptance and
instruction to continue implementation. This supersedes the original decision's
fixed-output restriction with the rules below, retaining its allocation requirements.
Implementation and public-path verification are tracked separately.

**Implementation checkpoint:** implemented in development; the
[Windows verification](../release/2026-10-19-active-output-verification.md) passes
62 public-output cases on selected 4.1.1/3.1.5 across both ownership families and
257 consolidated stable/MSRV/ABI/consumer/native cases. These bounded results
preserve the conditional trust and allocation limits below; final release
archives remain separate.

### Problem and selected boundary

The raw ABI can describe active output independently of context capacity and
texture allocation, but the public wrapper always derives `upscaleSize` from
the output texture. Add direct per-frame access while retaining exact maximum
allocations. This keeps external allocation changes out of the first output
slice and preserves the existing resource profile. It is a wrapper scope choice,
not an AMD requirement or proof that maximum allocations bound shader access.

The [source assessment](../research/upscaling-dispatch.md#variable-output-resolution-source-contract)
and [native follow-up](../research/upscaling-dispatch.md#variable-output-native-follow-up-2026-10-19)
are the evidence basis. The latter includes the correction to the record's
oversized/sharpened footprint summary: writes reach 640×368 in that arm, beyond
the 640×360 context maximum. Neither smaller readbacks nor debug-layer success
establish out-of-resource access safety. This amendment therefore explicitly
retains actual-provider trust rather than introducing a numerical safety claim.

### Public API and defaults

Add a private `Option<Dimensions>` field to the existing DX12-gated
`UpscaleDispatch<'a>`, with these ordinary local accessors:

```text
active_output_size(&self) -> Option<Dimensions>
set_active_output_size(&mut self, value: Option<Dimensions>)
```

The existing `UpscaleDispatch::new` initializes it to `None`. The getter returns
the stored request; it does not report an applied provider size. The setter
only changes Rust frame data, performs no COM/native inspection and cannot
certify provider support. `None` resolves to `options.max_upscale_size()` when
the frame is inspected; `Some(maximum)` has the same dispatch meaning. Reusing
the frame data with a different context resolves `None` against that context.
`Dimensions` continues to enforce nonzero axes without platform dependencies.
No new frame constructor, context option, capability object or raw ABI field is
needed. Both local and movable upscalers consume the same request and inspection.

### Geometry validation and error behaviour

Let `M` be `max_upscale_size`, and `U` the resolved active output. Check each
axis independently; do not clamp, round or rewrite the caller's request.

| Context / request | Result |
|---|---|
| Dynamic option false, `None` or `Some(M)` | Accept output geometry `M` |
| Dynamic option false, any `Some(U)` different from `M` | `DispatchValidation::ActiveOutputSize` |
| Dynamic option true, nonzero `U.width <= M.width` and `U.height <= M.height` | Accept output geometry `U` |
| Either requested axis exceeds its maximum | `DispatchValidation::ActiveOutputSize` |

Expose that new variant through existing `Error::InvalidDispatch { reason }`.
Requiring the existing dynamic option for a smaller output is deliberate wrapper
policy consistent with active render size. The spike does not establish a
universal native flag prerequisite; its 4.1.1 output differences also rule out
treating the flag as irrelevant. Estimates and creation keep the existing
matching flag conversion, with no automatic option changes during dispatch.

Keep eligibility/poison first. Preserve existing required-mask precedence, then
check active render and active output before COM inspection or FidelityFX entry.
Leave the remaining existing checks in their order. Optional
`validate_dispatch_inputs` and compulsory dispatch inspection use the same
geometry rules; dispatch always repeats inspection. A geometry/resource error
does not poison a usable context and permits correction/retry. Native errors
retain their operation/code and existing terminal-use and cleanup policy.
Successful preflight establishes inspectable compatibility only.

Bounds introduce no generic alignment, aspect-ratio or render/output-ratio rule.
The actual provider must support the requested numerical/profile domain. Existing
render geometry and its validation remain independent of the new output field.

### Allocation, native mapping and motion

Keep current allocation validation, formats, usage and device/identity checks:

| Resource | Required allocation | Active content / descriptor mapping |
|---|---|---|
| Colour, depth, supplied masks | Exactly `max_render_size` | Existing active render region |
| Render-resolution motion | Exactly `max_render_size` | Active render region |
| Display-resolution motion | Exactly `max_upscale_size` | Active output region |
| Output | Exactly `max_upscale_size` | Requested active output, anchored at `(0, 0)` |
| Supplied exposure | 1×1 | Existing explicit/automatic exposure rules |

Reject smaller and oversized textures with the existing resource extent error,
even when they cover the requested active image. Reactive-mask generation keeps
its existing render geometry and receives no output-size option.

Native resource descriptions continue to report actual allocation dimensions.
Add resolved output to private `DispatchGeometry`; map it directly to nonzero
`ffxDispatchDescUpscale::upscaleSize`. `renderSize` still uses active render.
For UV motion, `motionVectorScale` uses active render dimensions for render
motion and active output dimensions for display motion. Pixel motion retains
`(1, 1)`. No pixel conversion or resampling occurs. Current-frame quality/jitter
queries use the intended active dimensions when the caller requests those
calculations, with matching selected-provider routing; they are not invoked
implicitly by dispatch. Maximum-based planning queries remain available.

### Provider support and safety obligations

The API records a request under a provider compatibility obligation.
`dispatch` returning `Ok(())` acknowledges successful native recording; it is
not a report that the provider applied the requested dimensions. Do not add an
`Applied` result, name/version allow-list, implicit fallback, trial dispatch or
inferred capability from enumeration/resource masks. A provider that ignores
active output cannot satisfy a caller's variable-output integration requirement.
The recorded 2.3.4 smaller-output path is such a case; it is not a supported
smaller-output configuration under this contract. The wrapper does not detect
that condition at runtime. Full-output use is not rejected merely by its name.

Keep provider requirements at the existing explicit unsafe boundaries:

- Unsafe runtime acquisition covers the actual default/selected providers used
  for the chosen context and safe query domains, preserving existing construction,
  retained-chain, safe-query non-retention and native coordination requirements.
  It does not promise variable-output capability for every enumerated provider.
- Unsafe dispatch additionally requires actual-provider support for the chosen
  render/output transitions, dynamic flag, motion profile and sharpening setting.
  The provider must consume temporary CPU dispatch descriptors synchronously
  without retaining their addresses, safely access supplied allocations and
  internal resources, restore the declared boundary states on success and preserve the
  existing terminal-destruction contract on native error. Numerical bounds,
  maximum allocations and preflight do not establish these properties.
- The renderer supplies matching active input content and valid input texels
  throughout any additional sampling footprint required by that provider.
  Inactive input texels cannot be assumed unread. The full supplied output
  allocation must be available for native writes; texels outside active output
  have no preservation or image-content guarantee. Permission to write the
  allocation is not permission to access beyond it.
- Existing residency, non-aliasing, resource states, command-list validity,
  submission/fence ordering, retention and Configure-idleness obligations remain
  in force on both ownership families. Output shrink/grow does not create a fence.

This amendment selects that explicit conditional native-trust boundary.
It does not settle the empirical out-of-resource safety question or
prove that every bounded request is valid on 4.1.1/3.1.5. The evidence supports
only the recorded combinations. If those provider obligations cannot be
established for an intended configuration, that configuration must not be used
through unsafe dispatch; passing a smaller texture in the spike is no substitute.

### History, compatibility and alternatives

Forward the caller's `reset` unchanged on every frame, including size changes.
The renderer decides first-frame/cut/reset handling and continuity. Context
maxima remain immutable; changing them requires recreation. Resource replacement
retains the existing recording and completion obligations. No temporal-quality
claim or reset recommendation is selected.

Existing constructors and default fixed-output descriptors retain their meaning;
`None` keeps their current output dimensions and display-motion scale. The new
non-exhaustive error variant distinguishes output geometry from render geometry.
Public frame/resource types stay Windows/DX12-gated; checked dimensions and pure
bounds checks stay portable. No dependency or `fsr-sdk-sys` ABI addition is needed.
Widening the unsafe contract and public geometry remains an explicit behavioural
change accepted here and requiring implementation verification.

Coverage-only allocation validation (`allocation >= active`) would admit smaller,
intermediate and oversized textures, but the spike cannot certify their access
boundaries. Keep that extension separate. Requiring guessed workgroup alignment
would encode an unproven general rule. Gating on provider names or treating OK as
capability would contradict the observations. A separate unsafe dispatch method
would duplicate the existing unsafe recording boundary without solving access
safety. These alternatives are not recommended for this first slice.

### Implementation and verification

1. Add frame storage/accessors, portable output bounds/error handling and private
   geometry mapping shared by both owners. Update both unsafe acquisition and
   dispatch contracts, frame/resource Rustdoc and renderer examples together.
2. Use controlled tests for defaults, getter/setter clearing, independent axes,
   dynamic false/true, render/output variation separately/together and exact
   metadata/active-size separation. Exercise both owners, all render/display
   UV/pixel combinations, reset forwarding, poison precedence, no COM/FFX on
   geometry rejection, reusable validation failures and terminal native failures.
   Confirm smaller/oversized allocations still reject and preflight/dispatch agree.
3. Check paired C++ descriptor/resource parity, portable/backend isolation, MSRV,
   downstream consumers and unchanged default descriptors. Raw ABI declarations
   remain unchanged; the new mapping still needs independent verification.
4. Run both public ownership families on the pinned Windows/DX12 stack with
   explicitly selected 4.1.1 and 3.1.5, maximum output/display-motion allocations,
   stable/aligned/rounded and independent-axis shrink/grow, sharpening off/on and
   render/display UV/pixel motion. Audit inputs, descriptor mapping, finite/written
   active output, padding observations, fences, debug/device status and cleanup.
   Compare controlled matched arms where meaningful; require no padding preservation
   or GPU-byte identity across different machines. Do not execute unsupported
   2.3.4 smaller-output calls through the accepted public contract to test rejection.
5. Retain the raw spike and its correction as separate bounded evidence. Record
   public-path results and remaining provider/access limitations; final extracted
   release-package verification remains separate. Completion establishes SDK
   integration for the documented profile, not image quality or universal safety.
