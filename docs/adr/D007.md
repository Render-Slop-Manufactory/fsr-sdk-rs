# D007 — Keep runtime acquisition explicit and deploy the v2.3.0 DX12 upscaler DLL beside the executable

- Recorded: 2026-09-22
- Status: accepted — deployment/acquisition policy explicitly accepted by the maintainer

**Context:** D004 loads the FidelityFX API loader from a caller-supplied path
without defining runtime discovery, installation or deployment. The pinned SDK
v2.3.0 uses a loader DLL plus effect-provider DLLs such as
`amd_fidelityfx_upscaler_dx12.dll`.

AMD's tagged DX12 sample copies the loader, upscaler and frame-generation DLLs
to the executable output directory; its denoiser guide explicitly instructs
executable-adjacent loader/denoiser deployment. This is AMD deployment guidance,
not documentation of the loader's exact internal provider-resolution algorithm
or a loader-relative private-directory contract.

A separate signed-runtime experiment tested loader/provider placement with the
v2.3.0 loader and upscaler DLLs on one Windows x64/MSVC configuration. It used
absolute loader paths, separate empty working directories and fresh processes,
without probe/runner DLL-search-path mutation.

**Choice:** Runtime acquisition remains explicit and application-controlled.
`fsr-sdk-sys` does not discover, download, install or select FidelityFX runtimes.
The caller supplies the concrete loader DLL path under D004. Relative paths
remain permitted and are canonicalized against the current working directory;
this is explicit path resolution, not ambient runtime discovery. PATH, registry
and machine installation state are not supported runtime discovery mechanisms.
The crates introduce no runtime manager or process-wide DLL-search configuration
changes, including `SetDllDirectory` or `AddDllDirectory`.

For the tested signed v2.3.0 Windows x64/DX12 upscaler baseline, the supported
deployment policy is to place `amd_fidelityfx_upscaler_dx12.dll` beside the
application executable. The loader may remain in a private directory and be
loaded through D004's explicit path: that arrangement succeeded in the experiment.

Colocating only the loader and provider in a private directory, separate from
the executable and working directory, is not a supported provider-resolution
mechanism:

```text
runtime/
  amd_fidelityfx_loader_dx12.dll
  amd_fidelityfx_upscaler_dx12.dll
```

In the tested layout, loader acquisition succeeded but the count-only upscaler
version query returned `FFX_API_RETURN_NO_PROVIDER`. This policy does not claim
that executable-adjacent placement is universally necessary or that AMD's
undocumented internal search algorithm is known. It also does not promise
isolation from ambient Windows dependency/provider resolution.

**Rationale:** Explicit acquisition preserves D004's narrow loading boundary
and avoids adding discovery based on ambient machine configuration. The
executable-adjacent upscaler layout follows AMD's sample deployment and has
bounded signed-runtime verification. Colocation alone in a private directory
failed that verification. Changing process-wide search state to support another
layout would add global side effects and a native contract outside this choice.

**Consequences and limits:**

- Applications and their packaging systems remain responsible for obtaining
  and placing required AMD runtime binaries. The Rust crates do not automatically
  download an SDK or runtime; ordinary builds need no installed FidelityFX SDK.
- `external/` remains a maintainer/test input, not a runtime acquisition
  mechanism or a dependency to bundle in the Rust packages.
- This decision neither authorizes AMD binary redistribution nor settles
  crates.io/package licensing or release readiness. Existing findings and
  remaining checks in the [licensing and distribution synthesis](../research/licensing-and-distribution.md)
  remain separate.
- The deployment experiment establishes count-only enumeration and the loaded
  upscaler DLL path, not provider identities, device compatibility or GPU dispatch.
  It covers one run per layout with one signed DLL pair on one Windows
  configuration, not clean-machine deployment or arbitrary Windows search policy.
- Other providers, releases, operating systems and future backends need their
  own evidence. Multiple same-named runtime versions, provider collisions,
  alternate provider overrides, transitive dependency closure and private
  side-by-side FidelityFX installations remain unresolved.
- A future SDK release or separately verified provider-loading mechanism may
  justify superseding this policy; neither automatically changes it.
- This decision does not choose a future ergonomic `fsr-sdk` runtime API or
  require public safe constructors to accept paths. It only constrains the
  native acquisition/deployment behavior they may rely on. D004's unsafe loading
  obligations remain unchanged.

**Evidence:** [DX12 provider DLL source investigation](../research/records/2026-09-21-src-dx12-provider-dll-resolution.md)
and [signed-runtime provider-resolution experiment](../research/records/2026-09-22-exp-dx12-provider-dll-resolution.md).
All four layouts acquired the loader. The count-only query returned OK/count 2
with both DLLs beside the executable and with a private loader plus an
executable-adjacent provider. Both successful cases identified the staged
executable-adjacent DLL's module path. A private loader/provider pair and a
private loader without a staged provider each returned NO_PROVIDER/count 0.
These observations support this bounded deployment policy, not a reconstruction
of AMD's internal DLL-search implementation.
