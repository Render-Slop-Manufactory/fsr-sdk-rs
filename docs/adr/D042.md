# D042 — Coherent upscaling setup and frame composition

- Recorded: 2026-10-26.
- Status: **accepted** — the maintainer accepted the comparative assessment of
  both same-date API reviews and requested this decision and its roadmap
  transition. The target and its inclusion in `fsr-sdk 0.3.0` are selected;
  U07 setup/acquisition, U08 composition, U09 checked requests, U10 errors/metadata
  and U11 terminal usability are implemented and verified within recorded bounds;
  U12 source integration is implemented and verified within recorded bounds. P08
  and final release verification remain separate.
- Baseline: development `fsr-sdk 0.3.0` / `fsr-sdk-sys 0.1.2`, Rust 1.88,
  AMD SDK v2.3.0, supported Windows x64/MSVC + DX12 target.
- Scope: public upscaling assembly and operation boundaries, both local and
  optional movable families, portable values and consumer migration. No new
  backend, SDK effect, native capability or dependency is selected.

## Context and evidence

The [consistency audit](../research/records/2026-10-26-src-public-api-consistency-and-architecture-audit.md)
finds the native ownership and operation architecture suitable, recommending
targeted provider, motion, portability and documentation corrections. The
[redesign review](../research/records/2026-10-26-src-public-api-usability-and-extensibility-redesign.md)
reassesses the same source baseline with less weight on preserving signatures.
It proposes setup scopes, portable frame data and named resource assembly as
canonical integration boundaries. It builds on the first audit rather than
providing independent confirmation of every finding.

The comparative assessment checks those proposals against the actual
[provider workflow](../../crates/fsr-sdk/examples/provider_choice.rs),
[frame assembly](../../crates/fsr-sdk/src/upscaler/dx12/dispatch/frame.rs),
[tuning](../../crates/fsr-sdk/src/upscaler/tuning.rs),
[eligibility](../../crates/fsr-sdk/src/context_policy.rs) and
[errors](../../crates/fsr-sdk/src/error.rs). Repeated selection branches,
backend-coupled numerical preparation, same-typed positional resources and
dormant motion settings are current integration costs. The next planned Vulkan
slice makes portable composition particularly relevant without establishing
its future native contract.

The maintainer prioritizes a coherent caller experience and useful extension
boundaries while adoption is low. Select the second review's structural
direction, with the first review's preservation of justified native boundaries.
Neither review's complete recommendation list or illustrative spelling is
accepted wholesale. Their proposed APIs remain uncompiled sketches; source
reasoning supplies no new runtime, GPU, performance or general soundness proof.

## Decision

### 1. Bind planning and creation through an effect/backend setup

Introduce a concrete DX12 upscaler setup that binds the runtime, device and one
provider request. Provider enumeration, quality/size/jitter and resource queries,
memory estimation and context creation belong to that setup. Remove the separate
provider store from creation configuration and replace paired default/explicit
planning routes as the canonical public API.

Use the named default/explicit selection value
`ProviderSelection::{Default, Explicit(ProviderId)}`. It expresses a request,
not a reservation or capability. Setup construction and selection changes do
not make native calls. Preserve applicable pure checks before enumeration,
fresh membership validation for every explicit operation, no fallback, exact
native errors and the post-create effective-provider check. Default selection
may resolve differently on separate calls; the setup must not silently cache
membership or results.

Created contexts independently retain their runtime, device and creation
storage and do not borrow the setup. They remain usable after dropping the
setup and public runtime under their lasting contracts. Local and movable setups
remain concrete and return their corresponding owner families. A setup borrow
serializes only its own CPU use; common-domain coordination remains external.

Separate loader/ABI trust from lasting effect/backend integration trust in the
target acquisition design. Establish the effect assumptions at an explicit
unsafe setup-acquisition boundary before enabling safe planning or creation.
Keep loader initialization, partial-failure/unload and common threading duties
at loading; callback/diagnostic installation and GPU recording retain their
separate unsafe boundaries. Derived owners retain effect obligations after the
setup is dropped.

On 2026-10-27 the maintainer approved U07 after the
[concrete contract](../design/upscaler-setup.md) and bounded spike. Adopt its
independent runtime/device borrows and loader/effect duty allocation, covering
safe operations, Drop/unwind, ordinary error release, exceptional retention and
movable auto traits. Loading establishes arbitrary-destination loader cleanup
before a movable runtime enters safe Send code; setup acquisition establishes
all effect assumptions for safely reachable providers and input domains.
Those duties persist in derived owners after the setup/public runtime drops.
Safe rebinding cannot introduce an unstated unsafe obligation.

The production names are unsafe `Runtime::load` / `MovableRuntime::load`,
unsafe `upscaler_dx12`, concrete `dx12::UpscalerSetup` /
`dx12::MovableUpscalerSetup` and portable `query::ProviderSelection`.
Retain `UpscalerOptions` without provider storage. Planning/create are safe
through setup; callback creation and global diagnostics stay explicitly unsafe.
Remove the old Runtime effect facade and public static owner constructors.
The [implementation record](../release/2026-10-27-upscaler-setup-verification.md)
separates the checked API from conditional native assumptions and release work.

### 2. Make portable frame parameters the canonical recording data

Separate portable upscaling frame parameters, borrowed backend resources and
the command list. The ordinary recording operation accepts those three inputs;
the combined consuming `UpscaleDispatch` is replaced as the canonical assembly
route. Reuse private inspection and descriptor mapping with one source of data
and defaults.

Portable parameters have private fields, checked explicit jitter/time/camera/
history inputs and complete accessors and updates. Do not fabricate a default
camera, time or jitter. A named continue/reset choice is appropriate at the
required-input boundary. Preserve existing optional defaults and scalar bits.
Document updates on every frame, including clearing the initial reset request
for continuing history; reusing parameters performs no automatic temporal
progression. Keep the evolving
aggregate `Debug + Clone` without a blanket `Copy` or equality commitment.

Use named resource builders with private extensible storage, optional masks
and a pure missing-binding error. Require an explicit texture/automatic exposure
choice; omission of a required role must not silently select automatic exposure.
Assembly performs no COM/native work or independent COM retention. Mandatory
recording inspection remains, including reinspection after optional preflight.
Prefer a straightforward builder over public typestate machinery.

Apply the same parameters/resources/command-list separation to reactive-mask
generation, preserving its distinct inputs, active region and operation. The
renderer still provides ordering and transitions before upscaling. Do not
generalize these effect-specific parameters to Frame Generation, Ray Regeneration
or Radiance Caching without their own contracts.

The concrete U08 production names are `upscaler::{FrameParameters,
ReactiveMaskParameters, HistoryAction}` and DX12 `UpscaleResources` /
`ReactiveMaskResources` with their named builders. Both families expose unsafe
`record` / `record_reactive_mask` and safe `validate_upscale_inputs` /
`validate_reactive_mask_inputs`, taking list, borrowed bindings and portable
parameters separately. Builders report pure `Error::MissingBinding { role }`;
no capability, GPU inspection or automatic exposure is inferred. Full error
restructuring remains U10. [Implementation verification](../release/2026-10-27-frame-composition-verification.md)
records current compiler/controlled/native evidence separately from the spike.

### 3. Store one complete effective setting

- Replace motion units plus override with one portable
  `MotionVectorScale::{Uv, Pixels, Native(scale)}` choice. Preserve active-motion
  geometry for UV, `(1, 1)` for pixels and literal finite native bits, including
  signed zero and subnormals. Remove dormant fallback storage and ambiguous old
  accessors; callers save and restore a temporary choice themselves.
- Make `NativeSharpness` and `Sharpening` portable upscaler values. Preserve
  direct native semantics, disabled versus enabled zero, checked domains and
  defaults.
- Represent the colour hint and its context-mismatch permission in one portable
  request with one setter and inspectable components. Preserve checked
  Unspecified as the default and the explicit bypass of only the pairing rule.
  HDR, classification, exposure and signal conversion remain separate concerns.

### 4. Stage checked tuning requests before native mutation

Make a portable, private-field `TuningRequest` containing a parameter and its
checked value the canonical input to `request_tuning`. Validate complete desired
lists before entering native mutation, using the same domain rules as the
operation boundary. Preserve explicit `ProviderDefault`, original accepted
bits, entry eligibility checks and terminal native-error precedence. Do not
retain a competing optional checked/unchecked operation pair.

Native requests remain ordered and nontransactional. A later native error may
follow earlier acknowledgements and remains terminal. Checked requests prove
neither application/support nor GPU idleness and introduce no rollback, batch
transaction or automatic wait.

U09 implements `TuningRequest::new(parameter, value)` with private fields and
`parameter()`/`value()` accessors, reexported from `upscaler` and `common`.
The constructor owns the one unchanged parameter-domain validator. Both families
accept only `request_tuning(request)`; the operation checks context eligibility
before mapping/FFI. Pure construction is independent of terminal state. The
renderer example checks a complete desired list before applying it in caller
order, including duplicate parameters and explicit defaults. See the
[implementation verification](../release/2026-10-27-tuning-request-verification.md).

### 5. Expose known terminal usability without claiming GPU readiness

Both owners now expose `usability() -> upscaler::ContextUsability` and safe local
`mark_recording_abandoned()`. The portable, non-exhaustive snapshot is
`Debug + Clone + Copy + PartialEq + Eq`, without Default; its variants are
`Usable` and `Unusable(error::TerminalCause)`. Explicit abandonment is
`TerminalCause::RecordingAbandoned`, with no native error source.
Retain the first terminal cause, distinguishing native upscaling, generation,
tuning/other context Configure errors and explicit abandonment. Ordinary query
errors preserve the existing eligibility policy.

An unusable owner rejects recording, live queries, tuning and context-dependent
preflight and context diagnostics before inspection or FFI. Local status access
and terminal destruction remain available under existing duties. Marking abandonment makes no native call, releases nothing,
waits for nothing and revives nothing. The renderer marks every affected context
and still retains dependencies through list invalidation and GPU completion.
This is eligibility, not submission tracking or a recovery state machine.
[U11 production verification](../release/2026-10-27-context-usability-verification.md)
records 593 passing stable/MSRV/consumer/ABI/native cases, including successful
recording followed by renderer abandonment and terminal cleanup on both families.

### 6. Make errors and metadata fit public composition

Distinguish pure input rejection, precise native operation/code failures,
backend inspection, invariant violations and terminal causes in structured owned
errors. Preserve unknown native codes, HRESULTs, resource-role attribution and
source chains. Remove the obsolete unreleased `UnsupportedResource` rejection.
The main error guarantees `Debug`, `Display`, `std::error::Error` and
`Send + Sync + 'static`, without blanket `Copy` or equality commitments. Small
native/reason values may retain those traits. Keep loading's owned error boundary.

Allow lossless public numeric `ProviderId` conversion and public `ProviderInfo`
assembly for pure resolver/policy tests and data round-trips. They establish no
provenance, persistent identity, membership or capability; native validation
remains unchanged. Explicit numeric zero is not default selection. Update
runtime-output-only descriptions when adding these constructors. Keep name-based
generation policy in optional utilities and adapt its output to the selection
value. The later [D036 release amendment](D036.md#release-selection-amendment--2026-10-27)
selects its inclusion in 0.3.0. Add minimal resource-mask
composition while retaining unknown bits.

The maintainer approved the [concrete U10 contract](../design/errors-and-provider-metadata.md)
for implementation on 2026-10-27. Production now supplies the six error categories,
original backend/allocation sources, precise mutating operation labels and the
first terminal native cause, plus lossless provider/mask composition. Its
[verification](../release/2026-10-27-error-metadata-verification.md) records checks
separately. U11 supplies the public usability/abandonment operations in §5.

### 7. Keep one discoverable route and the justified native architecture

Portable effect data has a canonical path under `upscaler`; concrete DX12
owners/resources remain under `upscaler::dx12`. Preserve type-identity reexports
where useful without keeping parallel stores or equally canonical old/new
facades. Resolve names consistently during migration; a wholesale rename to
`Config`, `Extent2D` or new catch-all modules is not selected by this decision.

Keep two crates, independent runtime/context ownership, concrete local/movable
families, shared private mechanics, mandatory validation, renderer-owned GPU
orchestration, terminal cleanup and explicit unsafe callback integration.
Preserve [D040](D040.md)'s external callback targets and exceptional retention,
[D041](D041.md)'s documentation convention and [D033](D033.md)'s phase and
core/utility/integration boundaries. Introduce no public universal backend,
effect, ownership-mode or policy trait and no safe closure/unregister facade.

## Relationship to earlier decisions and migration

This decision supersedes only the following public-shape choices for the selected
0.3.0 transition. Earlier rationale and bounded verification remain evidence of
their original implementation, not verification of the replacements.

| Earlier choice | Replacement and preserved boundary |
|---|---|
| D014 combined frame/resource assembly | Portable parameters, named resources and separate recording arguments; native sharpening and unsafe GPU duties remain |
| D028 provider in options and paired flat query methods | One setup-bound selection through planning and creation; membership, identity, no-fallback and native coordination remain |
| D029 raw parameter/value operation signature | Canonical checked request; mandatory domains, acknowledgement-only success and idle/terminal policy remain |
| D034 units plus overriding native scale | One effective choice; exact scale mapping, numerical domains and resource/view rules remain |

The detailed trust distribution also refines the acquisition contracts described
by D004/D008/D018/D022/D028/D029/D030; U07 now maps them to loader and
effect setup acquisition. Provider metadata construction updates D018/D028's public opacity
choice without making IDs meaningful or stable. This ADR does not mark all of
those decisions superseded. U07 implementation is recorded above; the remaining
public-shape transitions are separate work.

Deliberate wrapper source and trait breaks are accepted for 0.3.0. Document
construction, selection, frame, tuning, error and abandonment migration through
both ownership families. Do not retain forwarding methods with changed hidden
precedence as apparent compatibility. The raw package remains at 0.1.2 unless
its own actual declarations justify a separate version review. SDK pin, Windows
dependency, native support boundary and distribution terms remain unchanged.
[D031](D031.md)'s reserved Vulkan feature and conditional 0.4.0 target remain.

## Delivery and acceptance

[Roadmap U07–U12](../../ROADMAP.md#next-actions) tracks implementation: first
settle the acquisition/setup contract; then implement the portable data,
requests, errors/metadata and usability slices, followed by integrated consumer
migration. U07 acceptance and implementation are recorded above; historical
research records and their verification outcomes remain unchanged.

Compile external consumer walkthroughs for (1) simple upscaling, (2) explicit
provider planning and creation and (3) portable preparation followed by DX12
recording and abandonment. Cover both families, setup-independent context
lifetime, required per-frame updates and the feature/MSRV boundaries. Preserve
mapping, validation order, literal bits, first terminal cause and native partial
failure through appropriate controlled and existing native regressions.

Reconcile docs/examples and targeted current contract contradictions. Final
archive and registry-consumer verification remains separate under the existing
[release preparation](../release/0.3.0-preparation.md). Earlier feature checks
do not certify the redesigned source or final archives. No new image-quality
gate, broad native research campaign or performance claim is selected by D042.
The later [D043](D043.md) separately requires a candidate performance check
before every release; P08 follows U12 for 0.3.0.

## U12 integration follow-up — 2026-10-27

The canonical setup/frame/request/error/usability APIs now compose through
complete local/movable consumer workflows and optional utility selection. The
[0.3 migration guide](../MIGRATING_0_3.md) distinguishes published 0.2 source
breaks from earlier development APIs. Type-identity reexports remain aliases of
one implementation; no old forwarding facade or blanket renaming is added.
Targeted must_use annotations protect consuming resource builders, with_provider
and pure usability snapshots. DebugLevel is non-exhaustive like the other
extensible request choices, without new filters or mapping changes. Existing
constructor/trait, native ownership, lifetime and coordination contracts remain.
The [U12 verification](../release/2026-10-27-api-transition-verification.md) records
the audit, compiler cases, native bounds and remaining exact-archive obligations.
P08 and final qualification remain required before any release claim.

## Alternatives and consequences

- **Only the first audit's R1–R4:** smaller migration, but leaves the main
  portable-preparation and resource-assembly friction in place. Rejected as the
  preferred target under the maintainer's priorities.
- **Adopt every second-review sketch verbatim:** coherent direction, but exact
  borrowing, trust distribution and naming still need concrete validation.
  Select the boundaries above rather than treating sketches as compiled design.
- **Keep additive parallel facades indefinitely:** preserves syntax but adds
  learning and maintenance cost and weakens one canonical integration route.
- **Generic effects/backends or automatic synchronization:** requires native
  contracts and consumers absent from this decision's evidence.

The selected design adds setup, builder, request and status concepts and requires
consumer migration and renewed checks. Their value is explicit responsibility
and complete intent in current workflows. It does not promise that future
mandatory native inputs can be added without breaks, certify closed-provider
behaviour or solve renderer synchronization and callback quiescence.
