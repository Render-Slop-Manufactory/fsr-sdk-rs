# D043 — Performance verification before every release

- Date: 2026-10-27.
- Status: **accepted**, under the maintainer's explicit instruction that
  performance must be checked before every release, starting with 0.3.0.
- Scope: release verification for the wrapper and raw crate; workload selection
  follows the candidate's changes and supported native target.

## Context

P01–P07 supply bounded measurements of earlier development sources. Their
completion does not measure D042's replacement API or the final release inputs.
Earlier planning selected no recurring performance prerequisite. The maintainer
now requires one; historical measurements and their original limits remain
unchanged.

## Decision

Every release requires a fresh, reproducible performance check of its candidate
and a documented review of the result before publication. An absent or invalid
check is incomplete release verification. A material regression must be resolved
or explicitly accepted by the maintainer before release closure.

Before timing, select representative workloads, a comparable baseline, repetition
and noise treatment, and criteria for regression review. Record source/package
identities, build settings, SDK/provider, hardware and driver. Use optimized
builds and separate wrapper CPU recording cost, allocations, GPU intervals and
setup/lifecycle costs where relevant. Reuse existing equipment and baseline
workloads; justify changes in coverage and any unavailable comparison. Invalid
execution or uncertain GPU completion is not a performance result.

Bind the measurements to the release candidate's inputs and final package
identities. Later changes require an impact assessment and repetition of affected
measurements; earlier measurements cannot silently certify different code.
Record the result and its review in a self-contained release verification record.

This accepts the recurring check, not an unreviewed numerical threshold or a
universal speed-parity claim. In particular, P06's experimental 5 µs budget is
not automatically a release threshold. Image-quality research remains deferred;
no exhaustive hardware/resolution/feature sweep is implied.

## Delivery and consequences

[P08](../../ROADMAP.md#performance) tracks the first check for 0.3.0 after U12's
API closure and before final release qualification. The
[prepared P08 adaptation](../design/release-performance.md) records its selected
protocol/baseline and review criteria. P08 is now
[closed with maintainer-accepted limits](../release/2026-10-29-performance-review-closure.md),
including the temporal exclusion and provider/deployment disposition below.
Final archive qualification and publication remain separate. Subsequent releases
repeat the check through the normal release checklist rather than creating
another permanent milestone for each run.

This is a recurring prerequisite, fulfilled for the recorded P08 candidate by
its measurements, qualified review and explicit maintainer disposition. Existing
performance profiles remain equipment; a historical pass or an ordinary
`release` profile pass alone does not fulfil this decision.
It does not change native ownership, supported targets or publication authority.

## P08 selection amendment — 2026-10-27

The maintainer accepted reuse of P06/P07 and the proposed 5 us average additional
CPU-cost criterion for 0.3.0. P08 therefore explicitly adopts the existing P06
five-workload method and strict one-sided 95% upper-bound test against 5 us,
with a fresh pilot/selection/confirmation, plus three P07 setup processes.
GPU/setup/lifecycle results remain descriptive and require regression review.
This is an explicit P08 selection, not an automatic universal budget for future
releases or a promotion of historical samples. The unattended runner records
source-matched candidate archive identities; final exact-package qualification
remains separate. Preparation launches no timing batch; the maintainer runs the
command and requests analysis after completion.

## P08 independent confirmation amendment — 2026-10-28

Following the completed but CPU-inconclusive initial P08 run, the maintainer
requested a new fixed length. Use 256 fresh paired blocks per workload, all five
workloads, unchanged frames and strict 5 us one-sided upper-bound criterion.
The prior 26-block result supplies planning dispersion, runtime and equipment
only; no pooling, new adaptive pilot, early success or optional extension. Retain
both results and require review after this confirmation, including an inconclusive
outcome. Pointwise confidence on a new run does not control repeated retries.

The 500 ns planning-margin target needs at least 228 even blocks under the
observed worst SD; 256 provides headroom. The five-hour primary watchdog is a
runtime allowance, not a whole-batch deadline or acceptance criterion. The
[dated plan](../release/2026-10-28-performance-confirmation-plan.md) records the
initial values, calculation, identities, limits and manual command. The original
P06/P08 protocol and completed data remain unchanged. Preparation launches no
new native measurements; release approval remains separate.

## P08 temporal exclusion review amendment — 2026-10-29

After completion, the maintainer reported playing Return of the Obra Dinn during
the run and explicitly authorized discarding disturbed measurements. The
[derived review](../release/2026-10-29-performance-time-window-review.md) uses the
already diagnosed 22:15 CET cutoff, excludes complete original two-block balance
groups before that time, and retains blocks 35–256 for all workloads and both
arms. This is an explicit exception to the original no-exclusion protocol for
this review, not a default automatic filter or a claim that the original run
passed. Raw evidence, original verdict and later excursions remain unchanged.

All five retained nominal CPU upper bounds are below the unchanged 5 us budget.
The selection was post hoc; nominal 95% coverage after selection is not
established, and timing does not prove the retained period idle or identify game
times. Complete GPU/setup/allocation/lifecycle regression review and final
candidate reconciliation remain required. No extra measurement or release
publication is authorized by this amendment.

## P08 supplemental review status — 2026-10-29

The [completed review](../release/2026-10-29-performance-supplement-review.md)
records zero observed Rust allocator events across 1,920 warmed calls and no
additional wrapper-specific GPU/lifecycle slowdown established by the current
matched pairs. It also records shared absolute increases versus historical P06:
GPU intervals about 9.8–11.3% longer, context creation around 63–67 ms rather than
50 ms, and unused destruction around 13.4–13.6 ms rather than 3.2–3.3 ms. The
initial P08 run already shows this shift with the current provider/driver; no
crate source changed between P08 runs. Historical/current driver, provider and
some helper inputs differ, so the cause is not isolated.

The review proposed accepting these shared costs as the observed baseline of
this deployment, with limitations retained. The provider follow-up and maintainer
disposition below resolve that previously open decision. Final archive
qualification and publication authorization remain separate.

## P08 closure and maintainer disposition — 2026-10-29

The [current-driver provider comparison](../research/records/2026-10-29-exp-provider-performance-comparison.md)
passes all 30 cases. Its eight pairs measure 1.047/1.059 ms GPU intervals for
explicit 4.1.1/default 4.1.2 *, without a clear GPU difference in this small
sample; context creation/destruction costs differ more clearly. Enumeration and
uncontrolled cross-run conditions prevent attributing historical differences to
the driver, wallpaper, provider or Rust API alone.

After reviewing these results, the maintainer considered the remaining differences
immaterial for 0.3.0 and requested the documentation/readiness update. Accept
them as non-blocking for this recorded candidate/deployment, retaining all
observations and limits. This supplies the disposition required by this decision
and closes P08 as a bounded review; see the [closure record](../release/2026-10-29-performance-review-closure.md).

The original full CPU outcomes remain inconclusive. The accepted 222-block
post hoc subset has nominal upper bounds below 5 us, with unestablished coverage
after selection; it is not promoted to an independent confirmatory pass. This
case-specific acceptance does not select future thresholds, change default
provider routing, authorize more benchmarks, or approve publication. Final exact
archive qualification and impact assessment of later runtime changes remain.
