## Problem and existing foundation

At proposal time D028 implemented provider selection, pre-create resource
requirements and private unsafe Configure forwarding in the runtime state and
context owner. The five controls lacked raw descriptor/key bindings and public
typed access. This decision supplies their value policy, GPU-ordering contract
and post-error eligibility; implementation is recorded separately above.

The source study establishes synchronous float copying and null-default reset
in open FSR3. Its values persist across dispatch and history reset. Open FSR2
instead ignores the descriptor and returns OK. There is no effective-value query
or reliable capability predicate. These observations do not establish closed
providers' lifetime, ordering or failure guarantees.

## Selected public API

Add portable non-exhaustive enums in `upscaler::common`, reexported from
`upscaler` like the other common inputs:

```text
TuningParameter::{
    VelocityFactor,
    ReactivenessScale,
    ShadingChangeScale,
    AccumulationAddedPerFrame,
    MinDisocclusionAccumulation,
}

TuningValue::{ProviderDefault, Value(f32)}

TuningRequest::new(parameter: TuningParameter, value: TuningValue)
    -> Result<TuningRequest, Error>
TuningRequest::{parameter(), value()}

Upscaler::request_tuning(&mut self, request: TuningRequest) -> Result<(), Error>
MovableUpscaler::request_tuning(&mut self, request: TuningRequest) -> Result<(), Error>
```

These selected signatures are implemented in development; this sketch is not
an executable example.
`TuningParameter` derives `Debug`, `Clone`, `Copy`, `PartialEq`, `Eq` and `Hash`;
`TuningValue` derives `Debug`, `Clone`, `Copy` and `PartialEq`. Neither has an
implicit `Default`. Under D042, `TuningRequest` has private fields, derives
`Debug`, `Clone`, `Copy` and `PartialEq`, and has no `Default` or unchecked
constructor. Its accessors return the complete checked pair; changes require
a new constructor check. Native methods retain the existing Windows/DX12 and movable
feature gates; common enums remain usable on other hosts without backend features.

One call addresses one parameter on the context's actual provider through its
live handle. No provider override or runtime-global setting is accepted here.
Success is `Ok(())`: native acknowledgement, without proof of application,
effective value, or support. The request-oriented name exposes that limit.
Provider support, native acknowledgement and actual application are distinct:
open FSR2 ignores these keys; open FSR3 implements setters; closed-provider
application remains unestablished. These are source observations, not new GPU
verification. Neither enumeration (effect-level selection), resource masks,
provider names/IDs nor trial OK calls supply a per-key capability predicate.
No `Applied`/`Ignored` result can be fabricated for an unknown provider.
No cached effective getter, support probe, provider
name allow-list, batch transaction or automatic rollback is introduced.

Existing construction options remain unchanged: creating a context makes no
Configure call. These are explicit context operations, not frame arguments.

## Values and provider-default reset

| Parameter | Native key | SDK clamping domain | Open FSR3 creation/null-reset value |
|---|---:|---|---|
| `VelocityFactor` | 0 | `[0, 1]` | `1.0f` |
| `ReactivenessScale` | 1 | `[0, +∞)` | `1.0f` |
| `ShadingChangeScale` | 2 | `[0, +∞)` | `1.0f` |
| `AccumulationAddedPerFrame` | 3 | `[0, 1]` | `1.0f / 3.0f` |
| `MinDisocclusionAccumulation` | 4 | `[-1, 1]` | `-1.0f / 3.0f` |

Require finite values within the table's domains in portable `TuningRequest::new`,
before any native mutation. The constructor is the single domain validator;
private fields and immutable accessors preserve its invariant through native entry.
Direct `Value(f32)` construction and reuse across parameters cannot bypass it.
Reject outside-domain input rather than silently clamp it; preserve all accepted
bits, including negative zero and subnormals. `TuningValue` alone is unchecked;
`TuningRequest` is the validated parameter/value pair. There is one checked
operation input and no unchecked sibling or separate public validator.

Prepare the complete desired list with a fallible collection before applying
requests in caller order. This prevents a later invalid input from causing partial
native changes. It adds no batch operation, sorting, duplicate coalescing, rollback
or transaction. A later native error can follow earlier acknowledgements.
Constructor errors are pure and independent of context eligibility. At operation
entry, existing terminality still rejects before descriptor construction or FFI.
This D042 amendment replaces the earlier per-call raw-pair validation placement.

These are intentional provider-independent wrapper input contracts derived from
AMD's shared v2.3.0 upscaler header, not inferred solely from FSR3's setter or
presented as universal provider maxima. Native finite out-of-range clamping remains
a legitimate raw API behaviour; the ergonomic wrapper deliberately chooses early
programming-error detection. The mathematical unbounded domains still exclude
literal infinities. No quality preset or hidden transformation is selected.

A future documented wider domain must review this same validator, native trust
and behavioural compatibility: formerly rejected values would enter native code.
Do not infer wider domains or support from provider names/IDs. A genuinely different
parameter meaning needs an explicit extension rather than silently reinterpreting
an existing key. Raw bindings remain faithful to AMD's interface.

`ProviderDefault` passes a null value pointer for that key. It requests the
actual provider's default, without hardcoding the table's FSR3 values or the
header's rounded ±0.333 literals. It is a separate Configure operation, subject
to the same acknowledgement, ordering and error rules as `Value`.

No Configure call automatically requests a history reset. Do not automatically
reapply controls on dispatch, history reset or thread handoff. The observed FSR3
persistence is documented as provider-specific evidence; neither acknowledgement
nor a history reset certifies another provider's effective state.

## Safety boundary

Keep `request_tuning` safe under explicitly extended unsafe acquisition and
dispatch contracts. Provider trust belongs at `Runtime::load_unchecked` and
`MovableRuntime::load_unchecked`; dynamic GPU obligations belong additionally at
the existing unsafe dispatch boundary. This extends D028, whose accepted trust
contract deliberately did not yet cover public Configure.

### Actual-provider requirements at unsafe acquisition

For every default or explicitly selected provider actually used with these
controls, require the caller to establish that:

- A valid descriptor, any value within that parameter's finite wrapper domain
  and null-default request are processed safely or rejected with an ordinary
  native error. Values outside that domain never reach native Configure.
- Descriptor and float storage are consumed synchronously and not retained or
  accessed after return, on success and error. Configure launches no deferred
  GPU work or callback requiring extra shutdown or retention.
- Configuration of an idle context is compatible with its existing resources
  and other contexts under common-domain native coordination. It introduces no
  uncoordinated mutation of sibling contexts. These five controls do not change
  resource-input requirements or invalidate the context's retained requirement
  snapshot, allocation limits or validated creation profile.
- An error leaves a valid terminally destroyable handle under existing teardown
  rules. No error atomicity, rollback or safe continued use is assumed.
- D013's common-domain serialization, non-reentrancy, destination-thread and
  shutdown obligations cover Configure as well as other native calls. Moving
  an owner never establishes GPU completion or permits concurrent use.

These are caller-established conditions, not universal AMD guarantees or facts
proved by enumeration, successful calls or the open FSR3 implementation. A
provider known to ignore a request can acknowledge it; no-op acknowledgement
must not be mistaken for pointer retention or unsafe processing.

### Ordering obligations at unsafe dispatch

Extend both dispatch methods' `# Safety` contracts: before any subsequent
`request_tuning` on that context, all previously submitted work using the
context must have completed, with renderer-established fence/queue ordering.
There must be no executable, unsubmitted recording referencing the context
which can be submitted after Configure. A new context satisfies this condition
without a wait. Between completed rendering phases it is the renderer's duty to
establish the idle condition; the wrapper neither submits nor waits on queues.

The normal path is record → submit → wait for completion → configure → record
the next frame. Abandoning a successful recording retains D011's terminal-use
rule: invalidate it and destroy that context rather than configure and resume.
A failed native dispatch likewise leaves the context terminal. This decision
does not relax either rule.

The extended dispatch contract is a lasting obligation of that unsafe call,
like its current completion-before-destruction requirement. Safe Configure must
have no additional caller-only safety precondition hidden in its own Rustdoc:
its idle condition follows from prior unsafe dispatch obligations, while native
compatibility and serialization follow from unsafe acquisition. An owned
`&mut self` alone is not a fence. This conditional-safe boundary is a substantive
contract extension accepted under D029, not implied by D028's acceptance.

## Errors and eligibility

Add `Operation::Configure`, `Error::InvalidTuningValue { parameter:
TuningParameter }` for non-finite or out-of-domain input, and `Error::ConfigurePoisoned` for a
context previously rejected by native Configure. Preserve `Error`'s existing
`Debug`, `Clone`, `Copy`, `PartialEq`, `Eq` and non-exhaustive contract; invalid
floating-point payloads need not be stored in it.

Use one shared private eligibility state for both families, recording the first
native failure origin (`Dispatch` or `Configure`) instead of the current
dispatch-only boolean. Every dispatch, live query and Configure operation must
check it before descriptor construction, resource validation, COM inspection or native entry.
Pure checked-request construction is independent of that state.

| Event on a usable context | Result | Later dispatch/live query/Configure |
|---|---|---|
| Non-finite or out-of-domain `Value` at request construction | `InvalidTuningValue { parameter }`; no native call | Remain available |
| Native OK | `Ok(())`; acknowledgement only | Remain available |
| Native non-OK | `Native { operation: Configure, code }` with exact public code | Return `ConfigurePoisoned` without native entry |
| Existing native dispatch failure | Preserve existing dispatch failure transition | Return `DispatchPoisoned`, including from Configure with a checked request |

Ordinary query errors do not set or clear either poison state. Reset-to-default
is not recovery and cannot clear poison. Independent runtime/pre-create queries
and sibling contexts remain available under the existing coordination contract.

After a Configure error, stop using that context and destroy it normally. The
idle precondition means there is no earlier outstanding recording/work to
recover. Configure receives no command list: do not invent a failed list to
discard or copy dispatch's failed-list rule into its error documentation.
Several acknowledged single-key changes followed by an error are not rolled
back; the poisoned context offers no continued-use guarantee.

Explicit destruction and Drop remain terminal, with no retry and exceptional
dependency retention on destruction failure. Keep the owner/effect separation:
the generic native owner forwards and retains dependencies; the shared upscaler
core owns parameter mapping and eligibility.

## Raw ABI and implementation boundary

Bind `FFX_API_CONFIGURE_DESC_TYPE_UPSCALE_KEYVALUE`, the five named
`FFX_API_CONFIGURE_UPSCALE_KEY_*` keys and `ffxConfigureDescUpscaleKeyValue` faithfully
from the pinned header. Preserve the header, `key: u64`, `u64: u64` and
`ptr: *mut c_void` field layout and the const Configure entry-point signature.
Add paired Rust/C++ assertions for the tag, key values, field types, offsets,
size and alignment on Windows x64/MSVC.

Each invocation uses a zero-initialized descriptor with the correct tag,
`pNext = null`, the selected key and `u64 = 0`. `Value` points to address-stable
call-local `f32` storage; `ProviderDefault` uses null. Do not encode float bits
in the pointer or integer field. Keep storage live through the synchronous call
and use the context owner's matching live handle. No backend or provider
override node belongs in this live-context descriptor.

Expose no generic raw key/pointer API. Global diagnostics, callbacks and custom
allocation remain U04/R03; reactive-mask generation remains U01. No public
runtime-global Configure operation or new dependency is part of this decision.

## Alternatives and acceptance boundary

- Typed unsafe Configure methods could attach idle-context obligations directly
  to each call. Not selected: retain the chosen acquisition
  trust model and extend the existing unsafe dispatch boundary explicitly.
- Finite passthrough preserves native clamping but conceals programming errors.
  The amendment selects strict domains at the operation boundary instead;
  Rust-side clamping would conceal a transformation.
- Safe continuation after a native Configure error would need a stronger actual-
  provider failure contract. Prefer terminal eligibility with normal destruction.
- A GPU-completion token or queue-owning wrapper would widen the renderer
  integration scope. No such machinery is selected.

The maintainer originally accepted finite passthrough on 2026-10-18 and later
superseded that value policy through the API coherence amendment above. The
conditional-safe acquisition/dispatch boundary, explicit provider-default
operation and terminal native-error policy remain. Implementation was initially
deferred. A subsequent explicit instruction on the same date authorized
implementation. Neither acceptance nor implementation establishes native
verification or grants commit, publication or deployment authorization.
