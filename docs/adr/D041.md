# D041 — Distinguish safety obligations from rendering and SDK requirements

- Recorded: 2026-10-26.
- Status: **accepted** — the maintainer authorized the refined convention and
  its Rustdoc implementation on 2026-10-26, after the ecosystem follow-up.
- Scope: repository-wide public API documentation convention, including raw,
  local, movable, callback-bearing and future backend/effect APIs. No signature,
  trait, validation, ownership, runtime trust or release-scope change.

## Context

[D011](D011.md) already distinguishes jitter/motion/camera semantics from
memory-safety duties. [D014](D014.md) asks documentation to preserve that
distinction. [D008](D008.md) separates wrapper safety, native validity and bounded
numerical runtime trust; [D013](D013.md) requires complete lasting movable
obligations in public `# Safety`.

At the proposal baseline, `Upscaler::dispatch` grouped image interpretation,
resource lifetimes and actual-provider assumptions in a single long safety
section. Local/movable acquisition and newer feature contracts also mixed
application semantics with safety-sensitive native assumptions. The
[source investigation](../research/records/2026-10-26-src-safety-and-rendering-requirements.md)
classifies these obligations and records the evidence and unresolved cases.

The missing decision concerns common presentation and uncertainty, rather than
a replacement dispatch design or a newly discovered soundness defect. Without
a convention, documentation can imply either that bad pixels are necessarily
Rust UB or that GPU/native violations cannot threaten memory safety.

## Decision

### Classify obligations by consequence

- **Safety:** a caller-established invariant needed to prevent Rust/FFI undefined
  behaviour or memory unsafety. Explain the applicable mechanism, such as wrong
  ABI, dangling CPU pointers, out-of-bounds native writes, invalid ownership or
  CPU data races. Native C/C++ memory unsafety is relevant even when the wrapper's
  own Rust code uses valid references.
- **Correctness:** a condition for intended rendering or SDK behaviour within an
  otherwise supported, memory-safe domain. Examples include matching jitter to
  projection, motion direction and colour/pre-exposure interpretation. These
  remain requirements; documenting them here does not promise good image quality.
- **Uncertain:** available evidence does not establish the safety consequence.
  Do not label the violation proven Rust UB or harmless. Preserve the applicable
  conservative native obligation until a reviewed guarantee or access analysis
  supports reclassification.

Split mixed requirements. Signal meaning and the provider's safe numerical or
sampling domain are different obligations: D011's semantic distinction does not
waive [D024](D024.md)'s allocation/access trust, [D027](D027.md)'s profile
compatibility or [D034](D034.md)'s literal-scale conditions. An input's checked
finiteness or successful native return is not an access-safety certificate.

### Use `# Safety` for the complete safety contract

Every public unsafe function must explain the extra safety conditions its caller
establishes. Include lifetimes, ownership, applicable threading/coordination,
asynchronous completion, failure and cleanup, and any obligations that persist
after return or after the public runtime is dropped. Distinguish what the wrapper
enforces from what its caller or trusted native implementation must establish.

Keep safety-relevant uncertainty here under a subsection such as
`## Native assumptions and uncertainty`. For each such assumption, state:

1. The concrete property required, the affected runtime/provider/backend and
   operation, and whether it is a native guarantee, project trust decision or
   unresolved conservative condition.
2. Why it matters to safe memory access, ownership or later safe operations, and
   what is unknown about the consequence of violating it.
3. Who establishes it and how long it lasts, including error, unwinding,
   retained-dependency and hidden-native-activity cases where applicable.

For example, temporary descriptor non-retention protects CPU pointer lifetime;
GPU backing lifetime and truthful boundary states also remain required, while
their general mapping to Rust/host-memory UB is unresolved. A native specification's
use of “undefined behaviour” is not automatically a statement about the Rust
abstract machine. Equally, GPU isolation or device removal is not a demonstrated
guarantee that every invalid access is contained.

Do not move a safety condition into another section solely because the wrapper
cannot check it or its failure has not been reproduced. Do not replace a lasting
contract with an ADR link, warning, “valid SDK usage”, or “caller assumes all
risks”. D013's full public acquisition contract remains required; shared Rustdoc
links can connect operations without hiding essential local duties.

### Explain correctness in prose or descriptive sections

Explain short conditions in ordinary prose or on the relevant input types.
When several conditions need grouping, use a descriptive heading appropriate to
the operation, such as `# Input conventions`, `# Rendering requirements` or
`# Provider semantics`. It covers signal conventions, intended feature
application and renderer workflow requirements whose violation, within the
supported safety domain, does not itself invalidate the safety argument. State
observable consequences and limits where known; do not add empty sections
mechanically.

Keep changes to renderer bindings and output interpretation visible here or in
ordinary behaviour documentation. Keep validation failures and returned native
codes under `# Errors`; document `# Panics` where applicable. A safe function
must not acquire an unchecked memory-safety precondition merely by putting it
under `Requirements` or another heading.

`# Safety` follows [Rust API Guidelines C-FAILURE](https://rust-lang.github.io/api-guidelines/documentation.html#function-docs-include-error-panic-and-safety-considerations-c-failure).
The [ecosystem follow-up](../research/records/2026-10-26-src-rustdoc-requirements-ecosystem.md)
finds actual `Requirements` headings, but no established ecosystem meaning of
“non-safety obligations”. Ordinary prose and descriptive headings also carry
semantic contracts in established APIs. `# Requirements` remains an allowed
optional grouping when its scope is clear, rather than a prescribed or preferred
repository-wide spelling. These headings use Rustdoc's
[Markdown documentation](https://doc.rust-lang.org/rustdoc/how-to-write-documentation.html#markdown),
with no standardized safety category or enforcement mechanism. The substantive
classification is binding; the non-safety heading spelling is flexible.

### Require `unsafe` where the safety boundary needs it

An operation needs a public unsafe boundary when soundness depends on extra
caller-established safety conditions that types, validation, ownership and
previously established unsafe invariants do not discharge. The
[Rust Reference](https://doc.rust-lang.org/reference/unsafe-keyword.html#unsafe-functions-unsafe-fn)
describes that caller proof obligation. Merely calling FFI internally, accepting
an imperfect image or relying on an uncheckable logical convention is not enough
to justify an unsafe public function.

For uncertain native safety, identify a concrete, reviewable conditional contract
and preserve the unsafe boundary where that contract is necessary. `unsafe` is
not by itself evidence of soundness or a way to turn arbitrary unknown behaviour
into an acceptable API. A new API still needs justification for its supported
native assumptions and for every later safe operation it enables.

Preserve D008's safe ordinary construction under accepted acquisition trust,
D011/D014's unsafe dispatch, D013's conditional `Send + !Sync` family and
[D040](D040.md)'s separate unsafe callback/diagnostic operations. Earlier unsafe
calls can establish lasting invariants relied upon by later safe calls and Drop;
document that dependency rather than adding a new hidden safety condition at the
later safe call. Distinguish an obligation from a native guarantee actually
verified or supplied upstream.

## Application to existing and future APIs

| Surface | Application of this convention |
|---|---|
| `Runtime::load_unchecked` | Retain code/ABI, initialization/termination, actual-provider memory/descriptor/query and common native coordination assumptions in `Safety`. Separate feature application/interpretation from safe processing of its inputs. |
| `MovableRuntime::load_unchecked` | Retain the complete arbitrary-thread and lasting shared-state contract, including safe use, cleanup/unwinding, hidden workers and exceptional retention. Native compatibility remains caller-established, not an AMD guarantee. |
| Local/movable `dispatch` and generation | Separate matching signal semantics from numerical/access support. Keep existing GPU state, aliasing, residency, lifetime, submission/order, Configure-idleness and failed/abandoned-recording duties in `Safety`, marking unresolved native consequences explicitly. |
| Safe construction, preflight, Configure, queries and destruction | Describe enforced checks and limits; connect to earlier acquisition/recording/installation invariants. Metadata validation does not establish pixel meaning, native support or GPU completion. |
| Callback-bearing and future SDK/backend APIs | Apply the same classification to ABI, pointer/allocator ownership, callback state, threading and asynchronous resources, using evidence for that actual backend/effect. Do not infer Vulkan or another effect's contract from DX12. |

This decision changes no current safety guarantee or caller obligation. It does
not authorize removing `unsafe`, relaxing any D008/D011/D013/D014 or later
accepted precondition, weakening validation or widening native support. A future
contract reclassification that weakens an existing precondition needs explicit
review of its safety and compatibility consequences. The maintainer separately
authorized the documentation migration with acceptance; it adds no release
prerequisite.

## Alternatives and rationale

- **No new ADR:** D011/D014 already settle the substantive distinction for
  dispatch. This avoids repetition but leaves repository-wide structure and
  uncertain native requirements unspecified. This decision adds only those rules.
- **Everything in `Safety`:** preserves obligations but obscures the reason an
  unsafe call needs review and can misrepresent image mistakes as memory unsafety.
- **All GPU requirements in `Requirements`:** unjustified; actual lifetimes,
  storage reuse and native access hazards cannot be assumed harmless.
- **One universal correctness heading:** `Requirements` is permissible but has
  no special ecosystem standing. Prefer prose or a descriptive heading suited
  to the API: `Rendering requirements` fits frame inputs, while provider
  semantics fit acquisition/query behaviour. Bare `Preconditions` can describe
  safety as well as correctness; `Notes` does not clearly express mandatory
  conditions. None replaces `Safety` on an unsafe API.

## Consequences and evidence limits

Contracts should become easier to audit without inventing a GPU/Rust memory
model. Classification requires reasoning and sometimes leaves uncertainty; it
cannot be inferred mechanically from the presence of `unsafe`, a native error
code, debug-layer output or a successful GPU run.

The [source record](../research/records/2026-10-26-src-safety-and-rendering-requirements.md)
contains the per-obligation classification, direct Rust/Microsoft references,
baseline and unresolved questions. Closed-provider domains, GPU-only violation
consequences and general native non-retention/threading/termination properties
remain unresolved. The implementation reorganizes Rustdoc and labels native
assumptions without changing executable Rust, API signatures or unsafe
boundaries. No native experiment or new native safety guarantee follows.
