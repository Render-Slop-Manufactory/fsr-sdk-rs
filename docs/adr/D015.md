# D015 — Separate common upscaler inputs and the DX12 backend

- Recorded and accepted: 2026-10-09, by maintainer authorization of this separation.
- Follow-up accepted: 2026-10-09, by maintainer authorization to expose common
  inputs independently while retaining native gates and contracts.
- Status: **accepted**.
- Release: current source only; no release selected by this decision.

## Decision

Expose `fsr_sdk::upscaler::common` for `Dimensions`, `UpscalerOptions`,
`JitterOffsetPixels`, `FrameTimeMillis` and `CameraParameters`. These existing
types contain no GPU object dependencies. Keep their fields, checked domains,
traits and meanings unchanged.

Expose `fsr_sdk::upscaler::dx12` for `Upscaler`, `UpscaleDispatch`, the accepted
DX12 interface types, and feature-gated `MovableUpscaler`. Place construction,
COM/resource validation, descriptor translation and recording under this backend.
Keep the existing `fsr_sdk::upscaler` imports as reexports of the exact same types;
introduce no replacement wrappers or conversions.

The original decision retained the whole upscaler module's Windows plus `dx12`
gate. The accepted follow-up removes that gate from `upscaler`, `common` and
the common-type reexports. Only `upscaler::dx12` and its backend reexports retain
the Windows plus `dx12` gate; `MovableUpscaler` also requires `movable`.

Runtime acquisition remains in `fsr_sdk::runtime`, using the existing Windows
DLL loader. `RuntimeState` retains only `FfxLibrary`, with no device or GPU
resources, so no `runtime::dx12` module is introduced. Backend-neutral ownership
does not establish a portable native contract: runtime and raw loader retain
their Windows/DX12 gates, and acquisition, thread compatibility and cleanup
obligations remain unchanged, especially for `MovableRuntime`. A future platform
port must review symbol-resolution guarantees and native contracts independently;
no loader reorganization was selected by the original common-input separation.

The original separation made no ABI, dependency, GPU behavior, ownership,
threading or safety contract changes. `fsr-sdk-sys` already separated common
and DX12 declarations. The subsequently authorized loader follow-up below changes
only loader organization and the production dependency boundary.

Vulkan remains unsupported, including the existing feature compile error.
Do not expose an empty Vulkan module, placeholder GPU types or a backend trait.
A future backend requires an actual upstream integration path and its own
resource, platform, lifetime and synchronization contracts. The new module
boundary creates room for that work without asserting that it is implemented.

## Rationale and verification

Separate backend-independent values from concrete GPU integration while keeping
existing consumers source-compatible. This implements platform isolation under
[SCOPE](../../SCOPE.md) without selecting speculative cross-backend abstractions.
[D014](D014.md) remains the separate accepted dispatch-input and sharpening
decision. Its [M8 implementation checks](../release/2026-10-09-m8-implementation-verification.md)
are complete; M9 GPU execution and final artifact verification remain pending.

Preserve existing validation, ownership, error, ABI and native regression tests.
Update exact native-test filters for their new module paths. A downstream test
must accept common inputs and DX12 owners through both old and explicit paths,
including the optional movable family. Validate default and movable builds,
common inputs without default features, Rustdoc, and the selected native lifecycle
and GPU regressions. Results and concrete limits belong in the implementation
verification record, separately from this accepted design. The
[2026-10-09 implementation verification](../release/2026-10-09-common-dx12-verification.md)
records passing consumer, feature, ABI and six selected native checks.

The follow-up splits portable input tests from Windows/DX12 compatibility tests.
Downstream positive controls must accept common values through both paths and
common raw ABI types without native APIs. Separate negative controls must prove
that runtime, the DX12 module, backend reexports, raw loader and raw DX12 module
are unavailable when their gates are disabled, including `movable` without DX12.
CI covers Windows without DX12 and non-Windows with and without native features.
The [portable-common verification](../release/2026-10-09-portable-common-verification.md)
records executed checks and explicitly distinguishes local Windows results from
Linux checks deferred to CI.

## Loader organization follow-up (2026-10-09)

**Accepted:** the maintainer authorized implementation after task-prompt review.
This extends the original decision's scope; its earlier statement that no loader
reorganization was selected was not a prohibition on this later refactor.

Keep `fsr_sdk_sys::loader` behind `all(windows, feature = "dx12")`. Its minimal
`loader/mod.rs` documents the interface and reexports `FfxLibrary` and `LoadError`
from a private `loader/windows.rs`. Move the existing implementation intact,
preserving explicit-path canonicalization, five required exports, private
function pointers, errors and sources, library retention and unsafe contracts.
There is no shared loading framework or new public platform module.

Make raw `libloading` optional under `cfg(windows)`, activated by the existing
`dx12` feature. Common-only production consumers no longer need dynamic loading;
the wrapper's portable fixtures retain their direct dev-dependency. No dependency
version or third-party licence changes. Preserve both crates' default features,
the unsupported Vulkan error and movable semantics.

The OS target and graphics feature remain independent conditions. This organizes
the only existing native path; it adds neither Linux nor Vulkan implementation.
A future platform module requires its own ABI, symbol validation, deployment and
native safety review. `fsr_sdk::runtime` remains in place and owns no DX12 device.

Verification and unavailable native checks are recorded in the
[loader refactor verification](../release/2026-10-09-loader-platform-verification.md).
