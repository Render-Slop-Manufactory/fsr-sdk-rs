## Problem and evidence boundary

Supplied masks already reach main upscaling under D025. That is distinct from
the SDK operation which compares opaque-only and opaque-plus-translucent colour
and writes a reactive texture. At proposal time, its descriptor/tag `0x10006`
and four flags were not bound or exposed in production. They are now bound and
exposed below. D028 supplies explicit provider routing; D029 supplies
shared context eligibility, including Configure failure.

The pinned shared header and open FSR3 adapter expose this separate `ffxDispatch`
route. The latter forwards its resources, region, scalars and flags to the open
generator. This is source evidence, not a signed-provider capability, numerical
domain or resource-restoration guarantee. No existing supplied-mask test verifies
generation. Actual-provider generation remains unverified; the later test-only
preparation is described below.

## Public API

Portable `ReactiveMaskOptions` is available in `upscaler::common`, reexported from
`upscaler`, with private fields and `Debug + Clone`:

```text
ReactiveMaskOptions::new(scale: f32, cutoff_threshold: f32, binary_value: f32)
    -> Result<Self, Error>
scale(), cutoff_threshold(), binary_value() -> f32

apply_tonemap() / set_apply_tonemap(bool)
apply_inverse_tonemap() / set_apply_inverse_tonemap(bool)
apply_threshold() / set_apply_threshold(bool)
use_components_max() / set_use_components_max(bool)
```

The constructor checks all three scalars for finiteness and initializes all
toggles to false. Getters borrow `self`; setters return `()`. Scalars remain
unchanged after construction; construct new options to change them. There is
no implicit `Default`, numerical recommendation or preset. Every finite value,
including negative zero and values outside `[0, 1]`, maps unchanged. No header
guarantee establishes universal scalar ranges or native clamping for this
operation; finite validation is not certification of a provider's full domain.
Option construction is independent of any context and cannot change eligibility;
the recording method checks context eligibility first before its own preflight.

The DX12 borrowed request type has private fields and `Debug + Clone`:

```text
GenerateReactiveMaskDispatch<'a>::new(
    command_list: &'a ID3D12GraphicsCommandList,
    color_opaque_only: &'a ID3D12Resource,
    color_pre_upscale: &'a ID3D12Resource,
    output: &'a ID3D12Resource,
    render_size: Dimensions,
    options: ReactiveMaskOptions,
) -> Self

command_list(), color_opaque_only(), color_pre_upscale(), output()
    -> the corresponding original borrow
render_size() -> Dimensions
options() -> &ReactiveMaskOptions

unsafe Upscaler::generate_reactive_mask(
    &mut self, dispatch: GenerateReactiveMaskDispatch<'_>,
) -> Result<(), Error>

unsafe MovableUpscaler::generate_reactive_mask(
    &mut self, dispatch: GenerateReactiveMaskDispatch<'_>,
) -> Result<(), Error>

Upscaler::validate_generate_reactive_mask(
    &self, dispatch: &GenerateReactiveMaskDispatch<'_>,
) -> Result<(), Error>

MovableUpscaler::validate_generate_reactive_mask(
    &self, dispatch: &GenerateReactiveMaskDispatch<'_>,
) -> Result<(), Error>
```

These signatures describe the current development API. The
request lives in `upscaler::dx12` and is reexported from `upscaler` under the
existing Windows/DX12 gate. Movable methods keep their existing feature gate;
the borrowed request is `Send + Sync`, without `Copy` or GPU-completion claims.
Request construction/cloning only assembles borrows and options: no COM/native
calls, resource allocation, independent COM retention or hidden work occurs.
No additional three-texture bundle, command queue, fence or manager type is needed.

The operation records into the caller's list on the live context's actual
provider. There is no per-call provider override, new context or runtime-global
operation. Existing creation options, main dispatch signatures, independent
supplied masks and transparency/composition input remain unchanged.

The optional validation methods reuse the recording operation's complete
role-aware inspection, check existing eligibility first and call no FidelityFX
entry point. They may inspect DX12 COM metadata before command-list opening or
resource transitions, without recording commands, changing eligibility or
retaining extra resource references. Failure leaves a usable context usable.
They cannot inspect actual states, heap overlap, pixels, submission/completion,
or native support. Generation always repeats all checks; separate validation is
never a safety prerequisite or a provider capability certificate. No prepared
resource cache or new ownership/session abstraction is introduced.

## Exact flags and raw mapping

| Option | Native `FFX_UPSCALE_AUTOREACTIVEFLAGS_*` suffix | Bit |
|---|---|---:|
| `apply_tonemap` | `APPLY_TONEMAP` | 0 |
| `apply_inverse_tonemap` | `APPLY_INVERSETONEMAP` | 1 |
| `apply_threshold` | `APPLY_THRESHOLD` | 2 |
| `use_components_max` | `USE_COMPONENTS_MAX` | 3 |

Forward all 16 combinations exactly, including both tonemap bits together.
The inspected shared header declares no mutual-exclusion rule. The wrapper must
neither reject that combination on speculation nor promise cancellation or a
provider-independent interpretation. The actual provider may reject a request;
preserve its result. Scalars are validated even when a flag makes them unused.

Bind `FFX_API_DISPATCH_DESC_TYPE_UPSCALE_GENERATEREACTIVEMASK`, all four constants
and `ffxDispatchDescUpscaleGenerateReactiveMask` faithfully. Preserve the common
header, command-list pointer, three `FfxApiResource` values, `renderSize`, three
`f32` fields and final `flags: u32` in pinned-header order. Use the const dispatch
signature and a null `pNext`; no creation/backend/provider extension belongs in
this live-context request. Descriptions retain actual allocation dimensions;
`renderSize` contains the explicit active region.

## Resource and geometry profile

| Role | Format/allocation | Required capability/boundary state |
|---|---|---|
| Opaque-only colour | RGBA16F, context `max_render_size` | Shader-readable; `NON_PIXEL_SHADER_RESOURCE` |
| Full pre-upscale colour | RGBA16F, context `max_render_size` | Shader-readable; `NON_PIXEL_SHADER_RESOURCE` |
| Reactive output | R8_UNORM, context `max_render_size` | UAV-capable and shader-readable; `UNORDERED_ACCESS` |

All three are single-sample, single-mip, single-slice Texture2D resources on the
context's device. The list must be DIRECT and on that device. Validate shape,
format, exact allocation extent, relevant flags and canonical device identity
before native entry, reusing existing inspection/conversion helpers. Output
must have distinct canonical COM identity from either input. The two read-only
inputs may be the same texture; do not impose the main dispatch's all-distinct
rule on them. Actual write/read backing-storage overlap remains an unsafe caller
obligation because COM identity does not prove separate allocations.

The explicit `render_size` is nonzero and bounded on each axis by the context
maximum. Its image occupies the top-left region without an offset. Generation
is a standalone operation: do not gate its bounded region on the main upscaler's
dynamic-resolution flag or change that flag automatically. D024 still governs
main dispatch. If the result is supplied to main upscaling, the generated region
and frame must match the consumer's active render region; a fixed main context
therefore needs a mask generated for its full render size. The wrapper does not
track texture contents or silently select the next main dispatch's region.

Both colour textures must represent the same frame, projection/jitter, exposure
and signal conventions, differing in the intended translucent contribution.
The renderer establishes the actual provider's accepted signal/scalar/extent
domain, including any native arithmetic or GPU dispatch limits. Do not guess
encoding conversions, rescale inputs or copy the main dispatch's pre-exposure
field into this descriptor: the generator has no such field.

These are accepted wrapper-profile and safety choices, not proof of universal
provider support. Broader formats remain U05. Resource-requirement query bits
are not generator-capability detection and must not gate this operation or the
subsequent supplied-mask route.

## GPU, lifetime and coordination contract

Keep the public recording method unsafe, like main dispatch. Lasting ABI,
actual-provider compatibility and common-domain coordination remain obligations
at both unsafe runtime acquisitions. Extend that trust to synchronous consumption
of temporary generation descriptors, safe processing of valid requests in the
established provider domain, and success restoring the declared boundary states.
That restoration is an explicit trust requirement to verify, not a new native
observation. The per-call unsafe contract supplies the live list/resources,
matching contents, supported parameters, truthful states and ordered GPU use.

The renderer keeps resources, backing storage, list/allocator, context and runtime
valid and resident through GPU completion. Avoid conflicting access, premature
reuse or allocator reset. A Rust borrow lasts only through CPU recording; native
return does not complete GPU work. The wrapper submits and waits for nothing.
Native calls and cleanup remain serialized/non-reentrant in the common domain;
movable ownership does not authorize concurrent use or establish completion.

For generation followed by main upscaling:

1. Establish shader-read state for both colours and UAV state for output, then
   record generation.
2. On success, order output writes and transition the reactive texture from UAV
   to shader-read for the consumer. A UAV barrier followed by the transition is
   an explicit conservative sequence; the renderer owns the barrier commands.
3. Supply that texture via `UpscaleResources::set_reactive_mask(Some(...))` and
   record main upscaling with matching frame/active region. Keep D025's ordinary
   supplied-mask checks and any separate mandatory inputs.
4. Execute successful recordings in order on the queue. Across queues, establish
   appropriate producer-fence/consumer-wait dependencies. Restore UAV state only
   after all prior readers finish before generating the next mask.

Same-list composition does not require a CPU wait between the two operations.
Generation may also be submitted alone without feeding main upscaling; an unused
output is not an abandoned recording. There is no implicit barrier insertion,
main dispatch, resource retention token, history reset or temporal-frame advance
performed by the wrapper.

Extend both generation and main dispatch's unsafe contracts so that all submitted
work from either operation is complete, with no executable unsubmitted recording,
before subsequent safe Configure. D029's idle-context reasoning must cover both
GPU-producing routes. Finish work and invalidate failed/abandoned recordings
before explicit destruction or Drop, including unwinding and thread handoff.

## Errors and eligibility

Use D029's shared eligibility state before numerical/resource validation, COM
inspection or native entry. `ConfigurePoisoned` and `DispatchPoisoned` preserve
their current meaning; neither main dispatch nor generation can revive a context.

Extend existing non-exhaustive error categories rather than add a parallel error
hierarchy. Add `DispatchScalar::{ReactiveScale, ReactiveCutoffThreshold,
ReactiveBinaryValue}` for non-finite options and
`ResourceRole::{OpaqueOnlyColor, ReactiveMaskOutput}`; reuse `Color` for full
colour. Existing active-size, command-list, resource-property and HRESULT errors
describe the corresponding preflight failures. Preserve `Error`'s current traits.

| Outcome | Result and context policy |
|---|---|
| Scalar/options, region or resource validation failure | Existing structured `InvalidDispatch`/`Dx12Inspection`; no generation commands added and a usable context remains eligible |
| Native OK | `Ok(())` means recording acknowledgement, not submission, completion, mask consumption or application |
| Any native non-OK, including unsupported operation | `Native { operation: Operation::Dispatch, code }` with exact code; shared eligibility becomes `DispatchFailed` |
| Later generation, main dispatch, live query or Configure | `DispatchPoisoned`, before validation/inspection/FFI |

Both recording routes use `Operation::Dispatch` because both invoke `ffxDispatch`.
Do not fabricate a capability error, retry another provider, silently fall back
to a supplied mask, or special-case unsupported codes as safe continuation.

After native failure, do not submit the failed list: it may contain partial
commands, and resource post-states are unspecified. Invalidate its recording,
finish earlier submitted work and destroy the poisoned context normally. A
successfully recorded operation that is abandoned also requires stopping use of
that context, invalidating the recording and terminal cleanup, as under D011.
Preflight failure of a later operation does not undo earlier successful commands;
the renderer may correct that preflight failure while obeying the earlier work's
submission/lifetime obligations. There is no two-operation transaction.

Ordinary query errors still do not alter eligibility. Destruction remains one
terminal attempt with existing dependency retention on failure; generation adds
no callback, allocator or public native handle to the owner.

## Support discovery and recovery

There is no proven generic support query. Do not try a possibly unsupported
generator on the application's live history merely to discover capabilities.
Where the renderer deliberately probes a trusted deployment, it may use a
disposable context with valid resources and a real command list, under the same
unsafe native/domain and cleanup obligations. Successful recording must be
submitted and fenced before teardown; a failed list must never be submitted.
Record exact provider/runtime/device/profile, return codes and actual GPU
execution separately. A disposable context protects that context's history,
not necessarily shared provider state, and is neither process isolation nor
proof that an unknown provider safely handles the request. No automatic probe,
fallback, support cache or separate permanent generator context is selected.

After native failure or abandonment, invalidate every affected unsubmitted
recording, finish earlier submitted work and replace all affected FSR contexts.
Fresh contexts need an initial main-upscale history reset. Keep ownership while
renderer cleanup is incomplete; do not consume/drop the context merely because
completion returned an error. Configure has no failed command list of its own.
Neither optional preflight, Configure nor `reset` clears poison or undoes an
acknowledged recording. Error-code-specific continuation and abandoned-recording
reuse need separate provider-pinned evidence and decision review.

## Implementation and verification

The [isolated raw spike](../WINDOWS_FOLLOWUP.md#2-isolated-d030-raw-spike) is
prepared in test equipment only. It can establish bounded actual-provider
support, mask writes, declared state boundaries and generated-to-consumer
execution independently of the public implementation. It does not exercise these
public signatures. Both-family public fixtures and paired production ABI checks
are prepared; their Windows execution remains open.

The local implementation adds raw ABI/assertions, portable options, a borrowed
DX12 request, separated validation/descriptor mapping and both public methods
using the shared recording/error policy. It reuses the sealed owner/core and
inspectable metadata helpers; the read-only-input alias rule is specific to this
operation. Both acquisition/recording contracts and the movable field/lifetime
audit are updated. The renderer composition example records explicit barriers.

Verification must cover:

- Paired Rust/MSVC C++ tag, four-bit, field-type, offset, size/alignment assertions
  against pinned headers; all 16 flag combinations and exact scalar/region mapping.
- Portable finite/non-finite option boundaries, explicit zero flag default,
  aliases/traits and native feature gates; stable and exact Rust 1.88 checks.
- Controlled fixtures for both public families: matching live handle/device/list,
  every resource/extent/usage/state field, same read-only input acceptance,
  output-identity rejection, preflight priority/no calls, arbitrary errors and
  unsupported codes, both poison origins, no calls after poison, outer moves,
  terminal cleanup and failed-destroy retention.
- Optional-preflight/recording parity, zero FidelityFX calls and unchanged COM
  ownership during validation, reinspection after changed input metadata, and
  poison precedence. An unsupported-code fixture must preserve terminality;
  native probe results must not be inferred from that fixture.
- A renderer example for generate → barrier/transition → supplied-mask upscale,
  caller-owned submission/completion, subsequent Configure and exceptional cleanup.
- Bounded actual-provider native recording/readback/cleanup, all four flag bits,
  active-region shrink/grow within fixed allocations and generated-to-consumer
  ordering. Record explicit rejection/acknowledgement separately from observed
  writes and execution; the wrapper's composition checks do not prove provider
  consumption. Final extracted-package checks remain separate.

Windows execution was initially deferred on 2026-10-18. The subsequent
[2026-10-19 Windows batch](../release/2026-10-19-windows-upscaler-verification.md)
passes fixtures and independent MSVC ABI. [Native probes](../research/records/2026-10-19-exp-reactive-mask-providers.md)
pass both public families/all flags on 3.1.5; 4.1.1 and 2.3.4 return OK but leave
masks unchanged. Their complete profiles remain failed. This changes no support
policy, successful-recording obligation, terminality contract or platform boundary.

## Alternatives and review focus

- Hiding generation inside main dispatch would obscure the extra colour input,
  output UAV, barriers and failure boundary. Select the explicit separate operation.
- A new generation context/resource owner would duplicate the actual SDK context
  route and renderer ownership. Reuse the existing owner and borrowed resources.
- Rejecting both tonemap bits, aliasing of read-only inputs or finite scalars on
  guessed rules would narrow SDK access without an established precondition.
- Safe GPU recording or an implicit submission/fence helper would require a
  different renderer ownership model. Keep the existing unsafe recording boundary.

Review should assess the independent active-region contract, finite passthrough,
input/output alias rules, success-state restoration assumption, ordered
generation-to-consumer path and shared terminal error/Configure obligations as
one coherent proposal. No U01 implementation is authorized until this contract
is accepted and the maintainer separately requests implementation.
