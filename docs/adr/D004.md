# D004 — Load an explicit DLL with private entry points

- Recorded: 2026-09-20
- Status: accepted — explicit-path scope and private pointers with five unsafe
  forwarding methods authorized by the maintainer

**Choice:** `fsr-sdk-sys::loader::FfxLibrary` owns a `libloading::Library` and
private values of the existing five `PfnFfx*` types. `unsafe load` resolves a
caller-supplied file and all five exports. Relative paths are canonicalized
against the current directory, avoiding a name-only Windows search for the main
DLL. The existing Windows/DX12 module gate remains in effect.

**Rationale:** A public pointer table or dereferenceable symbol guard would allow
callers to copy pointers out of their owner. Instead, methods named after the
native exports borrow the owner and forward raw arguments and return codes.
No raw accessor, context management, descriptor validation or safe wrapper is
introduced. Failed loads drop any partially acquired library ownership.

**Consequences:** Loading is unsafe because initialization/termination and export
ABI compatibility are caller obligations. Calls retain the DLL during invocation,
but native contexts, callbacks and pending work may outlive an invocation; their
lifetimes and synchronization remain caller obligations. Windows resolves DLL
dependencies; this step does not implement discovery, installation, signature
verification, search-path mutation or distribution policy.

**Evidence:** [Loader verification](../research/records/2026-09-20-exp-explicit-dll-loader.md).
The local SDK identifies `amd_fidelityfx_loader_dx12.dll` as the API entry point;
the successful load-only test is not evidence of query or effect execution.
