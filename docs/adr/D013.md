# D013 — Optional movable runtime/upscaler family

- Recorded: 2026-09-29
- Updated: 2026-10-07 (status aligned with the 2026-09-30 native evidence).
- Status: **proposed** — compile/host, Windows fixtures and bounded fenced native
  transfers passed; not accepted, and no public movable API is implemented
- Scope: existing SDK v2.3.0 Windows/DX12 upscaler profile on
  `x86_64-pc-windows-msvc`
- Timing: work after the released `0.1.0`; no release version or public
  implementation milestone is selected

## Context and motivation

**Decision at a glance:** this remains a proposal for a separate movable family.
Production uses `Rc`; the private owner's sealed retention parameter allows the
experiment to reuse real lifecycle behavior rather than copy it. Its `Arc`
instantiations occur only in tests, so it adds no production ownership
choice or public threading guarantee. Keep this small shared seam while the
proposal is evaluated; remove it with the experiment if the proposal is rejected.
Compile and serialized fixture results cannot establish AMD thread-transfer safety.
The later native spike passed three serialized, fenced transfer scenarios on one
recorded configuration. Provider termination on the destination thread and the
public conditional contract still require review; the spike does not accept D013.

[D008](D008.md) confines `Runtime` and its dependent `Upscaler` objects to the
runtime's acquiring thread. Both public types are `!Send + !Sync`; an internal
`Rc<RuntimeState>` keeps the loader alive through context cleanup. D005's owner
also has an explicit `PhantomData<Rc<()>>` marker. These restrictions reflect
missing native threading guarantees, not evidence that every thread transfer
necessarily fails.

A renderer that needs to transfer its SDK ownership between threads cannot
store these types directly in a transferable owner. A dedicated thread that
creates, uses and destroys the local family, receiving commands through a
channel, remains an alternative. A concrete project integration, including one
developed here, can justify a movable API under [SCOPE.md](../../SCOPE.md);
an external consumer request is not a prerequisite.

Bevy's [pipelined rendering source](https://github.com/bevyengine/bevy/blob/main/crates/bevy_render/src/pipelined_rendering.rs)
transfers the render sub-app through channels. The
[DLSS wrapper](https://github.com/bevyengine/dlss_wgpu/blob/main/src/sdk.rs)
uses `Arc<Mutex<DlssSdk>>` and manual `Send`/`Sync` implementations. These sources
were inspected on 2026-09-29; the links track upstream `main` and are illustrative
prior art, not pinned compatibility inputs or AMD evidence. Neither establishes
that a DX12/wgpu integration is feasible or that AMD permits thread transfer.

## Proposed choice

Add an optional Cargo feature named `movable`, exposing `MovableRuntime` and
`MovableUpscaler` only in the Windows/DX12 API. The intended public traits are:

| Family | Runtime | Upscaler | Internal runtime retention |
|---|---|---|---|
| Existing local API | `!Send + !Sync` | `!Send + !Sync` | `Rc` |
| Optional movable API | `Send + !Sync` | `Send + !Sync` | `Arc` |

Movable acquisition would use `unsafe MovableRuntime::load_unchecked(path)`.
Construction would accept only that family's runtime and produce only a
`MovableUpscaler`. No public pointer generics, native handles, safe conversion
from local objects, or public Clone implementation are proposed. A feature flag
does not authenticate a runtime or discharge the unsafe contract.

Keep loader, construction, validation, dispatch, errors and terminal ownership
logic shared. A private core parameterized over audited `Rc`/`Arc` ownership is
the candidate implementation; it must not become an unrestricted generic native
owner accepting arbitrary `Deref` implementations. The precise internal bounds
and forwarding technique remain implementation details. Public documentation
must state each family's threading contract without duplicating inconsistent
safety descriptions.

This would extend D005/D008's thread-confinement policy **only for the new
family**. Their existing public types and terminal cleanup behavior remain.
D011's unsafe GPU boundary, poisoning and abandonment rules, and D012's options
contract continue to apply. This proposal adds no provider, format, callback,
Query/Configure, backend or image-quality support.

## Conditional safety contract

`Send` is a conditional Rust safety guarantee once unsafe acquisition has
established the required invariants. Calling the API "not thread-safe" cannot
replace those invariants. The proposed acquisition contract adds the following
to D008's trusted ABI, dependency, configuration and native-lifetime obligations:

1. **Family-wide serialization and non-reentrancy.** All native calls and
   cleanup touching the family's state must be non-overlapping, non-reentrant
   and ordered across thread transfers. This includes acquisition, creation,
   dispatch, consuming destruction, implicit Drop, error cleanup and DLL
   termination. Synchronization must establish a happens-before relationship;
   elapsed time is not synchronization.
2. **Potentially shared native state.** The caller must coordinate with sibling
   contexts, other local or movable families, and external FidelityFX users
   wherever runtime/provider/global state may be shared. Different paths,
   devices, type families or locks do not prove isolation. Separate per-context
   mutexes cannot enforce this obligation.
3. **Native thread transfer.** The actual loader, dependencies, selected
   providers and driver must permit the intended transfers and subsequent
   calls, cleanup and device-reference release on destination threads. This
   includes destruction on a thread other than creation and final DLL unload
   on a thread other than acquisition, including partial-load cleanup.
   Serialization alone does not establish absence of thread affinity.
4. **Lifetime of the obligation.** The caller must arrange ownership and
   synchronization so that safe calls and automatic destruction preserve these
   invariants, including during unwinding. Dropping the public runtime while a
   context survives does not end the obligations. D005's exceptional retention
   does not establish native quiescence or automatically end them either.
5. **GPU and D3D12 obligations.** D011 remains in force: thread transfer and
   CPU synchronization do not establish GPU completion, resource states,
   residency, ordered execution or permission to reuse recording objects.
   Any additional native transfer preconditions with outstanding GPU work must
   be satisfied; this proposal establishes no such capability experimentally.

No built-in mutex or family scheduler is proposed. Keeping every member in one
exclusively transferred application owner is one possible way to serialize the
family; coordination with other native users remains necessary. A
`Mutex<MovableUpscaler>` permits sharing that individual object, but says nothing
about its siblings. A channel orders only the ownership actually transferred.
Implicit cleanup must occur while the required coordination is still in effect.

The transfer assumption is currently **unresolved native behavior**. Acceptance
would require explicit maintainer approval of this caller-established trust
boundary for identified runtime inputs; missing AMD guarantees must not be
presented as proof of unrestricted movability. A successful native experiment
can support one configuration, not prove a universal contract. The movable
acquisition adds threading obligations; dispatch itself remains unsafe under
D011 rather than becoming safe through acquisition.

## Rust ownership and trait requirements

Source inspection on 2026-09-29 of the repository and locally cached, locked
dependency sources establishes:

- The current `RuntimeState` contains only `FfxLibrary`, whose fields are native
  function pointers and `libloading::Library`. The locked `libloading` 0.9.0
  library implements both `Send` and `Sync`.
- Consequently, replacing the current runtime's `Rc` with `Arc` alone would
  make it `Sync` as well as `Send`. The new runtime needs an explicit `!Sync`
  marker, such as private `PhantomData<Cell<()>>`; an `unsafe impl Send` does
  not remove `Sync`.
- Pinned `windows` 0.62.2 declares `ID3D12Device: Send + Sync`. This describes
  the Rust COM wrapper, not FidelityFX provider affinity.
- The current context owner and pinned descriptors contain raw pointers and
  explicit local-family markers. `Arc` does not make an entire upscaler
  automatically transferable.

The dependency observations came from `libloading` 0.9.0 `src/safe.rs`
(explicit `Send` and `Sync` implementations for `Library`) and `windows` 0.62.2
`src/Windows/Win32/Graphics/Direct3D12/mod.rs` (explicit implementations for
`ID3D12Device`). The corresponding dependency declarations are visible in
[Cargo.lock](../../Cargo.lock); source references are
[libloading 0.9.0 Library](https://docs.rs/libloading/0.9.0/libloading/struct.Library.html),
[windows 0.62.2 ID3D12Device](https://docs.rs/windows/0.62.2/windows/Win32/Graphics/Direct3D12/struct.ID3D12Device.html)
and the [Rust Arc contract](https://doc.rust-lang.org/std/sync/struct.Arc.html#thread-safety).
The two versioned docs.rs pages could not be fetched during preparation;
the observations above use the cached source, not those pages. These are source
observations. The later
[compile/host experiment](../research/records/2026-09-29-exp-d013-movable-compile-host.md)
confirms the trait claims on the Windows target and exercises concrete test-only
movable shapes through the real private owner. It is not a public implementation
or evidence of AMD transfer compatibility.

Keep explicit public trait guarantees independent of incidental field contents.
Any manual `Send` implementation must be narrow and audit the retained runtime,
device, address-stable descriptor storage, native handle and every cleanup path.
Do not add blanket `Send`/`Sync` implementations to `RuntimeState`, the generic
owner or arbitrary dependency bundles to make compilation pass. No actual
`Rc`-owned dependency may survive inside a movable bundle. Future dependencies
or callbacks require renewed review rather than inheriting movability blindly.

Moves must preserve native pointer validity, shared-library lifetime, cleanup
order and D005's exceptional retention. `Arc` addresses shared reference-count
safety; it does not serialize native operations or make provider state safe.

## Public documentation requirement

If implemented, movable acquisition and both public types must explain their
contract in Rustdoc. A short overview should cover family-wide serialization
and non-reentrancy, caller-established native transfer compatibility, cleanup
on destination threads, and the separate GPU obligations. The acquisition's
`# Safety` section must contain the complete lasting obligations, including
other native users, implicit Drop, unwinding and exceptional retention.
Construction, dispatch and destruction documentation must connect those rules
to the corresponding operation. An ADR link supplements this documentation;
neither the link nor a four-line overview replaces the full public contract.

## Verification required before claiming support

The [2026-09-29 experiment](../research/records/2026-09-29-exp-d013-movable-compile-host.md)
passed Windows-target trait compilation and eight host probes, including Rc/Arc
controls, sibling retention, serialized transfers, terminal errors and unwinding.
It introduced a sealed private retention parameter while keeping the public
local types unchanged. The subsequent
[Windows fixture execution](../research/records/2026-09-29-exp-d013-windows-fixtures.md)
passed the same eight probes using the production Windows loader.
The [2026-09-30 native spike](../research/records/2026-09-30-exp-d013-native-thread-transfer.md)
then passed load/create on A, dispatch/fence on B, destroy/final loader release
on C; a moving three-frame transfer; and two siblings with early external-runtime
drop and final cleanup elsewhere. All three same-thread controls and the existing
public lifecycle/dispatch regressions passed on the changed source. Every transfer
followed completed GPU work. The loader unloaded on C, but the provider remained
loaded in both controls and transfers, so provider/dependency termination on C
was not observed.

This completes the requested bounded native transfer spike, not public API
verification or a general AMD transfer guarantee. Provider termination, native
error/unwind transfer paths, partial-load cleanup across threads and unfenced
work remain unverified. Miri/ThreadSanitizer were not run. The public integration,
conditional-contract and acceptance review below remains open. Required coverage
for an eventual public family is:

| Evidence | Required coverage | Limit |
|---|---|---|
| Windows/DX12 compilation | Assert local types remain `!Send + !Sync`, movable types are `Send + !Sync`, and families cannot mix; check feature-disabled and feature-enabled consumers | Traits and API availability only; host compilation omits the real Windows types |
| Host and Windows fixtures | Exercise both retention mechanisms; dependency cleanup order, returned create failure, OK/null creation, destruction failure/no retry, poison teardown and library release | Wrapper ownership policies, not signed-provider behavior |
| Threaded fixtures | Serialize a runtime and two sibling contexts across separate threads; include runtime dropped before contexts, final release elsewhere and cleanup during unwinding | Synchronization/cleanup of the fixture, not AMD affinity |
| Native Windows/DX12 | Load/create on A, dispatch on B, destroy on C; moving multi-frame smoke; ordered sibling lifecycles and final library release on another thread | Actual observations for the recorded inputs only |

The native harness must preserve fences, GPU lifetimes, debug-layer checks,
device-removal checks and timeout isolation. Initially fence submitted work
before the next transfer; that result establishes no transfer capability with
outstanding GPU work. If an integration needs that case, investigate it
separately. A CPU `join` never substitutes for a GPU fence. Do not deliberately
violate the serialization contract against the AMD runtime as a negative test.

Keep commands, source state, SDK/DLL fingerprints, observed provider, GPU,
driver, results and limitations in a self-contained
[experiment record](../research/PROCESS.md). Repeat relevant local-family and
native dispatch regressions after a shared-core refactor. Revalidate new release
artifacts rather than reusing historical evidence from the released `0.1.0`.

## Alternatives and consequences

| Alternative | Assessment |
|---|---|
| Dedicated acquiring/render thread with a command channel | Lowest-impact option; sufficient where SDK ownership can remain on that thread |
| Manual `Send` on existing `Rc` types | Rejected for this proposal: independent transfers can race reference counts and remove the existing local contract |
| `Arc` throughout, with explicit local markers | Technically possible; adds atomic ownership to the local path without demonstrated need. `Arc` alone is not a native safety claim |
| Public generic family marker | Possible, but exposes additional public type machinery without a demonstrated benefit over separate types |
| One transferable owner for the whole family | Can prevent splitting siblings at the API level; reconsider if caller-managed serialization proves impractical |
| Unsafe transfer instead of unsafe acquisition | Does not by itself constrain subsequent sibling calls or Drop; would need a complete lasting ownership contract |

Separate types preserve the existing local API and avoid public generics. Costs
include a shared-core refactor, two families of documentation/fixtures, additional
native evidence and a lasting conditional safety contract. Performance impact
must be measured where relevant; no zero-overhead claim is made. The new feature
is intended to be additive, subject to verifying the existing API and traits
remain unchanged. It is not scheduled for `0.2.0` by this record.

## Review and acceptance gates

Keep this record **proposed** until review establishes:

1. The maintainer reviews a concrete integration scenario explaining why
   transferable SDK ownership is needed and what required behavior or practical
   integration cost makes the existing local-thread/channel approach inadequate.
   An integration plan, example or spike can provide that evidence; proving
   every alternative impossible or obtaining an external consumer request is
   not required.
2. The intended native runtime scope and conditional transfer assumption are
   explicitly approved; unresolved affinity is not misrepresented as verified.
3. The public family contract is usable, including implicit Drop and exceptional
   retention, and the implementation direction preserves explicit traits and
   dependency ownership without widening existing guarantees.

Acceptance authorizes a design only when the maintainer says so; implementation
and support verification remain separate work. If these gates fail, retain the
local API and revisit the ownership approach. Documenting the local-thread
pattern may be useful independently; this ADR does not claim such an example
has been added.
