# D013 — Optional movable runtime/upscaler family

- Recorded: 2026-09-29
- Updated: 2026-10-09 (design accepted; optional API implemented and bounded public-path verification completed).
- Status: **accepted** — explicitly authorized finalization after soundness
  review; implementation and bounded public-path verification recorded separately below
- Scope: existing SDK v2.3.0 Windows/DX12 upscaler profile on
  `x86_64-pc-windows-msvc`
- Timing: work after the released `0.1.0`; outside `0.2.0` scope, with no later
  release version selected

## Context and motivation

**Decision at a glance:** accept a separate optional `Send + !Sync` family,
acquired through an explicit unsafe operation with lasting caller-established
native compatibility and serialization requirements. The
[completed soundness review](../research/records/2026-10-09-src-d013-soundness-architecture-review.md)
found no confirmed Rust soundness defect and recommended acceptance with the
revisions below. The optional `movable` feature now implements the public family
through the private owner's sealed retention seam: local owners retain `Rc`,
movable owners retain `Arc`. The [implementation verification](../release/2026-10-09-d013-public-api-verification.md)
records the field audit, consumer fixtures and selected fenced native checks.
Historical experiments and current checks establish no universal AMD threading guarantee.

[D008](D008.md) confines `Runtime` and its dependent `Upscaler` objects to the
runtime's acquiring thread. Both public types are `!Send + !Sync`; an internal
`Rc<RuntimeState>` keeps the loader alive through context cleanup. D005's owner
also has an explicit `PhantomData<Rc<()>>` marker. These restrictions reflect
missing native threading guarantees, not evidence that every thread transfer
necessarily fails.

The concrete integration scenario is migration of renderer-owned state: an
application hands an exclusively owned renderer, including its runtime and
history-bearing upscaler contexts, to another worker between rendering phases.
It may initialize on one thread, record successive frames on other workers,
and shut down on a final thread. The existing types prevent that owner from
being `Send`. Recreating contexts at each handoff would discard temporal history;
keeping SDK state on a dedicated thread would require a separate command and
lifetime protocol for renderer-owned resources and recording objects.

A dedicated thread that creates, uses and destroys the local family remains a
valid alternative where ownership can stay there. The migration scenario
justifies the optional family without requiring every alternative to be
impossible or an external consumer request. It is framework-independent: no
Bevy dependency, integration or implementation is selected or claimed complete.

## Choice

Add an optional Cargo feature named `movable`, exposing `MovableRuntime` and
`MovableUpscaler` only in the Windows/DX12 API. The intended public traits are:

| Family | Runtime | Upscaler | Internal runtime retention |
|---|---|---|---|
| Existing local API | `!Send + !Sync` | `!Send + !Sync` | `Rc` |
| Optional movable API | `Send + !Sync` | `Send + !Sync` | `Arc` |

Movable acquisition uses `unsafe MovableRuntime::load_unchecked(path)`.
Safe `MovableUpscaler` construction accepts only `&MovableRuntime` and retains
an independent `Arc` from precisely that runtime. It produces only a
`MovableUpscaler`; local construction continues to accept only `&Runtime`.
No conversion API is selected, including safe conversions in either direction.
No public pointer generics, native handles, or public Clone implementation is
selected. Converting a movable owner back to a thread-confined shape would not
revoke the lasting
native obligations. A feature flag does not authenticate a runtime or discharge
the unsafe contract.

Keep loader, construction, validation, dispatch, errors and terminal ownership
logic shared. Reuse the existing sealed private `Rc`/`Arc` retention seam in a
shared private core; it must not become an unrestricted generic native
owner accepting arbitrary `Deref` implementations. The precise internal bounds
and forwarding technique remain implementation details. Public documentation
must state each family's threading contract without duplicating inconsistent
safety descriptions.

This extends D005/D008's thread-confinement policy **only for the new
family**. Their existing public types and terminal cleanup behavior remain.
D011's unsafe GPU boundary, poisoning and abandonment rules, and D012's options
contract continue to apply. This decision adds no provider, format, callback,
Query/Configure, backend or image-quality support.

## Conditional safety contract

The following are actual requirements of
`unsafe MovableRuntime::load_unchecked`, to be included in its public `# Safety`
contract. `Send` is a conditional Rust safety guarantee once this unsafe
boundary has established the lasting invariants; describing the API as "not
thread-safe" or presenting these requirements only as warnings is insufficient.
The caller must guarantee all of the following, in addition to D008's bounded
construction trust and D011's dispatch contract:

1. **Trusted acquisition and native lifetimes.** The loader and every resolved
   dependency/provider, including driver providers, must be trusted,
   ABI-compatible with the selected v2.3.0 Windows/DX12 profile, and safe to
   initialize, operate and release, including returned-error and terminal paths.
   Preserve compatible process/provider configuration and do not prematurely
   release dependencies relied upon by any context. Partial-load failure cleanup
   occurs within the acquisition call, on its calling thread, before any movable
   value exists; no partially acquired runtime is transferred.
2. **Arbitrary destination threads.** The actual loader, selected providers,
   contexts, driver and relevant native dependencies must permit movement and
   every subsequent operation on any thread where these general `Send` owners
   may be used or dropped. This covers context creation, dispatch, any affected
   queries/configuration, explicit destruction, implicit Drop, error cleanup,
   COM/device-reference release and final wrapper-owned DLL release/unload.
   Destruction must not require the creating thread, and final library release
   must not require the acquiring thread. Compatibility restricted to a chosen
   A-to-B handoff or subset of threads cannot support this API. Serialization
   alone does not establish absence of native affinity.
3. **Common-domain serialization and non-reentrancy.** All application/native
   operations potentially touching shared FidelityFX runtime, provider or global
   state must be non-overlapping and non-reentrant. This includes acquisition,
   creation, dispatch, queries, configuration, explicit destruction, implicit
   Drop, returned-error cleanup and final library release. Coordinate sibling
   contexts, separate acquisitions, local and movable families, and external
   FidelityFX users wherever native state may be shared. Different DLL paths,
   devices, type families or per-context locks do not prove isolation. Independent
   coordination domains are permitted only when isolation is established.
   Queries/configuration are covered when performed by affected native users;
   this decision introduces no public Query/Configure API.
4. **Ordered handoffs.** Synchronization must establish a happens-before
   relationship from the previous operations to the next thread's use or cleanup.
   Transfer exclusive ownership only after prior CPU operations finish and keep
   the required shared-state coordination in force. Correctly used channels,
   joins or locks can establish ordering; elapsed time cannot. `Send`, `!Sync`,
   `&mut self` and atomic reference counting alone do not establish that ordering
   for independently held owners or native users.
5. **Automatic cleanup and lasting obligations.** Arrange ownership and
   coordination so every safe call, consuming destruction and implicit Drop
   preserves these requirements, including Drop during Rust unwinding. Where a
   guard provides coordination, cleanup must finish before that guard is released;
   any recovery from a poisoned lock must preserve the same invariant. The
   obligations last for the runtime and every derived context, even after the
   public runtime is dropped.
   D005's exceptional retention can keep the critical dependency bundle alive
   indefinitely; disappearance of public owners or retained dependencies does
   not prove native quiescence or authorize other users to ignore shared state.
6. **Native internal activity and termination.** The selected implementation
   must safely handle its own hidden workers, callbacks and termination under
   these serialized application operations. An application lock does not govern
   such internal activity. Any native termination that occurs must be safe on
   its actual executing thread. The wrapper's last library release has no fixed
   thread and is distinct from provider/dependency termination: neither provider
   unload nor its time or thread is promised.
7. **Independent D3D12/GPU obligations.** Preserve D011's full unsafe dispatch
   contract: an open DIRECT command list and valid allocator on the context's
   device; truthful resource states, non-overlapping active backing storage,
   residency and no conflicting accesses; list/allocator/resource/allocation/
   context lifetimes as required by D3D12 through completion; execution of each
   successful recording once, in temporal order, including
   required cross-queue waits; and no premature reuse/reset of resources or
   recording objects. Complete every submitted dispatch and invalidate every
   unsubmitted recording referencing the context before destruction or Drop.
   Failed dispatch recordings must never be submitted; abandoned successful
   recordings require terminal handling under D011. CPU handoff is not GPU
   completion. Satisfy any additional native transfer preconditions involving
   outstanding GPU work; the existing experiments establish only fenced
   transfers, not that outstanding-work transfers are safe.

If the chosen native configuration and all subsequent uses cannot satisfy these
requirements, the caller must not acquire the movable family. Passing an owner
to other safe code does not discharge the originating unsafe obligation.

No built-in mutex or family scheduler is selected. Keeping every member in one
exclusively transferred application owner is one possible way to serialize the
family; coordination with other native users remains necessary. A
`Mutex<MovableUpscaler>` permits sharing that individual object, but says nothing
about its siblings. A channel orders only the ownership actually transferred.
Implicit cleanup must occur while the required coordination is still in effect.

**Rust-enforced invariants:** the implementation must enforce distinct families,
exclusive context ownership, the declared traits, stable retained descriptor
addresses, independent device/runtime retention, D005's terminal cleanup and
D011's poison policy. `&mut self` excludes simultaneous Rust access to one
upscaler; `Arc` protects reference counts and library retention. Neither enforces
native affinity, shared-state serialization, external-user cooperation, hidden
worker quiescence or GPU completion. Those remain caller-established native and
renderer assumptions under the unsafe boundaries above. Movable acquisition
does not make `unsafe dispatch(&mut self)` safe or promise concurrent use.

## Rust ownership and trait requirements

Source inspection on 2026-09-29 of the repository and locally cached, locked
dependency sources establishes:

- The current `RuntimeState` contains only `FfxLibrary`, whose fields are native
  function pointers and `libloading::Library`. The locked `libloading` 0.9.0
  library implements both `Send` and `Sync`.
- Consequently, replacing the current runtime's `Rc` with `Arc` alone would
  make it `Sync` as well as `Send`. The new runtime needs an explicit `!Sync`
  marker, such as private `PhantomData<Cell<()>>`; an `unsafe impl Send` does
  not remove `Sync`.
- Pinned `windows` 0.62.2 declares `ID3D12Device: Send + Sync`. This describes
  the Rust COM wrapper, not FidelityFX provider affinity.
- The current context owner and pinned descriptors contain raw pointers and
  explicit local-family markers. `Arc` does not make an entire upscaler
  automatically transferable.

The dependency observations came from `libloading` 0.9.0 `src/safe.rs`
(explicit `Send` and `Sync` implementations for `Library`) and `windows` 0.62.2
`src/Windows/Win32/Graphics/Direct3D12/mod.rs` (explicit implementations for
`ID3D12Device`). The corresponding dependency declarations are visible in
[Cargo.lock](../../Cargo.lock); source references are
[libloading 0.9.0 Library](https://docs.rs/libloading/0.9.0/libloading/struct.Library.html),
[windows 0.62.2 ID3D12Device](https://docs.rs/windows/0.62.2/windows/Win32/Graphics/Direct3D12/struct.ID3D12Device.html)
and the [Rust Arc contract](https://doc.rust-lang.org/std/sync/struct.Arc.html#thread-safety).
The two versioned docs.rs pages could not be fetched during preparation;
the observations above use the cached source, not those pages. These are source
observations. The later
[compile/host experiment](../research/records/2026-09-29-exp-d013-movable-compile-host.md)
confirms the trait claims on the Windows target and exercises concrete test-only
movable shapes through the real private owner. It is not a public implementation
or evidence of AMD transfer compatibility.

Keep explicit public trait guarantees independent of incidental field contents.
The context's manual `Send` implementation must be limited to the audited
concrete `MovableUpscaler`, covering its retained runtime, device,
address-stable descriptor storage, native handle and every cleanup path.
The `Arc<RuntimeState>` runtime shape derives `Send` from its fields and must
explicitly exclude `Sync` with `PhantomData<Cell<()>>`; it needs no manual Send
implementation. The movable upscaler must also remain explicitly `!Sync`.
Do not add blanket `Send`/`Sync` implementations to `RuntimeState`, the generic
owner or arbitrary dependency bundles to make compilation pass. No actual
`Rc`-owned dependency may survive inside a movable bundle. Future dependencies
or callbacks require renewed review rather than inheriting movability blindly.

Moves must preserve native pointer validity, shared-library lifetime, cleanup
order and D005's exceptional retention. `Arc` addresses shared reference-count
safety; it does not serialize native operations or make provider state safe.
Retain the pinned creation allocation and independent owned COM reference through
terminal cleanup. Each context holds its own strong runtime reference, permitting
early public-runtime Drop. Attempt native destruction at most once; on success
release state, then device, then runtime; on destroy failure or OK/null creation
retain the entire critical dependency bundle. Returned create failure continues
to use D005's existing bounded RAII trust assumption, without destroying an
ambiguous output handle. No cleanup scheduler or fixed unload thread is added.

## Public documentation requirement

Movable acquisition and both public types must explain their
contract in Rustdoc. A short overview should cover family-wide serialization
and non-reentrancy, caller-established native transfer compatibility, cleanup
on destination threads, and the separate GPU obligations. The acquisition's
`# Safety` section must contain the complete lasting obligations, including
other native users, implicit Drop, unwinding and exceptional retention.
Construction, dispatch and destruction documentation must connect those rules
to the corresponding operation. An ADR link supplements this documentation;
neither the link nor a four-line overview replaces the full public contract.

## Verification required before claiming support

The [2026-09-29 experiment](../research/records/2026-09-29-exp-d013-movable-compile-host.md)
passed Windows-target trait compilation and eight host probes, including Rc/Arc
controls, sibling retention, serialized transfers, terminal errors and unwinding.
It introduced a sealed private retention parameter while keeping the public
local types unchanged. The subsequent
[Windows fixture execution](../research/records/2026-09-29-exp-d013-windows-fixtures.md)
passed the same eight probes using the production Windows loader.
The [2026-09-30 native spike](../research/records/2026-09-30-exp-d013-native-thread-transfer.md)
then passed load/create on A, dispatch/fence on B, destroy/final loader release
on C; a moving three-frame transfer; and two siblings with early external-runtime
drop and final cleanup elsewhere. All three same-thread controls and the existing
public lifecycle/dispatch regressions passed on the changed source. Every transfer
followed completed GPU work. The loader unloaded on C, but the provider remained
loaded in both controls and transfers, so provider/dependency termination on C
was not observed.

The [2026-10-07 failure fixtures](../research/records/2026-10-07-exp-d013-transfer-failure-cleanup.md)
add 14 owner children and six acquisition failures, covering transferred poison,
preflight/recovery, terminal retention and coordinated ready/poisoned unwind.
These controlled errors are wrapper-policy evidence, not AMD error recovery.
The [2026-10-08 native follow-up](../research/records/2026-10-08-exp-d013-native-transfer-cleanup.md)
reruns all 11 native prerequisites after the dispatch-policy extraction, then
passes all 30 new children. It covers load/create/dispatch/destroy on four
persistent workers, 64-frame history with 63 handoffs, independently held
siblings and successful native owner Drop during Rust unwind outside FFI.
All 516 new frames and 42 actual native destroys pass, including 12 unwind
cleanups; all 96 selected packed RGBA16F hashes match controls/repetitions.
Every submitted frame completes its fence, and a common domain covers calls
and implicit cleanup, including unwind and sibling poison recovery.

Staged release now observes the provider remaining loaded after all audited
application frame/device/helper refs and ordinary worker exit. Loader/helper
absence does not establish actual COM device destruction, provider/dependency
termination or its thread. The [source intake](../research/records/2026-10-07-src-d013-transfer-cleanup-contract.md)
still lacks the requested pinned implementation audit and an affirmative AMD
transfer guarantee. No tested result requires revising D005/D011's policy.

These bounded spikes are complete; public API verification and a general AMD
transfer guarantee do not follow. Native returned-error/partial-load cleanup,
hidden work, external native users, provider termination, outstanding GPU work
and other configurations remain unverified. Partial-load cleanup is acquisition-
local, not transfer of an incomplete runtime. Miri/ThreadSanitizer were not run.
The review recommends accepting these uncertainties as explicit caller-side
assumptions, not unresolved design blockers. No further general research or
exploratory native experiment is required before implementation. Verify the actual public wrappers
and final artifacts; historical test bundles do not substitute for that work:

| Evidence | Required coverage | Limit |
|---|---|---|
| Windows/DX12 compilation | Assert local types remain `!Send + !Sync`, movable types are `Send + !Sync`, and families cannot mix; check feature-disabled and feature-enabled consumers | Traits and API availability only; host compilation omits the real Windows types |
| Host and Windows fixtures | Exercise both retention mechanisms; dependency cleanup order, returned create failure, OK/null creation, destruction failure/no retry, poison teardown and library release | Wrapper ownership policies, not signed-provider behavior |
| Threaded fixtures | Serialize a runtime and two sibling contexts across separate threads; include runtime dropped before contexts, final release elsewhere and cleanup during unwinding | Synchronization/cleanup of the fixture, not AMD affinity |
| Native Windows/DX12 | Reuse selected existing fenced transfer scenarios through the actual public family across distinct workers, including final Drop, and rerun local-family lifecycle/dispatch regressions | Actual observations for recorded inputs only; no new exploratory matrix or provider-termination/error-recovery proof is required for design acceptance |

The native harness must preserve fences, GPU lifetimes, debug-layer checks,
device-removal checks and timeout isolation. Initially fence submitted work
before the next transfer; that result establishes no transfer capability with
outstanding GPU work. If an integration needs that case, investigate it
separately. A CPU `join` never substitutes for a GPU fence. Do not deliberately
violate the serialization contract against the AMD runtime as a negative test.

Keep commands, source state, SDK/DLL fingerprints, observed provider, GPU,
driver, results and limitations in a self-contained verification record.
Repeat relevant local-family and
native dispatch regressions after a shared-core refactor. Revalidate new release
artifacts rather than reusing historical evidence from the released `0.1.0`.

### Implementation verification completed 2026-10-09

The [public-path verification record](../release/2026-10-09-d013-public-api-verification.md)
records the actual optional API, its concrete `MovableUpscaler` Send audit,
feature/family controls, terminal-error fixtures and local-family regressions.
The [consumer example](../../crates/fsr-sdk/examples/movable_upscale.rs) provides
common-domain cleanup for independently transferred siblings, including unwind,
failed handoff and poisoned-lock recovery; the library adds no internal lock.
Selected native regressions and two fenced public movable dispatches pass on
the recorded configuration, with implicit destruction on separate destination
threads and release of the last runtime reference. These checks complete this
implementation milestone, select no release and resolve none of the missing
native guarantees listed above.

## Alternatives and consequences

| Alternative | Assessment |
|---|---|
| Dedicated acquiring/render thread with a command channel | Lowest-impact option; sufficient where SDK ownership can remain on that thread |
| Manual `Send` on existing `Rc` types | Rejected: independent transfers can race reference counts and remove the existing local contract |
| `Arc` throughout, with explicit local markers | Technically possible; adds atomic ownership to the local path without demonstrated need. `Arc` alone is not a native safety claim |
| Public generic family marker | Possible, but exposes additional public type machinery without a demonstrated benefit over separate types |
| One transferable owner for the whole family | Can prevent splitting siblings at the API level; reconsider if caller-managed serialization proves impractical |
| Unsafe transfer instead of unsafe acquisition | Does not by itself constrain subsequent sibling calls or Drop; would need a complete lasting ownership contract |

Separate types preserve the existing local API and avoid public generics. Costs
include a shared-core refactor, two families of documentation/fixtures, additional
native evidence and a lasting conditional safety contract. Performance impact
must be measured where relevant; no zero-overhead claim is made. The new feature
is intended to be additive, subject to verifying the existing API and traits
remain unchanged. It is not scheduled for `0.2.0` by this record.

## Acceptance rationale and remaining assumptions

Accepted on **2026-10-09** under explicit authorization to finalize the reviewed
design if no soundness blocker remained. The
[completed review](../research/records/2026-10-09-src-d013-soundness-architecture-review.md)
recommends acceptance with revisions and identifies no confirmed Rust soundness
defect. Its investigation date, reviewer identity and reviewed revision were
not supplied; 2026-10-09 is its intake date. Existing source and records support
the ownership direction; the review adds no execution result or AMD guarantee.

The prior acceptance gates are satisfied by the renderer-state migration
scenario above, explicit acceptance of the conditional native trust boundary,
and the revised lasting contract covering all destination threads, common-domain
coordination, implicit Drop/unwind and exceptional retention. Separate types and
a narrow concrete Send audit preserve D005/D008/D011/D012 for the local family.
No concrete contrary finding requires changing those accepted policies.

Remaining caller-side assumptions are native freedom from relevant thread
affinity for every subsequent use/drop, safe cleanup and native termination on
their actual threads, safe internal activity under serialized application calls,
and effective coordination with every user of potentially shared state. Native
returned-error behavior, provider retention/termination and outstanding-work
transfers are not newly verified; D008's construction trust and D011's separate
unsafe GPU obligations remain in force. An affirmative AMD threading guarantee
or observation of provider unload is not a prerequisite for this explicitly
unsafe design. If these assumptions cannot be upheld, the movable API must not
be used; contrary safety evidence requires revisiting the contract or scope.

**No unresolved soundness blocker remains for design acceptance.** Acceptance
established the implementation contract without another general research phase;
it supplied no runtime result. The subsequent implementation, field/cleanup
audit, Rustdoc and bounded public-path verification are recorded separately
above. No release is selected, and D014 and `0.2.0` scope remain unchanged.
