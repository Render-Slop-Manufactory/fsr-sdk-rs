## Public-shape replacement selected — 2026-10-26

[D042](D042.md) supersedes the units-plus-override storage and accessors with one
effective UV/pixel/native scale choice for 0.3.0. U08/U12 remain open; the current
source still implements the precedence below. Exact native bits, numerical
domains, active geometry and resource/view rules remain binding, and historical
verification does not certify the replacement API.

## Problem and evidence boundary

At proposal time, the wrapper derived native motion scales from UV or pixel units and
accepted only RG16F motion. Applications with different per-axis encodings had to
rewrite motion textures even though the native descriptor already carried two
independent floats. That format converter also could not describe RG32F.

The source record distinguishes documented external roles, generic DX12
conversion, generated SRV/UAV views and actual-provider support. In the spike,
4.1.1/3.1.5 execute typed RG32F render-motion inputs. Positive and signed
asymmetric encodings match the RG16F pixel baseline exactly; independent X/Y
wrong-sign controls change post-reset output. All 43 final cases pass, including
120 dispatched frames and four control frames, on one RX 9060 XT configuration.
The initial blocked attempt is retained in that record.

That evidence covers small exactly representable values, raw local contexts,
render-resolution motion and inputs without UAV allocation flags. It does not
verify a public implementation, display-motion RG32F, UAV-capable RG32F inputs,
arbitrary finite scale domains or additional formats. The decision below selects
contracts to implement and verify; it does not relabel those gaps as passed.

## Decision: public scale API

Add portable `NativeMotionVectorScale` in `upscaler::common`, reexported from
`upscaler`, following the existing checked scalar types:

```text
NativeMotionVectorScale::new(x: f32, y: f32) -> Result<Self, Error>
NativeMotionVectorScale::x(self) -> f32
NativeMotionVectorScale::y(self) -> f32

UpscaleDispatch::motion_vector_scale_override(&self) -> Option<NativeMotionVectorScale>
UpscaleDispatch::set_motion_vector_scale_override(&mut self, Option<NativeMotionVectorScale>)
```

The type has private `f32` components and derives `Debug`, `Clone`, `Copy` and
`PartialEq`. It has no `Default` or unchecked public constructor. Ordinary float
equality does not promise bit identity; forwarding preserves the stored bits.
The frame stores an optional value, default `None`; its existing constructor,
resource bundle and dispatch signatures remain intact.

| Frame selection | Native `motionVectorScale` |
|---|---|
| Override `None`, units `Uv` | Active motion width/height under D024: active render for render motion, active output for display motion |
| Override `None`, units `Pixels` | `(1, 1)` |
| Override `Some(scale)` | Exactly `scale.x()` / `scale.y()`, irrespective of the fallback units |

`set_motion_vector_units` changes only the fallback units; it does not clear an
explicit override. `motion_vector_units()` reports that fallback. The new getter
reports whether an override takes precedence. Clearing it with `None` restores
the current UV/pixel calculation using that frame's active geometry. Document
this precedence at both setters and in the renderer example; add no second
effective-units enum or implicit setter coupling.

The override is the native dispatch parameter, not an already normalized UV
multiplier or an automatic NDC conversion. In reported open FSR3 arithmetic,
sampled motion is multiplied by `S / T`, with `S` the supplied scale and `T` the
active motion extent. For example, stored `(2, -0.5)` with scale `(-2, 4)` encodes
pixel-equivalent `(-4, -2)` displacement. Open FSR2's configured-display
denominator differs; forwarding does not promise the FSR3 interpretation for
every provider or change the existing D024 defaults/support obligations.

When active geometry changes, an explicit override stays literal. The renderer
updates it when its encoding requires that; the wrapper performs no rebasing,
sign correction, pixel rewriting, jitter conversion or implicit history reset.
With an override, resource/frame documentation must describe stored components
whose scaled interpretation matches the provider's current-to-previous motion
convention. Existing UV/pixel documentation continues to require +X right/+Y down
when no override is present. Context-selected motion resolution and jitter
inclusion still apply in both cases.

### Numerical policy and error semantics

Accept every finite component, including positive/negative values, subnormals,
`f32::MAX`, zero and negative zero. Reject NaN and either infinity. Preserve
accepted bits through storage, getters, cloning and native descriptor mapping;
apply no absolute value, clamping, epsilon, sign normalization or zero sentinel.
An override with both components zero supplies literal zero scales; only `None`
selects fallback mapping.

This is an explicit checked-wrapper policy. Public headers supply no positive-only
motion-scale domain; reported open debug warnings are not hard validity bounds.
Finiteness excludes non-finite inputs but does not establish finite downstream
products, meaningful reprojection or safe native access. The unsafe dispatch
contract must require the actual provider to support the supplied scales and
their combination with texture content, active geometry and other options.
The constructor and safe preflight certify no provider-safe numerical range.
Acceptance of zero/extreme finite values is not a claim of native verification.

Add `DispatchScalar::{MotionVectorScaleX, MotionVectorScaleY}`. Construction rejects
X first, then Y, through the existing `Error::InvalidDispatch` /
`DispatchValidation::Scalar` path. Compulsory dispatch-input checking reuses the
same pure finite check before COM inspection; it does not depend on the caller
having run optional preflight. Poison precedence remains first at operation entry.
Validation errors perform no FidelityFX call and leave an eligible context usable.

## Decision: typed format profile

Select RG32F as an additional main-upscaling motion input for render and display
resolution, subject to the metadata/device checks below and actual-provider
obligations. Public display-resolution integration remains required verification.
Inspect the resource's real DXGI format; expose no separate format selector that
could disagree with `GetDesc` and no resource/view reinterpretation override.

| Operation / role | Accepted allocation formats |
|---|---|
| Main colour and upscaling output | Existing `R16G16B16A16_FLOAT` |
| Main device depth | Existing `R32_FLOAT` |
| Main motion vectors | Existing `R16G16_FLOAT`, plus `R32G32_FLOAT` |
| Explicit exposure | Existing `R32_FLOAT`, 1×1 |
| Supplied reactive and transparency/composition masks | Existing `R8_UNORM` |
| Reactive generation: both colour inputs | Existing `R16G16B16A16_FLOAT` |
| Reactive generation: output | Existing `R8_UNORM` |

Separate the private DXGI-to-native lookup from operation/role acceptance. A
mapped constant does not permit that format in every role. New RG32F colour,
depth, exposure, output or generation resources still reject with the existing
role-specific `ResourceProperty::Format`. No public format registry, conversion,
copy, view creation or generic raw-resource escape hatch is introduced.

Add only `FFX_API_SURFACE_FORMAT_R32G32_FLOAT = 6` to the selected raw binding
slice, with existing AMD source attribution. Verify its value independently
against the pinned header and preserve all C layouts/tags. Broader enum coverage
is a separate U05 task, not evidence of high-level format support.

### New-format device and generated-view checks

Keep existing formats' checks unchanged in this slice. For RG32F motion, after
shape/role/extent and canonical device membership checks, call
`CheckFeatureSupport(D3D12_FEATURE_FORMAT_SUPPORT)` on the retained context
device for the actual typed format. Reuse this inspection in compulsory dispatch
and optional preflight; do not cache results or invoke an SDK capability query.

Require `TEXTURE2D`, `SHADER_LOAD` and `SHADER_SAMPLE` in `Support1` as this new
wrapper SRV profile. Requiring both load and sampling is a conservative explicit
wrapper condition, not a claim that every provider shader uses both methods.
Actual allocation flags remain authoritative. If the input also has
`ALLOW_UNORDERED_ACCESS`, require `TYPED_UNORDERED_ACCESS_VIEW` because the
reported backend may create a UAV descriptor even for a read-only input. Preserve
its native UAV usage bit; never hide that allocation capability to avoid a check.

Do not require `Support2::UAV_TYPED_LOAD` or `UAV_TYPED_STORE` for this read-only
SRV role merely because a UAV descriptor exists: typed shader accesses are
distinct from view creation. Future output/other shader-access roles must review
their own typed-load/store requirements. No general device/view/provider
certificate follows from this query, nor does it prove which shader accesses
the closed provider performs.

Missing required bits yield `DispatchValidation::Resource` with role
`MotionVectors` and new `ResourceProperty::FormatSupport`. A failed DX12 query
preserves HRESULT through existing `Error::Dx12Inspection`, object
`InspectionObject::ContextDevice`, and new `InspectionOperation::CheckFormatSupport`.
Both outcomes occur before FidelityFX entry and do not poison the context.
Optional preflight may run before transitions; it proves no resource state,
content, residency, submission, synchronization or provider support.

## Ownership, safety and compatibility

Both owner families share the same frame, scale selection, role conversion and
device-inspection path. Preserve thread confinement and optional `Send + !Sync`;
add no context, device or resource caching and no retained frame references.
Resource descriptions retain actual allocation metadata. D024's exact maximum
allocations, single sample/mip/slice, identity/backing-storage obligations,
mask presence rules and operation-specific aliasing rules remain binding.

The renderer retains motion/content conventions, GPU transitions and barriers,
queue submission, fences, resource lifetimes and recording abandonment duties.
Native recording errors keep the existing terminal policy and consuming cleanup.
Device format bits, provider names and resource-requirement query bits do not
authorize a format or scale combination. Add no provider allow-list/fallback.
The spike's 4.1.1/3.1.5 evidence remains configuration-specific; 2.3.4 gains no new
verification claim, and its existing smaller-output limitation remains.

The checked type and scalar diagnostics are portable and available without
Windows/DX12 dependencies. COM/resource/device checks stay behind Windows plus
`dx12`. Existing `MotionVectorUnits` variants and `Eq` remain intact; the new
frame override is additive. ABI structs, dependency versions, SDK acquisition,
licensing/distribution and creation/memory-estimate flags do not change.

   Check both axes for NaN/infinities; preserve exact positive/negative zero,
   subnormal and extreme finite bits in controlled descriptor tests. Check
   default/clone/clear/precedence behaviour and active render/output changes,

2. Add the raw constant and reviewed role mapping; extend independent Rust/MSVC

3. Add new-format device-query fixtures for each missing bit, query HRESULT,
   input UAV flags, short-circuit/no-query baseline formats, no native entry,
   retry and poison precedence. Optional preflight and dispatch must agree;
   dispatch repeats checking after preflight. Native query success is not a
   substitute for these controlled error paths.
4. Run a bounded public-path Windows/DX12 batch on selected 4.1.1/3.1.5 for both
   owners, RG32F render/display motion, positive/signed asymmetric encodings and
   X/Y-sensitive controls. Add a mixed-sign asymmetric scale case with nonzero,
   changing projection jitter and `MotionVectorJitter::Included`. Encode the
   jitter contribution consistently with the explicit scales and check equivalence
   to the corresponding pixel-motion reference, exercising the interaction between
   scale and jitter cancellation. Include a D024 display-motion active-output
   transition, unchanged default routes and RG32F input with/without UAV capability
   where the device supports that view; missing capability must reject before SDK entry.
   Retain independent input/output readback, pinned C++ resource parity, fences,
   diagnostics and terminal cleanup. The raw spike is not this public verification.
5. Run relevant stable/MSRV, portable/no-default and downstream API checks; update
   Rustdoc, examples, raw ABI inventory and development release documentation.
   Keep final extracted-package verification separate. Zero/extreme finite values
   need portable/controlled bit tests, not an unsafe broad GPU domain campaign.

No additional broad source survey or raw-spike repetition is a prerequisite for
this slice. Investigate concrete wrapper defects if found. Native validation
does not select GBV, reconstruction-quality criteria or a performance gate.

## Alternatives and completion boundary

Adding raw floats to `MotionVectorUnits` would remove its derived `Eq` or require
new equality semantics. A checked optional override preserves that existing type
and explicitly separates native parameter forwarding from the fallback units.
Its cost is documented precedence; silently clearing one setting from another
setter would make that state harder to inspect.

Rejecting zero or guessing a maximum magnitude would impose an unsupported
provider-domain restriction. Accept finite bits with explicit native trust
instead. Accepting every converter format would conflate representation with
role/view/provider support; the proposed extension stays reviewed and typed.

Remaining U05 formats must still be accounted for before complete 0.3.0 upscaling
coverage is claimed: RGBA32F/packed/normalized colour and candidate outputs,
R16F depth, sRGB/BGRA interpretations and DSV/typeless depth families. Resolve
each applicable candidate's role/view/device contract and access route; document
non-applicability with evidence where appropriate. Further native probes follow
the claims selected for those extensions. This proposal neither silently defers
them beyond 0.3.0 nor makes all converter entries mandatory supported roles.

Acceptance authorizes this first U05 implementation slice and its bounded
verification. It does not mark U05 or the release complete. The maintainer accepted
four concrete choices together: optional override precedence,
finite-bit policy including zeros/extremes, typed RG32F motion scope and the
new-format device/view checks. Public implementation and verification are
separate checkpoints from this acceptance.

## Implementation checkpoint, 2026-10-21

Implemented in both public families. [Verification](../release/2026-10-21-native-motion-verification.md)
passes 129 stable CI cases, 112 MSRV cases and 102 public native cases with 252
dispatched/12 control frames. All 56 encoding/sensitivity criteria pass on the
recorded 4.1.1/3.1.5 configuration, including the reviewed mixed-sign jitter case.
The bounded source-package audit also matches extracted source/licence bytes
and compiles all targets with movable; its Cargo workspace-verifier limitation
is retained in the record. This completes this bounded slice, not wider U05
formats or final release-archive verification.
