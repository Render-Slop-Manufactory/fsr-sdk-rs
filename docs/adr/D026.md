# D026 — Opt-in linear HDR upscaling

- Date: 2026-10-15.
- Status: **accepted** under explicit maintainer authorization to implement the
  first slice of the reviewed HDR concept.
- Scope: M16's linear HDR slice, pinned SDK v2.3.0, existing DX12 profile and both
  ownership families. Non-linear colour remains open.
- Extends D012's options and D020/D023's exposure profile; preserves D014/D015's
  input representation and D016's direct provider controls.

## Decision

Add private `high_dynamic_range: bool` to portable `UpscalerOptions`, with
`high_dynamic_range()` and `set_high_dynamic_range(bool)`. The default is false.
Existing constructors, traits and resource borrows are unchanged. A context
retains its creation options; later setter calls on other options do not reconfigure it.

When enabled, add `FFX_UPSCALE_ENABLE_HIGH_DYNAMIC_RANGE` (`1 << 0`) to the shared
conversion used by context creation and pre-create memory estimation. All other
creation bits remain independent. Add only this constant to `fsr-sdk-sys` from
the already represented `ffx_upscale.h`; descriptor layouts and exports are unchanged.
Dispatch flags stay zero. No colour-space enum or sRGB/PQ dispatch hint is added.

The renderer supplies linear pre-tonemap RGBA16F colour and receives RGBA16F
output in the input signal domain. HDR describes the input signal, not a monitor
or swapchain. The wrapper performs no encoding, decoding, tonemapping, clamping,
gamut conversion or pre-exposure multiplication. D020's positive finite factor
still reports multiplication already applied to RGB; D023's explicit/automatic
exposure choices and resource-presence checks are unchanged. No automatic history
reset, extra query or additional dispatch resource is introduced.

## Safety and limits

The trusted actual provider must support the selected HDR/exposure profile,
including its signal domain, through estimation, creation, recording and teardown.
Resource requirements establish no colour capability. Extend existing unsafe
acquisition/dispatch documentation accordingly; keep resource metadata checks,
GPU lifetime/state/ordering, poisoning and terminal cleanup rules unchanged.
Movable acquisition inherits the same query/profile trust and dispatch obligations.

RGBA16F remains the only colour/output format. Non-linear input needs a separate
signal/provider contract, especially PQ normalization, transfer encoding versus
pre-exposure, output domain and exposure interactions. This slice adds no
provider override, colour conversion, display setup, dependency or platform support.

## Verification

Portable tests cover opt-in defaults, option clones and independent/combined
creation bits. Public Windows fixtures cover both families, matching estimate/
creation flags, both exposure modes, unchanged per-frame pre-exposure and zero
dispatch flags, immutable context options, format rejection and unpoisoned retry.
The raw constant has paired Rust and independent C++ assertions.

Prepare two native contexts, one per exposure mode, each with three continuous
frames at fixed 320×180 render / 640×360 output. A constant linear scene RGB
`(8,4,2)` uses matching pre-exposure `0.25 → 1 → 4`, alpha 1, constant depth,
zero motion and explicit exposure 1 (omitted from dispatch in automatic mode).
Reset only frame zero. Read back full fixture colour/depth/motion/exposure and
compare uploaded bytes after fencing. Require finite, fully written output,
red values strictly above 1 and below 64, clean diagnostics/device status and
explicit terminal teardown. Those broad bounds catch clipping and stale sentinel
values; they select no reconstruction-quality criterion.

The native case is selected for source and extracted-package verification.
Execution status and exact local commands are recorded in the
[implementation checks](../release/2026-10-15-linear-hdr-verification.md).
Windows fixture/C++ ABI/GPU and MSRV execution remain pending on this host;
prepared tests and Windows Rust compilation are not native confirmation.
