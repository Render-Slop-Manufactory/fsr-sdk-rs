# D031 — Retain the Vulkan feature and require backend isolation

- Date: 2026-10-18.
- Amended: 2026-10-24, with explicit maintainer implementation authorization.
- Status: **accepted as amended**. The amendment reverses feature removal and
  its sys compatibility-series bump; backend isolation remains binding.
- Scope: development `fsr-sdk 0.3.0` / `fsr-sdk-sys 0.1.2`, with initial Vulkan
  upscaling selected as the wrapper's `0.4.0` release target. This restores
  [D015](D015.md)'s unsupported Vulkan feature/compile error and preserves its
  portable-input, native-module and dependency boundaries.

## Decision

Retain `vulkan = ["fsr-sdk-sys/vulkan"]` in the wrapper and `vulkan = []` in the
sys crate. Enabling Vulkan deliberately emits the sys crate's `compile_error!`
on every host, including when combined with DX12 or all features. It reserves
the published feature name without claiming a working backend in `fsr-sdk 0.3.0`.
Do not expose empty Vulkan modules, placeholder GPU types or replacement stubs.
Vulkan is a **required future support target**.

Select initial usable Vulkan upscaling for `fsr-sdk 0.4.0`: public context
creation, one bounded GPU dispatch with readback and clean teardown on a named
OS/architecture/provider configuration, with documented resource and synchronization
obligations. This is an initial integration target, not complete Vulkan SDK coverage
or a promise of native Linux support. A usable official SDK/runtime and the
[B01 evidence gates](../research/platform-and-backends.md#b01-evidence-gates)
remain prerequisites; the target does not select a Vulkan API design or SDK migration.

Windows/DX12 implementations, native public types, loaders and dependencies
**must** remain behind their platform/backend gates. Common APIs and future
Vulkan consumers must not require Windows/DX12 dependencies. OS and backend
selection remain distinct: Vulkan is not a synonym for Linux. Keep these rules
visible in [scope](../../SCOPE.md#platform-and-compatibility-boundaries), public
documentation and [code guidance](../CODE_HEURISTICS.md#native-boundaries).

The current supported native target remains Windows x64/MSVC + DX12. Vulkan
implementation needs a usable upstream SDK/runtime path and separately verified
device, resource, synchronization, loading and teardown contracts. The pinned
modern SDK v2.3.0 path does not provide that integration. At the amendment's
October 24 cut-off, [B01](../../ROADMAP.md#backends-and-runtime) lacked an
inspectable modern Vulkan ABI/runtime, with the initial slice targeted at `0.4.0`.
This amendment introduces no new dependencies,
SDK downloads, native backend, platform-support claim or licence change.

**Source-status update, 2026-10-29 (no decision amendment):** the
[SDK 2.4 source report](../research/records/2026-10-29-src-sdk-240-vulkan-api-compatibility.md)
now identifies an official modern Vulkan header and release. Binary acquisition,
selected-ABI comparison and native proof remain pending. The
[current assessment](../research/platform-and-backends.md#sdk-24-and-release-sequencing)
and roadmap separate conditional SDK-only preparation/adoption from 0.4.0 Vulkan.
This changes neither the 0.3.0 feature contract nor the accepted SDK 2.3 pin.

## Rationale and compatibility

The original 2026-10-18 decision removed the marker because it intentionally
rejected enabled and all-features builds. The
[public-API review](../research/records/2026-10-18-src-full-public-api-extensibility-and-v020-break-review.md)
identified removal as a concrete feature-compatibility choice. On 2026-10-24,
following the upstream Vulkan announcement, the maintainer reversed that choice:
preserve the feature contract for `0.3.0` and plan the first working slice for `0.4.0`.

Restoring the feature avoids the removal-based compatibility break against
`fsr-sdk 0.2.0` / `fsr-sdk-sys 0.1.1`; enabling it still fails deliberately.
The sys version returns from the unpublished `0.2.0` plan to `0.1.2`, with the
wrapper dependency, lockfile and release metadata updated together. Existing raw
declarations and loader contracts are retained; the added declarations remain
additive. No native ABI or SDK version change follows. Wrapper `0.3.0` remains
selected independently, including its stronger unsafe acquisition contracts.

## Verification contract

Compile implemented feature combinations explicitly for each crate. In source,
MSRV and packaged consumer profiles, require the reserved manifest features and
their forwarding, then verify the deliberate Rust compile diagnostic for each
crate with Vulkan alone and with all features. A Cargo missing-feature error,
unrelated build failure, abort or timeout is not a passing control. Preserve
positive common-type consumers and negative native-API consumers on disabled
platform/backend gates. `--all-features` is an expected failure until Vulkan is usable.

Check normal dependency graphs for Linux and Windows, with and without DX12 and
movable. Both `windows` and production `libloading` must be absent for portable
use; `windows` belongs only to the Windows/DX12 wrapper and `libloading` only to
Windows/DX12 loading. Dev-only fixture dependencies are separate. Graph checks
do not execute Windows code or establish Vulkan support. Report actual checks
and unavailable native execution separately.

The historical [implementation checks](../release/2026-10-18-backend-feature-verification.md)
record the original removal's passing host consumers/tests, dependency boundaries,
Windows compilation, MSRV and local package inspection, with native and final
release limits explicit.
The subsequent [coherence checkpoint](../release/2026-10-18-api-coherence-verification.md)
checks the then-selected sys `0.2.0` dependency/lockfile and exact development
archives through isolated consumers; it is not native or final release verification.

The [2026-10-24 restoration checks](../release/2026-10-24-vulkan-feature-restoration.md)
verify the amended feature contract and version pair through Windows CI, exact
MSRV and isolated package consumers. They establish no new native Vulkan support
and do not replace final release verification.
