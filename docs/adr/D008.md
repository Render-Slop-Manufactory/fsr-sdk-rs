# D008 — Bound the first public DX12 upscaler construction contract

- Recorded: 2026-09-23
- Status: accepted — maintainer authorized the bounded numerical runtime trust
  assumption and acceptance after review on 2026-09-23; M5 is not implemented

**Context:** M4 implements private, unsafe upscaler construction with exclusive
`FfxLibrary` ownership, an owned DX12 device, nonzero dimensions and retained
creation descriptors. M5 evidence supports sequential coexistence of two
contexts through one runtime on the tested signed v2.3.0 configuration. It does
not establish concurrent use or a complete safe numerical input domain.
Zero in any creation dimension aborted the tested child before a native result
was returned. Five nonzero cases succeeded; this is not a general rejection
contract for every other nonzero value.

**Choice — ownership:** Introduce a Windows/DX12 public `Runtime` that owns one
loaded `FfxLibrary` through a private `Rc`-owned runtime state. A runtime can
create multiple independently owned `Upscaler` contexts sequentially. Each
context retains a strong reference to that same state; dropping the public
runtime does not invalidate existing contexts. The last dependent cleanup
releases the loader, except on D005's exceptional retention paths. This owns
the loader; it does not independently pin or expose provider DLL handles.

Sharing is an internal ownership mechanism, visible to callers only as reuse of
the same runtime for construction. Do not expose `Rc`, make `Runtime` Clone,
or expose native entry points or context handles. `Upscaler` is neither Copy nor
Clone and retains D005's consuming destruction and Drop behavior. `Rc` is
appropriate because all dependent owners stay on the acquiring thread; `Arc`
would add no justified concurrency capability. A context's exceptional
retention must retain its strong runtime reference as well as its device and
descriptor storage, even after the public runtime is dropped.

**Choice — unsafe acquisition and execution scope:** Public runtime acquisition
remains an explicit-path unsafe operation, conceptually `Runtime::load(path)`.
It preserves D004's trusted initialization/termination, compatible v2.3.0 exports,
partial-load cleanup and native threading obligations, and D007's deployment
policy. Trust covers resolved dependencies and providers, including driver
providers, rather than merely the named loader file. Successful symbol resolution
does not authenticate those components or establish context compatibility.

For the lifetime of the wrapper-owned runtime family, the acquiring caller must
ensure that external/native FidelityFX use which may touch the same
runtime/provider/global state does not violate the wrapper's lifetime and
serialization assumptions. In particular, external integrations must not make
overlapping or reentrant FidelityFX calls against potentially shared state, make
incompatible changes to relevant process/provider-wide FidelityFX configuration,
or prematurely unload or release native dependencies relied upon by the wrapper
family. Raw or separately wrapped FidelityFX use touching the same state must
obey compatible lifetime and serialization requirements. Independent DLL paths
or devices do not prove isolation. These are explicit unsafe integration
obligations, not discovered AMD threading guarantees.

These obligations remain while any dependent context is live, including after
the public runtime value is dropped. Serialization alone does not establish that
the runtime/context family may move between threads; it remains bound to the
acquiring thread. D005 exceptional retention does not establish that native state
is quiescent, so disappearance of the public owners alone does not prove that
these obligations have ended.

Both `Runtime` and `Upscaler` are explicitly `!Send + !Sync`. Safe operations in
one family execute sequentially on the acquiring thread; no callbacks or raw
access allow reentrant calls through this API. Creating another family remains
unsafe and cannot silently bypass the reservation. No mutex is used to claim
`Sync`, and neither these traits nor a per-object lock proves process-wide
isolation. No safe conversion from an arbitrary raw `FfxLibrary` is introduced.

**Choice — construction inputs and validation:** The intended safe entry point
borrows a runtime and a DX12 device and takes explicit maximum render and
upscale dimensions. A small descriptor/value type suffices; no generic effect
builder or public descriptor chain is needed. The following boundaries apply:

| Category | Contract |
|---|---|
| Wrapper safety | Reject zero in all four dimension components before any native call, using checked dimensions backed by `NonZeroU32`. Own every native dependency; build correctly tagged, address-stable descriptors internally. |
| API validity | Always include exactly the upscaler root, required `FFX_UPSCALER_VERSION` node and DX12 backend with the supplied valid device. The required descriptor kinds, tags, version and backend information are part of the contract; the implementation preserves its already-tested relative ordering internally without treating that ordering as an AMD API requirement. Do not expose version numbers, extension pointers or duplicate nodes. |
| Flags | The first constructor fixes flags to zero, an explicitly permitted native value. No arbitrary bitmask or configurable flags are exposed in M5; additional typed options need their own supported contract. |
| Numerical domain | Reject zero; delegate further provider/device/resource-specific limits to the trusted runtime under the bounded assumption below. Do not invent a maximum, alignment, aspect-ratio rule or render ≤ upscale restriction. Nonzero does not guarantee support or an ordinary error return. |
| Native capability failures | Preserve returned provider/device/allocation errors, including unknown codes. Neither successful construction nor conversion of every native failure into a Rust error is guaranteed. |
| Optional ergonomics | Quality presets, size calculation, jitter helpers, memory estimates and tuning are deferred. No Query/Configure call is required by this constructor. |

**Bounded numerical runtime trust assumption (option B):** For structurally
valid creation inputs with nonzero dimension components and all known native
preconditions satisfied, the wrapper trusts the supported signed AMD runtime
path to handle further provider/device/resource-specific numerical limits
without introducing memory unsafety or undefined behavior at the FFI boundary.
This includes handling internal size arithmetic for the accepted `u32` inputs.
The wrapper enforces known safety preconditions; it does not treat absence of a
documented restriction as proof that every input is supported. The runtime may
accept or reject inputs, and a controlled process abort is not excluded. Neither
successful construction nor an ordinary `Result::Err` for every unsupported
value is promised. An abort alone is not proof of memory unsafety.

The scope is the supported v2.3.0 Windows/DX12 upscaler path acquired under
D004/D007, including the providers and dependencies actually selected by that
path, which may include AMD driver providers. A signature on the loader alone
does not establish this scope or authenticate every selected component. This
assumption does not extend automatically to arbitrary replacement DLLs,
source-built providers, other releases or other effects. Provider identity from
a successful context and residency of a staged DLL do not identify every
participating implementation; failed calls in the boundary spike did not yield
a provider identity. Compatibility claims must preserve those evidence limits.

This is an explicit project trust decision, analogous to but separate from
D005's returned-create-failure assumption, not a proved property of all
providers. It supplies the numerical basis for implementing ordinary safe
construction without asking each safe caller to establish undocumented size
limits. It does not waive descriptor, device, lifetime or threading obligations.
New evidence of memory unsafety, FFI undefined behavior or additional safety
preconditions requires revisiting validation, supported runtime scope or this
safe contract. Such evidence cannot be dismissed merely as a trusted-provider
bug. D005's cleanup policy remains unchanged.

The latest boundary spike passed equal render/upscale maxima of `16383x720`,
`16384x720` and `16385x720`. All three returned `FFX_API_RETURN_ERROR` with null
handles and normal child exits. This adds evidence of ordinary rejection for
some extreme nonzero inputs; it identifies neither the rejection cause nor an
actual construction limit at 16384. No numeric bound follows from it. Neither
an arbitrary 8K cap nor the DX12 texture-coordinate limit is adopted as a
wrapper maximum. No further numerical research or spike is required for this
decision; implementation and verification remain separate work.

**Choice — DX12 device:** Accept
`&windows::Win32::Graphics::Direct3D12::ID3D12Device` and explicitly clone/AddRef
it once per construction attempt after Rust input validation. The caller keeps
its reference and can drop it after the call. The wrapper retains its independent
owned reference through native teardown and D005 retention paths; it never
relies on the provider taking a COM reference. The public parameter is neither
an optional device nor a raw pointer. A well-formed COM interface value supplies
device identity and lifetime, not proof of provider compatibility.

Expose/reexport that exact device type in the Windows/DX12 surface. The current
`windows` dependency is 0.62.2; its type identity becomes part of the public Rust
API, and changing to an incompatible dependency version needs API compatibility
review. A reexport aids consumers but does not make other `windows` versions
interchangeable. This deliberate coupling is smaller than a new device wrapper
or unsafe raw-pointer ownership protocol. No Vulkan/wgpu abstraction is added.

**Lifecycle and errors:** D005 is unchanged: returned create failure produces
no owner and no destroy; OK/null retains the entire dependency bundle; destroy
is terminal, and a destroy error retains dependencies without retry. Stable
effect-specific state remains private throughout native lifetime. Load errors,
Rust validation failures, unchanged native operation/code errors and native
invariant violations remain distinguishable. Drop does not panic or report an
error; consuming `destroy` can report the native failure. No native exception
recovery or promise that all runtime faults become Rust errors is introduced.

**Rationale and limits:** Sequential runtime reuse follows the new bounded
coexistence evidence and avoids requiring a new library owner for each context.
Explicit thread confinement and acquisition obligations avoid inventing global
native concurrency support. Independent COM ownership and retained descriptors
remove lifetime obligations from ordinary callers. Fixing flags to zero and
omitting optional Query/Configure keep the first contract small. The accepted
numerical trust assumption closes the policy question without claiming a proved
universal numerical domain. Implementation must uphold the remaining wrapper
invariants and document the assumption; acceptance does not establish a working
safe API.

Evidence covers one signed DLL pair, OS/GPU/driver configuration and two
coexisting same-device contexts. It does not establish arbitrary multiplicity,
cross-device/provider sharing, provider-module reference counts or guaranteed
module unloading. The observed provider DLL remained resident even after the
last loader owner was dropped; that is neither a required leak nor proof that
Rust library retention can be omitted. Compatibility beyond the bounded baseline
requires its own justification.

M5 excludes Dispatch/resource wrappers, command-list ownership, resource-state
transitions, synchronization of GPU work, Frame Generation, denoising, custom
allocators, message callbacks, public provider overrides, global debug settings,
quality/tuning APIs, wgpu/Bevy integration and Vulkan. M6 must establish its own
resource and execution contract; successful construction is no promise of safe
dispatch or correct reconstructed images. This is not a permanent all-effects
API design, and its acceptance does not complete M5.
