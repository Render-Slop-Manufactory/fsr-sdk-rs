# Source investigation: proportionate performance testing for `fsr-sdk-rs`

- **Investigation date:** 2026-10-15 (Europe/Berlin).
- **Evidence cut-off:** 2026-10-15; external sources accessed 2026-10-15.
- **Question:** What performance properties belong to an engine-independent Rust wrapper around AMD's FSR SDK, what do comparable graphics projects actually measure, and what tests are worth maintaining here?
- **Method:** Read-only examination of the supplied repository ZIP, its research rules, Rust implementations, native fixture, verification inventory and roadmap; comparison with AMD, Microsoft, Chromium/Dawn, Khronos and benchmark-tool primary documentation. No compilation, Windows/GPU execution, SDK acquisition, benchmark implementation, repo edit or performance-gate decision.
- **Evidence status:** **Verified source fact** means established from inspected source or primary documentation, *not* reproduced hardware behavior. **Upstream claim** means reported by a vendor/maintainer without independent execution here. **Reported local observation** refers to the P01 data supplied in the investigation brief, whose absent record/harness could not be audited. **Inference**, **recommendation** and **unresolved** are identified explicitly.

## Recommendation

**Recommendation:** Keep **wrapper cost and regression detection** as the first responsibility; measure the SDK's **CPU recording cost** to place that overhead in context, and use **GPU timings as a controlled integration/parity diagnostic**, not as a claim about Rust GPU speed. Keep creation/destruction, queries and memory measurements separate. Do **not** adopt game FPS, AMD shader-performance ranking or a fixed Rust/C++ percentage as a wrapper release requirement. Use an intentionally small matrix and descriptive distributions until repeatability and practical impact justify an acceptance policy.

**Start a bounded P02 now** for the already implemented subset, without waiting for masks or HDR: compare the complete optimized Rust call with an *independently compiled minimal C++ SDK consumer*, on one shared 640×360-output fixture, and also retain the in-Rust prepared raw call as a diagnostic control. This can expose a language/toolchain/ABI-specific discrepancy that Rust-versus-Rust P01 cannot. It is **partial P02**, not full feature-parity certification. Next introduce a small DX12 GPU timestamp probe at 1080p output, **before** enlarging the benchmark suite for active-render transitions. Add one fixed-allocation shrink/grow case afterward. Full P02 should revisit relevant M15/M16 cases after those contracts exist. None of these recommendations changes roadmap status or authorizes implementation.

The practical first-phase matrix is **(i)** existing small, fixed, explicit-exposure, no-sharpening case for CPU continuity and C++ comparison; **(ii)** one provider-reported render size at 1920×1080 output with valid repeated temporal inputs for GPU timestamps; **(iii)** one fixed-output, fixed-maximum-allocation active-render shrink/grow sequence, once the timestamp method is validated. These are *three purposeful cases, not their Cartesian product*. Motion-vector variants, sharpening, automatic exposure, another GPU and 4K are directed follow-ups, not mandatory cells.

### Relevant implementation boundary

- **Verified source fact:** [`Upscaler::dispatch`](../../../crates/fsr-sdk/src/upscaler/dx12/dispatch.rs) runs checked pre-native inspection and forwards one descriptor to `NativeContextOwner`; a successful return means **CPU recording**, not GPU completion. Submission, fences, resource states, ownership and command-list lifetime remain application obligations.
- **Verified source fact:** [`resources.rs`](../../../crates/fsr-sdk/src/upscaler/dx12/dispatch/resources.rs) checks command-list type, five optional resource roles, COM identities, `GetDesc`, formats, allocation dimensions, `GetDevice`, and context device identity. It builds an FSR descriptor on success. [`frame.rs`](../../../crates/fsr-sdk/src/upscaler/dx12/dispatch/frame.rs) builds borrowed frame/resource values without its own COM inspection. [`descriptor.rs`](../../../crates/fsr-sdk/src/upscaler/dx12/dispatch/descriptor.rs) maps active render dimensions, full output dimensions, exposure, sharpening, motion-vector scaling and reset/history inputs. This is real wrapper CPU work; it cannot be labelled "zero cost" from type signatures.
- **Verified source fact:** M14 accepts an active render region smaller than the maximum while underlying texture allocation dimensions and output remain fixed; the native [`active_render.h`](../../../crates/fsr-sdk/tests/native/active_render.h) generator can vary image regions and check intact input guards. M15 supplied masks, M16 HDR/non-linear colour and variable output are **not** implemented in the inspected dispatch descriptor: reactive and transparency fields are null and output size is fixed. This finding is specific to the supplied ZIP.
- **Verified source fact:** [`UpscalerCore::new`](../../../crates/fsr-sdk/src/upscaler/dx12.rs) creates native context state, clones a device reference and conditionally queries requirements for automatic exposure; local and [movable](../../../crates/fsr-sdk/src/upscaler/dx12/movable.rs) wrappers share a core. [Verification](../../../tools/verification/README.md) already separates bounded native, consumer, ABI and GPU checks. These are useful correctness controls, not timed workload results.

## What may legitimately be claimed?

| Quantity / boundary | Legitimate question and interpretation | Not justified by that measurement |
|---|---|---|
| **End-to-end wrapper CPU recording**, from entering public `dispatch` until return | How much host-thread wall time does a checked SDK recording cost in this configuration? Useful for application integration and regressions. | GPU execution, submit/fence latency, or universal per-frame cost. |
| **Prepared raw SDK call through the same Rust loader** | How much of that recording time might be attributable to the wrapper's inspection/mapping/policy under the **chosen** raw reference? Paired delta is a *reference-dependent increment*. | A language-neutral Rust-versus-C++ verdict; raw has skipped validation and warmed/deserialized metadata. |
| **Inspection/descriptor-only control** | Locate changes in validation and COM inspection; isolate a wrapper-owned candidate for optimization. | A component that may automatically be subtracted from separate dispatch medians: caches, temporality and driver effects are not additive guarantees. |
| **Independent C++ consumer, matched native work** | Test for material differences when integrating the same SDK/provider in two consumer languages/toolchains; separate minimal/raw and equivalently validated policies. | An algorithm-independent Rust overhead number unless both validation contracts and reference boundaries genuinely match. |
| **GPU timestamp interval around recorded FSR work** | Characterize the **provider/driver GPU workload for one input sequence** and detect gross asymmetry between equivalent consumers. | Rust executing shaders faster/slower; whole-renderer FPS, frame latency, real-world quality or supported performance guarantees. |
| **Context creation, destruction, query, memory inspection** | Setup cost, query latency and returned native metadata for a specified provider; inform cache/recreation decisions. | Per-frame dispatch cost or portable memory consumption of a game. |
| **Whole application elapsed frame/FPS** | End-user performance of **that** scene, renderer, synchronization, queue usage, presentation and GPU stack. | Small-wrapper acceptance or universal SDK property. |

**Inference:** For a faithful wrapper, GPU commands should be materially equivalent *given identical native descriptors and ordering*. Any reproducible GPU discrepancy is first evidence to audit mapping, initialization, histories and the harness, **not** evidence that Rust alters AMD shader execution. Conversely, a GPU parity observation does not prove full input equivalence or integration safety; correctness controls are mandatory.

## What comparable projects actually do — classified evidence

1. **Vendor sample, implemented capability rather than wrapper precedent.** At the [pinned AMD v2.3.0 commit, FSR sample documentation](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/docs/samples/super-resolution.md), AMD presents a C++ DX12 integration through a dedicated render module, with controls for upscaling version, scale, reset, masks and sharpening. AMD's [FSR SDK 2.3.0 sample-running manual](https://gpuopen.com/manuals/fsr_sdk/samples/getting-started/running-samples/) documents **actual Cauldron** `-benchmark` CSV/JSON export, `F2` performance UI, CPU/GPU validation switches, `-cpulimiter`/`-gpulimiter`, and PIX/RenderDoc capture options. **Verified documentation / upstream claim:** those tools exist for the sample, and AMD explicitly warns GPU validation has serious performance implications. **Transfer:** separate profiling from correctness and control workload/rate. **Non-transfer:** Cauldron's rendered-frame benchmark, dynamic scene and present behavior is not a direct raw-FFI versus checked-wrapper benchmark. The manual is live versioned documentation; its contents were not executed or independently traced through every SDK source file here.
2. **Maintained graphics abstraction performance suite: direct precedent for CPU separation.** The Chromium **Dawn** project's [testing documentation, commit `074d0e5ea441d1fcc24977948ec00c32bda379f2`](https://dawn.googlesource.com/dawn/+/074d0e5ea441d1fcc24977948ec00c32bda379f2/docs/dawn/testing.md) specifies implemented `dawn_perf_tests` and distinguishes `cpu_time`, `wall_time`, `validation_time`, `recording_time`, iteration/step/trial and bounded steps in flight. It describes small draw, binding and upload variations as microbenchmarks. **Verified source fact:** this is directly analogous to isolating wrapper validation and native recording, but Dawn is itself a multi-backend graphics implementation and owns much more GPU scheduling than `fsr-sdk-rs`; its matrix and infrastructure size should **not** be copied.
3. **GPU timestamp example, methodology not acceptance rule.** Khronos's [Vulkan timestamp-query sample](https://docs.vulkan.org/samples/latest/samples/api/timestamp_queries/README.html) actually demonstrates command-buffer timestamp placement around render passes for approximate GPU profiling. **Verified documentation:** this shows separate GPU timing is a real graphics-integrator technique. **Non-transfer:** Vulkan pool rules and timings do not establish support for this repository or remove the need for DX12-specific query/queue synchronization.
4. **Microsoft / AMD profiling guidance, not observed wrapper practice.** Microsoft's [DX12 Timing](https://learn.microsoft.com/en-us/windows/win32/direct3d12/timing) specifies bottom-of-pipe timestamps, per-queue frequency and `ResolveQueryData`; Microsoft's [PIX Timing Captures](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/timing-captures/pix-timing-captures) distinguish CPU submission from GPU work and explicitly note capture overhead varies with enabled instrumentation. AMD's [RGP manual](https://gpuopen.com/manuals/rgp_manual/) offers event, queue, barrier and synchronization diagnostics. **Recommendation:** use PIX/RGP for *occasional diagnosis* of unexpected findings, not as always-on microbenchmark instrumentation.
5. **Benchmark tooling and first-hand caution.** Google's maintained [Benchmark user guide](https://github.com/google/benchmark/blob/main/docs/user_guide.md) documents warm-up, repetitions, wall versus CPU time and randomized interleaving; its [variance guide](https://github.com/google/benchmark/blob/main/docs/reducing_variance.md) identifies CPU boost, scheduling and cache effects. [`criterion` documentation](https://docs.rs/criterion/latest/criterion/struct.Criterion.html) independently distinguishes noise thresholds from statistical significance. A first-hand [Microsoft PIX GPU capture engineering explanation](https://devblogs.microsoft.com/pix/gpu-captures/) describes repeated GPU replay and overlapping work. **Transfer:** reproducibility, arm-order balancing, different time boundaries and significance versus impact. **Not established:** there is no evidence from these few examples of a community-wide requirement for 4K, 1% parity, one profiler, one number of frames or one benchmark framework; no new dependency is warranted just to imitate a tool.

**Evidence assessment:** Vendor profiling documentation, actual sample features, Dawn test implementation/documentation and Khronos executable sample are different kinds of evidence. They converge on **separating CPU from GPU and defining intervals**; they do not establish a universal library benchmark policy. Single-developer preferences and game-review FPS comparisons have not been used as acceptance evidence.

## Audit of supplied P01 observations (not independently reproduced)

The investigation brief reports an optimized **2026-10-15 Windows 11** baseline: Ryzen 5 5600, Radeon RX 9060 XT, driver `32.0.31041.1004`, provider `4.1.1`; 320×180 render → 640×360 output, explicit exposure, standard finite depth, render-resolution UV motion, zero jitter, pre-exposure 1, sharpening off. Each of three independent processes used 32 warm-ups and 128 timed calls/arm; every successful call was submitted and fenced before reuse. A separate debug-enabled run and sentinel controls checked execution. The following are **reported descriptive medians across those processes**, not universal benchmarks:

| Reported item | Observation | Interpretation limit |
|---|---:|---|
| Complete Rust wrapper CPU dispatch | 35.5–40.2 µs | Per recorded dispatch, not submit/fence/GPU time |
| Prepared raw `FfxLibrary::ffxDispatch` via Rust | 33.9–38.5 µs | Same Rust loader; descriptor pre-inspected |
| Paired wrapper − prepared raw | 1.3–1.4 µs | Small *chosen-control* differential; individual negative differences and appreciable noise |
| Separate inspection/descriptor construction | 1.7–2.0 µs | Measured independently; not algebraically reconcilable without matched timing conditions |
| Context create / destroy | 66–70 ms / 3.1–3.2 ms | Setup/teardown, not steady dispatch; teardown includes test-only environment lookup |
| Controlled allocations / COM calls | 0 Rust allocations / 42 external COM calls | Rust-executable allocation counter only; no native DLL/driver heap accounting; COM stubs differ from production path |

**Confirmed by available code:** repeated DX12 COM metadata/identity/device inspection belongs in the complete Rust path; `ffxDispatch` is reached only afterward; the wrapper itself does not submit/fence. **Not verified:** the particular P01 arms, metadata warming code, COM/instrumentation counting and timer boundaries, because its record and files are absent from the ZIP.

**Audit and limited changes, ordered by value:**

- **Retain:** optimized release builds; SDK/provider/GPU/driver identifiers; **separate** lifecycle, inspection and dispatch measurements; isolated submission/fences; debug-off timed path plus independent debug and sentinel validity controls; independent process repetitions. These choices are defensible for a reference-dependent CPU baseline (project supplied protocol; [PIX instrumentation caution](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/timing-captures/pix-timing-captures)).
- **Fix the comparison description, not necessarily the code:** say *incremental full-wrapper versus pre-inspected Rust-raw path*, not "Rust overhead over C++". Pre-inspecting native resource metadata before timed pairs can warm COM vtables, object/cache lines and possibly provider state before both arms; repeated complete wrapper inspections are then measured against a raw arm that skips equivalent validation. **Inference:** this may favor or stabilize different components; the direction and magnitude are **unresolved** without an experiment. Do not retroactively correct the 1.3–1.4 µs figure by adding or subtracting 1.7–2.0 µs.
- **High-value small follow-up:** record whether raw descriptor pre-inspection occurs *before all timed arms or on each re-recording*; for a targeted control, compare prewarmed/prepared raw, construction/inspection-only, and full wrapper under one randomized/alternating process-block design. This isolates a methodology assumption more cheaply than a new instrumented COM framework. Do not force artificial 'cold inspection' every frame if the actual caller is warm and reuses resources; report both warm-state definitions where informative.
- **Do not overreact to counters:** 42 counted COM calls tells where to profile, not whether those calls are expensive; zero observed Rust allocations is reassuring only for the instrumented Rust allocator path. Further native heap hooks, COM stubs active inside the hot timing interval, ETW or driver tracing are **not** proportionate absent a concrete regression, leak or contention hypothesis. Keep their instrumentation out of normal timed runs.
- **Remaining limitations:** only three process-level repetitions, no inspectable raw distributions here, single provider and very small output, no GPU timestamp, uncertain block order and clock/thermal behavior. Timed call-level samples from one process are correlated; 3 × 128 is **not** 384 independent experimental units. No numerical performance gate follows from these observations.

## Measurement protocol: supported facts versus local experiments

### Host CPU timing and references

**Verified source facts:** `dispatch` comprises metadata inspection and a native FFX entry point; it never submits a queue ([dispatch.rs](../../../crates/fsr-sdk/src/upscaler/dx12/dispatch.rs)). Benchmarks can measure a complete call and a descriptor-prepared FFX call with matching input/resource lifetimes. [Google Benchmark](https://github.com/google/benchmark/blob/main/docs/user_guide.md) supports repetitions/warm-up/random interleaving, but does not supply this project's sampling independence or validity rules.

**Recommendation:** Use an optimized Rust build and optimized C++ (`/O2` or equivalent), comparable CRT/runtime/SDK deployment, with debug/checking off in timing. Record high-resolution **elapsed wall time on the calling CPU thread** directly before and after **one** public `Upscaler::dispatch` / one raw `ffxDispatch`/ one independently compiled C++ SDK call; explicitly omit resource preparation, command-list opening/closing, submission, fence wait, readback, console output and logging. The SDK may still synchronously call the driver inside that interval—that is part of *CPU recording cost*. Use the same clock source where feasible (Windows `QueryPerformanceCounter`, with overhead characterized by a no-op/control) or document differing clocks; do not subtract a noisy tiny clock baseline blindly. Control compiler dead-code elimination by checking return codes, using real recordings and submitting/fencing successful calls **outside** the measured interval. Separate a matched *validator/descriptor-building* C++ arm only if the minimal native comparison reveals a question whose interpretation needs that extra work. A bare `ffxDispatch` with prebuilt descriptors is not a fair stand-in for a checked C++ consumer.

**Unresolved on the hardware:** cost of the timer itself, COM inspection warmth, whether Rust/C++ optimizer/runtime invocation differences are repeatable at µs scale, if inlining/LTO changes a meaningful boundary, and how native provider scheduling affects CPU recording. Resolve by controls and process-block results rather than presuming costs.

### GPU timestamp scope

**Verified DX12 facts:** `EndQuery` timestamps occur after preceding work on that GPU queue (bottom of pipe), direct queues use `D3D12_QUERY_HEAP_TYPE_TIMESTAMP`, timestamps are 64-bit ticks resolved with `ResolveQueryData`, and the **queue's** `GetTimestampFrequency` gives Hz; perform floating-point conversion `Δt_µs = 10^6 × (t_after − t_before) / frequency`. A direct/compute queue supports timestamps; arbitrary cross-queue work does not become one comparable interval ([Microsoft DX12 timing](https://learn.microsoft.com/en-us/windows/win32/direct3d12/timing), [DirectX counters specification](https://microsoft.github.io/DirectX-Specs/d3d/CountersAndQueries.html)).

**Recommendation:** On a clean DIRECT list, place timestamp **A immediately before the FSR-recorded commands** and **B immediately after `dispatch` has recorded them**, identically for Rust/C++; do not bracket uploading the synthetic textures, transitions from fixture preparation, unrelated render passes, copies for readback or fences. Resolve A/B into a readback-capable buffer *after B* on the same list/queue, submit once, wait for the matching fence, then read and convert both `u64` ticks. Validate queue/frequency, resolved data, nonnegative plausible deltas, list closure/once-only submission and sentinel output separately. Include provider-command internal barriers/synchronization in the FSR interval because they are genuine recorded costs; if callbacks or auxiliary queues appear, trace them with PIX rather than claiming the one-queue interval covers all GPU work. An empty timestamp bracket controls the instrument's granularity/overhead but should **not** automatically be subtracted. The resulting number is *GPU elapsed interval under serial-fenced execution*, not shader-exclusive execution or application latency. [Microsoft PIX](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/timing-captures/pix-timing-captures) provides an independent diagnostic of CPU/GPU overlap and capture perturbation.

**Unresolved experimentally:** timestamp resolution/quantization and jitter on the RX 9060 XT; whether native SDK work produces any auxiliary GPU queue; sensitivity to clock ramp, power management and the timestamp bracket itself. `SetStablePowerState` is a developer/debug option rather than a requirement for normal shipping-equivalent runs; if used, report the changed power state and do not silently compare against ordinary clocks ([Microsoft timing](https://learn.microsoft.com/en-us/windows/win32/direct3d12/timing)).

### History, warm-up and repetitions

**Recommendation:** Use *separate persistent contexts* per arm with identical creation flags, provider, maximum dimensions, command lists/resources, frame-indexed generated input data, depth/motion units, camera, jitter, reset and history. Distinguish **cold context creation, first dispatch/shader initialization, warm-up and steady-state**; do not hide cold costs inside warm steady-state medians. Fix a provider-appropriate nontrivial temporal sequence, not a constant output sentinel mistaken for real upscaling; zero-jitter constant test frames can remain the P01 continuity case. A warm-up count of 32 is a precedent, **not** proof of steady clocks/pipelines on a new size or provider. Examine sequence/time drift before declaring steady state; use a bounded warm-up extension if necessary.

Balance AB/BA or ABBA block order **across repeated independent processes** or use seeded randomized blocks, retaining exact order. For independent Rust/C++ executables, pair *nearby process-block summaries* under similar thermal conditions, not individual calls that have no cross-process pairing. Avoid changing the history trajectory when interleaving: each arm must receive the same ordered frame sequence on its own context. Keep release/power mode, foreground/background workload, adapter selection, memory pressure, CPU core/scheduler conditions and GPU clocks/thermals as stable as practical; retain observations and outliers with reasons. Report median, dispersion/range and per-block paired differences; intervals/bootstraps should resample at the independent-process/block level rather than treating all per-frame samples as iid. [Google Benchmark variance guidance](https://github.com/google/benchmark/blob/main/docs/reducing_variance.md) documents relevant scheduling, boost and cache confounders. Do **not** silently trim inconvenient negative paired differences or pool dissimilar warm/cold populations.

**Serial-fenced versus throughput:** Serially submitting and fencing every recorded dispatch isolates one call, controls resource reuse and makes history ordering auditable, but suppresses pipeline overlap and introduces idle/clocks artifacts. Multiple frames in flight would instead measure throughput, scheduling, transient resources and application choices, and is **optional** only after the currently bounded recording-ahead contract is separately safe. Never combine serial GPU intervals with present latency or claim throughput/FPS. Query GPU memory usage or resource requirements *outside* timing if needed; memory figures depend on provider, context dimensions and timing of the query.

### Benchmark validity (separate from speed acceptance)

A performance sample is **valid** only when the prepared SDK/runtime binary and provider ID are recorded and match per comparison; API/backend/context flags, dimensions, allocation formats, resource states, descriptor fields and temporal inputs are matched; dispatch succeeds and records; submission and GPU completion are verified before reuse; output changes from a sentinel in both arms; and independent debug-enabled/inspection control finds no contract violation. For the single synthetic workload, a bounded comparison of equivalent outputs or invariants is appropriate *only* to establish equivalent execution; no sharpening-effect, reconstruction-quality, provider ranking or new image-quality threshold is permitted. Failure, timeout, unsupported timestamp, missing runtime or mismatched inputs is **invalid/blocked**, not a poor performance score. [Repository verification boundary](../../../SCOPE.md), [dispatch contract](../../../crates/fsr-sdk/src/upscaler/dx12/dispatch.rs) and [PIX profiling perturbation](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/timing-captures/pix-timing-captures) support this separation.

**Minimal initial combinations:** `S` = legacy P01 small, fixed explicit/no-sharp (CPU + independent C++); `G` = fixed 1080p output/provider-selected render size, steady coherent temporal frames (GPU timestamp, optionally CPU comparison); `D` = same max render/output allocations as G but one bounded shrink/grow history (GPU and CPU *delta versus its own stable-size reference*). Only add alternative provider flags on the case whose effect is under investigation. Prefer one output size over indiscriminate 1080p/1440p/4K scaling sweeps. The one-minute benchmark clock budget is not prescribed; terminate based on sufficient valid blocks and stable estimates, or document instability.

## Parity, regression and gates

**Recommendation:** Begin with **descriptive reporting and confidence-aware comparisons**, not a hard CPU/GPU parity gate. Record both the **absolute paired difference in µs** and, where the denominator is material and stable, the **relative difference**. A 1.3 µs difference divided by near-zero additional wrapper work makes a "percentage overhead" meaningless; express it relative to complete dispatch time only with that denominator explicitly labelled. For GPU/provider intervals in hundreds/thousands of µs, a relative effect may communicate more, but absolute latency still matters.

First estimate (a) timer/query granularity and any measurable systematic instrumentation bias, (b) between-process/block variability, and (c) a project-relevant performance **budget** based on the caller's expected CPU/GPU time cost, before proposing any tolerance. Use a paired block confidence interval or a predeclared robust equivalent appropriate to independent units. A *statistically distinguishable* nonzero difference can be inconsequential; "not statistically different" does **not** establish parity. To make an eventual **equivalence** claim, its uncertainty interval would need to fit within a separately justified ±practical margin; for **non-inferiority**, a one-sided upper bound would need to be within an agreed maximum overhead. With only three reported process repetitions, neither margin nor such a conclusion is established. Benchmark validity gates from the previous section can be strict immediately; speed acceptance remains an explicit separate decision. [Criterion noise discussion](https://docs.rs/criterion/latest/criterion/struct.Criterion.html), [Google Benchmark guidance](https://github.com/google/benchmark/blob/main/docs/reducing_variance.md).

A regression investigation may use a per-machine historical control under the **same** driver, provider, workloads and exact instrumentation. If a change coincides with a driver/provider update, record a **new stratum**, not "wrapper regression" by subtraction. Treat intervals crossing a practical margin or inconsistent signs as **unresolved/retest**, not forced pass/fail. Do not invent a 1%, 5% or other threshold in advance of resolution and actual variability.

## Ordered programme and stopping conditions

## Concrete first experiment: independent C++ CPU reference

**Hypothesis to examine, not assume:** The observed P01 wrapper-versus-prepared-Rust-raw increment is small relative to overall recording time; nevertheless the shared Rust loader/reference cannot establish equivalence with an independently compiled C++ client. Independent consumer comparison is therefore informative now.

1. **Prepare two independently built consumers** on the same Windows host: optimized Rust public wrapper executable and optimized native C++ executable using the pinned FFX API and its own ABI declarations/build, both targeting one verified provider/backend. Keep the C++ raw/minimal path labelled **minimal**, not checked-equivalent; retain the existing Rust-raw arm as a bridge. Specify release optimizer flags, hashes, SDK DLL/symbol resolution, GPU, driver and provider identity.
2. **Canonicalize one S input spec**, not just a vague screen-size match: exact render/output allocations and formats; device/queue/list type; context flags (depth, motion, dynamic off, exposure mode, provider/version); depth projection and units; UV motion scale; color/exposure/pre-exposure; camera/jitter/frame interval/reset; sharpening disabled; deterministic valid frame sequence; declared D3D resource states; sentinel. Both implementations receive equivalent frame *indices*, not necessarily the same pointer values.
3. **Preflight outside timing:** independent controlled/debug-enabled execution, successful returned codes, list submission and fence completion, output modified from sentinel, equivalent descriptors and bounded output consistency checks. Fail invalid comparisons rather than recording a "slow" or "fast" number.
4. **Measure only the CPU recording boundary.** Warm both contexts, use an initial 32-dispatch warm-up as a starting point and inspect stability; run an initial **3 independent process blocks** with **128 timed calls/arm/block** only as continuity with P01 (increase blocks if needed). Alternate Rust/C++ process order AB/BA, record timestamps/ordering/cold effects. Submit/fence all successful calls *outside* the host timer before any resource/allocator reuse; do not enable debug, callbacks, logging, allocation hooks or COM counters in timed iterations. Independent executables make **process-block differences**, not call-level pairs, the independent comparisons.
5. **Report** signed absolute Rust-full minus C++-minimal difference per block, separate Rust-prepared-raw minus C++-minimal difference, complete-call distributions and any uncertainty. Interpret unmatched validation as intentional confounding; if it dominates the inference, add a narrowly equivalent validation arm rather than proclaiming C++ faster. If results are noisy/inconsistent, report that and stop after a bounded attempt or rerun with a measured stability fix. Do **not** require the difference to be under an invented percentage.

**Pass/fail meaning:** The experiment succeeds as research when its hardware/source identities, workload validity, full timing boundaries and sufficiently interpretable or explicitly inconclusive comparison are retained. It does **not** finish full P02, create an acceptance gate, show GPU time, prove any particular FPS or reopen image quality. Source inspection cannot predetermine the measured result.

## Baseline delta and outstanding questions

- **Confirmed:** Separation of Rust wrapper validation, SDK CPU recording, separate GPU execution and lifecycle is supported by the actual dispatch code and external DX12/Dawn/AMD practices. The M14 **render** sub-feature is implemented in this ZIP; a performance follow-up is meaningful. The user-supplied P01 structure is broadly credible as a bounded CPU baseline, and its independent debug/sentinel controls address meaningful validity risks.
- **Challenged:** A prepared SDK call reached through Rust **is not independent C++ parity**. P01's reported 1.3–1.4 µs is a reference- and warm-state-specific difference, not a universal language overhead or production FPS penalty. The original roadmap's *full* P02 sequencing after masks/HDR need not block an **earlier partial** comparison; its pending P01 status conflicts with the newer reported baseline and should be reconciled only through separately authorized repository integration.
- **Unresolved:** The absent 2026-10-15 P01 record/harness; exact wrapper Git identity of the ZIP; timer granularity/noise and the influence of pre-inspection warmth; whether true C++ minimal/full client timing differs; hardware 1080p timestamp stability, GPU clock response, independent provider queues and any driver-specific synchronizations; practical tolerances and application use frequency; shader initialization amortization; costs of first dispatch and active-render transitions.
- **Prerequisites for any native study:** A working Windows x64/MSVC DX12 host, trustworthy v2.3.0 DLL/provider deployment, recorded driver/GPU; optimized tools; real executable/list, consistent managed resources and fence capability; repeatable input/history sequence; and explicit native-error/timeout cleanup. No native performance tests were run for this record. Unsupported hardware, missing trust input, GPU timestamp failure, or noise can produce a legitimate **blocked/unresolved** report.
- **Scope and integration:** This is a **source recommendation only**. No benchmark source, public API, verification profile, roadmap, default CI gate, dependency, acceptance margin or research synthesis has been added. M15/M16 and variable-output timing are deferred until their own integration contracts exist. No additional reconstruction/sharpening-effect research is proposed.
