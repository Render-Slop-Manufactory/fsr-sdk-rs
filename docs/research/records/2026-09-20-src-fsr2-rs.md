# Source investigation: fsr2-rs raw binding architecture

- **Investigation date:** 2026-09-20
- **Topic and scope:** Static source investigation of `NotAPenguin0/fsr2-rs` as a contrasting low-level Rust binding for the older standalone FidelityFX FSR2 API. Focus: ABI fidelity, binding generation, context representation and lifecycle, pointer/lifetime ownership, backend state, callbacks, errors, Vulkan/D3D12 differences, thread-safety, reproducibility, and FFI safety implications.
- **Baseline and evidence cut-off:** Comparison baseline is the set of FidelityFX SDK v2.3.0 concerns supplied for `fsr-sdk-rs`. `fsr2-rs` itself binds the older standalone FSR2 2.2.0 API and is not treated as evidence for FidelityFX SDK v2.3.0 behavior.
- **Method and exclusions:** Source inspection only. Inspected repository Rust sources, manifest, build script, custom FSR2 fork headers and implementation, and project documentation. No repository modification, compilation, ABI probe, GPU execution, failure injection, sanitizer run, or concurrency experiment was performed.
- **Repository revision/commit inspected:** `NotAPenguin0/fsr2-rs`, branch `master`, as served on 2026-09-20. GitHub reported 36 commits, but the available source/search interfaces did not expose a trustworthy HEAD object ID; exact SHA therefore remains unresolved.
- **Native source revision:** `NotAPenguin0/FidelityFX-FSR2`, `master`, via the repository submodule relationship. Exact gitlink SHA was not recoverable through the inspected web source.
- **Access date:** 2026-09-20
- **Primary repository:** <https://github.com/NotAPenguin0/fsr2-rs>
- **Custom FSR2 fork:** <https://github.com/NotAPenguin0/FidelityFX-FSR2>

## Scope and repository revision

**Verified —** The repository describes itself as providing “unsafe, 1:1 Rust bindings” for FSR2 2.2. The Rust constants in `fsr2-sys/src/lib.rs` are `FFX_FSR2_VERSION_MAJOR = 2`, `FFX_FSR2_VERSION_MINOR = 2`, and `FFX_FSR2_VERSION_PATCH = 0`. The custom fork's `src/ffx-fsr2-api/ffx_fsr2.h` reports the same `2.2.0` version and `FFX_FSR2_CONTEXT_SIZE = 16536`. Sources: <https://github.com/NotAPenguin0/fsr2-rs>, <https://raw.githubusercontent.com/NotAPenguin0/fsr2-rs/master/fsr2-sys/src/lib.rs>, <https://raw.githubusercontent.com/NotAPenguin0/FidelityFX-FSR2/master/src/ffx-fsr2-api/ffx_fsr2.h>.

**Verified —** The native implementation is supplied through `fsr2-sys/src/vendor/fsr2`, configured as a git submodule pointing at `https://github.com/NotAPenguin0/FidelityFX-FSR2`. The repository therefore does not target a system-installed FidelityFX SDK. Source: <https://github.com/NotAPenguin0/fsr2-rs/blob/master/.gitmodules>.

**Upstream claim —** The README says its FSR2 fork differs from upstream by removing the `cauldron-media` dependency, not building sample backends by default, and changing the Vulkan backend so it does not link Vulkan directly but instead receives Vulkan function pointers during initialization. Source: <https://github.com/NotAPenguin0/fsr2-rs>.

**Unresolved —** The exact `fsr2-rs` HEAD SHA and native submodule gitlink SHA could not be established through the available source endpoints. A local/full Git checkout or GitHub API/commit endpoint that exposes object IDs is required for cryptographic revision pinning of this record.

**Unresolved —** No standalone Rust example program was identified in the inspected sources. The concrete Rust usage encountered is the `test_linkage` test in `fsr2-sys/src/lib.rs`, which calls `ffxFsr2GetUpscaleRatioFromQualityMode`. The investigation did not obtain a recursive tree sufficient to prove that no example file exists elsewhere.

## Binding generation and build model

**Verified —** The Rust ABI definitions are handwritten, not generated during the Cargo build. `fsr2-sys/Cargo.toml` contains runtime dependencies on `bitflags` and `widestring` and build dependencies on `anyhow` and `fs_extra`; it has no `bindgen`, Clang, libclang, `cc`, or equivalent header-binding dependency. Source: <https://raw.githubusercontent.com/NotAPenguin0/fsr2-rs/master/fsr2-sys/Cargo.toml>.

**Verified —** `fsr2-sys/build.rs` does not generate Rust bindings. It invokes `cmake`, hard-codes `-A x64`, configures `-DGFX_API=VK` or `-DGFX_API=DX12`, builds the vendored native implementation, copies generated native artifacts out of the fork's `bin` directory, and emits `cargo:rustc-link-lib` directives. Source: <https://raw.githubusercontent.com/NotAPenguin0/fsr2-rs/master/fsr2-sys/build.rs>.

**Verified —** Cargo features are:

```text
default = ["vk"]
vk = []
dx12 = []
```

and `build.rs` rejects enabling both through `compile_error!("Only one of the Vulkan or DirectX12 backends may be enabled.")`. Source: `fsr2-sys/Cargo.toml`, `fsr2-sys/build.rs`.

**Inference —** Reproducibility is split between checked-in Rust ABI declarations and a submodule-pinned native implementation. This removes consumer dependence on bindgen/Clang versions and makes the Rust ABI text directly reviewable, but correctness depends on manually keeping those declarations synchronized with the exact native headers.

**Inference —** This is a general raw-FFI trade-off rather than an FSR2-specific property: checked-in bindings improve auditability and deterministic source review, while generated bindings reduce manual transcription drift if the generator/toolchain is itself pinned.

**Verified —** The crate still has a build-time dependency on the native fork's headers and source because CMake compiles the standalone FSR2 library from `./src/vendor/fsr2`. “No bindgen dependency” therefore does not mean “no SDK/native-source dependency”.

**Upstream claim —** The README records build-time shader permutation generation as capable of freezing the machine briefly because generation uses many threads. This is a build-system caveat rather than a Rust safety property. Source: <https://github.com/NotAPenguin0/fsr2-rs>.

## Raw ABI structure

**Verified —** The public Rust surface is intentionally C-shaped: `#[repr(C)]` structures, raw pointers, integer/bitflag types, and free `extern "C"` functions. `FfxDevice`, `FfxCommandList`, `FfxRootSignature`, and `FfxPipeline` are aliases for `*mut c_void`. `FfxResource` contains `resource: *mut c_void` plus name, description, state, depth flag, and descriptor metadata. Source: `fsr2-sys/src/types.rs`, <https://raw.githubusercontent.com/NotAPenguin0/fsr2-rs/master/fsr2-sys/src/types.rs>.

**Verified —** `FfxFsr2Context` is not a pointer handle. It is represented as:

```rust
#[repr(C)]
pub struct FfxFsr2Context {
    pub data: [u32; FFX_FSR2_CONTEXT_SIZE],
}
```

with `FFX_FSR2_CONTEXT_SIZE = 16536`, matching the standalone header's caller-allocated opaque `uint32_t data[FFX_FSR2_CONTEXT_SIZE]`. Source: `fsr2-sys/src/lib.rs` and native `src/ffx-fsr2-api/ffx_fsr2.h`.

**Verified —** `FfxFsr2Context` derives `Copy` and `Clone`.

**Inference —** This is a significant ownership mismatch if the Rust value is interpreted as an owning context. The native code overlays this byte/word buffer with `FfxFsr2Context_Private`, which contains device state, callbacks, resource identifiers, and pipeline/backend-associated state. Bitwise copying the Rust value can therefore create two Rust values describing the same native resources. The binding does not prevent destroying or using both copies.

**Verified —** The binding is “1:1” in architectural intent but not mechanically identical to the C declarations. Examples include Rustified field/variant naming, `bitflags` wrappers for C bitmasks, handwritten Vulkan handle wrappers, and Rust enums replacing some C integral definitions.

**Verified —** `fsr2-sys/src/error.rs` defines:

```rust
#[repr(i32)]
pub enum FfxErrorCode { ... }
```

whereas the native `ffx_error.h` uses `typedef int32_t FfxErrorCode` followed by integral constants. Sources: <https://raw.githubusercontent.com/NotAPenguin0/fsr2-rs/master/fsr2-sys/src/error.rs>, <https://raw.githubusercontent.com/NotAPenguin0/FidelityFX-FSR2/master/src/ffx-fsr2-api/ffx_error.h>.

**Inference —** The Rust representation narrows the native value domain. If a custom backend or future native code returns an `int32_t` not represented by one of the Rust enum variants, the FFI boundary can produce an invalid Rust enum value. A transparent integer/newtype would more literally model the native typedef; `fsr2-rs` therefore demonstrates that handwritten “raw” bindings can inadvertently become less ABI-permissive than the C API.

**Verified —** `FfxFsr2Pass` and `FfxFsr2MsgType` in `fsr2-sys/src/interface.rs` use `#[repr(u8)]`, while the native headers declare C/C++ enums without an explicitly fixed underlying integer type. `FfxFsr2Pass` crosses callback boundaries through `FfxFsr2CreatePipelineFunc`; `FfxFsr2MsgType` crosses through `FfxFsr2Message`. Source: <https://raw.githubusercontent.com/NotAPenguin0/fsr2-rs/master/fsr2-sys/src/interface.rs>.

**Unresolved —** Source inspection is insufficient to prove ABI equivalence of those `repr(u8)` definitions with the C++ compiler and calling convention used by the native build. A C++/Rust ABI probe should compare sizes, alignments, parameter passing, and callback invocation on the actual supported target.

## Context lifecycle

**Verified —** The lifecycle is exposed almost literally as:

```rust
ffxFsr2ContextCreate(
    context: *mut FfxFsr2Context,
    description: *const FfxFsr2ContextDescription,
) -> FfxErrorCode;

ffxFsr2ContextDestroy(
    context: *mut FfxFsr2Context,
) -> FfxErrorCode;
```

There is no Rust owner wrapper, `Drop`, live/dead state, consumed `self`, or constructor returning an initialized context. Source: `fsr2-sys/src/lib.rs`.

**Inference —** Exact-once destruction is entirely a caller obligation. Rust's type system does not prevent zero destroys, repeated destroys, destruction through one `Copy` of the context followed by use/destruction through another copy, or calls after destruction.

**Verified —** In the native fork, `ffxFsr2ContextCreate` performs `memset(context, 0, sizeof(FfxFsr2Context))` before validating that `context` is non-null. Source: `src/ffx-fsr2-api/ffx_fsr2.cpp`, function `ffxFsr2ContextCreate`, <https://raw.githubusercontent.com/NotAPenguin0/FidelityFX-FSR2/master/src/ffx-fsr2-api/ffx_fsr2.cpp>.

**Inference —** Passing a null output pointer appears to dereference it before the intended `FFX_ERROR_INVALID_POINTER` check. This is a source-visible potential defect in the old fork; no runtime experiment was performed.

**Verified —** `fsr2Create` first zeroes `FfxFsr2Context_Private`, sets `context->device`, and copies the complete `FfxFsr2ContextDescription` with `memcpy`. It then invokes `fpCreateBackendContext`, `fpGetDeviceCapabilities`, creates internal resources, and creates pipelines. Multiple failures return early through `FFX_RETURN_ON_ERROR` or `FFX_VALIDATE`. Source: `ffx_fsr2.cpp`, `fsr2Create`.

**Verified —** No create-level rollback block was found around those early returns. For example, internal resources are created in a loop through `fpCreateResource`; `createPipelineStates` is then called and its error returned directly.

**Inference —** A failed create can leave the caller-provided context buffer containing partially initialized state. The source does not establish a single Rust-visible “failed/uninitialized” sentinel.

**Unresolved —** It is not established whether `ffxFsr2ContextDestroy` is supported after every possible failed-create point. Answering that requires either explicit old-API documentation or fault-injection tests at each backend/resource/pipeline failure location.

**Verified —** `ffxFsr2ContextDestroy` forwards to `fsr2Release`. `fsr2Release` calls every pipeline destroy callback, clears selected external resource slots, calls `fpDestroyResource` over the internal resource array, then calls `fpDestroyBackendContext` if the private `device` field is non-null. `fsr2SafeReleaseDevice` sets that private `device` field to null after backend destruction. Source: `ffx_fsr2.cpp`, `fsr2Release`, `fsr2SafeReleaseDevice`.

**Verified —** The context storage is not globally zeroed on destroy. Only selected state is modified; notably the private `device` field becomes null.

**Verified —** Dispatch checks `contextPrivate->device` and returns `FFX_ERROR_NULL_DEVICE` when it is null.

**Inference —** The old native implementation therefore has a partial post-destroy marker, but Rust has no type-level representation of it. A destroyed `FfxFsr2Context` has exactly the same Rust type as a live context.

**Inference —** The implementation should not be assumed idempotent merely because the device field is nulled. `fsr2Release` invokes pipeline/resource destruction before `fsr2SafeReleaseDevice`; a second destroy therefore traverses those callbacks again.

**Unresolved —** Whether a second destroy happens to survive with the supplied Vulkan backend is a runtime question and was not tested.

## Lifetime and ownership handling

**Verified —** Rust lifetimes are not represented in the raw ABI structures. Relevant fields include `FfxFsr2Interface::scratch_buffer: *mut c_void`, `FfxResource::resource: *mut c_void`, resource initialization pointers, wide-string name pointers, pipeline array pointers, and graphics-device/command-list pointer aliases. Sources: `fsr2-sys/src/interface.rs`, `fsr2-sys/src/types.rs`.

**Verified —** Native `fsr2Create` copies the complete `FfxFsr2ContextDescription` into private context storage. The copied value includes `callbacks`, `device`, and `fpMessage`.

**Inference —** Any pointers reachable from the copied callback/interface description that native code consults later acquire a create-to-destroy or otherwise persistent lifetime requirement, despite no Rust lifetime parameter encoding that relationship.

**Upstream claim —** The old standalone `FfxFsr2Interface` documentation says `scratchBuffer` is preallocated memory used internally by a backend and that custom backends are not required to use it. Source: <https://raw.githubusercontent.com/NotAPenguin0/FidelityFX-FSR2/master/src/ffx-fsr2-api/ffx_fsr2_interface.h>.

**Verified —** The supplied Vulkan backend does use the scratch allocation persistently. `ffxFsr2GetInterfaceVK` assigns:

```cpp
outInterface->scratchBuffer = scratchBuffer;
outInterface->scratchBufferSize = scratchBufferSize;
BackendContext_VK* context = (BackendContext_VK*)scratchBuffer;
context->physicalDevice = physicalDevice;
context->vkInstanceFunctionTable = *instanceFpTable;
```

and later callbacks repeatedly recover `BackendContext_VK*` by casting `backendInterface->scratchBuffer`. Source: `src/ffx-fsr2-api/vk/ffx_fsr2_vk.cpp`.

**Inference —** For the supplied Vulkan backend, the scratch allocation must remain allocated, correctly aligned, and otherwise usable for as long as the context/backend may invoke callbacks. The Rust binding provides no borrow or ownership relationship enforcing that lifetime.

**Verified —** The Vulkan function-pointer table passed to `ffxFsr2GetInterfaceVK` is copied by value into `BackendContext_VK`, rather than retaining the pointer to the caller's table object.

**Inference —** The table object itself therefore need not remain allocated after `ffxFsr2GetInterfaceVK` returns, but the function addresses stored in the copied table must remain callable whenever the backend later uses them.

**Upstream claim —** The standalone interface documentation explicitly states that resources passed into dispatch may cease to be valid after that dispatch; the backend is expected to register them temporarily as `FfxResourceInternal` and clear them at the end. Source: `ffx_fsr2_interface.h`, documentation for `FfxFsr2RegisterResourceFunc`.

**Inference —** This distinction is useful when reasoning about raw FFI lifetimes: persistent create-time backend/scratch state and per-dispatch external resources have different native lifetime contracts even though both appear as unparameterized raw pointer values in Rust.

## Unsafe boundaries

**Verified —** Calls to the top-level `extern "C"` functions require an `unsafe` call site in Rust, but constructing, copying, moving, and inspecting most raw ABI structures is ordinary safe Rust.

**Verified —** Most backend callback aliases in `fsr2-sys/src/interface.rs` are plain safe function-pointer types such as:

```rust
pub type FfxFsr2CreateBackendContextFunc =
    extern fn(*mut FfxFsr2Interface, FfxDevice) -> FfxErrorCode;
```

rather than `unsafe extern fn`.

**Inference —** Those function pointers have pointer-validity, initialization, aliasing, resource, and backend-state preconditions that are not represented by the function-pointer type. If a Rust caller obtains one of these callback values, invoking it with arbitrary raw pointers is syntactically a safe Rust operation despite relying on unsafe native invariants.

**Verified —** The Vulkan loader function pointers in `fsr2-sys/src/backend/vk.rs` are instead represented as `unsafe extern "system" fn`.

**Inference —** The crate therefore applies inconsistent unsafe-function typing: Vulkan loader callbacks explicitly advertise unsafe invocation while core FSR backend callbacks with comparable raw-pointer preconditions do not.

**Verified —** Function-pointer fields in `FfxFsr2Interface` are non-optional Rust function pointers. `FfxFsr2ContextDescription::fp_message` is also a non-optional `FfxFsr2Message`.

**Verified —** Native `fsr2Create` explicitly tests `context->contextDescription.fpMessage == nullptr` when debug checking is enabled and, if null, disables the debug-checking flag.

**Inference —** The Rust definition does not faithfully expose native nullability for the message callback. Representing a nullable native function pointer as a non-`Option` Rust function pointer narrows the native ABI contract.

**Verified —** There is no explicit Rust `userdata` field in `FfxFsr2Interface`. Backend callbacks receive `*mut FfxFsr2Interface`, and supplied backend state is recovered through fields such as `scratchBuffer`.

**Inference —** For custom backends, the interface/scratch buffer effectively provides the state-carrier role often handled by a separate userdata pointer.

## Backend and resource handling

**Verified —** The Vulkan Rust backend module defines its own minimal Vulkan handle types rather than depending on `ash` or another loader crate. Types such as `VkDevice`, `VkImage`, `VkBuffer`, and `VkCommandBuffer` are transparent `u64` newtypes with `from_raw` constructors. Source: `fsr2-sys/src/backend/vk.rs`.

**Verified —** Comments in that module explicitly say some Vulkan structures are left as `*mut c_void` to avoid depending on `ash` or another Vulkan loader, for example the outputs of `vkGetPhysicalDeviceProperties` and related functions.

**Verified —** The custom fork introduces `FfxFsr2InstanceFunctionPointerTableVk`, containing Vulkan loader functions including `vkEnumerateDeviceExtensionProperties`, `vkGetDeviceProcAddr`, and physical-device query functions. Both `ffxFsr2GetScratchMemorySizeVK` and `ffxFsr2GetInterfaceVK` accept the table. Sources: Rust `src/backend/vk.rs` and native `src/ffx-fsr2-api/vk/ffx_fsr2_vk.h`.

**Upstream claim —** The repository README identifies this loader/function-table mechanism as a custom fork change designed so the FSR2 Vulkan backend does not link Vulkan directly.

**Verified —** `CreateBackendContextVK` converts the abstract `FfxDevice` into `VkDevice` and stores backend state in `BackendContext_VK` obtained from `backendInterface->scratchBuffer`.

**Verified —** `DestroyBackendContextVK` destroys backend-owned buffers, memory, descriptor pool/layouts, and samplers, then sets `backendContext->device = nullptr`. It does not call `vkDestroyDevice`. Source: `ffx_fsr2_vk.cpp`, `DestroyBackendContextVK`.

**Inference —** The supplied Vulkan backend borrows the application's logical Vulkan device rather than owning the device itself. It does own native objects it creates through that device.

**Verified —** The scratch allocation remains application-owned memory even though it contains mutable backend state and native handles for the lifetime of the backend.

**Verified —** `FfxResource` is a copyable descriptor around a raw resource pointer; it is not a Rust RAII owner. Vulkan helpers such as `ffxGetTextureResourceVK` and `ffxGetBufferResourceVK` construct these descriptors from existing Vulkan handles.

**Inference —** Passing an `FfxResource` does not transfer ownership of the underlying external resource. Native validity remains contingent on the external graphics resource satisfying the old FSR2 dispatch contract.

**Verified —** Vulkan and D3D12 support are asymmetric in the Rust repository. `vk` is the default Cargo feature and `src/backend/vk.rs` contains concrete bindings. `src/backend/dx12.rs` is an empty file. Source: <https://raw.githubusercontent.com/NotAPenguin0/fsr2-rs/master/fsr2-sys/src/backend/dx12.rs>.

**Upstream claim —** The README lists “Bindings for the DirectX12 backend are currently missing” as a known issue.

**Verified —** `build.rs` nevertheless has a `dx12` path that configures native CMake with `GFX_API=DX12` and links `ffx_fsr2_api_dx12_x64`.

**Inference —** The native build machinery knows how to build the D3D12 backend, but the Rust crate does not expose the corresponding backend helper ABI. Vulkan is therefore the only backend for which the Rust-side low-level integration surface is materially complete in the inspected revision.

## Error handling

**Verified —** All principal native operations expose `FfxErrorCode` directly. There is no Rust `Result`, error wrapper, `std::error::Error` implementation, or safe constructor that returns only an initialized context on success.

**Verified —** The Rust enum contains the old API codes `Ok`, `InvalidPointer`, `InvalidAlignment`, `InvalidSize`, `Eof`, `InvalidPath`, `ErrorEof`, `MalformedData`, `OutOfMemory`, `IncompleteInterface`, `InvalidEnum`, `InvalidArgument`, `OutOfRange`, `NullDevice`, `BackendApiError`, and `InsufficientMemory`. Source: `fsr2-sys/src/error.rs`.

**Verified —** A source comment notes that the native headers contain both `EOF` and `ERROR_EOF` style constants and says the author does not know why.

**Inference —** That comment is representative of the project's binding philosophy: native oddities are largely exposed directly rather than normalized behind a higher-level Rust error model.

**Inference —** Raw error propagation preserves the old API's exact control-flow questions for the caller, including the difficult case “create returned an error; what state is the output context now in?”

## Thread-safety

**Verified —** `FfxFsr2ContextDescription` has an explicit:

```rust
unsafe impl Send for FfxFsr2ContextDescription {}
```

in `fsr2-sys/src/lib.rs`.

**Verified —** No explicit `Sync` implementation was found for `FfxFsr2ContextDescription`. Because it contains raw pointer-bearing state through `FfxFsr2Interface`, its thread traits are not simply inherited as ordinary value semantics; the explicit `unsafe impl Send` deliberately overrides part of that.

**Verified —** `FfxFsr2Context` itself consists only of `[u32; 16536]` and has no negative thread-safety marker. Its Rust representation therefore acquires the ordinary auto-traits of that array, including `Send` and `Sync`.

**Inference —** Those Rust auto-traits describe only the storage representation, not the hidden native object overlaid onto it. They should not be read as evidence that concurrent native operations on one FSR2 context are supported.

**Verified —** The native core and Vulkan backend mutate per-context/per-backend data during operation, including resource indices, registered resources, job queues, barriers, descriptor-related state, and ring-buffer indices. No synchronization primitive was identified around those mutable fields in the inspected paths.

**Inference —** `fsr2-rs` does not structurally serialize access to a context. If the old native API requires external synchronization, the binding leaves that requirement entirely to the caller.

**Unresolved —** Source inspection alone cannot determine the complete thread-safety contract. An authoritative standalone-FSR2 threading statement or native concurrency experiment is required before classifying specific simultaneous calls as supported or unsupported.

## Useful patterns for fsr-sdk-rs

**Verified —** `fsr2-rs` demonstrates the auditability benefit of keeping raw ABI declarations as ordinary checked-in Rust. Reviewers can inspect `FfxFsr2Context`, callback typedefs, resource layouts, enums, and native function signatures without running bindgen.

**Inference —** That property generalizes to raw Rust FFI: checked-in bindings can make ABI review and code review easier, particularly when paired with an exact native-source revision.

**Verified —** The project keeps the native implementation alongside the binding through a dedicated submodule/fork rather than silently binding whichever SDK headers happen to be installed on the build machine.

**Inference —** This provides a useful reproducibility pattern: the ABI definitions and the source revision they are intended to match can be reviewed together. The pattern only works reliably if both commit IDs are actually pinned and recorded.

**Verified —** The Vulkan backend's function-pointer-table mechanism isolates the binding from a particular Rust Vulkan loader dependency and from direct Vulkan loader linkage.

**Inference —** The generalizable lesson is dependency inversion at the raw boundary: opaque native handles and caller-supplied function pointers can keep a `-sys` layer loader-agnostic. The exact `FfxFsr2InstanceFunctionPointerTableVk` mechanism is specific to this fork of standalone FSR2.

**Verified —** The backend interface visibly separates application-owned device/resource handles from backend-created internal resources.

**Inference —** That separation is useful evidence for later ownership modeling, but it does not by itself specify which Rust ownership abstraction should be used in FidelityFX SDK v2.3.0.

## Patterns that should not be copied blindly

**Inference —** `Copy`/`Clone` on an opaque native context buffer is a major hazard if any later Rust layer treats the value as a unique owner. The native context contains identity-bearing resource/backend state, while the Rust derives imply ordinary value duplication.

**Inference —** Raw free functions for create/destroy do not solve exact-once destruction, failed-create state, or use-after-destroy. They expose the native ABI faithfully at the cost of leaving temporal invariants outside Rust's type system.

**Inference —** Handwriting C enums as Rust enums requires particular care. `FfxErrorCode` narrows an open `int32_t` domain, while `FfxFsr2Pass` and `FfxFsr2MsgType` use an underlying representation not explicitly specified in the native source.

**Inference —** Safe `extern fn` callback aliases can hide unsafe semantic preconditions. The absence of `unsafe` on a function-pointer type is not evidence that arbitrary callback invocation is sound.

**Inference —** An explicit `unsafe impl Send` or automatic `Send`/`Sync` on opaque storage is not a substitute for an upstream concurrency contract.

**Inference —** Raw pointer exposure makes ownership neutrality easy, but create-to-destroy pointer lifetimes become documentation-only obligations unless a higher-level wrapper encodes them.

**Verified —** The project itself acknowledges incomplete D3D12 Rust bindings. Its backend coverage should therefore not be interpreted as a general model for multi-backend API completeness.

## Comparison with our FidelityFX v2.3.0 findings

**Inference —** `fsr2-rs` is most useful as a control case for a deliberately thin raw layer. It demonstrates what is gained when Rust avoids policy and what remains unresolved when native lifecycle and pointer contracts are reproduced almost directly.

**Verified —** The old standalone FSR2 context is caller-allocated opaque storage whose contents are interpreted internally as a private context. This is an old-API property and must not be projected onto FidelityFX SDK v2.3.0 without independent evidence.

**Verified —** The old standalone backend architecture is based on `FfxFsr2Interface`, callback function pointers, an abstract device value, and optional/application-provided scratch storage. This architecture is likewise specific to the old API.

**Inference —** The general raw-FFI lesson is independent of those API details: when native creation copies a descriptor that contains pointers or interfaces used later, Rust must either encode the resulting lifetime relationship or clearly delegate it to `unsafe` callers.

**Inference —** `fsr2-rs` gains direct ABI visibility, low abstraction cost, loader/backend flexibility, and minimal semantic reinterpretation.

**Inference —** It loses structural enforcement of uniqueness, exact-once destruction, live/dead state, pointer lifetime relationships, backend/device ownership relationships, and synchronization requirements.

## Limits and follow-up

**Unresolved —** Source inspection does not prove runtime behavior. A native ABI conformance test is required to compare `sizeof`, alignment, field offsets, enum representation, and callback signatures between the Rust definitions and the exact pinned C/C++ headers. Particular targets are `FfxFsr2Pass`, `FfxFsr2MsgType`, `FfxErrorCode`, `FfxFsr2ContextDescription`, `FfxFsr2DispatchDescription`, `FfxFsr2Interface`, `FfxResource`, and the handwritten Vulkan types.

**Unresolved —** A failed-create fault-injection harness is required to answer lifecycle questions that static inspection cannot settle. Failures should be injected immediately after backend creation, during each resource-creation stage, and during pipeline creation, followed by controlled attempts to destroy the resulting context.

**Unresolved —** Double-destroy and post-destroy dispatch should be tested using the supplied backend with Vulkan validation and memory/resource diagnostics. Static source shows that Rust does not prevent these calls and that native destruction does not simply clear the entire context, but this is not proof of a specific runtime result.

**Unresolved —** Thread-safety requires either authoritative standalone-FSR2 documentation or controlled concurrent tests. The automatic Rust `Send`/`Sync` properties of the opaque context storage must not be treated as evidence about the hidden native implementation.

**Unresolved —** The exact repository and submodule commit IDs should be captured from a full Git checkout before this investigation is used as a permanent revision-pinned research artifact.

**Unresolved —** No conclusion in this record should be treated as establishing FidelityFX SDK v2.3.0 semantics. Any analogous v2.3.0 lifecycle, backend, pointer-retention, ownership, or threading behavior requires independent inspection of the v2.3.0 headers and implementation.
