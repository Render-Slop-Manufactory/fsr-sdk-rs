# Rust FFI callback and allocation practices for a FidelityFX SDK wrapper

**Investigation date / source access:** 2026-10-25 (UTC)  
**Proposed record name:** `2026-10-25-src-rust-ffi-callback-allocation-practices.md`  
**Scope:** FidelityFX SDK v2.3.0, upstream commit `60f4ea81909200d8542eca14dccb2628b763a9a3`; `fsr-sdk-sys` 0.1.2 / `fsr-sdk` 0.3.0 under development; Rust 1.88 MSRV; Windows x64/MSVC and DirectX 12 only. Research is from public online primary sources. **The SDK implementation, uploaded project archive, binary ABI, and runtime behaviour were not examined or tested.** This is a recommendation record, not an accepted design or an SDK-contract audit.

## 1. Recommended direction and dependency on native evidence

**Propose a deliberately narrow, explicitly unsafe FFI-facing interface for U04 diagnostic registration and the five no-user-data R03 DX12 callbacks; preserve faithful raw ABI exposure in `fsr-sdk-sys`.** Do not present these registrations as context-owned closures unless the pinned SDK establishes an unambiguous callback-to-registration association, a bounded lifetime, and safe replacement/removal/quiescence. A typed *unsafe* layer can still validate creation flags, check combinations, classify the five callback roles, and describe invariants without hiding native concepts. Keep effect-scoped creation debug controls and per-frame debug-view inputs in their actual native operation scopes; do not omit them merely because message registration may be module-global. [N1][N2][A1][G1]

**Treat host allocation separately.** Its supplied user-data pointer makes an owned `Box<State>` plus fixed `extern` trampolines viable *in principle*, but only if the SDK's allocation/free pairing, callback and user-data retention, invocation threads, cancellation, and failure semantics support the adapter. The first release could instead expose a documented unsafe host-allocation registration; a small owned adapter is a reasonable next increment *if* those facts are confirmed. Vulkan's explicit allocation-callback rules show precisely which extra native promises make such an adapter safe; FidelityFX has not been shown to make them. [N1][V2][A2]

**Do not tie message registration, callback-state reclamation, or unloading exclusively to a context's `Drop`.** Earlier SDK work *reports*, but has not independently established here, module-global message state and possible retention after its installing context. A module/process-level concept may therefore be needed. Several Rust runtime handles can refer to one loaded Windows DLL image: Windows increments the existing module's reference count rather than creating a separate module when the same DLL is already mapped. Different DLL paths can refer to different images. Thus “one callback per Rust runtime object” must not be inferred from the number of Rust handles. [W3][L1][G2]

**Release callback state or callback code only after positive quiescence evidence**: a native contract (and matching lifecycle ordering) that no invocation is active or can start; or an equally sound externally enforced shutdown protocol. Replacing a callback function pointer, dropping a guard, taking a mutex, or observing a successful destroy return is not *by itself* that proof. When destroy fails or ownership is uncertain, retain *exactly the still-reachable dependencies* (callbacks, state, COM owners, module handles) until a later proven safe point or process shutdown. This is exceptional containment, **not** a recommendation to leak on successful ordinary paths. The Rustonomicon specifically requires no later native callbacks before their target is destroyed. [N1][V1][L1]

**Decisions justified now:** preserve raw ABI; expose relevant U04 flags and frame controls; document no-unwind and native-thread obligations; separate host and DX12 allocator roles; ensure correct COM transfer and GPU lifetime; avoid an undocumented per-context closure or synthetic routing scheme. **Conditional decisions:** safe owned host-allocator adapters, safe diagnostic closures, safe registration guard `Drop`, and `Send`/`Sync` surface for callback-bearing objects all require further SDK evidence. [R1][R2][W1][D1]

## 3. Callback shape, identity, and registration

**Native function pointers.** A noncapturing `extern "C"`/`extern "system"` function with exactly the declared parameter and return ABI is the baseline. The raw type must not be fabricated from a Rust closure or silently transmuted. On Windows x64, Rust's `"C"` and `"system"` ABIs coincide for conventional calls, but preserve the header's intended ABI in `fsr-sdk-sys`; Rust Reference explains why `"system"` differs on x86_32. Return-by-value struct ABI is still layout-/type-sensitive: the Microsoft x64 ABI may return a qualifying small aggregate in `RAX`, while other aggregates require caller-allocated return storage passed as a hidden pointer. A *source-level* by-value struct must not be rewritten as an explicit Rust output pointer, regardless of the machine-level hidden return convention. The FidelityFX constant-buffer result needs an exact C/Rust signature and ABI comparison. [R1][A2][W4]

**Typed unsafe hooks.** A public `unsafe fn register_message_callback(raw: ... )` or an `unsafe` callback table can document a precise contract: signature, argument validity, thread affinity, reentrancy, code residency, registration conflicts, state lifetime through creation/destruction and failure, and native ownership transfers. A method accepting a *safe* Rust closure but asking the user to promise its lifetime is not safe merely because installation is syntactically convenient. The Rust API Guidelines call for documenting caller-provided invariants under `# Safety`. [N2][N1]

**Closures with native user data.** When each invocation reproduces a registration-specific pointer, a stable `Box<CallbackState>` can be passed via a raw pointer and recovered by a static callback trampoline, without changing the `Box` allocation's address. A borrowed `&T` or `&mut T` is possible only where native calls are provably bounded by its lifetime and access exclusivity; `FnMut` must not be invoked concurrently or recursively through the same unique borrow. `Box` suffices for address stability if the allocation stays owned and the pointee has no pinning-sensitive invariant. `Pin<Box<T>>` is warranted for `!Unpin` / self-referential state requiring a *pinning guarantee*, not simply because C holds a pointer. Neither `Box` nor `Pin` establishes unregistration/quiescence or thread safety. [N1][N3]

**Closures without native user data.** They require *some independent, justified* association: a single documented global registration, an explicitly unique native registration identifier, or a proven per-registration native dispatch mechanism. Merely knowing an `effectId`, thread ID, `Runtime` handle, or frame call site is insufficient. Thread-local “current context” breaks if a callback is asynchronous, nested/reentrant, or originates on a different native thread. A global map requires an actual distinguishing key; a mutex only protects the map's mutation, not correctness of routing or reclamation. Generated trampolines / a finite slot table introduce slot reuse, code-lifetime, exhaustion, and dispatch problems and are not justified by the provided SDK evidence. [G1][G2][V1][N1]

**Module/global registration:** if the SDK confirms a module-global callback, offer a module-scoped unsafe configuration method or an exclusive registration object **associated with the loaded module identity**, not an apparent per-context setter that claims independent ownership. Explicitly document last-writer-wins or reject conflicting registration according to a *verified* native model. Handles to the same loaded DLL may share global state, even when Rust runtime objects are different. A process-wide Rust singleton is *not automatically sufficient*: other Rust crate versions, third-party consumers, or native code can also register a callback. Conversely, a global Rust registry should not be constructed until it solves a demonstrated native requirement. [W3][G1][L1]

**U04 boundaries:** expose diagnostic severity/configuration and native global setters at the granularity established by SDK source, independently of create-time debug checking/visualisation controls and frame-scoped debug-view requests. For frame-scope settings, prefer checked values borrowing the frame only if native consumption is shown to be synchronous; otherwise retain their backing storage. A message callback should make **no claim** of context identity without evidence of actual routing. U04's creation, destruction, and frame operations can be exposed even when diagnostic callback registration must remain unsafe. *(Project applicability inference; SDK routes not independently audited.)*

## 4. Lifetime, replacement, teardown, and quiescence

A callback that can run during **creation** must be installed and made fully initialized before entering native creation (glfw-rs does this for initialization errors [G2]). Conversely, callback installation *performed within* a creation call needs proof about whether native code calls it before returning, including in partial-failure paths. Keep the native module, capture allocations, user data, diagnostics, and relevant device references alive whenever callbacks can execute. The supplied wrapper already retains movable families' runtime code, device and address-stable create descriptors through teardown; that invariant should extend to any installed callback state but is **not enough** to cover a genuinely module-global callback surviving context teardown. [N1][G2][L1]

A native callback registration guard is safe to drop *only* when its destructor can both (1) end future callbacks (and avoid restoring a stale previous registration over another owner's newer registration) and (2) wait for, or otherwise prove completion of, every already-started callback **before releasing target memory and code**. The guard's lifetime can be longer than any individual context. Externally synchronized teardown is a normal native requirement: Vulkan specifically disallows destroying its messenger while a callback is active [V1]. For a module-global registration with no documented removal/quiescence, do **not** give an ordinary safe RAII guard a `Drop` that unregisters and immediately frees callback state. Even a successful native unregister call might only change the pointer used for *future* dispatch. [N1][V1]

For **replacement**, distinguish a successful native setter from proof that the old user callback cannot be executing. Identify who owns the previous registration and its backing state, whether a setter returns/retains the old function, and whether configuration can be changed from callbacks. A wrapper-held mutex may serialize Rust callers but is not a native barrier; holding it during a native create/destroy/evaluate operation can deadlock when that operation synchronously invokes a callback that needs the same lock. Rust `Mutex::lock` explicitly leaves same-thread recursive locking behaviour unspecified [N5]. Prefer not holding registration/state locks across arbitrary native entry. If a stateful callback must record diagnostics, use short, bounded internal operations and a bounded queue/channel **only when** the no-allocation, no-lock-inversion and overload policies have been considered.

If creation partially fails, recover and free only what native code affirmatively did not retain. If native destroy fails, preserve the original one-attempt destroy policy and all still-reachable callback/module/device/allocator dependencies; don't retry native destroy or unload code merely to make `Drop` tidy. Possible containment options include a *recoverable* explicit failure return holding ownership, a retained failed-lifecycle object, or exceptional process-lifetime retention when the native API leaves no provably safe reclamation route. The latter must be documented and measurable, not applied on the ordinary successful path. *(Project lifecycle policy plus inference from [N1][L1]; not an observed FidelityFX guarantee.)*

## 5. Threading, reentrancy, panic, and diagnostics

- **Three distinct assertions:** an object can be *moved to another thread* (`Send`), a shared reference can be accessed from multiple threads (`Sync`), and a native callback can *actually run concurrently/reentrantly*. The first two are Rust type properties; neither proves or authorizes the third. An unsafe `Send` implementation for a callback owner needs evidence that transfer and eventual teardown are legal on the destination thread, with all dependencies transferred or synchronized. `Sync` requires demonstrable safe sharing, including callback-state mutation. Raw pointers and `UnsafeCell` intentionally prevent automatic derivation without proof. The gpu-allocator maintainer explicitly removed manual unsafe `Send`/`Sync` implementations when documented-agile windows-rs COM types made automatic derivation possible, so future field additions would be checked by the compiler. That is a concrete safer-maintenance pattern, **not** evidence that a FidelityFX callback owner is agile or synchronized. [N4][D4]
- **Local vs movable families:** the local family can support a callback bound to its owner thread *only if* native callback affinity is proven; `!Send` on a wrapper does not stop the DLL invoking a callback on a background thread. For movable families, allow transfer without allowing overlapping native use; an in-flight callback or native use must complete before transfer/destruction. Do not attach `Send + Sync` to diagnostic or allocator closures as decoration: bounds should express required sharing, and internal synchronization does not establish native thread safety. [N1][N4][V1][G1]
- **Reentrancy:** default to a restrictive documented callback policy: do not call the same runtime/context from a callback and do not reconfigure callbacks from within callbacks unless native sources explicitly permit it. Avoid holding wrapper locks over native calls; make sinks minimize blocking, allocation, and potentially recursive logging. A `Fn(&Event) + Send + Sync` sink supports safe concurrent *Rust* access only if its implementation meets its bounds; it still needs a native-thread and recursion policy. [N5][V1]
- **Unwinding:** callbacks to a non-unwinding ABI **must not unwind**. For wrapper-provided trampolines, surround user code with `catch_unwind(AssertUnwindSafe(...))` where its unwind safety has been reviewed, and perform only ABI-valid fallback behavior. On panic, mark a poison/disabled state, optionally queue a nonblocking failure report, and return a defined native-compatible value if one exists; **do not automatically resume the panic through FFI**. For an `extern "C"` callback that panics outwards, Rust aborts safely; `catch_unwind` catches only *unwinding* panics and cannot save `panic=abort` programs. An unwinding panic payload's destructor can itself panic; avoid invoking user code or allocating/logging in a panicking fallback where possible. Foreign C++ exceptions are not safely dealt with by indiscriminate `catch_unwind`. [R2][N1][N6]
- **Error channels:** a `void` diagnostic callback has no native `Result` channel. Log/copy, drop with a measurable counter, or stage an error for an **explicit later** read; none retroactively fails the native operation. For DX12 callbacks returning HRESULT, pointer/null, or a restricted struct, map failures only to **documented** legal return values. If the SDK supplies no defined failure encoding, a Rust `Result` from the callback must not be silently fabricated into a valid output. A deliberate abort on violation can be safer than returning invented COM objects or malformed handles; that is a documented policy choice, not graceful recovery. [N6][D2]
- **Windows messages:** treat an incoming UTF-16 pointer as a transient borrowed buffer. First establish pointer validity, nullability, termination or explicit length, and maximum safe extent from the SDK callback signature/contract; make an owned `Vec<u16>` or `String` *before* callback return or enqueue. `String::from_utf16` yields a decoding error on malformed UTF-16; `from_utf16_lossy` replaces invalid units. Preserve raw units when exact diagnostics matter. The native GLFW case independently illustrates why transient message buffers cannot be held past return; it is UTF-8, **not** a FidelityFX encoding precedent. [R3][G1]

## 6. Custom host and DX12 allocation boundaries (R03)

**Host allocation** must use the exact native protocol—not automatically `GlobalAlloc`'s Rust interface. `std::alloc::Layout::from_size_align` rejects zero/non-power-of-two alignment and overflowing layouts; `GlobalAlloc` requires matching deallocation layouts and does not allow unwinding. These Rust rules help implement a policy but do not prove the SDK's zero-sized request, size/alignment origin, null result, allocation scope, or free callback behaviour. In particular, if a native deallocator receives only a pointer, a Rust allocator requiring `(ptr, Layout)` needs reliable size/alignment metadata stored by the adapter or supplied externally; mixing CRT heaps, `new/delete`, `HeapAlloc`, and Rust allocators across alloc/free is invalid without a documented compatible pairing. Decide how `NULL` is interpreted only after checking the SDK; Vulkan explicitly defines it for *Vulkan*, not FidelityFX. [N7][N8][V2]

**Required host allocator invariants (proposed):** the same backend frees its own pointers; each live block remains allocated and suitably aligned; state and callback function code stay valid until its final matching native free; size-zero/null/invalid-alignment cases have explicitly defined behaviour; outstanding allocations can outlive a creating context if the SDK retains them; cancellation/partial-create failure does not incorrectly free native-owned blocks. An owned Rust adapter may expose a small trait returning `Result<NonNull<u8>, AllocError>` internally, but it must map that result through the *actual native return type* without panicking. If the native failure protocol does not permit null, refuse a supposedly safe fallible adapter or document abort-on-exhaustion. Avoid casually using an arbitrary global Rust allocator callback to recursively invoke the same allocator. Vulkan's specification supplies an unusually complete example: it documents user-data forwarding, compatible create/destroy allocators, same-thread synchronous calls, null return/OOM behaviour, and callback lifetime [V2]; no such FidelityFX assurances are established here.

**DX12 callbacks:** keep the **five roles explicit**—resource allocation/free, heap allocation/free and constant-buffer allocation—even if a future typed adapter groups them. Native role signatures (including the return-by-value constant-buffer structure) define the exposed unsafe function-pointer types. Without general user data there is no automatically sound per-renderer captured allocator object. A small adapter may safely normalize return HRESULTs/COM types and owned payload slices **only if** all ownership and routing guarantees are documented. Otherwise expose an unsafe native callback table with typed descriptions of sizes, resource descriptors, COM pointers and error semantics. Never misinterpret the constant-buffer callback's `data` as user state: it is payload bytes under the supplied constraints. *(SDK constraints supplied, not independently verified.)*

**COM transfer:** clarify separately for *every* role whether returned `ID3D12Resource`/`ID3D12Heap` is a borrowed interface pointer (native code must `AddRef` before retaining it), an owned reference transferred to native, or a wrapper-retained resource with native use. Use `Interface::as_raw` only for borrowed access and `into_raw` only for intentional transfer; recreating a Rust owner with `from_raw` without owning a reference risks double `Release`, while forgetting transfer leaks. Exact semantics require native source inspection. The `windows-core` pattern is evidence of the distinction, **not** evidence of what FidelityFX expects. [W1][W2]

**Lifetime beyond COM:** keeping a heap object alive does not prevent an allocator reusing the same heap range; keeping a resource interface alive does not synchronize the GPU. `gpu-allocator` specifically forbids freeing a suballocation while its placed resource exists, and Microsoft's `CreateCommittedResource` notes the GPU must be finished reading/writing before the last resource reference is released. For constant buffers, copy exactly the documented `data` payload size to durable upload storage if native code may outlive the call; ensure alignment, any required map/upload visibility, descriptor/GPU-address and resource/binding lifetime extend through GPU completion. A returned by-value descriptor can contain pointers/handles whose backing allocations must remain valid independently of the temporary result struct. Leave pooling, suballocation, residency decisions, GPU submission, frame scheduling and completion fences to the renderer. [D1][D2][D3]

**OOM stance:** `Result` and `E_OUTOFMEMORY` work for API operations with documented error returns; they cannot be assumed for FidelityFX's callbacks. Report and record failures where the native channel permits, otherwise choose an explicit containment/abort policy rather than promising recovery. The Vulkan allocator's `NULL`/`VK_ERROR_OUT_OF_HOST_MEMORY` path and DX12 `CreatePlacedResource` HRESULT are **comparisons**, not a FidelityFX callback failure contract. [V2][D2][N7]

Raw exposed via `fsr-sdk-sys` only** | Exactly correct ABI; caller maintains code/state, COM refs, thread discipline and teardown. | Caller installs/uninstalls through SDK; no managed guard. | Both, but safety entirely external; no inferred `Send`/`Sync`. | Caller must prevent unwind and use native error codes. | Minimal; no dependency; MSRV compatible. | Essential escape hatch, but insufficiently descriptive for `fsr-sdk` ownership goals. |

Per-context closure registry, TLS dispatch, slots or generated trampolines** | An injective routing key or explicit synchronous thread-affine invocation, safe slot reuse, registration drain, and predictable native dispatch. | Registry entries/code survive every native path; collisions, overwrite and hot reload managed. | Hard for multiple contexts/handles; async, concurrency and recursion invalidate naive TLS. | Additional lock/reentry/panic paths. | High; may introduce dependencies, executable-memory/security issues, or unsupported assumptions. | **Not recommended** absent strong new evidence. |

A minimal illustrative signature (not verified against the FidelityFX headers) is `unsafe fn configure_module_diagnostics(&Module, RawMessageCallback) -> Result<(), RegistrationError>`: the `unsafe` obligation includes callback code residency, exclusivity with other native consumers, reentrancy and quiescence before reclamation. A separate illustrative `unsafe fn with_dx12_callbacks(&mut CreateInfo, RawDx12CallbackTable)` makes the callback table and its native lifetime explicit. An owned host adapter could be `HostAllocatorRegistration::new(Box<dyn HostAllocator + Send + Sync>)`, but **only conditionally**; this sketch does not imply that the callbacks are actually threaded arbitrarily, that `Send + Sync` is necessary/sufficient, or that a sound registration `Drop` exists.

Recommended sequencing is **B plus A** for diagnostic and all five DX12 callback routes; preserve explicit U04 debug flags/per-frame requests; investigate C for host allocation; postpone D and decline E until evidence demands it. None of A–E establishes a native callback guarantee by itself. The wrapper should document separately which operation can be called safely, which installation is `unsafe`, and which creation/evaluation operations inherit the installed callback's unsafety.

## 8. Qualifications to the supplied baseline

1. The module-global message callback, retention beyond installing context, and effect-declaration/routing discrepancies are **previously reported hypotheses**, not reverified findings of this study. They warrant conservative interfaces and a native investigation, not assertions about all SDK builds or closed providers.
2. `effectId` is *not* established as a unique context identifier. Treat per-context dispatch as an unsolved association problem; multiple contexts and multiple Rust handles sharing one module make wrong attribution especially likely.
3. The DX12 constant-buffer `data` argument is **payload**, and the callback returns a **struct by value**. Do not convert either into user data or an out-pointer without exact ABI evidence.
4. A Rust movable runtime owner demonstrates permitted *transfer*, not native overlapping use, callback concurrency, COM apartment compatibility, or safe reentrant destruction. [N4][W1]
5. A stable boxed allocation does not promise pinned-state invariants or end native access. `Pin` is no substitute for a shutdown protocol. [N3][N1]
6. A `catch_unwind` wrapper improves *unwinding-panic* containment; it cannot promise error recovery in `panic=abort` configurations or catch arbitrary foreign exceptions. [N6][R2]
7. Windows `LoadLibrary` handle count is not a callback-registration namespace: repeated loads of the already loaded module share one image and its static data. [W3]
8. COM `Release` and an allocator's successful `free` are distinct from completing GPU work. Native resource ownership needs an explicit fence/completion relationship maintained by the renderer. [D2][D3]

| P0 | For host allocators, where is user data retained, how long after context failure/destroy can alloc/free occur, and what calls/signatures provide size/alignment and matching frees? Determines safe owned-box adapter and allocation metadata. |
| P0 | What precisely does native code do on null host memory, missing resource/heap, callback HRESULT failure, constant-buffer allocation failure, or callback exception? Include closed-provider paths and partial initialization. Determines whether `Result`, null, HRESULT or abort is sound. |
| P1 | Are debug-checking/visualisation flags actually routed per effect/context, and where are per-frame debug-view options consumed? Do any pointers escape the frame call? Determines safe checked debug inputs independently of registration. |
| P1 | Are callbacks serialized, concurrent, recursive, or invoked from worker threads? Is it legal to call SDK functions from within them? Determines `Send`/`Sync` and deadlock policy. |
| P1 | If DLL handles share an image, do SDK function tables and global callbacks also share static state across handles? Could independent copies of the same DLL be loaded simultaneously? Determines registration conflict domain. |

### Focused validation tasks — proposed only; **none run**

1. **Header/ABI audit** against the pinned SDK headers, raw Rust types and MSVC x64 struct-return rules: widths, packing, `extern` ABI, nullability and all five DX12 returns. A **controlled C/C++ ABI fixture** may be needed specifically for the constant-buffer by-value return and COM parameter ownership shape.
2. **Source call-graph trace** for U04 registration, callback dispatch, debug flags and frame requests, plus five DX12 callback invocation paths; record closed-provider blind spots rather than filling them by assumption.
3. **Controlled runtime fixture**, if source insufficient: two contexts on one runtime, then separate runtime handles to one DLL image; test message attribution, replacement, creation failure, destruction, nested diagnostics, and registration survival. Do not extrapolate fixture observations to every closed provider.
4. **Callback lifecycle/concurrency fixture** with barriers: callbacks active during removal/destroy, callbacks from another thread, reentrant calls, and failed destroy. Never deliberately dereference freed state to “test” safety; use guarded logging/instrumentation and stop before undefined behaviour.
5. **Allocator/COM fixture**: instrument size/alignment, null/zero requests, alloc/free pairing, addref/release counts and GPU-completion ownership, and deliberately injected allocation failures through documented paths. Verify both host and DX12 return channels without claiming graceful OOM support unless observed and specified.
