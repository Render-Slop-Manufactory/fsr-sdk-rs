# SRC — M10: Safety boundary of the five DX12 upscaler queries

**Date of investigation:** 2026-10-12 · **Method:** source analysis only · **Status:** research findings, **not** an adopted design decision or authorization to implement.

## Question, baseline, and exact inputs examined

Is the following extension of `fsr-sdk` defensible as a *safe* Rust API on top of an AMD runtime already acquired through an `unsafe` operation: `Runtime::upscaler_providers_dx12(&mut self, device: &ID3D12Device) -> Result<Vec<ProviderInfo>, Error>`, `Runtime::estimate_upscaler_memory_dx12(&mut self, device: &ID3D12Device, options: &UpscalerOptions) -> Result<GpuMemoryUsage, Error>`, and `Upscaler::{provider,resource_requirements,gpu_memory_usage}(&mut self) -> Result<…, Error>`, with the same five operations on `MovableRuntime`/`MovableUpscaler`? The assumed design has private result fields and getters, *immediate* copying of names, opaque provider IDs, preservation of unknown resource bits, and **no** provider override, quality, or jitter API.

## Direct primary-source findings

### 1. Names, IDs, and enumeration

1. **Verified (ABI):** `ffxQueryDescGetVersions` contains `createDescType`, `void* device`, `uint64_t* outputCount`, `uint64_t* versionIds`, and `const char** versionNames`; `outputCount` is an input capacity and an output count; a zero input requests counting ([`ffx_api.h` L85–106](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/ffx_api.h#L85-L106)). The live `ffxQueryGetProviderVersion` contains `versionId` (zero denotes invalid) and `versionName` (`nullptr` denotes an invalid query). The structure describes a name *for display*, not an explicit ownership or lifetime guarantee for that name.
2. **Verified (generic routing):** The count operation is a special case of `ffxQuery(nullptr, …)`: the `*outputCount == 0` or both-arrays-null branch invokes `GetProviderCount`; otherwise a local `capacity = *outputCount` is passed to `GetProviderVersions`. The generic branch returns `FFX_API_RETURN_OK` in either case ([`ffx_api.cpp` L102–121](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_api.cpp#L102-L121)). **Verified (implementation):** `GetProviderVersions` writes only while `count < capacity` and returns the number **written**, not necessarily the total number now available; IDs and names are sorted together within the same query when IDs are requested ([`ffx_provider.h` L163–169, L184–239, L241–271](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_provider.h#L163-L271)). If the provider set grows between count and fill, `OK` may accompany a **fully populated but truncated** list. If it shrinks, fewer array slots are populated; uninitialized slots must not be interpreted.
3. **Verified (internal provider):** `ffxProvider` stores `const char* VersionName` and returns that pointer from `GetVersionName`; the open FSR3 upscaler supplies a compile-time concatenated string literal ([`ffx_provider.h` L29–52](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_provider.h#L29-L52), [`ffx_provider_fsr3upscale.cpp` L53–61](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr3upscale.cpp#L53-L61)). Here the name is NUL-terminated and remains valid for the relevant module lifetime. **Verified (external enumeration):** Generic DX12 code has **`static char extProviderName[64]`**; its comment explains that the original external name may reside in a DLL that does not outlive the caller, and it copies the name using `strncpy_s`. The returned pointer therefore addresses **this reused global buffer**, not owned string storage ([`ffx_provider.h` L166–169, L210–220](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_provider.h#L166-L220)). The `strncpy_s` operation accounts for ordinary termination **given a valid external input string and normal return**, but does not prove that *every* pointer supplied by an external provider is valid or establish behavior for overlength/invalid input.
4. **Upstream claim:** AMD explicitly warns that names stored globally may be overwritten by later version queries and warns against pairing IDs and names obtained from **different** calls; copy names immediately and request IDs and names together ([API docs L205–231](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/docs/getting-started/ffx-api.md#L205-L231)). **Inference:** Copying **before any further native query and while effective shared CPU serialization is held** addresses subsequent invalidation; it does not guard against an unsynchronized foreign writer to the global C buffer, or against a pointer that is already invalid or unterminated.
5. **Verified (live routing):** With an existing context, `ffxQuery` calls its associated provider; when it receives `ERROR_UNKNOWN_DESCTYPE`, `ffxQueryFallback` answers `GET_PROVIDER_VERSION` using the provider's `GetId()` and `GetVersionName()` ([`ffx_api.cpp` L151–163](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_api.cpp#L151-L163), [`ffx_query_fallback.cpp` L186–199](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_query_fallback.cpp#L186-L199)). **Inference:** The open FSR3 provider's live pointer remains readable during a valid context/provider lifetime. **Unresolved:** A closed provider could return a different, temporary, or otherwise invalidatable pointer; the public interface states **no universal invalidation or termination guarantee** for the live name. `CStr::from_ptr` nevertheless requires a readable, NUL-terminated pointer. Even a bounded scan cannot make an invalid address safe to read. This is a **native trust assumption**, not something `Result`, `&mut`, or `String::from_utf8_lossy` can repair. Never publish opaque IDs as a numeric, ordered, or interpretable version scheme; zero is explicitly invalid at least for the live query.

### 2. Query pointers, devices, and retention

1. **Upstream claim:** AMD describes queries as writing results to caller-supplied output addresses. Only specified query types work without a context, including GetVersions and GPU Memory V2; `GET_PROVIDER_VERSION` requires a valid instance. For V2, the documentation instructs setting `device`, dimensions, `flags`, and output pointer **before calling** the query ([API docs L83–161](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/docs/getting-started/ffx-api.md#L83-L161); [`ffx_upscale.h` L169–200](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/include/ffx_upscale.h#L169-L200)). **Important distinction:** `ffx_api.h` explicitly requires pointers referenced by a **Create** `desc` to remain valid until `ffxDestroyContext` ([L120–140](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/ffx_api.h#L120-L140)). This is **not** a positive no-retention guarantee for queries, and the Create rule cannot simply be transferred to them.
2. **Verified (visible paths):** GetVersions reads the device/capacity and writes count/arrays synchronously inside `ffxQuery`; GetProviderVersion writes a pointer directly into the descriptor. The open FSR3 provider processes Memory V2, live memory, and resource masks directly: it checks for a null output, zeroes the memory output first, delegates live memory to `ffxFsr3UpscalerContextGetGpuMemoryUsage` and V2 to `ffxFsr3UpscalerGetGpuMemoryUsage`, and writes masks into the descriptor ([`ffx_provider_fsr3upscale.cpp` L193–305](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr3upscale.cpp#L193-L305)). For **these inspected open** paths, there is no observable retention of query descriptor, output address, or V2 device beyond the CPU call.
3. **Verified (FSR3 host and DX12):** V2 calculates resource descriptions and requests sizes from the supplied device; the DX12 backend uses `QueryInterface`/`GetResourceAllocationInfo` and `Release` within the call ([`ffx_fsr3upscaler.cpp` L1128–1187](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_fsr3upscaler.cpp#L1128-L1187); [`ffx_dx12.cpp` L1120–1185](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L1120-L1185)). Live memory invokes a backend function that copies `effectContext.vramUsage` from backend CPU structures ([`ffx_fsr3upscaler.cpp` L1115–1126](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_fsr3upscaler.cpp#L1115-L1126), [`ffx_dx12.cpp` L1108–1119](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L1108-L1119)). This is **not** merely a guaranteed immutable value: backend/context state is read. V2 `flags` are not forwarded into the calculation in the inspected FSR3 call, so do not promise universally flag-sensitive estimates. Notably, the V2 function accesses `resources[i]` rather than `sharedResources[i]` in the `sharedResources` loop ([FSR3 L1166–1184](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_fsr3upscaler.cpp#L1166-L1184)); consequently the numerical estimate cannot be interpreted as an exact allocation guarantee.
4. **Unresolved (closed providers):** The publicly visible `ffxQuery` contract does not explicitly prohibit a closed/driver provider from retaining a descriptor, output pointer, device, or derived addresses; using other threads; or reading those addresses later. The open FSR3 paths support the conventional pattern of synchronous stack descriptors but establish **no universal absence of retention**. **Inference:** Safe queries backed by stack outputs and a briefly borrowed DX12-device reference are defensible only if the **already unsafe** runtime-acquisition contract explicitly extends to query-specific non-retention and COM/thread/pointer validity for supported providers. Acquiring an additional COM reference only for the query protects against early destruction **during the call**, not against hypothetical retention afterward.

### 3. CPU and GPU synchronization; dispatch poison

1. **Verified (project):** `Runtime::load_unchecked` and `MovableRuntime::load_unchecked` are unsafe, with continuing obligations concerning trusted dependent providers, native coordination, non-reentrancy, and lifetimes; see D008 L49–85, `runtime.rs` L129 onward, and `runtime/movable.rs` L28 onward. Local `Runtime`/`Upscaler` are `!Send + !Sync`; the optional movable types are `Send + !Sync`. An `Upscaler` retains its context, its own COM device reference, and the runtime until terminal teardown: `upscaler/dx12.rs` L31–125 and `context.rs` L37–115. At present, `query.rs` contains only an SPDX header; `runtime/state.rs` L96–109 provides **only a test-gated** query path; `fsr-sdk-sys::loader/windows.rs` L241–256 exposes a raw unsafe query; `sys/api.rs` has GetVersions, whereas `sys/upscale.rs` has **none** of the three M10 upscaler-query descriptors. Thus the five safe methods are **not implemented** in the supplied project.
2. **Verified (CPU):** `&mut self` excludes aliasing/concurrency **on that particular Rust object**, not among distinct sibling `Runtime`/`Upscaler` objects, foreign FFX callers, or separate movable owners. D013's shared synchronization domain must cover queries, *copying global names*, dispatch, create/destroy, drop/unwinding, and final DLL unload. CPU happens-before at thread transfers remains an obligation. Local types prevent transferring the wrapper between threads but do not automatically prevent external reentrancy or native workers. **Inference:** A lock around only the first enumeration call, followed by unprotected reading of the global name buffer, is insufficient; suitably coordinate the **entire two-pass operation including copying**. Because the C buffer is static/global, unsynchronized enumeration by a foreign caller could even cause a native data race.
3. **Verified (GPU, open paths):** None of the five inspected open query paths takes a command list or records a GPU dispatch. FSR3 resource masks are fixed CPU-side assignments; the live-provider query reads ID/name; live-memory reads CPU backend accounting state; V2 uses DX12 allocation information. **Inference:** These facts do not establish a blanket requirement to fence every previous GPU operation before every query for the **inspected, CPU-serialized** FSR3 paths. Enumeration in particular is not equivalent to teardown. **Unresolved:** Closed providers may have hidden GPU activity, internal state sharing, interactions with GPU work in flight, particular threading requirements, or asynchronous internal access. Neither CPU `&mut self` nor a mutex/join acts as a GPU fence; conversely, a GPU fence does not prevent a CPU data race. The existing *unsafe dispatch* policy in D011 (caller owns submission, resource states, and GPU completion before destroy; **no** wait after every successful dispatch) does not automatically prove additional queries safe while GPU work is in flight. A further *query-specific* native trust/compatibility assumption is needed; alternatively, require GPU quiescence before live queries as a conservative integration contract. Quiescence alone does not prove safety with arbitrary providers. If that assumption cannot be included in `unsafe load_unchecked`, the affected queries cannot responsibly be advertised as unconditionally safe methods.
4. **Verified (poison):** Native dispatch failures set `dispatch_poisoned` in the shared `UpscalerCore`; later dispatch calls all return `Error::DispatchPoisoned`, while destroy remains possible (`dispatch_policy.rs` L9–28; `upscaler/dx12/dispatch.rs` L104–120; D011). **Unresolved:** AMD does not say all queries remain safe after a failed dispatch. **Inference / recommendation:** Reject **all three live queries** when poisoned, *before FFI*, using the existing poison category; the two runtime-level queries are not context-bound and may remain available subject to the normal family-wide coordination rules. D011 does not cover poisoning on query failure, which must not automatically be treated as a dispatch failure: an ordinary query error preserves context/dispatch eligibility **provided** that the defined native query-trust contract supports continuation. Reconsider the policy if concrete evidence shows a query corrupted a context.

### 4. Errors, invalid successful outputs, and bitfields

1. **Upstream claim:** Every non-OK return code is an error, including unknown future codes ([API docs L249–254](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/docs/getting-started/ffx-api.md#L249-L254)); generic codes 0–7 appear in [`ffx_api.h` L29–39](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/ffx_api.h#L29-L39). **Verified (project):** `Error::Native { operation, code }` preserves a `u32`, but `Operation` currently has only Create, Destroy, and Dispatch (`error.rs` L5–15, L125 onward). **API change:** Add `Operation::Query` (possibly finer-grained query kinds), as well as explicit errors for invalid successful query outputs and enumeration/capacity overflow. Never obscure the original native error code with a null or fallback output value.
2. **Verified:** For unsupported live `GET_RESOURCE_REQUIREMENTS`, `ffxQueryFallback` writes `~uint64_t(0)` into both masks and returns `FFX_API_RETURN_PROVIDER_NO_SUPPORT_NEW_DESCTYPE` ([`ffx_query_fallback.cpp` L186–208](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_query_fallback.cpp#L186-L208)). The null-context fallback also uses all-ones masks; however, its test at L127 compares `header->type` to an **error code** rather than `retCode`, so the intended error-code rewriting is not generally guaranteed along that path ([L120–138](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_query_fallback.cpp#L120-L138)). **Rule:** Check the return code first and **never** expose error-path all-ones masks as valid resource information. `FFX_API_QUERY_RESOURCE_*` defines six known bits, but the ABI returns `u64`; preserve unknown bits **unchanged** ([`ffx_upscale.h` L185–200](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/include/ffx_upscale.h#L185-L200)). Do not blindly reject unknown bits with `from_bits`, and do not assume identical masks or exposure rules across providers.
3. **Inference (validation):** Before each query, supply **valid, initialized** C descriptors and all `type`/`pNext`/output fields; AMD explicitly describes an incorrect `type` as UB ([API docs L29–42](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/docs/getting-started/ffx-api.md#L29-L42)). After non-OK, do not interpret outputs. After OK, outputs must be **initialized**: never read uninitialized slots or `MaybeUninit` contents. Preinitializing outputs to valid null/zero values, however, cannot reliably distinguish **unwritten** output from a legitimate zero. GetProviderVersion: reject `id == 0` or a null name on success as inconsistent. GetVersions: check the reported count is `<= capacity` and within the number of allocated slots; every used name pointer must be non-null and valid/terminated under the native-trust assumption. Memory: copy the two `u64` size values; do **not** reject zero universally, and apply a supposed invariant such as `aliasable <= total` only if its normative semantics have been established. Resource requirements: preserve raw `u64` required/optional masks; validate possible semantic contradictions (for example overlapping required/optional bits) only as an explicitly documented policy, never silently discard bits. A finite C-string scan limit cannot by itself guarantee pointer validity and is a separate representation/size policy to document.
4. **Inference (two-call enumeration):** (a) Request count using the `device`, correct Create tag, and null arrays, checking the return code; (b) perform checked `u64 -> usize` conversions, use `try_reserve`/a capacity limit to avoid allocation DoS, and allocate equally sized, **initialized** ID and pointer arrays; (c) fill using the **input capacity**, not treating count as an immutable output, and inspect the separately returned element count; (d) convert only slots actually filled after OK and copy names **immediately, before the next FFX operation**; (e) `returned_count < capacity` is consistent with shrinkage, so truncate accordingly; `returned_count == capacity` may mean the exact list fits **or** that it has grown and was truncated since the first pass. If completeness is a requirement, perform only a bounded count/fill retry and return a specific `Err` for instability, rather than silently claiming a complete `Vec`; even unchanged counts do not preclude changes in provider identity. If count is zero, return an empty `Vec`. No unbounded retry loop or automatic hard-coded provider-version selection. **Unresolved:** AMD provides no transactional snapshot operation across two calls, so absolute completeness and identity stability cannot be established from this ABI.

## Assessment of each proposed method

| Method (including the corresponding `Movable*` variant) | What the wrapper itself can enforce (**Verified** existing state / **Inference** M10 proposal) | Already covered by existing obligations | Additional assurance/policy or API change required | Assessment |
|---|---|---|---|---|
| `Runtime::upscaler_providers_dx12(device) -> Vec<ProviderInfo>` | Correct count/fill descriptors; retain devices during calls; request ID and name together; checked allocation; only process populated slots; copy names into owned storage immediately; preserve opaque IDs and keep library loaded. | **Verified:** `unsafe load_unchecked` trusts the native runtime and family-wide coordination; local types are thread-bound and movable types use the shared domain. | **Unresolved:** readable, NUL-terminated C names for *all* selected providers and no retention; serialize global-name access through the copying step; define snapshot/capacity policy and errors; extend acquisition-time trust to queries. | **Conditionally defensible**; do not promise unconditionally pure, thread-neutral getter semantics. |
| `Runtime::estimate_upscaler_memory_dx12(device, &options) -> GpuMemoryUsage` | Use the V2 null-context query with a valid device; validated nonzero maximum dimensions from `UpscalerOptions`; `flags = 0`; initialized `FfxApiEffectMemoryUsage`; exact native error codes. | **Verified:** D008's numeric trust for `u32` inputs and DX12 device; runtime retention; construction-like validation criteria, but a different query path. | **Unresolved:** query-specific size arithmetic and non-retention of query device/outputs in closed providers; D008 does **not automatically** cover V2. Document as an **estimate**, not an allocation/dispatch guarantee, and extend native query trust explicitly. | **Conditionally defensible**; relatively limited context/GPU exposure, but not without query-specific trust. |
| `Upscaler::provider() -> ProviderInfo` | Keep context/provider alive through ownership; copy ID/name; reject successful results with `id == 0` or null name; expose no foreign raw handle. | **Verified:** D008/D013 ownership and native serialization; open FSR3 + fallback directly provide the ID and a static literal name. | **Unresolved:** validity, termination, and stability of an external live name while copying; specify this trust. **Inference:** block before FFI after dispatch poison (conservative). | **Conditionally defensible**; copying by itself does not establish soundness. |
| `Upscaler::resource_requirements() -> ResourceRequirements` | Use the correct live descriptor; copy both `u64` masks including unknown bits; check errors before interpreting masks; no device parameter needed. | **Verified:** context retention; open FSR3 returns fixed masks; fallback can signal lack of support. | **Unresolved:** closed live queries with GPU work in flight; trust concerning context state, a poison check, and no retroactive implicit validation of required resources for prior dispatches. | **Conditionally defensible**; the FSR3 path is the clearest, but no universal mutation/GPU independence guarantee. |
| `Upscaler::gpu_memory_usage() -> GpuMemoryUsage` | Stage output, check error code, retain context, enforce CPU exclusivity, and describe results as a snapshot. | **Verified:** context/backend remain until destroy; D011 assigns GPU-lifetime obligations to the caller; FSR3 reads CPU backend accounting state. | **Unresolved:** foreign providers and concurrent backend/GPU activity; this is the **strongest live-query synchronization/trust concern**. Consider restricting integration to GPU-quiescent measurement points. Apply poison check. `Result::Ok` does not prove GPU completion. | **Conditionally defensible**; no blanket permission to query arbitrarily while GPU work is in flight. |

All five movable-family methods use shared internals, **without** an implicit mutex. Their `Send + !Sync` is an *a priori* property accepted under `unsafe MovableRuntime::load_unchecked` for every actual execution/cleanup-thread combination, **not** an additional threading guarantee obtained from query names or backend behavior. A shared core must not accidentally make local `Rc`-based owners `Send` or mix different runtime families.

## Changes relative to earlier findings and implications

- **Confirmed/refined** relative to `2026-09-22-src-m5-upscaler-query-configure.md`: null/live contexts, the five query categories, global enumeration names, provider selection, and API versions. **Newly verified directly:** the exact `static char[64]` buffer, sorting of jointly requested IDs/names, truncation at `capacity`, absence of snapshot semantics, fallback `~0` masks including the suspicious null-context fallback code comparison, and the live-provider name through `GetVersionName`.
- **Examined in greater depth:** The FSR3 V2 path uses direct device allocation information; the live-memory path **reads backend state** (`effectContext.vramUsage`), not GPU fences. The missing visibility concerns the external provider, not the inspected open FSR3 loop. Ignored flags and the `resources[i]` access in FSR3 V2 estimation limit claims about numerical accuracy.
- **New for M10:** `query.rs` is empty, M10 query descriptors are missing from `fsr-sdk-sys`, the internal production-query path is absent, and `Operation::Query` does not exist. These are **implementation/API gaps**, not intrinsically external soundness blockers. D011 poison blocks **only dispatch**, so safe live queries require a deliberate eligibility policy. D008's safe construction and D013's `Send` trust **do not automatically cover query-specific pointer/GPU assumptions**.

## Open questions, narrowly scoped possible follow-up, and source access

**Unresolved — closed providers:** The DX12 external-provider classes and driver/signed-provider implementations were not available as open primary sources for this review. The path `Kits/FidelityFX/amdinternal/api/internal/dx12/ffx_provider_external.h`, included by `ffx_provider.h`, returned **404 / was not publicly accessible** at the pinned GitHub raw URL on 2026-10-12; checking the corresponding `.cpp` also returned 404. Therefore no universal proof exists here of NUL termination or a valid copying window for driver names, query non-retention, absence of native synchronization concerns, internal workers, behavior with in-flight GPU work, error consequences, or provider teardown. Signed DLL internals were **not** disassembled or executed. An initially attempted `sdk/include/FidelityFX/api/ffx_api.h` URL returned 404, but the **correct pinned source** `Kits/FidelityFX/api/include/ffx_api.h` was subsequently opened successfully. The ZIP was locally accessible. Additional direct GitHub raw network access from the container failed due to DNS; the pinned primary sources were instead read through the browser. No current `main` or newer-version source was used in the findings.

**Inference — possible narrow follow-up work (explicitly not performed):** A *static* audit of any specifically obtainable closed-provider source, or an explicit AMD statement concerning query retention and synchronization, would be the appropriate source of general guarantees. Bounded Windows-native fixtures could test **specific experimentally decidable behavior**: count/fill under a controlled change in provider list, name-buffer overwriting after a second enumeration, returned codes/masks, live queries with fenced versus in-flight GPU workloads, and thread-sanitizer/debug-layer anomalies. Such observations might uncover bugs or justify an integration restriction, but **cannot prove general** pointer validity, no-retention, concurrency, or GPU safety for other providers, drivers, or releases. No test was performed here, and no proposed test is to be mistaken for proof merely because it passes.

**Research judgment (Inference):** None of the five methods is established as an unavoidable soundness blocker *merely because upstream documentation is silent*; conversely, a positive inspection of open FSR3 code cannot establish universal safety. A **safe** surface is **defensible as an explicitly conditional extension of the existing unsafe acquisition boundary**, *if* the maintainer accepts query-specific native-trust obligations for the supported signed providers and GPU states, specifies enumeration/string and error/poison policy, and avoids new guarantees about foreign-provider safety, exact memory estimates, or GPU quiescence. If that additional trust assumption is rejected, `unsafe` query methods, a narrower GPU-quiescent usage contract, or deferring individual queries are more consistent API alternatives. **This research assessment does not replace an ADR or maintainer design decision.**
