# AMD's 20 October 2026 Vulkan announcement: implications for `fsr-sdk-rs`

- **Record date / evidence cut-off:** 2026-10-23 (Europe/Berlin; public-source checks performed on this date).
- **Intended repository destination:** `docs/research/records/2026-10-23-src-amd-fsr-vulkan-announcement.md`.
- **Record type:** `src` — source and architectural investigation, **not** a native Vulkan experiment, accepted design decision, or release verification.
- **Project baseline:** `fsr-sdk` development `0.3.0`, `fsr-sdk-sys` development `0.2.0`; AMD FidelityFX/FSR SDK **v2.3.0**; verified native configuration Windows x64/MSVC + DX12. Snapshot supplied as `fsr-sdk-rs-main(45).zip`, archived 2026-10-22; no `.git` history was supplied. Its top-level archive comment is `9fde078492715fa378f1c798c2ed5692775ff5b7`, **not independently verified as a Git commit**.
- **Disposition:** Research only. No repository files, Cargo features, pinned SDK version, accepted ADRs, runtime binaries or implementation were changed.

## Research question and decision boundary

What did AMD actually announce on **20 October 2026** about Vulkan support for FSR; what *usable native developer interface* exists on **23 October 2026**; and what evidence would justify resuming B01 without confusing an announced SDK capability with a released, ABI-reviewed and GPU-tested backend?

This record distinguishes (1) announced developer Vulkan integration, (2) driver-side FSR model/provider availability, (3) third-party Vulkan interoperation, and (4) native Linux support. It covers FSR Upscaling first; other FSR effects are examined only to establish whether they were included in the Vulkan commitment. **No Windows, Linux, Vulkan, SDK 2.4 or physical GPU experiment was conducted for this record.**

**Evidence vocabulary:**

- **Verified:** An identified primary source or the supplied repository snapshot directly establishes the *source fact*. It does **not** imply GPU execution.
- **Upstream claim:** AMD's forward-looking product or capability claim, unverified by execution.
- **Inference:** Engineering conclusion derived from sources; not an upstream API specification.
- **Unresolved:** Public evidence is insufficient; named experiments or artefacts are necessary.

Read AMD's dated newsroom statement, AMD Gaming discussion, AMD Software 26.10.1 release notes, GPUOpen SDK/product documentation, official FidelityFX-SDK GitHub release and version-pinned header/API/README, contemporary reporting and an existing AMD developer reply. ## Findings: announcement versus deliverable

### 1. What AMD committed to

1. **Verified source statement / Upstream claim — Vulkan is on the official roadmap.** S01 explicitly says AMD announced **“FSR 4 Vulkan support”** on 2026-10-20, and S13 reports Huynh describing a future option **for developers to integrate** FSR into games. This is not merely a community request or a driver-only marketing inference. It is nevertheless a promise of future capability, **not confirmation of a working published SDK**.
2. **Upstream claim corroborated by secondary reporting — SDK 2.4 is the intended delivery vehicle.** S12 reports the AMD slide specifying integration from **FSR SDK 2.4**; S14 repeats developer access “in the coming weeks.” The retrieved S01 page does **not** itself state an SDK version, and S03/slides could not be independently inspected. Thus it is high-confidence, attributable reporting of an upstream plan, rather than direct inspection of versioned v2.4 headers. **No fixed date** was established.
3. **Verified — what is available now.** On 2026-10-23 S05 still lists **v2.3.0** as `Latest`; S04 still advertises **v2.3**. S06 expressly excludes Vulkan for that version; S07's actual integration guide supports only DX12 backend-specific functions. **SDK 2.4 is announced/anticipated, not established as publicly released or downloadable** in the checked channels.
4. **Scoped to FSR Upscaling, not all effects.** S01's surrounding announcement is about **Upscaling 4.1** and explicitly calls it FSR 4 Vulkan support. S12 identifies the slide as **FSR Upscaling 4.1** integration. The standalone FG frame-pacing improvement in S01 and S12 is a **different announcement**. **No inspected AMD primary text promises Vulkan native Frame Generation 4.x, FG swapchain/presentation, Ray Regeneration 1.x, or Radiance Caching.** Their inclusion in SDK 2.3 does not imply they are included in Vulkan 2.4. A reporter's headline “FSR 4” or Huynh's generic “FSR” is not an effect-by-effect support matrix.
5. **Upstream claim — a developer-facing Vulkan path, with architecture unresolved.** “Another way for developers to bring it into their games” (S13) plus the SDK 2.4 slide (S12) supports an intended **native Vulkan API integration path**. It does **not** identify whether the implementation is delivered by an SDK-managed Vulkan DLL/provider, driver-resident provider with public SDK descriptors, shader binaries or some combination. Calling the planned result *native Vulkan* describes the intended graphics-API integration, **not proof of direct Vulkan GPU dispatch today**.

### 2. Concurrent AMD announcements are not Vulkan integration contracts

- **Verified / Upstream hardware claim:** Adrenalin **26.10.1** (released 2026-10-20) expands FSR Upscaling **4.1** to **Radeon RX 6000**, **Ryzen AI Max 300/400**, and **Ryzen AI 9 300/400** series (S09). AMD describes optimized INT8 variants and a more efficient model for select handheld processors in S01. Previously eligible RX 7000 and RX 9000 classes remain part of the product story. **This describes FSR capability under the supplied Windows driver, not a Vulkan SDK 2.4 device guarantee.**
- **Upstream claim:** RX 9000 FSR Frame Generation frame-pacing improvements were announced separately (S01); S02 includes an unanswered 2026-10-23 user question about exactly which game-integrated versions receive that improvement. No new native Vulkan FG contract follows.
- **Verified negative evidence:** The SDK 2.3 GPUOpen page (S04) still states the automatic model-upgrade path for previously integrated FSR 3.1 games is **DX12 only**. S12 likewise cannot confirm an equivalent Vulkan driver toggle. The 26.10.1 driver update does not retroactively grant official Vulkan integration to an arbitrary game.
- **Unresolved:** Reporting from S12 says Windows driver **26.10.1** contains `amdvkffx64.dll` and third-party **OptiScaler v10** can invoke it. The exact PE identity, version/export table, provenance, signing, licensing, supported targets and whether it is a *public application SDK ABI* were **not checked**. Presence of a driver-internal Vulkan-named DLL would be consistent with implementation work, **not proof that `fsr-sdk-rs` can legally or safely load it as an SDK provider**. Do not confuse it with the SDK v2.3 `amd_fidelityfx_loader_dx12.dll`/effect DLLs.
- **Verified separate driver fact:** S11 lists new Vulkan extensions in **26.10.1**. No AMD SDK 2.4 header or document states these are mandatory FSR Vulkan features; **do not turn temporal coincidence into an extension requirement**.

### 3. Baseline SDK 2.3.0 and actual public API

**Verified from version-pinned upstream S05–S08:** v2.3.0 contains FSR Upscaling **4.1.1**, analytical FSR **3.1.5** and **2.3.4**, FSR Frame Generation **4.0.1**, analytical FG **3.1.6** and FG swapchain **3.1.7**, Ray Regeneration **1.2.0**, Radiance Caching **0.9.0 preview** (S04/S05). An **FSR SDK version is not an FSR effect version**; “SDK 2.4” therefore must not be confused with a presumed “FSR 4.2” algorithm.

S07 documents a five-entry-point C ABI: `ffxCreateContext`, `ffxDestroyContext`, `ffxDispatch`, `ffxQuery`, `ffxConfigure`, with `ffxApiHeader`/`pNext` descriptor chains and loader/provider split. Its text explicitly says backend-specific functionality is **currently only DX12**. S08 retains `FFX_API_BACKEND_ID_VK = 0x02000000` and an old/deprecated Vulkan frame-generation swapchain effect ID. Those symbolic values do not supply Vulkan device descriptors or a callable FSR 4.1 Vulkan backend. SDK v2.3's generic README introduction mentioning DX12 *or Vulkan* is contradicted/qualified by its explicit “Vulkan is currently not supported in SDK” row (S06); the explicit limitation governs the selected baseline. Old v1.1.4 Vulkan examples (S17) are not an equivalent modern ML-provider or deployment route.

The baseline GPUOpen SDK page specifies **Windows 10/11**, **DirectX 12**, prebuilt signed effect/loader DLLs, and **SM 6.6 / DX12 Agility** for its ML effects (S04). Those are **current DX12 integration requirements, not a specification of Vulkan SPIR-V, device feature bits, required extensions or Linux distributions**. AMD may revise its published GPU matrix and fallback policy with v2.4; do not import the current DX12 matrix as a Vulkan support list.

## Prospective native Vulkan integration contract: evidence and gaps

**No public SDK 2.4 Vulkan creation header, dispatch descriptor, sample, DLL inventory, source tag or ABI layout could be verified as of 2026-10-23.** Consequently the following is a requirements inventory, **not proposed AMD struct definitions**.

| Contract question | Established by public 2.3 material | What must be established from 2.4 artefacts / execution |
|---|---|---|
| **API entry points / ABI** | Five generic FSR API exports and descriptor-chain conventions in S07/S08, for v2.3 DX12 | Whether the same exports/versions remain applicable; new Vulkan descriptor tags, exact C layouts/alignment, calling conventions, platform-sized types, provider compatibility and C++-only helpers |
| **Creation / destruction** | `ffxCreateContext`/`ffxDestroyContext` and DX12 backend descriptor; native create-time descriptors may need retention | Vulkan backend attach/create form; which instance, physical/logical device, allocator, queues and callbacks it needs; teardown after failed create and while GPU work is pending |
| **Providers and discovery** | DX12 effect DLL discovery, device-aware version queries and provider overrides | Loader/provider names, location and dependencies for Vulkan; whether queries are global/device-specific and driver-dependent; IDs/names, default/forced providers, compatibility and acquisition failure semantics |
| **Command recording** | DX12 direct command-list dispatch recorded by existing wrapper | Whether SDK receives `VkCommandBuffer`, queue or another context; command-buffer recording state and supported queue family/capabilities; whether SDK submits internally or records only |
| **Images/resources** | Generic `FfxApiResource` and DX12 interpretations are published, but `ID3D12Resource` semantics are DX12-only | Exact expected `VkImage`/`VkImageView`/subresource and format mappings, image usage, image layout at entry/exit, memory binding, image aliasing, depth/view reinterpretation, view ownership and mutable formats |
| **Synchronization** | Current DX12 wrapper documents caller resource states, queue ordering and fence completion | `VkPipelineStageFlags2`/access/layout guarantees, transitions made internally vs caller-owned, queue-family transfer, semaphores/fences/timeline requirements and command-pool/descriptor lifetime |
| **GPU features** | DX12 Shader Model/Agility requirements, not Vulkan requirements | Vulkan core version, SPIR-V/compute features, subgroup/wave, precision, cooperative-matrix extensions if any, feature queries and guaranteed fallbacks per GPU/provider |
| **OS / runtime** | Published v2.3 supports Windows 10/11; Adrenalin 26.10.1 is a Windows driver | Windows Vulkan DLL/API path vs **ELF `.so` + native Linux provider**, ICD/driver versions, Mesa/RADV vs AMDVLK vs proprietary, architecture and supported distributions |
| **Distribution** | Existing signed DX12 SDK DLL + provider distribution model and notices | SDK 2.4 package identity, signatures/hashes, Windows/Linux binary terms, third-party runtimes, copyright notices, provider auto-upgrade and redistributable file list |

**Inference — Vulkan GPU safety differs materially from DX12.** Vulkan device handles are not COM-owned references; a Rust `Arc` to a local wrapper does not prevent an external caller from destroying a logical device. In the absence of a trusted resource owner, `VkImage` alone does not allow querying all application-side creation parameters/provenance. Image layouts and synchronization are explicit, include subresource and queue-family scope, and must be tied to the actual SDK operations; generic Vulkan correctness rules are not evidence of AMD's chosen layouts. A successful native `ffxDispatch` return cannot guarantee the recorded work was submitted or retired. Review Vulkan's normative [device lifetime](https://docs.vulkan.org/refpages/latest/refpages/source/vkDestroyDevice.html), [image creation](https://docs.vulkan.org/refpages/latest/refpages/source/VkImageCreateInfo.html), and [synchronization barrier](https://docs.vulkan.org/refpages/latest/refpages/source/VkImageMemoryBarrier2.html) semantics when SDK 2.4 specifies its usage. **Do not invent an `ffxCreateBackendVulkanDesc` or reuse a DX12 descriptor by reinterpretation.**

**Unresolved — non-ABI paths.** The driver-named `amdvkffx64.dll` (S12) could conceivably be an implementation/provider component, but its unexamined exports do not establish a public entry point. Likewise SDK 2.4 might keep the five generic functions while changing the backend descriptor chain; or it might introduce a distinct loader ABI. Either is compatible with the announcement. No conclusion is justified until headers, samples and binaries are compared.

**Verified distinctions:** S09 is explicitly a **Windows** 26.10.1 driver, supporting Windows 10/11; it further says the generic Adrenalin package **does not include handheld gaming device support** and directs users to OEM drivers. RX 6000/RDNA 2 support does **not** prove Valve Steam Deck support: architecture similarity does not establish the device's driver model, neural-model routing, ABI, GPU feature support or OS availability. This is a **version/channel and date mismatch**, not evidence that AMD revoked the new driver support. It is also **not proof** that SDK 2.3's developer-provided binaries automatically gain identical Vulkan or Linux functionality. Provider/generation must be queried and actually tested on the chosen native route.

## Comparison with D031 and the repository implementation

### Existing verified source architecture (S18)

- `docs/adr/D031.md` (**accepted 2026-10-18**) intentionally removed the **nonfunctional** `vulkan` features and deliberate compilation failure, **retained Vulkan as a required target**, and required OS/backend isolation. Its evidence requirement was a usable upstream path and independent device/resource/synchronization/lifecycle verification.
- `ROADMAP.md` **B01** says blocked pending usable upstream integration; **R06** separately calls for evaluation of a candidate new SDK baseline before migration. They are *different decisions*: publishing an SDK is not the same as authorizing a baseline change or completing B01.
- `crates/fsr-sdk-sys/src/{api.rs,upscale.rs}` retain a curated, portable-capable raw v2.3 ABI slice; `dx12.rs` and `loader/windows.rs` are behind `cfg(all(windows, feature = "dx12"))`. The raw `dx12` Cargo feature conditionally enables Windows `libloading`. There is currently **no Vulkan module or feature**.
- `crates/fsr-sdk/src/upscaler/common.rs` exposes backend-independent checked dimensions, options, camera, motion/jitter, exposure, colour, tuning and quality-related configuration; `upscaler/dx12.rs` and `upscaler/dx12/{dispatch,dispatch/resources}.rs` own real DX12 descriptor conversion, GPU inputs and native recording checks. Legacy reexports do **not** make the common module DX12-only. Wrapper `windows` dependencies are optional and targeted to Windows/DX12. `runtime.rs`, context ownership and native query helpers are currently DX12-oriented and gated; optional `movable` has a DX12-specific safety audit.
- `crates/fsr-sdk/src/context.rs` already contains a **private** retention/lifecycle mechanism parameterized by create-state/device/runtime retention, with explicit field/drop order and thread-affinity choices. This offers **potential reuse**, not a public generic backend contract or a proof that Vulkan can use DX12 ownership rules.
- Existing `docs/research/platform-and-backends.md` and dated Proton experiments distinguish preexisting **translated DX12 GPU execution** from a native Linux/Vulkan path. No new experiment was performed here.

### Baseline delta and decision assessment

**Verified:** The reason D031 removed the feature **remains correct for the pinned 2.3.0 SDK and current code**. AMD's October announcement does not resurrect a functional backend retroactively and does not invalidate feature removal. **Changed:** the claim “no prospective modern upstream Vulkan path announced” is now obsolete; AMD has publicly committed to one. **Unchanged:** D031's requirement for real upstream ABI/runtime artefacts and native execution evidence. **Recommendation, not acceptance:** retain D031, annotate B01's *upstream roadmap* status as partially unblocked when synthesis is separately authorized, and reopen R06 on actual SDK 2.4 availability. Neither a new ADR nor a public API break is demanded merely by the announcement.

### Architectural implications, conditional on v2.4

| Area | Preserve/reuse where proven | Conditional evolution / pitfalls |
|---|---|---|
| **`fsr-sdk-sys` ABI** | Shared five-call interface and effect descriptors **only if SDK 2.4 verifies compatibility** | Add *curated Vulkan native declarations* from the real versioned header, exact widths/layouts/calling convention; test against upstream C/C++ compiler. Do not bind speculative obsolete v2.3 IDs as if sufficient |
| **Loaders** | Explicit trusted-path acquisition, required-export checking, retention, owned errors | Separate OS library mechanics and SDK backend/provider selection. Windows loader can remain Windows-owned; a future Linux loader needs independent `dlopen`/null-symbol/error/thread/ELF audit. Do not assume Windows module-search patterns, filenames or driver DLLs port |
| **Runtime/provider** | Conceptual query/configure/dispatch and provider identities | Keep device-aware provider selection and native error states backend-specific until v2.4 exposes common semantics. Preserve actual provider IDs returned, avoid hard-coded IDs; respect distinct SDK loader and effect-provider layers |
| **Public common API** | `Dimensions`, quality/jitter/camera/motion/exposure/colour/tuning *value types* and checked scalar rules when semantically equivalent | Re-review version-dependent flags, colour/format defaults, provider support and validation limits. A common value type must not promise a Vulkan capability merely because DX12 allows it |
| **GPU backend** | Common high-level intent (upscale a temporally related frame) | Expose a concrete `upscaler::vulkan` adapter with its own device context, resource/image/view and command-buffer semantics. Do not expose DXGI, COM, `ID3D12*`, DX12 state assumptions or `windows` crate through portable/Vulkan APIs |
| **Native ownership** | Retention structure and failure/poisoning policies **if invariants match** | Vulkan dispatch likely holds non-owning opaque GPU handles; require external device/queue lifetime and GPU completion contract; avoid interpreting Rust borrows/`Arc` as GPU retirement. Re-audit `Send`, `Sync`, unsafe entry and Drop including `movable` |
| **Cargo** | Existing `dx12` feature and common-only builds, with independent OS gates | Add `vulkan` only alongside functional native integration and meaningful compile/link/load tests; support Windows+Vulkan *without* forcing Linux and Linux+Vulkan *without* Windows dependencies. No placeholder feature |
| **API coherence** | Common configuration under `upscaler::common`, backend modules under `upscaler::dx12`/future `::vulkan` | Prefer a small common checked configuration core plus **concrete backend dispatch types** before a public `GraphicsBackend` trait, raw-erased handle enum or broad runtime redesign. A coherent breaking 0.x API change is acceptable if evidence shows a real mismatch |
| **Licensing/distribution** | Existing MPL-2.0 crates, AMD header notice retention, explicit opt-in acquisition and no bundled SDK files | Compare 2.4 upstream LICENSE/THIRD_PARTY, signed binary exceptions, downloaded asset members, export/import licences, driver-provider distribution, OS-specific terms and redistributable dependency closure. Do **not** assume the 2.3 exception list covers `amdvkffx64.dll` or new binaries |

**Important negative portability finding:** The existing DX12 wrapper queries COM interfaces for device identity, resource metadata, format/view support and direct command-list type; those are **not interchangeable** with Vulkan's opaque handles. The current DX12 dispatch safety contract checks inspectable resource metadata but delegates content correctness, transitions, non-aliasing, submission and GPU completion to the caller. Vulkan must formulate its own inspectable-versus-caller-established separation; a compile-successful handle wrapper is not a safety argument. Existing cross-thread `movable` audits are not portable by analogy.

## Action plan and evidence gates

### A. Now — justified immediately, without adopting SDK 2.4

1. **Retain SDK v2.3.0 and D031 unchanged.** Keep the `vulkan` feature absent; document the **2026-10-20 upstream commitment** as source research, not implementation completion. Do not edit the roadmap/ADR as part of this record.
2. Create an **R06 comparison checklist** (in research/planning only): v2.3.0 vs eventual v2.4 ABI; upscaling effect version; platform/driver/GPU matrix; SDK loader/provider packaging; version-query compatibility; licence and notices; regression of DX12 behaviour. The existing Windows DX12 tests remain the migration control.
3. Define Vulkan acceptance conditions now (below) and prepare **OS × graphics-API × provider** verification cells. Prioritize Windows/Vulkan first *only if AMD ships that route first*, not because Vulkan necessarily means Windows.
4. Monitor AMD [official SDK releases][S05], [GPUOpen SDK page][S04], AMD Newsroom/[AMD Gaming][S02], actual versioned headers and the published package identities. A driver DLL or OptiScaler release is **not** the SDK availability gate.

### B. When a real SDK 2.4 artefact becomes available — source/ABI gate

1. Pin exact **tag, full commit, release timestamp, asset URLs/names/sizes/digests**, license/third-party notices; independently hash downloaded archives and binaries and verify signatures under explicit trust policy. Capture a versioned manifest rather than taking “2.4” alone as immutable.
2. Diff **all wrapper-used** 2.3 API headers against 2.4 (`ffx_api.h`, common types, upscaler, backend headers and provider semantics). Verify native sizes/alignments/offsets/enums/function prototypes with compiled C/C++ static assertions; add Rust ABI tests. Determine *which effects* and which providers are Vulkan-capable. Validate loader/effect DLL names, exports, discovery, query/override behaviour and failure cases. Check whether SDK acquisition is Windows-only or has native Linux artefacts.
3. Read the actual Vulkan samples/docs to establish queue, command-buffer, image/view, format, layouts, barriers, ownership, device features, precision/fallback and context lifetime. Write a bounded **backend-specific safety contract** before constructing a public safe façade. If samples are available but undocumented, explicitly mark inferred behaviour and request clarification or design conservative unsafe contracts.
4. Conduct a **separate R06 baseline decision**: upgrade the pinned SDK only after reviewing whether existing DX12 code, provider discovery, ABI tests and regression protocols remain valid. A 2.4 integration can first be evaluated on a private branch/local harness; **no requirement to migrate the entire wrapper before every targeted Vulkan feasibility test**, but shipping both DX12 and Vulkan against 2.4 requires a coherent supported baseline.

### C. Native experiments — hardware/runtime gate, after ABI contract is known

**Minimal meaningful native Vulkan PoC:** a small native Vulkan application using the **official SDK 2.4 Vulkan developer interface**, not DX12/Proton/OptiScaler. On a named OS, GPU, driver/ICD, SDK artefact and hardware provider: (i) create a Vulkan instance/device with actually required features; (ii) explicitly acquire official SDK loader/provider, enumerate and record selected upscaler provider/version; (iii) create one context; (iv) allocate distinct real input/output images with documented formats/usage/memory, supply coherent colour, depth, zero motion, exposure and reset-frame jitter; (v) transition/synchronize the documented layouts; (vi) invoke native Vulkan dispatch into a Vulkan command buffer and **submit** it; (vii) wait for a fence/timeline completion; (viii) read back output and perform bounded finite/nontrivial/spatial checks with an explicit reference/control; (ix) destroy context and all GPU/SDK resources in validated order without leaks, validation errors or device loss. Record both positive and deliberate negative cases (wrong resources, unavailable provider, missing library) without assuming all can safely be called on untrusted native code.

**Claim ladder** (do not conflate):

- **Source-ready:** published 2.4 ABI + SDK sample + package/terms analysed; permits implementation planning, **not Vulkan support claim**.
- **Build-ready:** a gated wrapper compiles; native C layout tests and SDK load/query tests pass on specified target; **not GPU-proven**.
- **Single-frame GPU PoC:** native Vulkan command recording, submit, fence, readback, output plausibility and clean teardown validated on an exact environment. This **partially validates** one integration path only.
- **Project-native support claim:** public `fsr-sdk` path, checked creation/dispatch and documented unsafe boundaries tested end-to-end; verified error/poisoning/cleanup and representative multi-frame motion/jitter/reset, resize/format variants, GPU pending-lifetime handling, provider fallbacks and distribution; CI target-gating and package/consumer checks. Name **OS, architecture, Vulkan ICD/driver, GPU generation, SDK and provider** explicitly. Wider OS/GPU generalization requires independent matrices.

For **Linux/Vulkan**, repeat with an actually published/authorized **native Linux** loader/provider and distro/ICD/hardware combination. Running a Windows SDK binary via Proton, even if Vulkan is the underlying graphics API, does **not** meet this gate. If AMD offers only Windows/Vulkan, B01's Windows cell may become feasible independently while native Linux remains blocked.

### D. Decisions to leave open

Do not preselect new `ffx` Vulkan Rust descriptors, a Vulkan resource wrapper type/handle owner, a provider trait hierarchy, a universal `Runtime` type, a Linux loader, a `vulkan` feature name activation, a baseline migration, or a binary redistribution policy without the artefacts/evidence above. In particular, **the announcement does not mandate a full architectural redesign**; the present common-input and concrete-backend split is an appropriate starting shape.

## Final status: B01

**Assessment as of 2026-10-23: B01 is *partially unblocked in upstream roadmap certainty*, but *still technically blocked for `fsr-sdk-rs` implementation and support claims*.**

**Explicit evidence:** AMD has announced FSR 4 Vulkan support (S01) and contemporary reporting identifies a developer path via the upcoming SDK 2.4 (S12–S14), overcoming the earlier absence of an announced modern path. Yet the official public SDK release index remains at **v2.3.0** (S05), that pinned SDK explicitly says Vulkan is unsupported (S06/S07), and no native Vulkan 2.4 headers, ABI, redistributable runtime, samples or submitted/fenced GPU execution have been established. D031's removal of the meaningless feature, its backend-isolation rules and B01's native-proof requirements therefore **remain sound**. Reassess **R06 on release of inspectable 2.4 artefacts**, and move B01 from “blocked” to “implementable” only when the actual Vulkan integration interface, platform binary/runtime and lifetime/synchronization contract can be pinned and reviewed; claim working support only after a native PoC and public wrapper verification.
