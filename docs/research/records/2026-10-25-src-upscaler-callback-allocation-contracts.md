# Upscaler callback, diagnostics and allocation contracts — source record

**Investigation date:** 2026-10-25  
**Status:** Source investigation only; no implementation, experiment or API selection  
**Scope:** `fsr-sdk` U04 (diagnostics) and R03 (CPU and DX12 allocation); Windows x64/MSVC, DirectX 12, applicable upscaling API

## 1. Answer and decisions remaining

**Verified source fact.** The ABI contains a host allocator pair with `pUserData`; a context-creation message callback without user data; two global-debug Configure descriptors; and a DX12 creation extension with resource, heap and constant-buffer callbacks, none of which carry callback user data. The DX12 `effectId` argument identifies an **effect type**, not a context instance. The constant-buffer callback instead receives a **payload** as its first parameter and returns a nontrivial struct **by value**. [API declarations](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/ffx_api.h#L58-L84), [DX12 declarations](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/dx12/ffx_api_dx12.h#L28-L57), [constant-buffer declaration](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/ffx_api_types.h#L196-L212), [backend effect slot](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L1279-L1288).

**Verified source fact.** The inspected open DX12 backend stores all five callback function pointers in **module-static variables**, updates them during context creation, and never unregisters them in the inspected destruction paths. A missing or partial callback pair does **not** clear previously registered callbacks. The loader likewise routes both global-debug Configure variants to a **module-global** message callback and ignores the new descriptor's `effectId`. Open FSR2/FSR3 providers copy their creation message callback into per-context state *and* install it in global state, without resetting that global registration at context destruction. [registration route](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_backends_dx12.cpp#L38-L80), [static slots and setters](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L3666-L3687), [global Configure](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_api.cpp#L81-L100), [open FSR2](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr2.cpp#L62-L118), [open FSR3](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr3upscale.cpp#L63-L103).

**Inference (decision inputs, not decisions).** A later API decision must explicitly address callback registration scope, absence of per-instance state in five DX12 signatures, replacement/unregistration and lifetimes beyond the installing context, serialisation and reentry, compatible host allocation/free and DX12 COM ownership, GPU completion before reuse/free, exact Win64 aggregate-return ABI, and native failure/cleanup behavior. **Unresolved:** the signed selected **4.1.1** provider's private implementation, actual callback timing/thread policy, null-allocation behavior, and reliable recovery after native errors. No Rust API shape, registry, lock policy or allocator strategy is selected in this record.

**Win64 aggregate-return detail (verified ABI rule, inferred layout pending independent assertion).** From the types, `FfxApiResourceDescription` has eight `uint32_t` slots (32 bytes); `FfxApiResource` on Win64 has a pointer (8), description (32) and state (4) plus tail padding (4), totaling **48 bytes**; `FfxApiConstantBufferAllocation` adds `uint64_t handle` for **56 bytes**, aligned to 8. Under the Microsoft x64 ABI a 56-byte user-defined aggregate result is returned through a **hidden caller-provided result pointer** in `RCX`; the visible `data` and `dataSize` arguments shift to `RDX` and `R8`, respectively, and the result pointer is returned in `RAX`. This is **not** a scalar `RAX` return. Exact layout and Rust/C interoperability remain suitable for a small independent ABI fixture. [types](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/ffx_api_types.h#L155-L212), [Microsoft return-value examples](https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention?view=msvc-170).

## 4. Retention, registration, invocation and cleanup

### 4.1 Distinguish the descriptor addresses from state lifetime

**Verified source fact.** The public header instructs callers to keep pointers in creation descriptors live until `ffxDestroyContext` ([`ffx_api.h`](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/ffx_api.h#L120-L130)). The open FSR2/FSR3 providers *read* creation dimensions/flags, *copy* `fpMessage` into their internal context, and give an FSR-specific function pointer to underlying native context initialization. Independently, the DX12 extension's function pointers are *copied* into module-global slots when the extension is encountered in `pNext`: the backend does **not** retain the address of that particular extension object. The underlying callback **code and any privately referenced state** must nevertheless remain valid as long as native code can still call the registered pointer. [FSR2 creation](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr2.cpp#L61-L100), [FSR3 creation](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr3upscale.cpp#L62-L103), [registration](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_backends_dx12.cpp#L59-L77).

**Verified source fact / upstream claim.** The loader constructs a short-lived `Allocator{memCb}` for create or destroy; its member is a borrowed pointer to the `ffxAllocationCallbacks` struct. The pinned integration guide explicitly says `pUserData` is forwarded unchanged, not dereferenced or stored by the API, and requires compatible allocator/data on destruction. This does **not** establish that state pointed to by `pUserData` can be freed before the allocator's last invocation, or that closed providers use the identical strategy. [loader](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_api.cpp#L39-L78), [allocator](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_api_helper.h#L69-L116), [guide](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/docs/getting-started/ffx-api.md#L256-L280).

### 4.2 Registration is shared and omissions are not resets

**Verified source fact.** `CreateBackend` walks the chained descriptors in order. It registers a resource callback **only if both allocation and free are present**, and a heap callback **only if both are present**; CB callback registers independently if nonnull. For omitted or incomplete sets, registration is skipped, **not reset**. Native fallback applies only while the corresponding static slot is actually null. Re-registering a different set replaces the module-static functions for **existing and future** contexts using that implementation. Reaching this code depends on selected provider/backend routing, not just on attaching a descriptor. [DX12 extension switch](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_backends_dx12.cpp#L37-L80), [static declarations](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L109-L114), [setters](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L3665-L3687).

**Inference.** Module-static is not necessarily process-wide across *different DLL images*; do not presume state changes in a loader image also update a different signed provider image. The [documented split](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/docs/getting-started/ffx-api.md#L18-L27) and closed-provider routing prevent treating all registrations as one universal process-wide singleton. Their actual cross-DLL behavior is **unresolved**.

### 4.3 COM objects, heaps, CB payload and GPU lifetime

**Verified source fact.** The DX12 backend obtains a resource through a callback for committed/upload resources; placed resources use `CreatePlacedResource` directly. At resource destruction, it dispatches an *unplaced* resource to the registered free callback or calls `ID3D12Resource::Release()`; placed resources are always directly released. Analogously, heap callback output contains an `ID3D12Heap*` and a byte start offset; its corresponding destructor receives the same offset and the **logical requested** heap size. All callback-deallocator return values are discarded. [resource creation](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L1642-L1669), [resource release](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L1865-L1898), [heap creation/destruction](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L2492-L2565).

**Inference (COM contract).** A successful resource/heap allocator must give the backend a valid usable COM interface reference and the matching deallocator must perform the release or equivalent lifetime accounting that `Release()` otherwise would. The backend does not automatically call `Release()` after calling the custom deallocator. It is not an indication that the native backend owns the application's overall residency or can retire in-flight GPU work. These are *ownership obligations implied by the open consumer*, not a documented closed-provider refcount transfer protocol.

**Verified source fact.** `StageConstantBufferDataDX12` copies incoming CPU bytes into its internal staging ring **before** a later GPU-job execution path calls the custom CB allocator with that copied payload. The custom allocator's result `.handle` alone becomes a DX12 root-CBV **GPU virtual address**; `.resource` is not consulted there. The native default creates a mapped upload-buffer ring, copies `dataSize` bytes, returns GPU VA in `.handle`, fills `.resource` with an empty value, and uses **256-byte alignment**. [staging](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L2568-L2589), [allocation/use](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L3445-L3461), [fallback](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L414-L454). [Microsoft](https://learn.microsoft.com/en-us/windows/win32/direct3d12/default-texture-mapping) requires 256-byte CBV alignment.

**Inference.** A custom allocator must put the payload in GPU-accessible backing and return an aligned GPU address usable as a root CBV, with contents stable through actual GPU consumption, not merely the CPU callback return. The returned struct offers no automatic allocation lifetime token or free callback. How an embedding application handles its backing lifetime is outside this investigation. As the baseline states, submission, synchronization, residency and completion are caller-owned.

### 4.4 Failures and partial lifecycle

**Verified source fact.** Host `ffxAlloc` is *documented* to be permitted to return null. But the inspected `Allocator.alloc` calls `memset(ptr, 0, sz)` without testing null when zeroing is requested; `construct` applies placement-new to the allocation without a null check. Therefore, the documented host OOM channel is **not uniformly safe** in this implementation and cannot establish an error-return guarantee. This is a source-level defect/risk, **not** proof that it caused the supplied historical `0xC0000005`. [header promise](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/ffx_api.h#L108-L119), [consumer](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_api_helper.h#L69-L106).

**Verified source fact.** Resource allocation errors are only asserted in inspected paths before the returned resource is used unconditionally; heap allocation callback status is entirely ignored; CB allocation has no status and returned GPU address is used without validation. Resource/heap free callback errors are ignored. A provider can return an error on create/destroy, but the public loader does not implement a general rollback/transaction: it conditionally frees a failed-create provider when its refcount is zero, and after destroy it may destruct the provider regardless of the return code if its refcount is zero. Open FSR3 creation and destruction contain multiple `TRY2` early returns; a failure can strand partially built context/backend resources. [resource alloc](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L1655-L1685), [heap alloc](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L2513-L2535), [loader](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_api.cpp#L39-L78), [FSR3 provider](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr3upscale.cpp#L82-L158).

**Unresolved / important negative result.** No inspected source establishes that a failed creation yields a destroyable context, that destroy can safely be retried after an error, that the context pointer will be nulled in every failed/successful destroy route, or that a failed destroy has no lingering callbacks. The [integration guide's statement that a context becomes null after destroy](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/docs/getting-started/ffx-api.md#L74-L81) is **not borne out uniformly** by the inspected FSR2/FSR3 provider destroy functions: they free their internal context but do not assign `*context = nullptr` ([FSR2](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr2.cpp#L106-L119), [FSR3](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr3upscale.cpp#L141-L159)). The wrapper's existing once-only destroy/dependency-retention baseline is not overturned by these findings.

## 5. State association, threading and reentrancy

**Verified source fact.** `FFX_API_EFFECT_ID_UPSCALE = 0x00010000` selects the upscaling **effect family**; backend `CreateBackendContextDX12` stores the `FfxEffect effect` in `effectContext.effectId`, separately from its per-context *slot index* `effectContextId`. The resource/heap callback signatures receive only the former. Hence two contexts of the same effect **cannot be uniquely distinguished through callback arguments alone**. Constant-buffer callbacks receive **neither ID**; messages receive only severity/text. [effect ID](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/ffx_api.h#L146-L156), [backend slot and effect](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L1278-L1288), [callback ABI](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/include/dx12/ffx_api_dx12.h#L27-L41).

**Verified source fact.** Global message callback/filter state consists of ordinary static variables written by `ffxSetPrintMessageCallback` without locks or atomics; message delivery calls that function pointer directly. DX12 registered allocation callbacks similarly use unsynchronized ordinary static slots. Open FSR2 creation passes `fpMessage` and then sets global debug callback at level **0 (silence)**, whereas open FSR3 creation installs the supplied message callback with **warnings** level. Both providers have internal per-context `fpMessage` fields, but those fields do **not** imply per-context routing for global messages. The deprecated provider-specific Configure handlers for `GLOBALDEBUG1` exist but the loader intercepts that descriptor before dispatching to providers. [global state](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_message.cpp#L37-L67), [FSR2 install](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr2.cpp#L87-L98), [FSR3 install](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr3upscale.cpp#L92-L103), [loader interception](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_api.cpp#L80-L99).

**Inference.** A callback pointer or referenced state may remain reachable after the context that registered it is destroyed. A new registration can divert messages, allocations and frees of an earlier context to a different function; static registration has no per-context restoration mechanism in this implementation. Multiple same-effect contexts cannot identify themselves without some **additional** scheme that the native ABI does not supply. These observations matter for static function pointers versus context-owned state; **no** particular state registry or ownership API is chosen here.

**Threading gap (unresolved).** Observed open-source call sites invoke callbacks on the caller's synchronous native stack (e.g. allocations during `CreateContext`, CB callback inside command recording, messages during `ffxPrintMessage`, deallocations during destroy); the fallback CB ring alone has a mutex around its local upload ring. That mutex **does not** synchronize global callback registration, arbitrary custom allocators, or callback delivery. There is no public guarantee that every selected signed-provider callback arrives on the invoking thread, is nonconcurrent, is nonreentrant, or ceases immediately when destroy returns. [CB fallback lock](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L414-L454), [CB direct invocation](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/backend/dx12/ffx_dx12.cpp#L3445-L3459). **Inference:** holding a nonreentrant wrapper lock across a native call can deadlock if the callback reenters code requiring that lock; lack of a documented reentry prohibition prevents claiming otherwise. Conversely, independent concurrent calls to unsynchronized native module state cannot be declared safe from the source.

## 6. Diagnostic routing and flag semantics

1. **Message callback versus global debug.** Creation `ffxCreateContextDescUpscale.fpMessage` is a descriptor-associated callback supplied to the chosen provider, but open providers also install it into shared output state, and the loader's global Configure controls a potentially different module's output state. `ffxConfigure` handles **both** global debug descriptors unconditionally before context/provider lookup, returning `FFX_API_RETURN_OK` and ignoring `context` and the new descriptor's `effectId` ([loader](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_api.cpp#L80-L99)). **Unresolved:** which signed provider output channels, if any, are affected by a loader-level successful Configure call.
2. **Wide string semantics.** The ABI is `const wchar_t*`, not UTF-8. On Windows its code units are UTF-16. The native function pointer receives neither an explicit length nor an ownership transfer; an inspected caller passes stack-backed `wchar_t msgBuf[512]` ([loader query diagnostic](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_api.cpp#L129-L148)). **Inference:** consume/copy during the callback, do not retain the pointer; handle native null/ill-formed text defensively because nonnull/normalization is not explicitly promised. No cross-thread delivery guarantee is made. With no registered callback, the inspected module prints to `OutputDebugStringW` at non-silent levels ([message code](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_message.cpp#L47-L67)).
3. **Assertions are separate.** `ffx_assert.cpp` uses `FfxAssertCallback`, `char*` text and `OutputDebugStringA` fallback—not `ffxApiMessage`. It is not evidence of an additional public U04 callback registration channel ([assert source](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/api/internal/ffx_assert.cpp#L31-L67)). An FSR provider explicitly marks its cast of the message pointer to another callback type as undefined behavior ([FSR3 comment](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr3upscale.cpp#L92-L96)); compatibility cannot be assumed on targets outside the selected Windows x64 scope.
4. **Three distinct knobs.** `FFX_UPSCALE_ENABLE_DEBUG_CHECKING` (creation) requests native input validation/messages; `FFX_UPSCALE_ENABLE_DEBUG_VISUALIZATION` (creation) advertises permission to allocate resources for debug visualization and notes possible **higher memory use**; `FFX_UPSCALE_FLAG_DRAW_DEBUG_VIEW` (dispatch) requests per-frame debug output. Global debug message level determines what text reaches the inspected global sink and does **not** itself enable validator work. [flag definitions](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/include/ffx_upscale.h#L42-L60), [FSR4 guide, debug checker](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/docs/techniques/super-resolution-ml.md#L263-L272).
5. **Capability versus implementation.** The open FSR2 and FSR3 flag-converters pass checking but **do not forward** creation `DEBUG_VISUALIZATION`; FSR2 dispatch does **not** forward `DRAW_DEBUG_VIEW`, while FSR3 forwards the per-frame flag and schedules a debug pipeline ([FSR2 conversion](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr2.cpp#L26-L46), [FSR2 dispatch](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr2.cpp#L252-L285), [FSR3 conversion](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr3upscale.cpp#L28-L47), [FSR3 dispatch](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr3upscale.cpp#L350-L359), [debug pipeline](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_fsr3upscaler.cpp#L1040-L1054)). **Upstream claim:** FSR4's documented debug view adds a pass overlaying internal debug information *onto the upscaled output*, not a separate unmodified color image ([FSR4 guide](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/docs/techniques/super-resolution-ml.md#L274-L277)). **Unresolved:** whether the selected signed provider requires creation visualization permission for this flag and how it reports unsupported combinations.
6. **Memory estimation parity.** `ffxQueryDescUpscaleGetGPUMemoryUsageV2` contains `device`, both maximum sizes and **creation flags**; a fair query for intended creation should provide **the same flags** as creation, including `DEBUG_VISUALIZATION` if requested, and the same provider/version override and sizes. This is an **inference from the contract** and SDK's consistent-version guidance, not a universal assertion that every provider uses every flag. In fact, open FSR2's V2 query calls `ffxFsr2GetGpuMemoryUsage` without passing `desc->flags`; the open providers therefore cannot establish signed-provider memory behavior ([V2 descriptor](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/include/ffx_upscale.h#L175-L184), [FSR2 implementation](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/upscalers/fsr3/internal/ffx_provider_fsr2.cpp#L208-L220), [guide version consistency](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/60f4ea81909200d8542eca14dccb2628b763a9a3/Kits/FidelityFX/docs/getting-started/ffx-api.md#L205-L213)).

## 9. Boundary of this record

This record supplies evidence for a later **U04/R03 API decision** only. It does not implement Rust bindings, select a global registry or synchronization policy, infer a closed provider's behavior from FSR2/FSR3, promise recovery after native failure, evaluate debug-overlay image quality, or allocate renderer-owned GPU memory. Claims above labeled **Inference** are safety-relevant design inputs, not native guarantees; **Unresolved** items remain unresolved until the bounded provider/ABI evidence exists.
