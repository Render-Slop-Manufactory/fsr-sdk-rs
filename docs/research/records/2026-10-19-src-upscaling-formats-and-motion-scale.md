## 1. Question, method, and evidence levels

Determine which *external* formats the public SDK actually specifies, which formats its DX12 surface converter can represent, which SRV/UAV formats its backend constructs, and what `ffxDispatchDescUpscale::motionVectorScale.{x,y}` means. The outcome is a set of possible changes and tests, not permission to expose unverified combinations.

Sources were inspected at the exact commit above: API enum and DX12 helper; the **actual dynamic resource registration and view creation** in the DX12 backend; modern upscaler API declarations; pinned FSR3/FSR4 integration documentation, FSR3 host/shader path and official sample. DX12 restrictions are cross-checked against Microsoft specifications linked below. The uploaded wrapper archive is a *separate*, unversioned local snapshot, not an upstream reference. There was **no native/GPU execution, SDK binary download, or inspection of closed provider source**.

In this record, **[H]** means verified pinned public header declaration; **[D]** upstream integration-documentation assertion; **[B]** pinned *generic* DX12 helper/backend implementation; **[O3]** verified open FSR3 host or shader path; **[O2]** verified open FSR2 host or shader path; **[S]** pinned application sample; **[R]** uploaded Rust snapshot; **[I]** reasoned inference; **[?]** unresolved for the actual provider/GPU. These levels are intentionally not interchangeable. “Map” never means “provider accepts and safely consumes”. Format information embedded in an SDK-internal intermediate resource is not evidence for an *external* resource role.

## 2. Supplied baseline and observed wrapper snapshot

**Supplied baseline [user evidence, not re-executed]:** two ownership families share dispatch inspection/mapping: thread-confined local; optional `Send + !Sync` movable. Current external textures: colour/output/opaque/post-translucency `R16G16B16A16_FLOAT`, depth and 1×1 exposure `R32_FLOAT`, motion `R16G16_FLOAT`, supplied masks and reactive output `R8_UNORM`. All are single-mip, single-slice, single-sample Texture2D on the context device. External allocations match the context maxima; variable *active* render/output rectangles independently use smaller origin-aligned regions on dynamic contexts. Renderer supplies valid content, states, storage non-aliasing except both read-only reactive-generation colours may alias, GPU lifetime and synchronisation. Current UV motion emits native scale `(active_motion_width, active_motion_height)`; pixel motion emits `(1,1)`. Scales cannot be explicitly signed or asymmetric.

**Supplied native baseline, not established by this investigation:** RX 9060 XT, Windows x64/MSVC, driver `32.0.31041.1004`; 62 public active-output cases (144 dispatched + 12 control frames), 257 consolidated cases, provider observations 4.1.1 and 3.1.5; 2.3.4 independently retained maximum output after smaller requests, rounded/wide output writes could escape the desired active/nominal maximum rectangles. Thus successful status, debug-layer silence and active-sized readback do not prove out-of-resource safety. Do **not** reopen allocation policy here or generalise matched UV/pixel imagery to arbitrary vectors.

**Archive [R] actually inspected:** `crates/fsr-sdk-sys/src/api.rs` defines only five raw surface constants (including `UNKNOWN`); `crates/fsr-sdk/src/upscaler/dx12/dispatch/resources.rs` `format` recognises the four concrete formats and `convert_desc` requires one precise DXGI format per role, retains `GetDesc` dimensions, derives `UAV` usage from the resource flag, and checks shader-read denial; `.../descriptor.rs` `build_descriptor` computes UV/pixel scales; `.../frame.rs` documents active-region, state and GPU-lifetime obligations. Separate local and movable family surfaces exist, and no snapshot change was applied. This corroborates the supplied baseline without treating archived Rust tests as new execution evidence.

## 3. External resource format matrix

### Reading the matrix

* A row labelled **documented role** cites [D] for semantic form, and [H]/[B] for the *representation*, **not** closed-provider compatibility.
* **Candidate** means the application-specified family admits a plausible representation and generic DX12 code can map it. It still needs explicit wrapper extension and a selected-provider verification; it is **not** an accepted external format today.
* `F(X)` is the literal `FFX_API_SURFACE_FORMAT_X` constant from [P1]; the table spells it out to prevent confusion. Component type (`FLOAT`, `UNORM`, `SNORM`, `UINT`, `SRGB`) determines decoded values and what FSR shaders see. `FLOAT` precision is per component (`16` half or `32` single). `UNORM` yields `[0,1]`, `SNORM` approximately `[-1,1]`; `SRGB` SRV sampling applies transfer decoding and is not a free colour-encoding policy switch. All listed render/output external textures remain Texture2D with current shape, device and size rules.

Conversely `A8_UNORM` maps to `FFX_API_SURFACE_FORMAT_R8_UNORM` in [P2], but alpha-only allocation/view semantics do not make it an accepted mask texture.

**Internal intermediate distinction:** Any FSR3 shader or backend-created internal texture format, including dilated motion vectors, reconstructed depth and accumulated history, follows provider-owned allocation and shader access and does not add an external role to the table. The observed open FSR3 shader float type (`Texture2D<FfxFloat32x4>` reading `.xy`) describes *shader access*, not an external DXGI allocation contract. FSR4 ML's internal pipeline and the 4.1.1 provider binary cannot be inspected here.

## 4. DX12 mapping and generated view trace

### 4.1 Actual call and data flow

1. **Public resource description [P2, B].** `ffxApiGetResourceDX12(ID3D12Resource*, state, additionalUsages)` calls `GetDesc()`, reports native format via `ffxApiGetSurfaceFormatDX12(desc.Format)`, sets actual width/height/depth/mips, sets `FFX_API_RESOURCE_USAGE_DEPTHTARGET`/`STENCILTARGET` for named typed depth formats, and adds `FFX_API_RESOURCE_USAGE_UAV` if actual allocation includes `D3D12_RESOURCE_FLAG_ALLOW_UNORDERED_ACCESS`. `READ_ONLY = 0` is a zero bit mask [P1, H]. The caller may provide a prepared equivalent descriptor; this helper is not mandatory for a Rust wrapper.
2. **Backend registration [P4, B].** `RegisterResourceDX12` reads the real resource `GetDesc` **and** `inFfxResource->description.format`. `patchDxgiFormatWithFfxUsage` chooses a view-basis format: `UNKNOWN` uses FFX supplied mapping; RGBA8 UNORM or `_SRGB` uses the FFX-supplied form; D32, D32S8, D24, D16 are specially recast; otherwise original DXGI is kept. `convertFormatSrv` and `convertFormatUav` then select typed view formats. For a typeless `R16G16` texture both select `R16G16_FLOAT`; for typeless `R32` both select `R32_FLOAT`; for typeless RGBA8 both select UNORM. These **hard-coded choices** do not express arbitrary user-selected view reinterpretations.
3. **View shape [P4, B].** Real `dx12Desc.Dimension` and `DepthOrArraySize` determine Texture2D/2DArray dimensions; for current single-slice, no `ARRAYVIEW`, an SRV is `D3D12_SRV_DIMENSION_TEXTURE2D`, with mip count from real allocation, shader component mapping `D3D12_DEFAULT_SHADER_4_COMPONENT_MAPPING`, plane zero. The backend separately copies FFX-supplied *metadata* format and dimensions into its internal resource description. These two inputs can disagree; `GetDesc` truth alone is not all metadata that downstream code observes.
4. **Descriptor creation [P4, B].** `CreateShaderResourceView` is called for a non-buffer dynamic texture. If the *real* resource `D3D12_RESOURCE_FLAG_ALLOW_UNORDERED_ACCESS` is present, the backend also calls `CreateUnorderedAccessView` for each mip. This is **not** gated purely by FFX usage bits and can therefore create a UAV descriptor for a resource only needed as an input. An incompatible typed view can be erroneous **before** the shader consumes it, even if its role is read-only. `Create*View` is a `void` call; a later `FFX_OK` is not proof of a meaningful descriptor or legal shader access.
5. **Transitions [P4, B; DX12].** The backend tracks supplied `FfxApiResource.state`, performs recording against that assumption, and attempts to restore dynamic resources to the recorded initial state on unregister. That cannot certify the renderer's actual command-list state, queue ordering, descriptors' GPU liveness, residency or non-aliasing.

### 4.2 Typed, typeless, depth/stencil, and sRGB boundaries

* **Normal typed colour/motion/exposure** is straightforward to represent for the four current formats, provided SRV/UAV support and shader semantics exist. One must still query/check format capabilities for **each selected view format**, not merely `DXGI_FORMAT` enum existence.
* **Typeless** is storage compatibility, not a typeless shader view. `R32_TYPELESS`/`R16G16_TYPELESS` need **typed** `R32_FLOAT`/`R16G16_FLOAT` SRVs. [P4] chooses some such reinterpreted formats automatically; it does **not** accept an independently supplied SRV handle or arbitrary SRV DXGI format. A future API accepting typeless allocations must define the compatible view interpretation deliberately (possibly a separate checked metadata choice), or keep them unsupported.
* **Depth target ≠ free scalar `R32_FLOAT` texture.** Typical D32+SRV use requires a format/view family such as `R32_TYPELESS` allocation, `D32_FLOAT` DSV, `R32_FLOAT` SRV and no shader-resource denial. D32S8 uses a 64-bit family with `R32_FLOAT_X8X24_TYPELESS` SRV selecting depth; stencil is discarded for upscaling. [P2] maps typed D32S8 to native `R32_FLOAT`; [P4] reconstructs the proper view from the real allocation. This illustrates *why* native surface enum does not encode the whole DX12 view. Whether all actual D32 typed allocation cases can legally be reinterpreted and all providers tolerate the mapping is **[?]**, not established by [P6]'s general prose. D24's `R32_UINT` helper mapping should not be mistaken for a float-depth certificate.
* **sRGB** has two layers. (a) A DXGI sRGB SRV can decode channel transfer (and a compatible typeless allocation can permit typed UNORM/sRGB view selection). (b) `FFX_UPSCALE_ENABLE_NON_LINEAR_COLORSPACE` at context creation and `FFX_UPSCALE_FLAG_NON_LINEAR_COLOR_SRGB`/`_PQ` at dispatch convey **algorithmic colour encoding** [P3/P5/P9]. These are not interchangeable and may cause double conversion if combined without a known contract. The backend's RGBA8 override uses the **native description** to choose sRGB/UNORM, so naive allocation-to-native mapping loses relevant view intent. Its `convertFormatUav` explicitly demotes RGBA8 sRGB to UNORM in that case, but sRGB UAV stores are not created. Not all typeless BGRA/RGBX cases behave identically; [P4] includes a `B8G8R8X8_TYPELESS` case returning `_SRGB` even from `convertFormatUav`, which should **not** be accepted as generic UAV proof.
* **Resource flags and feature bits.** Reader needs actual shader resource use permitted (`!D3D12_RESOURCE_FLAG_DENY_SHADER_RESOURCE`), supported texture/SRV sampling or load semantics and correct current state. Output needs `D3D12_RESOURCE_FLAG_ALLOW_UNORDERED_ACCESS`, a legal typed UAV format, and device support for the needed **typed UAV store**; only demand `D3D12_FORMAT_SUPPORT2_UAV_TYPED_LOAD` if the selected shader actually loads from that UAV, and `D3D12_FORMAT_SUPPORT2_UAV_TYPED_STORE` for stores. `CheckFeatureSupport(D3D12_FEATURE_FORMAT_SUPPORT,...)`/`D3D12_FORMAT_SUPPORT1` complement each other; format support **is device- and view-dependent**. RTV/DSV creation requirements matter for how the renderer produces textures, not automatically for upscaler SRV consumption. Merely seeing `ALLOW_UNORDERED_ACCESS` and a native `UAV` usage flag does not prove `RWTexture2D` legality.
* **Allocation metadata** (`GetDesc` and device identity) is necessary to check single-sample/slice/mip Texture2D, allocation maxima, flags and typed/typeless family. It is **insufficient** for independently chosen view reinterpretation, actual GPU contents, correct colour encoding, depth projection, SRV/UAV feature support, real command-list state and provider-specific shader assumptions. Existing one-mip/slice/sample boundary remains in place; no implicit array, planar or multisampled extension is proposed.

## 5. Per-axis `motionVectorScale`: exact trace and numerical contract

### 5.1 Public and open-source paths

**Header [P3, H].** `ffxDispatchDescUpscale::motionVectorScale` is a `FfxApiFloatCoords2D` (two `float` components) described only as the scale factor for motion vectors. The header contains **no explicit positive/nonzero/finite range check**, no magnitude limit and no `(0,0)` sentinel. `upscaleSize` has a documented two-zero optional-default behaviour; **it is a different field** [P3/P7]. Neither header nor converter adds a unit tag.

**Sample [P9, S].** SDK sample sets `dispatchUpscale.motionVectorScale=(renderWidth, renderHeight)`. Its actual motion shader computes `(previousNDC-currentNDC)+jitterCorrection`, multiplies by `(0.5,-0.5)` to yield top-down UV space, and then the host scale converts UV to pixels. That is a specific coherent example, not proof that all consumer vectors are UV or that NDC is accepted without a convention change.

**Open FSR3 [P7/P8, O3].** The host code sets `T = upscaleSize` when `FFX_FSR3UPSCALER_ENABLE_DISPLAY_RESOLUTION_MOTION_VECTORS`, otherwise `T = renderSize` (both are active dimensions), and writes the GPU constants

\[
C_x = S_x/T_x,\qquad C_y=S_y/T_y,
\]

where `S = (motionVectorScale.x,motionVectorScale.y)`. The HLSL reads `m=(inputMotion.xy)` and computes `d_uv = (m_x C_x,m_y C_y)`; with **jittered-motion** option it subtracts `(previousJitterOffset-currentJitterOffset)/T` per axis. Explicitly:

\[
\boxed{d_{uv,i}=m_i\,{S_i\over T_i}-\mathbf1_{\mathrm{jittered}}\,{J_{\mathrm{previous},i}-J_{\mathrm{current},i}\over T_i},\quad i\in\{x,y\}.}
\]

This operation occurs when loading/input dilating motion, before temporal reprojection/history use. Thus `S_i` is a **multiplier producing pixel-equivalent displacement per stored motion unit in the selected T-axis coordinate system**, not itself the final normalised-UV multiplier. `S=(T_x,T_y)` applies native UV vectors directly; `S=(1,1)` divides pixel vectors by active T to obtain UV displacement. Dynamic active dimensions affect the denominator **on each dispatch**; immutable allocation maxima are not the denominator for these visible FSR3 lines. Display-resolution vectors change `T` for **both scale and jitter cancellation**. The renderer still owns the current-to-previous sign and +X-right/+Y-down screen conventions; the wrapper does not invert or resample vectors. Neither UV/pixel selection nor explicit signed scales forces an implicit history reset.

**Open FSR2 [P10, O2].** The open FSR2 path performs the **same componentwise division and jitter-cancellation subtraction**, and its shader loads `.xy`, multiplies by its `MotionVectorScale` constant and subtracts jitter cancellation if enabled. However, FSR2 chooses **`context->constants.displaySize`** when display-resolution motion is enabled, otherwise active `renderSize` [P10]. `displaySize` is the context's configured display size, unlike FSR3's active `upscaleSize`. Thus, for FSR2 display-resolution motion with a requested smaller active output, the open expression's denominator is the fixed display dimension, and even a wrapper-supplied *active-output UV scale* would not constitute a general guarantee of identity UV scaling. This difference is material alongside the supplied observation that provider 2.3.4 retained maximum output. It is **not** a reason to change the wrapper's existing default or maximum-allocation policy in U05.

**Scope limit [?].** The above arithmetic is **proved for the pinned open FSR3 and FSR2 source paths** [P7/P8/P10], not for the proprietary FSR4 4.1.1 and not automatically for a particular installed 2.3.4 provider binary. Public sample/headers show field forwarding intent but no closed-source exact shader calculation. Additional open provider-specific forwarding layers between the public 4.1.1 descriptor and any closed runtime are not demonstrably exhaustively visible in this source record; avoid a claim of byte-for-byte closed-provider forwarding. The compiler, native provider and GPU can apply further transforms/precision truncations.

### 5.2 Sign, axes, and a documented contradiction

The public `FfxApiFloatCoords2D` has independent signed `float` fields [P1/P3, H]. The visible FSR3 and FSR2 host/HLSL paths multiply components separately without `abs`, clamping, sign normalisation or an `x==y` check [P7/P8/P10, O3/O2]. **A negative X or Y, and unequal magnitudes, are mathematically forwarded through these open paths**; they are **not expressly guaranteed** by the docs for *all* providers. To use signed/asymmetric values meaningfully, the renderer must explicitly define what its texture channels represent; for a raw conventional NDC delta `previousNDC-currentNDC`, top-down UV displacement would call for effective scale `(T_x/2, -T_y/2)` (with appropriate handling of jitter) **if no shader-side UV conversion has already occurred** [I]. But the pinned FSR4 guide [P5, D] presents that same raw NDC subtraction with *positive full `(width,height)`* host scales. This is **not generally equivalent** to Cauldron's `[0.5,-0.5]` conversion [P9, S]. Preserve this conflict; do not silently endorse the guide example as a universal NDC conversion. The correct scale depends on the **actual producer convention**, including viewport orientation, previous/current direction and jitter definition. Quality analysis is out of scope.

### 5.3 Numerical cases and what finiteness can promise

The pinned open FSR3 and FSR2 **debug message checkers**, not dispatch gates [P7/P10], warn if `S_x > maxRenderWidth` or `S_y > maxRenderHeight`, and **independently** if either component compares equal to `0.0f` [P7, O3]. It does **not** enforce the warning as a hard limit and uses an upper-only test: negative scales (including large negative magnitudes) evade that condition, and a legitimate display-resolution UV scale larger than max render size may trigger a warning. The exact public contract has **no positive-only precondition**. Per-component findings:

| Input | Documented/native visible treatment | Consequence for proposed Rust validation |
|---|---|---|
| Ordinary finite, nonzero, including asymmetric and negative components | Representable as `float` [H]; independently multiplied/divided without clamping in open FSR3 [O3]; negative acceptance across closed providers unknown [?]. | Permitting is reasonable as *explicit native request*, not a provider correctness guarantee. Do not use `abs` or replace sign. |
| `(0,0)` | No special scale sentinel [H]; debug checker warns twice conceptually (condition is OR) [O3]. | Do **not** treat as “use default”; it is a zero-scale request. |
| `(0,a)` or `(a,0)`, including `-0.0` | Any zero component triggers same warning (`-0.0f == 0.0f`); arithmetic makes that axis zero in FSR3 absent jitter term [O3]. | Finiteness alone admits them. May reject as a separately documented wrapper policy if needed, but zero is **not** a public forbidden value. Retain negative-zero bits if permitting. |
| Very small nonzero finite | No checked minimum [H/O3]; host divides by T and GPU may underflow/flush, later denorm/quantise [I]. | Finiteness cannot guarantee nonzero *effective* scale or useful reprojection. Do not invent `epsilon`. |
| Very large finite | No public max; FSR3 warns only if positive and above max render, not abort; downstream products `m*S/T` can exceed finite/representable ranges [I]. | No evidence-based universal magnitude cap; finiteness cannot guarantee finite products/read positions. |
| `NaN` | No public rule [H]; FSR3 comparisons to max or zero ordinarily fail for NaN, so warnings do not catch it [O3/I]. | Reject non-finite at Rust boundary, as a clear wrapper correctness policy. |
| `+∞` / `−∞` | Header type can carry them [H]; positive infinity triggers greater-than warning in FSR3; negative infinity generally avoids it [O3/I]. Invalid shader arithmetic may propagate [I]. | Reject non-finite at Rust boundary. |

**Assessment.** `x.is_finite() && y.is_finite()` is an **inspectable minimum hygiene policy**, not proof of valid motion or general provider safety. It admits zeros, extreme values and signed/asymmetric requests; the open path gives no safe universal numerical domain. Because the dispatch is already explicitly unsafe GPU recording, the renderer/provider compatibility and sound image content must remain documented preconditions. There is no defensible source-derived universal cap such as `[0,maxRenderSize]` or even a universal positive-only restriction. A stricter zero rule must be called an **independent wrapper decision**, with explicit impact on native expressiveness, never misrepresented as SDK validation.

## 6. Minimum raw bindings and possible checked API contract

### 6.1 Raw `fsr-sdk-sys` declarations [proposal]

No new native dispatch field is required: archive already defines `FfxApiFloatCoords2D` and the `motionVectorScale` field with `repr(C)` layout. To represent additional established DX12 converter cases, add *numerically verified*, exact [P1] enum constants to `api.rs`, maintaining their native discriminants and existing names; minimum high-value candidates: `FFX_API_SURFACE_FORMAT_R32G32_FLOAT` (**6**), `FFX_API_SURFACE_FORMAT_R32G32B32A32_FLOAT` (**3**), `FFX_API_SURFACE_FORMAT_R16_FLOAT` (**21**), `FFX_API_SURFACE_FORMAT_R8G8B8A8_UNORM` (**10**), `FFX_API_SURFACE_FORMAT_R8G8B8A8_SRGB` (**12**), `FFX_API_SURFACE_FORMAT_B8G8R8A8_UNORM` (**14**), `FFX_API_SURFACE_FORMAT_B8G8R8A8_SRGB` (**15**), `FFX_API_SURFACE_FORMAT_R11G11B10_FLOAT` (**16**), `FFX_API_SURFACE_FORMAT_R10G10B10A2_UNORM` (**17**); conditional depth-view research additionally needs `FFX_API_SURFACE_FORMAT_R32_TYPELESS` (**37**) and potentially corresponding 16/32/64-bit family names. Preserve the raw layer as faithful C ABI, without smuggling a “format supported” judgement into constants. The `FfxApiResourceUsage` bits are already sufficient for the current four formats. Do **not** add arbitrary native constants because an enum case exists but `ffxApiGetSurfaceFormatDX12` lacks implementation (e.g., 3×32 FLOAT) without separate explicit rationale.

Static ABI checks should compare raw numeric constants to [P1] and (for pre-existing structures) `sizeof`, `alignof` and `offsetof` of `FfxApiResourceDescription`, `FfxApiResource`, `FfxApiFloatCoords2D` and `ffxDispatchDescUpscale` against a C++ translation unit built with **the same pinned headers and Windows MSVC target**. A new scale policy should not silently change C ABI fields.

### 6.2 High-level `fsr-sdk` [proposal]

* Preserve `MotionVectorUnits::Uv` and `::Pixels` *exactly*: calculate `(active T.width, active T.height)` and `(1,1)` respectively. Existing defaults stay UV; users of either ownership family do not change behaviour or scale bytes as a result of adding another option.
* Add a **distinct explicit native-axis-scale choice** (e.g., `NativePerAxis { x: f32, y: f32 }` alongside the two existing variants, or an equally unambiguous optional override), with public documentation stating: “multiply sampled motion per axis into **pixel-equivalent displacement at the selected active motion resolution**; FSR3 then divides by that active extent to obtain UV displacement.” It is **not** an “NDC” or generic “UV scale” variant. Preserve exact finite supplied `f32` bit patterns, including negative zero if admitted; no clamping, rounding, sign rewriting, implicit conversion or history reset. Keep source-level defaults explicit, not `(0,0)` sentinel-based.
* Validate finiteness before writing the descriptor (not only at value construction if unchecked copies can reach dispatch). If zeros are rejected, document this as a deliberate checked-wrapper policy **stricter than public headers**, not as a native guarantee. A `NegativeZero` value remains equal to zero in normal comparisons but could still be forwarded bit-exactly when allowed. Store and forward raw `(x,y)` unchanged.
* Extend the *reviewed, role-aware* DX12 format converter rather than indiscriminately accept every `ffxApiGetSurfaceFormatDX12` branch. Use a role table of **documented supported-by-wrapper** alternatives only, with separate checks for SRV view compatibility, UAV typed stores and renderer's chosen colour/depth encoding. A format family may be documented and still remain a blocked/capability-conditional extension pending checks. Avoid implicit copy, resampling, staging, view creation or pixel conversion.
* Any new input format must be reachable through **both local and movable families** via the same shared mapping/inspection path; preserve local thread confinement and optional `Send + !Sync`. No changes to ownership design, public callbacks, unrelated SDK effects, or max-allocation policy.

### 6.3 Responsibility and safety partition

| Inspectable Rust/DX12 contract | Provider/device/runtime obligation [?] | Renderer obligation |
|---|---|---|
| MSVC C ABI, enum mapping; nonzero active dimensions and immutable maxima; actual DX12 resource shape (`TEXTURE2D`, 1 sample/mip/slice), device identity, `GetDesc` allocation extents and flags; presence of compatible legal SRV/UAV formats, `CheckFeatureSupport` bits where queryable; consistent FFX supplied description; motion-scale finiteness; disjoint identity policy and optional masks. | Selected installed provider supports the role+format+view+flags; actually consumes/scales each axis; does not read invalid regions or write outside allocation, particularly with dynamic output and sharpening; provider-specific image precision and depth/sRGB interpretation; descriptor creation and GPU use remain valid on the actual adapter. | Correct filled image content including input padding/footprints; normalised mask values; depth convention/projection; motion vector direction, origin, jitter and units; correct colour transfer; actual `NON_PIXEL_SHADER_RESOURCE`/`UNORDERED_ACCESS` transitions; backing-storage non-aliasing where required; residency, command recording, submission, barriers, fences, resource and command-list GPU lifetime. |

**Key contract conclusion [I]:** actual `ID3D12Resource::GetDesc` is a necessary allocation inspection, **not** a complete view or provider certificate. When a proposed format requires an explicit compatible SRV reinterpretation that the backend hard-codes differently, the current contract cannot honestly expose it without further targeted work. `ffxQueryDescUpscaleGetResourceRequirements` is an optional/required *resource* query [P5], not a format-capability query. Nor can the FSR4 4.1.1 API version be taken to imply matching semantics in 3.1.5 or 2.3.4 implementations.

## 7. Differences from baseline

1. **Broader *documented families*** [D]: colour is application-specified, depth is one floating component (precision app-chosen), and motion is two floating components. The current exact `RGBA16F/R32F/RG16F` selection is a **wrapper policy**, not the maximum suggested by those public descriptions. High-priority candidate for motion is `R32G32_FLOAT`; depth `R16_FLOAT` and colour families require distinct provider and DX12 validation. Exact `R8_UNORM` masks and `R32_FLOAT` exposure remain directly prescribed in FSR3 docs, without a source-backed generic alternative.
2. **Real DX12 backend is format-metadata-sensitive** [B]: native enum from real DXGI desc is *not* sufficient to describe all generated SRV/UAV semantics. The backend patches D32/D32S8/typeless and sRGB cases; typed UAV flags/capabilities and sometimes typed depth family need further inspection. This is a stronger finding than an enum-to-DXGI lookup list.
3. **Explicit signed/asymmetric scales are expressible in the C ABI and the visible FSR3 math** [H/O3]. The current UV and pixels routes can remain invariant while exposing finite native exact components, but *provider-wide* correctness and a numerical safe domain are unproved. FSR3 warns on zero but does not reject; there is **no motion-vector `(0,0)` sentinel**. The FSR4 raw NDC example conflicts with Cauldron's explicit NDC→UV half-scale/Y flip.
4. **The open FSR2 denominator differs:** display-resolution motion uses configured `displaySize`, not FSR3’s active output dimensions [P10]; current dynamic-output 2.3.4 behaviour therefore cannot be described using FSR3’s `T` without qualification. **No baseline safety result changes:** supplied maximum-allocation policy, distinct identities, active rectangles, optional-mask forwarding, renderer GPU obligations, owner-family parity, and the 2.3.4 output overrun uncertainty remain in force. The prior 62/257-case results were **not** rerun and do not verify any format addition or arbitrary scale.

## 8. Minimal verification after implementation and bounded spikes

The following are **future** checks, not work performed on 2026-10-19. Avoid a broad exploratory format × provider × resolution × sharpening matrix or subjective image quality campaign through 1.0.0.

### Ordinary regression/ABI verification

1. **C/Rust ABI and enum values:** compile a pinned MSVC comparison translation unit. Check all new enum discriminants, exact field offsets, structure alignment and sizes. This is a host-build check, no GPU.
2. **Deterministic converter tests:** for *each explicitly offered* role/format pair assert exact `DXGI_FORMAT` → `FFX_API_SURFACE_FORMAT_*`, required SRV/UAV view interpretation, flags, metadata and rejected wrong-role cases. Check `R32_TYPELESS`/`D32_FLOAT`/D32S8 and RGBA8 sRGB are **rejected** until implemented/verified separately. Test output without UAV, input with `DENY_SHADER_RESOURCE`, unsupported typed UAV store, MSAA/mips/array slices, wrong device, active/max dimensions, and accepted vs rejected aliases. Keep raw enum enumeration separate from policy.
3. **Scale-forwarding tests for shared descriptor construction:** verify existing UV `(active width,height)` and Pixels `(1,1)` on both motion-resolution selections, dynamically varying active dimensions, with optional jitter and both ownership families. For explicit values use positive unequal, negative unequal, `-0.0` (if admitted), single-axis zero, both zero, smallest/large finite and ±∞/NaN rejection. Inspect **bitwise** `FfxApiFloatCoords2D` on the emitted descriptor, no implicit reset, no sign/scale rewriting; ensure the family shares the same mapper. Controlled ABI forwarding does **not** prove actual GPU consumption.
4. **Targeted native smoke only after format/view preflight:** instantiate each selected proposed format on the pinned platform; create the *exact views the backend will create* with DX12 debug layer and GPU-based validation where available; check `CheckFeatureSupport` for reads/stores; dispatch into a guard-backed output with GPU fence and full-allocation readback, **including** active vs full-extent coverage and sharpening because of the supplied 2.3.4 negative results. Success requires no validation errors and no out-of-allocation writes, and correct data flow rather than `FFX_OK` alone. Start with the least expansive single-format test (`R32G32_FLOAT` motion at fixed allocations) rather than accepting all enumerated formats.

## 9. Open limitations, provenance, and acceptance boundary

* The proprietary FSR4 4.1.1 implementation and any closed provider dispatch validation/math cannot be traced with this pinned public tree. The 3.1.5 open FSR3 path demonstrates its *own* calculations only; the 2.3.4 binary's variable-output safety evidence in the supplied baseline is expressly negative. No closed-provider undocumented capability is inferred from version strings.
* No exhaustive provider **external format allow-list** was found in the inspected headers or docs. `APPLICATION SPECIFIED` identifies shape/semantic flexibility, not automatic support of arbitrary DXGI formats. DX12 feature support must be queried on the actual adapter and complemented by the provider spike if extending accepted formats.
