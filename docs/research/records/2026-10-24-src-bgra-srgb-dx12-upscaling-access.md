# Source investigation: BGRA8 and sRGB resource access through the pinned DX12 FSR API

- **Investigation date / source access:** 24 October 2026 (UTC).
- **Topic and scope:** BGRA8 UNORM, RGBA8 UNORM sRGB and BGRA8 UNORM sRGB allocations used as the main colour input, main output, opaque-only generation colour input, and pre-upscale generation colour input. Closely related typeless resources are included only to establish whether they provide an actual sRGB-view route.
- **Baseline and evidence cut-off:** User-supplied `fsr-sdk` 0.3.0 / `fsr-sdk-sys` 0.2.0 development baseline, targeting AMD FidelityFX SDK **v2.3.0**, immutable source commit [`60f4ea81909200d8542eca14dccb2628b763a9a3`](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/tree/60f4ea81909200d8542eca14dccb2628b763a9a3), Windows x64/MSVC, DX12. Public `ffx_upscale.h` in that tree identifies the API upscaler version as 4.1.1 [S4].
- **Method:** Read the public types and DX12 helper, the pinned generic DX12 backend's format conversion and resource registration, pinned open FSR3 shader callbacks and upscaler API/docs; compare with Microsoft's DX12 casting specification, feature-level format table and API documentation; inspect a small number of versioned primary-source integration examples. Distinguish demonstrated source code, documented contracts, deductions, and provider-dependent hypotheses. **No repository modification, build, shader compilation, GPU run, driver query or native spike was performed.**
- **Archive usage:** The supplied project ZIP was inspected only for conventions and relevant pre-existing records. Its record convention is `docs/research/records/YYYY-MM-DD-src-description.md`; the archive is *not* an independently established Git revision or evidence of new native testing. This record is standalone and can be imported at `docs/research/records/2026-10-24-src-bgra-srgb-dx12-upscaling-access.md`.

## 1. Question, boundary and principal findings

**Question:** Which of the three new allocation formats can the existing borrowed-`ID3D12Resource` API safely and meaningfully expose in each role, through the *actual pinned SDK backend*, and what minimal implementation and experiments are justified?

1. **Verified source fact:** The public helper recognises all three typed formats and both relevant typeless families; recognition is *not* role permission. `ffxApiGetResourceDX12` takes the allocation's `GetDesc().Format`, derives resource usage from its actual flags, and does not accept an SRV/UAV descriptor [S1–S2].
2. **Verified source fact:** `RegisterResourceDX12` derives both view formats from `patchDxgiFormatWithFfxUsage(GetDesc().Format, description.format)` and creates its own views. Typed RGBA8-sRGB and BGRA8-sRGB allocations generate **sRGB SRVs and UNORM UAVs**; BGRA8 UNORM generates **UNORM SRV and UNORM UAV**. Typeless RGBA8/BGRA8 allocations instead generate **UNORM SRVs and UNORM UAVs**, *not* sRGB SRVs [S3].
3. **Verified source fact:** The pinned `patchDxgiFormatWithFfxUsage` honours a supplied surface-format override for **fully typed RGBA8 UNORM/sRGB allocations**, but has **no corresponding BGRA case** and no typeless RGBA8/BGRA8 case [S3]. Thus an sRGB view of a typeless BGRA8 allocation is legal in DX12 but **not expressible via the pinned backend's ordinary borrowed-resource registration route**. A caller-created SRV is not passed through this API. This is a *concrete, narrower* capability gap, not a reason to add a generic public format override without demonstrated need.
4. **Verified DX12 rule:** `_SRGB` formats are legal SRV formats; **neither `_SRGB` format is a legal typed UAV format**. The backend correctly chooses same-family `_UNORM` UAV views, which may be legal even for a fully typed `_SRGB` allocation under DX12 relaxed casting. `R8G8B8A8_UNORM` typed UAV/store support is required at FL12.0; `B8G8R8A8_UNORM` typed UAV/store support is **optional and must be queried** [D1–D4].
5. **Inference from API and shader access:** An sRGB SRV yields decoded RGB shader values, whereas an UNORM SRV yields normalised encoded **byte values** if those bytes contain sRGB. The BGRA-labelled view supplies logical `r,g,b,a` to the shader; it is not an invitation for the wrapper to manually reverse `.rgb`. The transfer function, colour primaries, alpha convention and memory byte order are independent properties. Open FSR3 input callbacks read `.rgb`; its output callback stores `(rgb, 1.0)` through a UAV. This does **not** prove equivalent semantics of shipped closed providers [S5, D1, D5].
6. **Unresolved:** Actual closed-provider acceptance, signal processing under non-linear flags, and quality/correctness for the candidate views cannot be inferred from converter membership, native return codes or successful DX12 descriptor creation. In particular, prior supplied experiments establish generation writes only on provider 3.1.5; acknowledged non-writes on tested 4.1.1/2.3.4 configurations remain failures, not format support.

**Baseline delta.** Existing accepted colour allocations remain as supplied: `R16G16B16A16_FLOAT`, `R32G32B32A32_FLOAT`, `R11G11B10_FLOAT`, `R10G10B10A2_UNORM`, and `R8G8B8A8_UNORM`. BGRA8/sRGB candidates are **not yet accepted**. The investigation adds exact source-supported mappings, identifies optional BGRA output stores, distinguishes typed-sRGB from typeless access, and highlights the absence of automatic output sRGB encoding. It does not change allocation geometry, colour-control defaults, renderer ownership, context threading, or provider policy.

## 2. Exact source path: allocation → public helper → native format → backend view → shader

### 2.1 Source definitions and helper metadata

`FfxApiSurfaceFormat` contains `R8G8B8A8_UNORM`, `R8G8B8A8_SRGB`, `B8G8R8A8_TYPELESS`, `B8G8R8A8_UNORM`, and `B8G8R8A8_SRGB` [S1]. Note that the native names omit `UNORM` before `SRGB`. The helper maps the corresponding `DXGI_FORMAT_*` values, including `R8G8B8A8_TYPELESS`, to these native values [S2]. It assigns `description.usage = READ_ONLY` for an ordinary colour texture and adds `UAV` only when the allocation has `D3D12_RESOURCE_FLAG_ALLOW_UNORDERED_ACCESS`, independently of any additionally supplied usage bits [S2]. The owner still supplies correct resource states, command list, fences and lifetimes.

For the relevant allocation, the *default* public helper gives:

| Actual `GetDesc().Format` (DXGI prefix omitted) | Helper `FfxApiSurfaceFormat` (prefix omitted) | Backend `descFormat` after patch | Backend SRV | Backend UAV *when allocated with UAV flag* |
|---|---|---|---|---|
| `B8G8R8A8_UNORM` | `B8G8R8A8_UNORM` | `B8G8R8A8_UNORM` | `B8G8R8A8_UNORM` | `B8G8R8A8_UNORM` |
| `R8G8B8A8_UNORM_SRGB` | `R8G8B8A8_SRGB` | `R8G8B8A8_UNORM_SRGB` | `R8G8B8A8_UNORM_SRGB` | `R8G8B8A8_UNORM` |
| `B8G8R8A8_UNORM_SRGB` | `B8G8R8A8_SRGB` | `B8G8R8A8_UNORM_SRGB` | `B8G8R8A8_UNORM_SRGB` | `B8G8R8A8_UNORM` |
| `R8G8B8A8_TYPELESS` | `R8G8B8A8_TYPELESS` | `R8G8B8A8_TYPELESS` | `R8G8B8A8_UNORM` | `R8G8B8A8_UNORM` |
| `B8G8R8A8_TYPELESS` | `B8G8R8A8_TYPELESS` | `B8G8R8A8_TYPELESS` | `B8G8R8A8_UNORM` | `B8G8R8A8_UNORM` |

Native conversion: `ffxGetDX12FormatFromSurfaceFormat` [S3a]; RGBA8/BGRA8 sRGB UAV correction: `convertFormatUav` [S3b]; typeless SRV fallback: `convertFormatSrv` [S3c]; patch: `patchDxgiFormatWithFfxUsage` [S3d]; descriptor construction: `RegisterResourceDX12` [S3e]. The resource's *own DXGI format* is consulted during registration, not only the enum that appears in the public converter.

**Important qualification:** The table describes the backend's **attempted descriptor formats**, not guaranteed successful resource creation, legal stores on every adapter, or provider correctness. In an input-only role the backend creates an SRV; there need not be a UAV. Its UAV descriptor exists for flagged resources, regardless of whether the role later writes it. Conversely, the main output must actually permit UAV access. The public `additionalUsages` parameter does not manufacture a missing D3D12 allocation flag [S2, S3e].

### 2.2 The exact typed/typeless distinction

- **Typed sRGB allocation:** `R8G8B8A8_UNORM_SRGB` or `B8G8R8A8_UNORM_SRGB` is passed through unchanged for SRV creation, and converted to same-family `_UNORM` for UAV creation [S3b–S3e]. This paired view pattern is the *existing* path; no pre-created view or new wrapper abstraction is required. Its UAV legality remains conditional on resource-flag and device support, particularly for BGRA.
- **Typeless allocation:** DX12 can create compatible `*_UNORM` and `*_UNORM_SRGB` typed SRVs of a typeless family [D1–D2]. The pinned backend, however, selects `_UNORM` for both typeless families [S3c]. The public helper carries only the allocation-derived enum. For BGRA, supplying another `description.format` alone does not alter the backend view because the patch switch lacks BGRA cases [S3d]. For RGBA typeless it likewise falls through unchanged. **An sRGB decoder is therefore not selected by merely submitting a typeless texture.**
- **Fully typed `_UNORM` with encoded sRGB bytes:** DX12 relaxed casting may legally expose a same-family sRGB SRV [D1]. The pinned backend has a special **RGBA8** metadata override path, but its *default helper* does not choose that override; no parallel **BGRA8** override path exists [S2, S3d]. Current wrapper colour hints do not reinterpret allocation view descriptors. Treat this as a potential future requirement only upon concrete need, rather than introducing an open-ended public format override.
- **No RGBA/BGRA cross-family casting:** `R8G8B8A8_*` and `B8G8R8A8_*` are distinct DXGI format families; relaxed casting does not authorise a view of the former as the latter [D1]. Resource format naming and actual packed byte order are not a reason to reinterpret as another family.

### 2.3 Shader-visible values and alpha

The open pinned FSR3 HLSL callback declares `Texture2D<FfxFloat32x4> r_input_color_jittered`; `LoadInputColor` returns `.rgb` and `SampleInputColor` samples `.rgb` [S5a]. A second SRV `r_input_opaque_only` is read as `.xyz` by `LoadOpaqueOnly` [S5c]. The public reactive-generation descriptor identifies `colorOpaqueOnly` and `colorPreUpscale` as distinct renderer inputs [S4b]. Thus both are **read-oriented colour resources**; they may have different allocation formats when the *actual decoded signals* remain comparable. The shader-facing `float3` hides no physical swizzle requirement from the renderer, but a mismatched transfer function between these inputs will distort their difference metric.

The open output callback `RWTexture2D<FfxFloat32x4> rw_upscaled_output` assigns `float4(fColor, 1.f)` [S5b]. For that callback, no input alpha is preserved: output alpha is **1** in the shader store; actual bit pattern follows UAV conversion and quantisation. This is **shader-specific evidence**, not a universal public alpha contract for all provider generations or sharpening paths. Neither `InputColorSpace`/colour hints nor the `_SRGB` suffix specifies straight versus premultiplied alpha or Rec.709 versus other primaries. The wrapper must not synthesize alpha, tone mapping, channel swizzles, exposure, copies or history reset.

In DXGI terms, the *view* controls transfer decoding: `*_UNORM` maps integer bytes `n` to `n/255`, whereas `*_UNORM_SRGB` converts the RGB samples to linear-light values using the sRGB electro-optical transfer; **alpha stays un-gamma-corrected**. Logical shader components remain `(r,g,b,a)` for both BGRA8 and RGBA8 views. The application must distinguish the memory layout used to upload/read back data (BGRA8 bytes `B,G,R,A`) from the logical RGB signals. This affects `Texture2D.Load` as well as point or filtered sampling; filtered sRGB SRV sampling takes place in decoded signal space as defined by the graphics API [D5].

A typed UAV view with format `*_UNORM` normalises and quantises the shader's float store; **it does not apply the sRGB output transfer function**. No `_SRGB` UAV exists to encode automatically [D2]. Consequently the bytes written by the FSR output are UNORM quantisations of the shader-provided values. Whether those values were already encoded, linear, clamped, exposed, sharpened or transformed inside a particular provider is a *separate algorithm question*, not settled by the allocation name. Displaying the output through an sRGB SRV later applies **decoding**, not encoding. A renderer needing encoded sRGB bytes must own an appropriate final conversion/encode stage, unless it has independently established that the provider's output floats are already encoded.

### 2.4 Independent non-linear API controls

The pinned public API specifies `FFX_UPSCALE_ENABLE_NON_LINEAR_COLORSPACE` at context creation and per-dispatch `FFX_UPSCALE_FLAG_NON_LINEAR_COLOR_SRGB`/`_PQ` [S4a]. The supplied wrapper baseline maps these independently as `InputColorSpace::{Linear, NonLinear}` (default `Linear`) and `ColorEncodingHint::{Unspecified,Srgb,Pq}` (default `Unspecified`) with checked rules and a documented per-frame exception. The flag semantics refer to **input signal classification**, not to the DXGI descriptor transfer operation; they do not select a view format [S3d, S4a].

Potential signal mismatches that **must not** be conflated:

1. Encoded sRGB bytes + `_UNORM` SRV + no hint: shader sees encoded numbers but application classifies them as linear.
2. Encoded sRGB bytes + `_SRGB` SRV + an sRGB **non-linear** hint: shader already sees decoded values, while a provider may interpret them as still encoded, potentially creating *double decoding*. The actual provider response to the flag is unverified.
3. Linear numerical bytes + `_SRGB` SRV: the SRV decodes a signal that was not sRGB encoded, corrupting the intended values irrespective of the flag.
4. Encoded and decoded generation colour inputs mixed under different views: colour-difference metric is not measuring like signals.

AMD's pinned FSR4 integration guidance **prefers linear input** and presents the non-linear creation flag as an alternative where that is impracticable [S6]. This is an **upstream recommendation**, not source proof of provider transfer-function implementation. Do not reopen general PQ/HDR/exposure research here.

## 3. DX12 legality, queries and exact role/format matrix

### 3.1 Applicable checks

**Read-only inputs** (main colour, opaque-only, pre-upscale): the resource must be a renderer-owned, compatible single-sampled Texture2D with shader-readable state and a legal typed **SRV**; verify relevant `D3D12_FORMAT_SUPPORT1_TEXTURE2D` and `SHADER_LOAD` (plus `SHADER_SAMPLE`, where filtered) for the *actual SRV format*, and that the allocation does not have `DENY_SHADER_RESOURCE`. No `ALLOW_UNORDERED_ACCESS` or `UAV_TYPED_LOAD/STORE` is required by the role merely because the backend contains a UAV converter [D2–D4].

**Main output:** resource must have `D3D12_RESOURCE_FLAG_ALLOW_UNORDERED_ACCESS`; the **generated `_UNORM` UAV** needs `D3D12_FORMAT_SUPPORT1_TYPED_UNORDERED_ACCESS_VIEW` and `D3D12_FORMAT_SUPPORT2_UAV_TYPED_STORE` on the context device, not `_SRGB` UAV support. A read-only input capability test alone is insufficient. On an output allocation whose typed format differs from the generated typed view (e.g. `_SRGB` resource → `_UNORM` UAV), consult `D3D12_FEATURE_D3D12_OPTIONS3` / `CastingFullyTypedFormatSupported` and same-family compatibility, then check the *view format*. An UAV typed-load query is only relevant if an actually required shader path reads that UAV; the open store callback alone does not require it [D1–D4].

Microsoft's FL12.0 table lists RGBA8 UNORM typed UAV/store support as required, BGRA8 UNORM typed UAV/store as **optional**, and both sRGB typed UAV/store as **unavailable** [D2]. `CheckFeatureSupport(D3D12_FEATURE_FORMAT_SUPPORT, D3D12_FEATURE_DATA_FORMAT_SUPPORT{Format = view_format, ...})` is the per-device authority; `CastingFullyTypedFormatSupported` is distinct. These checks prove DX12 capabilities, **not** closed-provider recognition or correct colour handling. The actual allocation must also have compatible resource flags, usage and lifetime; provider restrictions remain unsafe-dispatch obligations.

**Necessary related typeless routes (not new role admissions):** `DXGI_FORMAT_R8G8B8A8_TYPELESS` → native `R8G8B8A8_TYPELESS` → S=`RU`, U=`RU` (when flagged); `DXGI_FORMAT_B8G8R8A8_TYPELESS` → native `B8G8R8A8_TYPELESS` → S=`BU`, U=`BU`. The ordinary backend **does not select sRGB SRVs** for either. The typeless allocations are not proof that a usable sRGB route exists under today's resource-only API, even though DX12 itself permits appropriately typed views. A concrete sRGB-typeless use case would require further SDK/backend investigation and possibly a *specific*, demonstrated extension, not a speculative generic override [S2, S3c–S3e, D1].

**Non-applicability versus unresolved access:** `_SRGB` **UAV view format** is definitively *not applicable* (DX12 disallows it). `_UNORM` UAV on an sRGB allocation is *potentially applicable* through same-family casting. BGRA output is *not globally disallowed*: it is applicable only on adapters reporting `BU` typed stores. Typeless sRGB **through this exact default backend path** is not currently expressed. All typed input/output candidates retain unresolved **provider** behaviour until bounded probes.

## 5. Open decisions, alternatives and recommended smallest slice

### 5.1 Constraints that are not design choices

- **Native/DX12:** The backend creates its own SRV/UAV; `_SRGB` is legal for reads, not typed UAV writes; typed output storage uses an `_UNORM` UAV; BGRA UAV stores are optional; same-family casting support must be checked [S3, D1–D4]. No adapter query certifies an actual FSR provider.
- **Renderer responsibilities:** Allocate the existing max-size single-mip/slice, single-sample Texture2D on the context device; select render/output *active regions* within allocations; choose and populate RGB encoding/primaries/alpha convention; honour upload/readback layout, transitions, command submission and fences; ensure comparable generator RGB signals and output presentation conversion. Do not change this geometry or ownership.
- **Wrapper policy:** Keep colour-space creation default `Linear`, per-frame hint default `Unspecified`, HDR separate, existing checked hint rules/exception, format-independent ownership models and unsafe dispatch boundaries. The wrapper can safely reject an output whose actual `_UNORM` view lacks typed UAV/store support, and can describe the backend-generated view per allocation without promising provider compatibility.

### 5.2 Recommendation and alternatives

**Recommendation (proposal, not acceptance):** Stage the smallest *source-justified and testable* admission as follows:

1. **First:** treat the two typed sRGB formats and typed `B8G8R8A8_UNORM` as *potential read-only* colour resources separately in **main input**, **opaque-only** and **pre-upscale** roles. Their exact SRVs follow directly from allocation format; no public view-format override is needed. Before accepting them as verified provider use, execute [T1] then [T3]/[T4] with correct signal controls. Document `_SRGB` view decoding separately from `NonLinear`/`Srgb` flags and require comparable generator signals.
2. **Then:** assess typed `R8G8B8A8_UNORM_SRGB` **main output** using its existing `_UNORM` UAV path, gated by allocation flag, same-family casting and UNORM typed store; use [T2]/[T3]. Avoid any suggestion that output will be sRGB-encoded merely because its *allocation* is suffixed `_SRGB`.
3. **Finally, but within the selected release target if applicable:** assess `B8G8R8A8_UNORM` and `B8G8R8A8_UNORM_SRGB` outputs with the per-device BGRA typed-store query, typed casting for the latter, and [T2]/[T3]. If the particular adapter cannot store `BU`, reject those outputs **on that device**, not globally. If a legal adapter/provider combination fails, keep it unresolved or rejected with concrete diagnostic evidence and a tracked explanation; do not fabricate support.

**Alternative A:** admit all device-legal typed resources at once with clear *unsafe provider obligations*, avoiding a provider allow-list. Smaller implementation surface but weaker evidence for particular provider behaviour; requires excellent dispatch documentation and validation that the wrapper does not accidentally promise closed-provider support.

**Alternative B:** support only read inputs first, postpone outputs until native proof; lower immediate DX12 risk, but only acceptable as a bounded sequencing step, **not permanent deferral of applicable access** from the selected release target.

**Do not add** a generic format override, conversion utility, caller-supplied SRV parameter, automatic fallback, invisible GPU probe, or provider allow-list. If a real user has typeless or typed-UNORM sRGB-encoded allocations requiring a specific sRGB SRV, first show the exact renderer allocation, target view, DX12 compatibility and observed backend failure. The narrow current backend gap, particularly for BGRA and typeless, may ultimately require upstream/backend changes rather than a Rust public option that is ignored.

## 6. Bounded proposed native spike protocols — **not executed**

All experiments require Windows x64/MSVC, a matching DX12 device/queue, *direct pinned-header C++ calls* to the exact SDK, named provider/version, logs of adapter/driver/`GetDesc()`/format queries, deterministic allocations at existing configured maxima, valid active extents, clean resource states and GPU-fence completion before readback. Preserve existing good controls and use no extra device-global validation campaign. Retain the source/command outputs, exact bytes, row pitches, input images, constants, native statuses, diagnostics and provider binary identity. A successful SDK return, no diagnostic or any changed pixel is **insufficient** for correctness.

### [T1] Independent backend-equivalent SRV signal and channel-order probe (highest priority)

- **Hypothesis:** A `BU` SRV yields correct logical R,G,B with no transfer decode; `RS` and `BS` SRVs yield correct logical R,G,B after sRGB decode; typeless resources with the pinned *default* conversion instead yield UNORM values.
- **Why source alone is insufficient:** Source specifies descriptor selection and graphics rules, but has not been executed on the target device, and does not validate the renderer's upload/readback byte ordering.
- **Minimal configuration:** Same device; 4×4 or 8×8 single-mip Texture2D, `BU`, `RS`, `BS`, and only if needed the corresponding typeless formats; shader-visible D3D12 SRVs with the exact view formats in §2.1, rather than a hypothetical caller-preferred SRV. Write a tiny independent HLSL compute shader that uses `Texture2D<float4>.Load` and point-sampling at known pixel centres, writes four floats to `R32G32B32A32_FLOAT` or a structured buffer. No FSR dispatch yet. Correct `RowPitch` on upload/readback.
- **Known bytes:** Logical colour A: `R=0x30, G=0x80, B=0xE0, A=0xA0`; store RGBA bytes `[30,80,E0,A0]` hex and BGRA bytes `[E0,80,30,A0]`. Colour B: `R=0xC0, G=0x40, B=0x10, A=0x7F`; use corresponding reversed BGRA order. Distinct RGB channels reveal R/B swaps. `UNORM` expected RGB(A) for colour A = `(0.188235294, 0.501960784, 0.878431373; 0.627450980)`; with sRGB SRV RGB = `(0.029556834, 0.215860500, 0.745404210)` while alpha stays `0.627450980`. Compute colour B expected values from the explicit formula below; do *not* use shader output as the expected reference.
- **Independent expected formula:** For `x = byte/255`, `srgb_decode(x) = x/12.92` when `x ≤ 0.04045`, otherwise `((x+0.055)/1.055)^2.4`; no decode on alpha.
- **Pass:** Each RGB component agrees with the independently calculated expectation to the precision of the float output (suggest `≤ 2×10⁻⁵` absolute for the float32 probe) and no channel swap; alpha unaffected by transfer decoding. **Fail:** Illegal descriptor, device removal, wrong RGB order, wrong sRGB/UNORM numerical result, or mismatch outside tolerance. **Inconclusive:** Invalid upload layout/coordinate mapping or test shader and expected data not independent.
- **Negative controls/cleanup:** Both BGRA and RGBA uploads for matching logical RGB; deliberately bind a same-family **UNORM** SRV to the encoded sRGB sample as a known numerical contrast; swap physical red/blue bytes as an additional detectable negative. Release descriptors/textures/temporary buffers only after fence. Do not reinterpret a typeless UNORM result as proof of an sRGB view.
- **Unlocks:** Source-vs-device agreement for actual *SRV interpretation*, not FSR-provider behaviour; whether typed candidate inputs can proceed to [T3]/[T4].

### [T2] Independent output UAV creation, typed store and byte-layout probe

- **Hypothesis:** `RS` allocation + `RU` UAV (with legal typed casting) stores ordinary UNORM bytes; `BS` allocation + `BU` UAV works **only** where BGRA typed UAV/store is reported; `BU` allocation + `BU` UAV uses BGRA layout; none implicitly sRGB-encodes shader floats.
- **Minimal configuration:** 8×8 single-mip `RU` reference, `RS`, `BU`, `BS` resources with `ALLOW_UNORDERED_ACCESS`; query `OPTIONS3.CastingFullyTypedFormatSupported`, and per-UAV-view `FORMAT_SUPPORT` (`TEXTURE2D`, typed UAV, typed store). For each supported route make the exact pinned-backend-equivalent UAV and run one trivial `RWTexture2D<float4>` write of `(48/255,128/255,224/255,160/255)` to all texels. Copy to readback with `GetCopyableFootprints`, check `RowPitch` and alpha. Also view read-only via the expected sRGB SRV where legal to demonstrate *decode at a subsequent read*, separately from storage.
- **Expected bytes:** `RU`/`RS` physical `[30,80,E0,A0]` hex; `BU`/`BS` physical `[E0,80,30,A0]` hex, allowing documented float→UNORM rounding tolerance if intermediate values differ. **No sRGB encode**: sRGB encoding of linear `0.1882`, `0.5020`, `0.8784` would yield different encoded bytes, which must not be mistaken for required UAV output.
- **Pass:** Flags/casts/format queries positive, resources/views valid, bytes and logical channels match UNORM storage, and read-only sRGB view demonstrates decode. **Fail:** Claimed-capable path cannot create/store, byte order wrong, spurious sRGB encoding. **Inconclusive:** The format is unsupported on the only test adapter (record *device-specific non-applicability* and seek another legal adapter rather than globally rejecting BGRA), or readback/fence invalid.
- **Negative controls/cleanup:** A `_SRGB` **UAV** view is a known-invalid control (do not treat its rejection as a product defect); no-UAV-flag allocation must not pass output validation; preserve `RU` reference. Fence and free all resources. **Unlocks:** Proper capability-gated role validation for main outputs; does *not* prove an FSR provider actually writes through the view.

### [T3] Direct pinned-header main-colour and main-output FSR dispatch, separately varied

- **Hypotheses:** (a) Each proposed typed sRGB/BGRA main input is consumable with the intended numerical signal when the rest of a known-good FSR3 configuration is held fixed; (b) each device-legal main output is really written with correct channel order and without assuming an automatic output encode.
- **Minimal configuration:** Reproduce a valid provider **3.1.5** pinned-header DX12 upscaling configuration using a known-good `R16G16B16A16_FLOAT` output and known-good **existing** main input; same active extents, camera jitter, depth, motion, exposure, pre-exposure, reset/history and sharpen controls on each arm. Use a small but genuine moving or edge-containing scene, e.g. render 320×180 and upscale to 640×360 with allocations at those maxima (or another proven valid size). Only change **one role**: input `BU`/`RS`/`BS` with fixed float output; then output `BU`/`RS`/`BS` with fixed known-good input. For sRGB input compare a correctly *encoded* copy of the same scene against its linear-float reference, distinguishing bytes from shader-visible values. Run direct C++ native API before any Rust integration.
- **Known signal and expected evidence:** Include the diagnostic two-colour RGB patches from [T1], an independently generated linear reference and equivalent sRGB-encoded inputs, a moving edge, controlled alpha, and a prior-frame reset. Exact upscaled pixels are *not* deterministically specified by the public ABI, so do not insist on cross-format bit equality. Predeclare region-specific tolerances from **same-format repeated reference** runs and known 8-bit quantisation; compare per-channel orientation, approximate signal/patch response, output-write sentinel replacement and per-frame continuity.
- **Pass:** Native call and diagnostics valid, defined output regions overwritten, no channel inversion, output signal consistent with matched valid control to justified tolerance, alpha inspected without extrapolating a universal contract. **Fail:** Creation/dispatch failure, no write, bad channel order, severe signal mismatch outside declared tolerance or device error. **Inconclusive:** Uncontrolled temporal history, colour flag/provider conversion ambiguity, dirty readback pitches, or unvalidated scene. Provider support remains limited to the exact tested provider/device/configuration.
- **Negative controls and isolation:** No-writes are failures even on `FFX_OK`; compare `NonLinear`/`Srgb` controls in *paired and separately labelled* tests only if necessary, never assume a flag decodes. Check output via raw byte readback **and** an independent typed view (no inference from display alone); include known-good RGBA8 UNORM and floating controls. Destroy after GPU idle; no broad image-quality, performance, provider sweep or cross-product campaign.
- **Unlocks:** Typed per-role output/input admission conditioned on native-provider obligations and appropriately bounded docs.

### [T4] Generated-reactive inputs, individually substituted on the writing provider

- **Hypothesis:** For each candidate `BU`/`RS`/`BS`, both generator colour-input roles read the intended comparable RGB signals and can produce the expected nontrivial `R8_UNORM` mask on provider **3.1.5**.
- **Minimal configuration:** Use the *previously demonstrated writing* generator provider 3.1.5; `R8_UNORM` UAV output initialised to sentinel e.g. `0xA5`, fixed scale/threshold/binary controls, and known-good colour pair. Run (1) opaque-only candidate + known-good pre-upscale colour, then (2) known-good opaque-only colour + pre-upscale candidate. Compare equivalent *decoded* RGB colours rather than arbitrary equal bytes; use same-format references with true differences in a few tiles and unchanged equal-signal tiles.
- **Expected result:** Equality tiles should show low/reactivity-reference-consistent mask; difference tiles should reproduce the reference's expected relative/threshold classification under fixed native controls. Establish exact byte expectations with an independent CPU implementation **only if** the pinned shader algorithm and flags are fully traced; otherwise use bounded same-format baseline tolerances and independent diagnostic classification, explicitly marking precision limits. Include RGB patches from [T1] to reveal BGRA swaps and sRGB-signal mismatches; alpha should not be treated as an automatically defined mask input.
- **Pass:** Sentinel overwritten in expected pixels; spatial mask response and colour-order differences agree with predeclared reference criteria; no uncontrolled change in the other role. **Fail:** No write, wrong spatial response or threshold classification, channel inversion, DX12 error. **Inconclusive:** Comparison uses different decoded colour spaces, uncontrolled threshold, or a provider without established writes.
- **Negative controls and cleanup:** Identical decoded pair should not react like a deliberately changed pair; a deliberately mismatched sRGB/UNORM pair should expose transfer mismatch rather than being labelled a supported workflow. Keep previous 4.1.1/2.3.4 acknowledgement-without-write cases **as failures**; do not reclassify them as successful generation on alternative formats. Fence and release resources. **Unlocks:** Each generator input role separately; no implication that main output is supported.

### Execution order and stop conditions

`[T1] → [T2] → [T3]` for the main roles; `[T1] → [T4]` for generation. Stop a branch when the necessary **view** is DX12-illegal or the device reports required support absent; document that adapter constraint rather than inventing output. Run the minimum provider/configuration sufficient to resolve each genuine wrapper design choice. Do not require GPU-based validation as a blanket gate; use targeted debug-layer diagnostics when a particular view failure merits it. These are **protocol proposals, not experiment results**.

## 7. Unresolved source questions and limits

1. **Closed-provider format and colour behaviour:** Are the three exact typed inputs and device-legal typed outputs accepted by each actually selectable provider, and what does each provider do with non-linear hints and output channel values? Public open callbacks and DX12 format queries do not answer this. Probe [T3]/[T4] separately; do not invent shader internals.
2. **Precise reactive algorithm and generation alpha semantics:** The public two-colour descriptor and the open `LoadOpaqueOnly`/main colour functions are identified, but this investigation has **not completely traced the generator's arithmetic kernel and flag-specific transformations**. Exact mask bytes should not be presented as source-verified until that kernel, its selected permutation and constants are verified. Use bounded reference/CPU calculations accordingly.
3. **sRGB encoding of final output:** No pinned public contract establishes universal linear or encoded output semantics for closed providers. `_SRGB` on a *resource* does not make a `_UNORM` UAV sRGB-encode. A presentation-stage conversion remains the renderer's decision until provider-specific data says otherwise.
4. **Typeless/typed-UNORM with sRGB-intended pixels:** Native DirectX has legal SRGB SRV routes, but the pinned backend defaults to UNORM for typeless and does not patch BGRA formats. A concrete renderer demand must be demonstrated before any change; if applicable to selected release target, keep it tracked to resolution, not silently discarded.
5. **Device class:** Microsoft's FL12.0 table gives mandatory versus optional features; no target GPU/driver or feature response was supplied or measured. Do not equate broad hardware availability with a format-support query.
6. **Historic observations:** Earlier 3.1.5 writing and 4.1.1/2.3.4 non-writing cases are **supplied project baseline**, not experiments independently reproduced here. The ZIP supplies naming and historical context only; it is not a verification of its Git commit or test logs.
