# Source investigation: complete DX12 upscaling surface for `fsr-sdk` 0.3.0

- **Investigation and source-access date:** 18 October 2026 (evidence cut-off).
- **Question:** Which public capabilities of the *pinned* AMD FidelityFX SDK v2.3.0 upscaling API remain inaccessible, unnecessarily constrained, or insufficiently justified in `fsr-sdk` 0.3.0 / `fsr-sdk-sys` 0.1.2, for Windows x64/MSVC and DirectX 12? What exactly must be implemented and verified before release?
- **Repository input:** supplied `fsr-sdk-rs-main(6)(2).zip`, SHA-256 `ccd27091a9c517e3602ad518d00c511a9629b70791e0e77653e6d9dab8fc3f14`. This is an archive snapshot, **not an independently identified Git commit**. Its manifests advertise the two development versions above. `AGENTS.md`, `.agents/INTRO.md`, the research process and its investigation/record skills were consulted first. Code, not roadmap ticks, determines the implementation baseline.
- **Upstream input:** `GPUOpen-LibrariesAndSDKs/FidelityFX-SDK`, release v2.3.0, **commit `60f4ea81909200d8542eca14dccb2628b763a9a3`**. Its public upscaler API version constant is **4.1.1**, a different number from the SDK release. All upstream hyperlinks below are pinned to this commit.
- **Method:** enumerate declarations, documented null-context routes and DX12 extensions; inspect the raw declarations, loader, context owner, both wrapper families, resource validation, tests and retained verification records; compare source contracts and evidence limits. No Rust compilation, runtime loading, GPU test, SDK upgrade, provider reverse engineering, implementation or other repository edit was performed. This is **source evidence**, not new native verification.
- **Exclusions:** image-quality research and tuning policy; other effects; Vulkan or other backends; new performance programmes; SDK updates; private provider implementation details which do not affect a public access or safety contract.

## Coverage matrix: every public upscaling descriptor, route and applicable common/DX12 extension

`Raw` reports **binding of that particular native entity**, not just a compatible function-pointer signature. `L/M` reports respectively the local `Runtime`/`Upscaler` and optional `MovableRuntime`/`MovableUpscaler`; `yes/yes` means separately callable in both, often via common private code. `—/—` means no high-level access in either. `Part/part` denotes an exposed but narrower contract. `ABI` means layout/constant verification for an *existing slice*, **not** evidence that all fields or providers were exercised. An absent entity has **no ABI/native proof** for that entity.

## What the narrow profile cannot establish

1. **Verified source fact — deliberate wrapper restrictions:** The wrapper fixes per-role formats and allocation extents, omits arbitrary native motion scale, hardcodes output `upscaleSize` from allocation, omits three debug flags and callback use, and does not let callers select providers, configure a live context, generate a reactive mask or supply allocators. These are actual code gaps (CO, D, B, V, C, RS), not assumptions based on milestone names.
2. **Upstream claim — wider documented data inputs:** G:85–100 describes application-selected colour and float depth/motion formats; G:109–116 describes NDC/scaled motion; U:92 explicitly permits per-dispatch output size, optionally defaulting to maximum. **Inference:** all three are public capabilities hidden by current fixed-profile validation. **Unresolved:** which exact alternate formats, shapes, active output transitions, states and provider combinations are accepted by each trusted binary. Solve access and validation without promising arbitrary shape or format compatibility.
3. **Verified source fact — supplied versus generated masks:** M15 forwards provided R8_UNORM images; this is not `ffxDispatchDescUpscaleGenerateReactiveMask`. E15 confirms GPU recording, fences and output in its selected profile, **not provider consumption or image-quality effect**. Generated-mask inputs/out buffer, flags and ordering create an additional GPU safety boundary; a generator must not replace the renderer's legitimate independent mask provision.
4. **Verified source fact — provider selection versus provider behaviour:** Enumeration and live identity work; explicit `ffxOverrideVersion` is absent. A:95–100 requires choosing an ID obtained by version query; Q:152–162 documents version-specific precreate queries. API version **4.1.1** must remain constant. **Unresolved:** signed/driver provider support is not established by returned names, numbers, a resource mask or a successful no-op.
5. **Verified source facts from pinned open-source investigation:** [The 15 October Configure study](2026-10-15-src-upscaler-configure-contract.md) traces the FSR3 five-key float pointer, null default reset and persistence, and observes **FSR2 returns OK while silently ignoring** the tuning descriptor. Thus **success is not proof of effective support**. Closed-provider pointer non-retention, error atomicity, GPU ordering and precise callback behaviour remain unproven. Finite-value checks prevent NaN/inf crossing into unknown numerical domains; provider default-reset is distinct from approximate numeric constants.
6. **Upstream claim and unresolved colour contract:** G:242–259 advises linear HDR and describes mutually exclusive sRGB/PQ hints; U contains no luminance-normalisation, primaries, input transfer ordering or tonemapping-control descriptor. The sample's flag selection is not a normative transfer formula. E16 demonstrates bounded frame execution but **15 changing-pre-exposure prediction failures**, with later static/reset controls passing; it does not isolate a Rust defect or establish PQ scaling or internal provider operations. **M16 remains a public integration-contract/documentation task**, not image-quality research.
7. **Renderer-owned, not missing SDK access:** correct linear/non-linear pixel values; pre-exposure multiplication and exposure input; matching projection/depth and motion conventions; camera jitter and `reset` decisions; opaque versus translucent scene captures for mask generation; mip bias; render→upscale framegraph placement; post-upscale tonemapping/HDR swapchain signalling; resource barriers, initial/returned states, alias-free backing storage, queue/fence ordering, residency and GPU completion. Rust validates available CPU/COM metadata but cannot inspect actual GPU contents, state, or submission abandonment (P). Wrapper documentation must state duties precisely; it must not turn them into automatic engine policy.
8. **Provider-dependent, not presumed defect:** unsupported flags, formats, per-frame output changes, generated masks, debug controls, allocator callbacks or Configure values may legitimately return SDK failure on a selected provider. Different declared functionality may be silently ignored (known FSR2 Configure example). Preserve native errors and public applicability conditions; do not promise every hardware/provider combination or demand private implementation disclosure. Unexplained memory-retention/threading requirements *are* integration issues if safe API use depends on them.

## Baseline delta, unresolved decisions and release rule

**Confirmed:** existing M10–M13/U03 routes, M14 variable-*render* region, M15 supplied masks, linear HDR and both local/movable ownership families are real source implementations with bounded pre-existing ABI/fixture/native evidence. They are *not* blanket provider guarantees. The previously stated **M14, M16, U01, U02 and R04** gaps remain. **Additional exposed gaps:** the complete debug checker/visualisation/message pathway; alternative documented texture format/usage conversion and arbitrary per-axis motion-vector scaling; context and DX12 custom allocation callbacks; and the **pre-create resource-requirements Query**, even though its live descriptor is already bound. These are independently identifiable in headers and code, not conjectured private features.

**Unresolved decisions requiring review, not silent research acceptance:** contract for selected-version ID validity and provider mismatch; typed Configure visibility, error poisoning and in-flight GPU work; resource format/shape/state validation without overpromising generic DX12 forms; variable output allocation versus active extent; callback/trampoline ownership and process-global native coordination (especially the movable family); whether custom allocator access is delivered as a narrowly unsafe reviewed extension rather than a universally safe API; and which provider colour/exposure combinations can be documented as actually supported. Closed-provider internals need only be investigated to the extent necessary for these public safety and usage boundaries.

**Release-completeness test:** each public upscaling descriptor/flag/compatible shared DX12 extension above must be (a) faithfully represented in `fsr-sdk-sys`, (b) accessible through a validated, ownership-preserving `fsr-sdk` contract in both families **or** explicitly recorded as an optional shared/runtime extension with a justified and publicly visible scope limitation accepted before release, and (c) backed by appropriately scoped ABI, controlled integration and targeted native evidence for every runtime support claim. Merely binding `ffxConfigure` or passing a roadmap tick does not meet (b) or (c). Nothing in this record approves narrowing the user's full-access release objective; deferring any listed public route requires an explicit scope/decision change, not silently marking it complete.
